## 0. 一句话现状

路线图的 **Phase 5（软件槽位管理器与密钥库）** 与 **Phase 6（密钥层级与备份恢复）** 的软件部分已经完整落地并通过测试，
外加 **Phase 0（软件参考 + KAT）**。整机形态是一个可嵌入的 C11 静态库，对外只暴露句柄。

**尚未开始**的是：对外标准接口（PKCS#11，Phase 9）、算法核硬件化（Phase 1–4）、
安全边界从"进程内存"收紧到"PL 硬件"（Phase 7）。

验收口径按 §0.1 的标准（"任何时刻明文私钥不出安全边界，且密钥可管理、可恢复、可销毁"）来看：
**可管理、可恢复、可销毁三条已经成立并有测试**；"不出安全边界"这一条目前只在**软件边界**内成立
（明文密钥在进程内存中，上层与调用方只见句柄），硬件边界要等 Phase 7。

### 技术栈与理由（摘要）

- **编排层 C11**：路线图 §5.7.1 与 Phase 5 本身写的就是 C；更重要的是**零化在 Python 里无法验证**
  （`bytes` 不可变、到处是副本），而 §8.7 的红线恰恰要求验证清零；且 PKCS#11 是 C ABI，
  这套代码最终要交叉编译到 Cortex-A。
- **密码运算 liboqs 0.16**：对齐**最终版** FIPS 203/204，不自己写算法。
- **对称原语 OpenSSL 3**：AES-256-GCM、SHA3-256、KMAC256。
- **向量流水线 Python → C**：ACVP 嵌套 JSON 由 Python 展平成 `key = hex` 文本，
  C 侧只需 60 行解析器。这批扁平文件正是 §5.1.3 要求的黄金向量，将来 cocotb/RTL 仿真复用同一批。

## 1. 已完成：五步纯软件原型

### 第 1 步　PQC 库集成与 KAT（对应 Phase 0、§10.1）

**做了什么**

- `include/pqchsm/pqc.h`：**crypto 后端 vtable**——keygen / keypair_from_seed / encaps /
  encaps_derand / decaps / sign / verify。这是整个项目最重要的接口边界：上层（槽位管理器、
  密钥库、备份恢复）只经它做密码运算，将来把算法核搬到 FPGA 时上层一行不改。
  为硬件后端预留的三条约束已写进设计：缓冲由调用方按 `pqc_alg_info()` 预分配（硬件端不做动态分配）、
  无隐式全局随机源（签名的 `rnd` 显式传入）、`keypair_from_seed` 是一等公民而非测试后门。
- `src/crypto/pqc_liboqs.c`：当前唯一后端。
- `src/crypto/oqs_rng.c`：**确定性随机源注入**。
- `tools/acvp_to_kat.py` + `tools/fetch_vectors.sh`：ACVP JSON → 扁平黄金向量，向量源钉死在
  ACVP-Server commit `ad33b3d`（2026-07-28）。

**测试覆盖**

| 向量文件 | 内容 | 通过 | 跳过 |
|---------|------|-----:|-----:|
| `mlkem_keygen.kat` | ML-KEM-512/768/1024 KeyGen(d,z)→(ek,dk) | 75 | 0 |
| `mlkem_encaps.kat` | Encaps(ek,m)→(c,k)，AFT | 75 | 0 |
| `mlkem_decaps.kat` | Decaps(dk,c)→k，VAL | 30 | 0 |
| `mlkem_keycheck.kat` | ek/dk 格式校验 | 0 | 60 |
| `mldsa_keygen.kat` | ML-DSA-44/65/87 KeyGen(ξ)→(pk,sk) | 75 | 0 |
| `mldsa_siggen.kat` | Sign，deterministic + hedged | 90 | 0 |
| `mldsa_sigver.kat` | Verify，含应当失败的负向量 | 45 | 0 |

单元测试另有 `test_pqc_meta`(64)、`test_pqc_roundtrip`(124)、`test_kat_parse`(22)、`test_util`(21)。

**关键设计点**

1. **全部使用最终版 FIPS 203/204 向量，不是 round-3**（§5.1.1 反复强调的版本陷阱）。
   `test_pqc_meta` 里有一条断言：`pqc_alg_by_name("Kyber768")` 必须返回 `PQC_ALG_NONE`。
2. **liboqs 的 `keypair_derand` coins 就是 `d‖z`**——75 条 keyGen 向量逐字节相符，顺序猜错一条都过不了。
3. **ML-DSA 没有去随机化 API**，本项目通过 `OQS_randombytes_custom_algorithm` 注入脚本化随机源解决。
   这不是测试后门：§7.6 的**种子存储优化**（每槽只存 32 B ξ，用时重展开）在生产路径上就需要它。
   实测消费字节数恰为 32，说明对后端随机数消费模型的判断正确；若不符会返回 `PQC_ERR_UNSUPPORTED`
   而不是悄悄给出可疑密钥。
4. **元数据表与后端运行时值对拍**：`src/crypto/pqc.c` 里那张长度表是上层分配缓冲的唯一依据，
   一旦与 liboqs 脱节就是缓冲区溢出，所以逐项断言而不是"抄一遍 FIPS 文档就完事"。

**跳过的 60 条不要当成全绿**：ML-KEM 的 `encapsulationKeyCheck`/`decapsulationKeyCheck`
（liboqs 不暴露独立的密钥格式校验 API），以及 ML-DSA 的 `internal` 接口与 `preHash` 变体共 12 组。
这些在 `tools/acvp_to_kat.py` 生成的文件头以 `# SKIPPED:` 记录，`kat_runner` 运行时原样打印。

### 第 2 步　槽位管理器（对应 Phase 5、§7）

**做了什么**

- `src/slot/fsm.c`：生命周期状态机，写成**显式转移表 + 纯函数**。
- `src/slot/slot.c`（1073 行）：token / session / object 模型，句柄化对象引用，SO / User 双角色 ACL，
  PIN 验证与锁定，用途互斥，种子存储策略。
- `src/slot/meta.c`：槽位元数据的确定性序列化与 KMAC256 完整性标签。
- `src/crypto/kdf.c`（KMAC256 / SHA3-256 / KDF）、`src/crypto/kdr.c`（设备根密钥**桩**）。

**测试覆盖**

| 测试 | 断言 | 覆盖 |
|------|-----:|------|
| `test_slot_fsm` | 94 | 5 状态 × 9 事件**全 45 组合**穷举 + 性质断言 |
| `test_slot` | 196 | ACL、PIN 锁定/解锁、句柄失效、用途互斥、种子存储、zeroize |
| `test_slot_meta` | 31 | KMAC 标签逐字段篡改检测 + 跨设备 sealing |
| `test_slot_concurrent` | 69 | 多线程分用/抢占槽位、会话表竞争 |
| `test_kdf` | 55 | NIST KMAC256 官方向量 #4/#5/#6 |

**关键设计点**

1. **状态机的期望表是照 §7.1 的图独立写第二遍的**，不是从实现抄的——否则测试只是在证明
   "表等于它自己"。45 组合中 30 组非法，这个数字本身也被断言，将来谁放宽了限制会立刻暴露。
2. **两处对 §7.1 的有意偏离**：
   - **SO 解锁后恢复到锁定前的状态**，而不是图上写的"一律回已装载"。锁定也可能发生在空槽位上，
     那时回"已装载"等于谎报槽位里有密钥。
   - **User PIN 失败锁槽位，SO PIN 失败只计数不锁**。§7.3 说"超限锁定槽位，仅 SO 可解锁"——
     但如果 SO 自己也被锁死，就没人能解锁，设备直接变砖。SO 凭证的兜底恢复交给第 4 步的
     Shamir M-of-N 仪式（备份里带着 PIN 材料，恢复即可重获登录能力）。
     **这是安全性与可用性的权衡，值得复核。**
3. **句柄带 generation**：`handle = (generation << 32) | (slot_id + 1)`，
   destroy / zeroize 递增 generation，旧句柄立刻变 `HSM_ERR_BAD_HANDLE`。
4. **生成与由种子装载走同一条代码路径**（都先有种子再展开），这样 §7.6 的种子存储策略
   不会变成一条没人走的旁路。SEED_STORAGE 槽位在装载时**立即销毁刚算出的私钥**，只留种子，
   签名/解封装时现场重展开、用后即清；测试里连续两次解封装都得到与主机一致的共享秘密，
   证明确实是重展开而不是留了副本。
5. **PIN 验证值 = KMAC256(pin_key, slot_id‖role‖salt‖pin)**，`pin_key` 是每槽位随机的 32 字节、
   只存在于 KEK/BEK 包裹内。不存明文也不存可离线爆破的哈希；比较走常量时间。
   （初版直接由 KDR 派生，被第 4 步的跨设备恢复测试证伪，详见下文。）
6. **元数据 KMAC 标签同时绑定 slot_id 与 KDR**：把 slot 3 的记录整条搬到 slot 5 会被检出，
   换一台设备旧标签立刻失效。
7. **并发（§7.4）**：每槽位一把互斥锁 + 一把会话表锁，**锁序恒为 tlock → slot->lock**；
   会话表访问返回拷贝而非指针，避免跨锁持有。审计写在放掉槽位锁之后（fsync 不该卡住持锁路径）。

### 第 3 步　KEK 包裹与密文密钥库（对应 Phase 5、§8.2、§7.5）

**做了什么**

| 模块 | 文件 | 要点 |
|------|------|------|
| 包裹 | `src/store/wrap.c` | AES-256-GCM；blob = `magic‖ver‖alg‖aad_len‖ct_len‖nonce‖ct‖tag` |
| 单槽位持久化 | `src/slot/persist.c` | blob = 明文元数据 ‖ wrap(密钥材料 + PIN 材料)，元数据同时是 AAD |
| 密钥库文件 | `src/store/keystore.c` | 全文件 KMAC + 原子写 `tmp→fsync→rename→fsync(dir)` |

**测试覆盖**：`test_wrap` 330 断言、`test_keystore` 71 断言。

**关键设计点**

1. **nonce 走 SP 800-38D §8.2.2 的 RBG 构造**（每次 `RAND_bytes` 现取 96 bit，无状态）。
   计数器方案跨重启会重置导致复用，随机方案没有这个坑；代价是同一 KEK 上限 2³² 次调用，
   本项目量级远达不到。`test_wrap` 里有一条**可执行的红线演示**：同 KEK 同 nonce 加密两条明文，
   两条密文的异或恰好等于两条明文的异或（密钥流被完全抵消），并断言正常路径不具备该性质。
2. **元数据放在包裹外、同时进 AAD**：密钥库要能不解密就列出槽位状态，而改一个字节就会让
   GCM 校验失败——这就是 §8.2 说的"元数据进 AAD，防改元数据复用密文"。
3. **每次 save 换一把新 KEK**（新随机 salt → 新派生），于是 §8.1 的"KEK 轮换"成了默认行为。
4. **全文件 KMAC 是必需的**：删一条记录、调换两条记录、截断文件——这些攻击单看每条记录都合法，
   只有全文件 MAC 能发现。
5. **掉电一致性**：`test_keystore` 用 `fork` + 写点计数钩子，**穷举 save 的每一个写点注入 `_exit(9)`**，
   验证重启后主文件仍是旧的完整文件且密钥可用；另有一条用例验证崩溃残留的 `.tmp` 不影响下次保存。
6. `test_wrap` 对 blob 的**每一个字节**做翻转扫描，`test_keystore` 对密钥库文件做 120 处抽样翻转，
   全部必须被检出。

### 第 4 步　备份与恢复（对应 Phase 6、§8.1–8.4）

**密钥层级（§8.1 / §8.3 的两条路径）**

```
KDR（设备根密钥，当前是桩）
 ├─ KDF ─→ KEK ─wrap→ 密钥库文件      绑定设备：拷走换台机器打不开（sealing）
 └─（不参与备份）

RMK（恢复主密钥，导出时现场随机生成，从不落盘、从不返回调用方）
 ├─ KDF ─→ BEK ─wrap→ 备份文件        不绑定设备：可跨机恢复
 └─ Shamir M-of-N ─→ N 份分片，离线保管
```

**做了什么**

- `src/backup/shamir.c`：GF(256) Shamir 门限分享，**常量时间乘法**（位掩码的俄罗斯农民乘法，
  固定 8 轮、无分支无查表）、加法链求逆、常量时间插值。
- `src/backup/backup.c`：导出（SO 会话）与恢复（设备级，无会话）。

**测试覆盖**：`test_shamir` 846 断言、`test_backup` 65 断言。

主线是 Phase 6 的验收演练：**建库 → 备份导出 → 整机清零 → 用 M 份分片恢复 → 原公钥能验证
恢复后签出的签名**，且**穷举 C(5,3)=10 种分片组合全部成功**。
负测试（不足 M 份、篡改分片、他人分片、篡改/截断备份文件）全部安排在恢复成功之前先跑，
以确认它们真的挡住了而不是碰巧。

**关键设计点**

1. **RMK 从不落盘、从不返回调用方**：导出结束时进程内已清零，此后世上只剩分片。
2. **分片不足 M 份时 Shamir 不会报错**——它会算出一个错误的 RMK，这是信息论安全的固有表现
   （分片里不存 M，combine 无从判断门限是否凑够）。本设计**特意依赖 GCM tag 作兜底**：
   错 RMK → 错 BEK → tag 校验失败 → `HSM_ERR_INTEGRITY`。这条依赖链写在 `backup.h` 里。
3. **只有带 `SLOT_POLICY_BACKUPABLE` 的槽位进备份**；其余是"纯 sealed 槽位"（如设备身份钥），
   设备损坏即密钥消失——这是 §8.3 的取舍，不是遗漏，测试里有对应断言。
4. **恢复是设备级操作，不要求会话**：典型场景就是一台空白新设备，上面没有任何 SO 凭证可登录。
   Phase 7 起这条路径必须由物理"恢复模式"信号 + SO 现场授权门控。
5. **跨设备恢复后自动重新 sealing**：装载时元数据标签用**本机 KDR** 重新盖，
   调用方随后 `hsm_keystore_save()` 即固化成本机密钥库；测试验证该库回到原设备打不开。

**本步抓到并修掉的设计缺陷**：PIN 验证值原先直接由 KDR 派生，导致**跨设备恢复出来的 token
永远登录不上**（新设备 KDR 不同 → 验证值对不上）。改为每槽位一把随机 `pin_key`、PIN 验证值由它派生，
`pin_key` 本身放在 KEK/BEK 包裹内。离线拿到密钥库文件仍无法爆破 PIN，安全性不降，可移植性解决。
**这是端到端演练抓出来的，单元测试抓不到。**

### 第 5 步　审计哈希链与 zeroize 验证（对应 §8.6、§0.2、§8.7）

**做了什么**

- `src/audit/audit.c`（529 行）：append-only 哈希链，`H₀ = SHA3-256("pqc-hsm/audit/genesis")`，
  `H_i = SHA3-256(H_{i-1} ‖ entry_i)`。定长记录，文件头存 `count` 与链头并就地更新。
- 已**接入槽位管理器**：`hsm_token_attach_audit()` 挂上之后，init_token / login / 登录失败 /
  锁定 / 生成 / 装载 / 签名 / 解封装 / 销毁 / 清零 / 解锁 / 备份导出 / 恢复 / KEK 轮换
  共 14 类操作自动落链，**失败也落**（§8.6 明确要求记录否定结果）。

**测试覆盖**：`test_audit` 177 断言、`test_audit_integration` 48 断言、`test_zeroize` 100 断言。

**关键设计点**

1. **截断检测**：文件头里的 `count` 与链头让 `文件大小 == 64 + 96×count` 成为恒等式。
   纯粹"一条接一条"的格式砍掉尾部后前缀仍自洽、发现不了，而尾部恰恰是最不能丢的一段。
   现在砍掉 k 条会当场失败并给出 `bad_seq`。
2. **测试独立重算整条哈希链**再与文件逐条比对，而不是只验自洽。
3. **诚实标注的局限，并有反向断言把它跑出来**：纯哈希链**挡不住能重写整个文件的攻击者**——
   算法公开、链头就写在文件头里，从任意一点重算整条链再把 `count`/`head` 改自洽即可。
   `test_audit` 里专门构造这种伪造并**断言 `verify` 返回 0**，让这个洞一直可见。
4. **detail 字段净化**：非可打印 ASCII 一律换成 `.`，避免给日志阅读器开注入口子。
5. **zeroize 验证**：`test_zeroize` 直接 include 私有头窥视槽位结构，断言清零真的落到内存——
   指针归零、`seed`/`pin_key`/salt/verifier 全 0、整个结构体里搜不到原私钥的任何片段；
   从全部 5 个状态各清零一次都干净。
   红线检查：密钥库文件、备份文件、Shamir 分片、审计日志里都搜不到明文私钥 / PIN / 验证值。

### 附：验证方法上的两点自查

这两件事值得单独说，因为"测试通过"本身可能是假象：

- **TSan 的反证**：并发测试在 TSan 下 0 race。但"没报"也可能是没检测到，
  所以另外把槽位锁临时去掉重编一遍，TSan 报 **9 处 race**——确认检测确实有效。
- **KMAC 向量的三方交叉验证**：KMAC256 的 NIST 官方向量（CSRC `KMAC_samples.pdf`）
  与 OpenSSL 实现、以及一份从零手写的 Keccak/cSHAKE 实现，三方逐字节吻合。
  Shamir 也当黑盒独立验过门限性质（10/10 有效组合恢复、m−1 份 0 次泄露）。

| 项 | 现状 | 说明 |
|----|------|------|
| **PKCS#11 v3.2 前端** | 未做 | 需要一个导出 `C_GetFunctionList` 的动态库。槽位管理器的 slot/token/object/session 模型是照 PKCS#11 设计的，天然对应；v3.2 已原生定义 ML-KEM/ML-DSA 机制码，不需要 vendor 扩展 |
| **命令接口（UART / TCP + TLV）与 CLI 工具** | 未做 | Phase 5 清单第 3 项。当前只有 C 库接口，没有进程外的命令通道 |
| **协议栈对接**（oqs-provider → TLS 1.3 混合密钥交换） | 未做 | 依赖 PKCS#11 前端先就位 |

### 2.2 属于 Phase 6 未完的部分

| 项 | 现状 | 说明 |
|----|------|------|
| **安全密钥注入（§8.5）** | 未做 | 注入端用设备的 ML-KEM 公钥封装一次性会话密钥、密钥材料密文注入。这是"用自己实现的 PQC 保护自己的密钥"的自举闭环，也是很好的整机演示场景 |
| **审计链头用设备 ML-DSA 身份钥签名固化（§8.6）** | 未做 | **这是当前审计模块最实质的缺口**。纯哈希链只保证"改动会向后传播"，不保证"改动无法被抹平"；需要把 `(count, head, 时间)` 签出去送到本设备改不到的地方（另一台机器/上级系统）。本模块已提供随时可被签的链头（`audit_head`），缺的是签名与外部锚点 |

### 2.3 属于 Phase 7（敏感存储与访问控制硬化）——**必须有板**

| 项 | 现状 | 为什么现在做不了 |
|----|------|------------------|
| **KDR 是桩** | `src/crypto/kdr.c` 里一段固定的假根密钥，源码注释写明"Phase 7 这段必须消失" | 真实根密钥要进 eFUSE / BBRAM / US+ 的 PUF，器件安全特性只能在真芯片上验证，且 eFUSE 烧录不可逆 |
| **明文密钥仍在进程内存** | Phase 5 允许的过渡性妥协（§0.2 明确说明边界此阶段放宽到"PS 内核态"） | 收紧到 PL 的 Key Vault BRAM 需要硬件 |
| **真实 `mlock` 生效性** | 代码里是 best-effort（失败不算错误） | 容器/无权限环境下 `mlock` 会失败；是否真的防住换页只能在目标平台上测 |
| **介质残留、断电即失** | 无法验证 | 需要真实掉电和物理介质 |
| **硬件 zeroize / tamper 线** | 只有软件路径 `hsm_slot_zeroize_forced()` 作为占位 | 全局清零广播线是 PL 逻辑 |
| **TRNG** | 当前用 OpenSSL `RAND_bytes` | 需要 PL 环形振荡器熵源 + SP 800-90B 熵评估 |

### 2.4 有意为之的设计取舍（不是缺陷，但接手的人要知道）

| 项 | 说明 |
|----|------|
| **SO PIN 失败只计数不锁槽位** | 锁死 SO 会让设备变砖；兜底是 §8.4 的 M-of-N 恢复。见第 2 步关键设计点 2 |
| **每槽位一个密钥对象** | 不是 PKCS#11 的任意多对象。对应 §7.6 的 8 KB/槽预算。做 PKCS#11 前端时可能需要放宽 |
| **纯 sealed 槽位不进备份** | 设备损坏即密钥消失，这是 §8.3 的取舍 |
| **审计模块假设单写者** | 不做文件锁，多进程同时 append 会互相覆盖 |
| **Shamir 分片的 4 字节校验不是 MAC** | 无密钥的 SHA3 前缀，挡随机损坏与意外，挡不住主动攻击者；真正的完整性判据是恢复后 GCM tag 是否通过 |

### 2.5 KAT 未覆盖的部分

- ML-KEM 的 `encapsulationKeyCheck` / `decapsulationKeyCheck` 共 60 条（liboqs 不暴露独立校验 API）；
- ML-DSA 的 `signatureInterface=internal` 与 `preHash`（HashML-DSA）共 12 组。

这些都在 `.kat` 文件头以 `# SKIPPED:` 记录并在运行时打印，不会伪装成通过。

## 3. 纯软件（无硬件）还能继续做的

> **2026-07-29 更新：本节 10 项已全部推进完毕**（8 项 done，2 项部分 done）。
> 逐项状态见 [`doc/无硬件推进报告.md`](无硬件推进报告.md)；下面保留原始规划正文作为对照。

路线图 §5.0 的判断是：**整条路线里实体板子只在最后约 20% 的工作中是必需品**。
下面每一条都能在现在这台机器上立即开工，且产出直接进入后续阶段——不是"临时凑合"。
按"投入产出比"从高到低排：

### 3.1 补上审计链的 ML-DSA 签名固化 —— 优先级最高

**为什么现在能做**：签名用的就是已经跑通 KAT 的 ML-DSA，链头 `audit_head()` 已经现成，
设备身份钥可以用一个普通槽位承载。整件事不碰任何硬件。

**做什么**：新增"审计锚点"操作——取当前 `(count, head, 时间戳)`，用设备身份签名钥签名，
输出成独立的锚点文件；验证侧检查签名并要求链头与锚点一致。这样就把 §2.2 里那个
"能重写整个文件的攻击者可以抹平"的洞真正堵上，而不是只在注释里承认它。

### 3.2 把 KDR 桩换成完整的派生层级（根密钥仍占位）

**为什么现在能做**：派生链的**结构**是纯软件（KDF 域分隔、每类子密钥的用途隔离、
KEK 轮换流程），只有"根密钥从哪来"这一个点需要硬件。现在把结构定死，Phase 7 只需替换
`pqc_kdr_derive()` 的内部实现，上层一行不改——这正是 `kdr.h` 已经写明的意图。

**做什么**：把根密钥抽象成一个"provider"接口（stub / eFUSE / BBRAM / PUF 四种实现），
补齐 KEK 显式轮换命令（现在是 save 时隐式轮换）与轮换审计，
并把"根密钥不提供读出接口"这条写成编译期可检查的约束。

### 3.3 PKCS#11 软件前端 + 用 pkcs11-tool / SoftHSMv2 对比验证

**为什么现在能做**：这是 §5.7.2 表里明确标注"无板可做到 90%"的一项。
槽位管理器已经是 slot/token/object/session 模型，PKCS#11 v3.2 已原生定义 ML-KEM/ML-DSA 机制码。
参考实现（SoftHSMv2）和测试客户端（OpenSC 的 `pkcs11-tool`）都是现成的开源件。

**做什么**：实现 `C_GetFunctionList` 动态库，映射 C_Initialize / C_GetSlotList / C_OpenSession /
C_Login / C_GenerateKeyPair / C_Sign / C_Verify / C_Encapsulate / C_Decapsulate / C_DestroyObject 等，
然后 `pkcs11-tool --login --list-objects` 全命令回归，与 SoftHSMv2 的行为逐条对比。
**这一步很可能倒逼两个改动**：每槽位多对象、以及对象属性模型的细化——早做早暴露。

### 3.4 命令接口（TCP + TLV）与 CLI 工具

**为什么现在能做**：§5.7.2 说得很直接——用 TCP 或 stdin 替代 UART，逻辑 100% 可完成。

**做什么**：定义 TLV 命令集、写一个 daemon 和一个 CLI。收益不只是"能用"：
它把库接口逼成**进程外接口**，会暴露当前 API 里隐含的"调用方是可信的"假设
（比如缓冲区所有权、错误信息粒度）。板子到手后把传输层从 TCP 换成 UART 即可。

### 3.5 安全密钥注入协议（§8.5）

**为什么现在能做**：注入协议的密码学部分（用对端 ML-KEM 公钥封装 CEK、再用 CEK 包裹密钥材料）
全部是已经跑通的原语。"制造模式 eFUSE 熔断"那一半才需要硬件，可以先桩实现。

**做什么**：实现注入端与设备端的握手与注入流程 + 负测试（重放、错误公钥、非注入模式下拒绝）。

### 3.6 Profiling 与热点量化（Phase 0 的剩余产出，§5.2）

**为什么现在能做**：只需要一台能编译 C 的机器。这是**决定先做哪个硬件核的唯一依据**，
而且必须在写 RTL 之前完成。

**做什么**：用 `perf` / `callgrind` 在 x86 上做函数级剖析，用 `qemu-aarch64` + TCG plugin
做 aarch64 指令计数（注意 QEMU 的数只能用来**排序**，不能做绝对性能预测）；
然后用 Amdahl 定律算出 ≥4 种硬件切分方案的端到端加速比上界，产出一句话决策。
路线图 §5.2.3 已经给了算例：只做 NTT 端到端只有约 1.37×，只做 Keccak 有约 2.09×，
两个都做约 4.82×，但 PS-PL 传输开销能吃掉一半——**这个结论直接决定接口设计**。

### 3.7 RTL / HLS 纯仿真开发（Phase 1–2 的主体，§5.3）

**为什么现在能做**：**RTL 开发的 90% 工作量在仿真器里完成，跟有没有板子毫无关系。**
Verilator + cocotb 全开源，黄金向量已经有了——而且格式当初就是按"C 与 cocotb 共用"设计的。

**做什么**：先按 §5.1.3 补齐 L0–L3 的**分层**黄金向量（Montgomery/Barrett 约减、单个蝶形、
完整 256 点 NTT、Keccak-f[1600] 单次置换、SHAKE、CBD 采样等）——
只导出整机 KAT 的话，RTL 一挂就完全无法定位。然后写 NTT 核、Keccak 核并与向量对拍。
注意 §5.3.1 的坑：**cocotb 不支持 Vivado xsim**，所以自研纯 RTL 走 Verilator/cocotb，
含厂商 IP 的顶层走 xsim——这个分层的副作用是好的，它强迫算法核写成不依赖厂商 IP 的纯 RTL。

### 3.8 用 Vivado 免费版做综合、拿资源与时序报告

**为什么现在能做**：§5.0 的表里明确：资源占用、时序收敛与 Fmax 估算、
甚至 `write_bitstream` 都**不需要板子**，只需指定 part。只有功耗数字是估算值（误差可达 2×）。

**做什么**：选定目标器件（如 KV260 的 XCK26）跑 out-of-context 综合，
拿 LUT/FF/DSP/BRAM 与 post-route WNS，反推 Fmax。**提前验证资源预算，避免买错板子。**

### 3.9 更多负测试与 fuzz

**为什么现在能做**：纯软件，且现有测试框架已经就绪。

**做什么**：对三个解析入口（密钥库文件、备份文件、审计日志）做结构化 fuzz——
它们都从不可信来源读定长/变长字段，是最典型的内存安全面。
可用 libFuzzer + ASan，语料从现有测试产生的合法文件出发。
另外把 §8.7 的红线清单逐条固化成自动化测试（目前覆盖了大部分，但还不是逐条对应）。

### 3.10 交叉编译到 aarch64 + QEMU 回归

**为什么现在能做**：§5.7 的核心技巧——先在 PC / QEMU 上开发 PS 侧固件。

**做什么**：用 `aarch64-linux-gnu-gcc` 交叉编译整个库与测试，在 `qemu-aarch64` 下跑全套回归。
这会暴露当前代码里潜在的**字节序、对齐、`size_t` 宽度**假设——虽然序列化已经全部显式小端，
但栈缓冲对齐和 `long` 宽度这类问题只有换平台才会现形。**这一步做完，板子到手当天就能跑起来。**

## 4. 拿到开发板以后怎么做

### 4.0 选板建议（与 §2.2 一致，另加一条安全理由）

路线图推荐 **AMD Kria KV260**（约 $284）作为密码机原型的首选平台，理由是 US+ 的
PUF KEK、AES-GCM 安全启动、XMPU/XPPU 内存隔离、TrustZone 正好覆盖第 7/8 节的硬化需求。

**再补一条路线图没写但对密码机很关键的理由**：Xilinx **7 系列（Artix-7 / Zynq-7000）的
比特流加密存在 Starbleed 漏洞（CVE-2020-8871）**——这是一个硅片级的设计缺陷，
攻击者可通过 JTAG/SelectMAP 把器件当解密预言机用，从而破解比特流的机密性与真实性，
**无法通过打补丁修复**。对普通 FPGA 应用无所谓，但对"信任根建立在比特流保护之上"的密码机是致命的。
**UltraScale+ 不受该漏洞影响**。所以如果最终形态要做成可信的密码机而不只是功能演示，
应当直接上 US+（KV260），不要在 7 系列上建信任根。
（用 PYNQ-Z2 / Arty A7 做算法核学习与对拍仍然完全没问题——只是别把根密钥托付给它。）

### 4.1 推进顺序

下面这个顺序的原则是：**每一步都建立在上一步已被验证的基础上，且每一步都有明确的验收判据**。

---

**第 ① 步：板级 bring-up 与软件基线搬迁**（约 1 周）

把已经在 QEMU 上跑通的库交叉编译上板，在 PetaLinux / 裸机下跑**完整的 22 个 ctest**。
此时算法仍是 liboqs 软件实现，PL 是空的。

*验收*：全部测试在板上通过，结果与 PC 上逐字节一致。
*意义*：把"软件正确性"与"硬件问题"彻底分离——后面任何失败都只可能来自硬件侧。

---

**第 ② 步：算法核进 PL，通过现有 vtable 缝接入**（Phase 1–3，约 6–10 周）

这是整个硬件化最省力的一步，因为**接口缝已经留好了**：
实现 `src/hal/pqc_accel.c`，填同一张 `pqc_backend_t` vtable，内部通过 AXI-Lite 寄存器 +
AXI-DMA 驱动 PL 里的核。上层槽位管理器、密钥库、备份恢复**一行不改**。

顺序上按 §5.2 的 profiling 结论决定先做 Keccak 还是 NTT（大概率是 Keccak，
因为它占 55%、端到端收益更大）。先 HLS 出架构、对拍通过后再手写 RTL 优化。

*验收*：把 `PQCHSM_VECTOR_DIR` 里那 390 条 ACVP 向量在**硬件后端**下重跑一遍，
必须与软件后端逐字节一致（§5.7.3 的"接口一致性"要求：同一套上层测试跑在
`accel_stub` 与 `accel_mmap` 两边，结果必须逐字节相同）。

---

**第 ③ 步：信任根落地 —— 根密钥进 BBRAM / eFUSE / PUF**（Phase 7，约 2–3 周）

把 §3.2 已经准备好的 KDR provider 接口换成真实实现：
Zynq-7000 用 BBRAM/eFUSE 的 AES-256 密钥；US+ 优先用 **PUF 生成的设备唯一 KEK**
（不消耗 eFUSE，且天然设备唯一）。KDF 派生链在 PL 或一级引导内完成。

⚠️ **eFUSE 烧录不可逆**——先在 BBRAM 上把整条流程跑通，确认无误再考虑 eFUSE。

*验收*：固件二进制与内存 dump 中搜不到 KDR/KEK 明文；把密钥库文件拷到另一块板子上打不开。

---

**第 ④ 步：安全边界收紧 —— unwrap 下沉 PL + Key Vault 无读回路径**（Phase 7，约 3–4 周）

- AES-GCM 核进 PL，**unwrap 改在 PL 内完成**：密文进 PL → 解包 → 明文密钥直接写入
  Key Vault BRAM，PS 全程只见密文；
- Key Vault BRAM **只接算法核的读端口**，PS 侧 AXI 只有"写入 / 触发 / 清零"能力，
  **无读回路径（在地址译码上物理不存在，而不是靠软件判断）**；
- Key Vault 按槽位划分固定大小窗口，跨槽位越界在地址译码层裁掉。

*验收*（§0.2 铁律的真正兑现）：PS 以**任何**地址组合读 Key Vault 必须失败或读到全零。
这一步做完，§0.1 的"明文私钥不出安全边界"才第一次在硬件意义上成立。

---

**第 ⑤ 步：硬件 TRNG 并通过 SP 800-90B**（Phase 7，约 2 周）

PL 环形振荡器熵源 + SHAKE 调理（或 US+ 的 PS 侧硬 TRNG）。
用 NIST 的 SP 800-90B 熵评估工具跑非 IID 测试，另跑 AIS-31。
在线健康监测（连续重复计数、自适应比例）必须常驻——§8.7 红线里明确要求。

*验收*：熵估计达标、健康监测在注入故障时会报警；wrap 的 nonce 源切换到 TRNG 后
`test_wrap` 的"大量 wrap 的 nonce 互不相同"仍然通过。

---

**第 ⑥ 步：硬件 zeroize、tamper 线与真机残留验证**（Phase 7，约 2 周）

一条全局清零广播线，由命令或 tamper 信号触发，清 Key Vault 与算法核内部状态。
这一步终于能验证 §2.3 里那三项"无法验证"的事：

- 真实 `mlock` 是否生效（在目标 OS 上实测换页行为）；
- **断电即失**：写入密钥 → 断电 → 上电 → 读 Key Vault 必须全零；
- **介质残留**：对外部 Flash/SD 做物理读取，确认只有密文。

*验收*：zeroize 后读回全零；断电重启后 vault 无残留；
现有的 `test_zeroize` 从"验证结构体字段"升级为"验证硬件状态"。

---

**第 ⑦ 步：比特流与启动链防护**（Phase 7，约 1–2 周）

启用 AES-GCM 比特流加密 + RSA/ECDSA 认证启动，关闭 JTAG（或设为需认证），
禁用回读。US+ 上配合 XMPU/XPPU 把密钥相关地址段对非安全世界屏蔽；
可选把 PIN 验证与会话管理迁入 OP-TEE（TrustZone）。

*注意*：如果这一步跑在 7 系列上，**Starbleed 使比特流加密的保护形同虚设**（见 §4.0）。
在 US+ 上则是有效防线。

---

**第 ⑧ 步：真机侧信道评估**（§9，约 3–4 周）

用 **ChipWhisperer Lite**（约 $300）或 **CW305 Artix-7 目标板**采功耗迹，做 TVLA t-test。
按 §10.3 的门限：|t| < 4.5 @ 10k traces 作为基础及格线。
先测未防护版本建立基线，再逐项加防护（常量时间修正 → shuffling → 一阶 masking）看 t 值下降。

*注意*：**masking 与常量时间段必须手写 RTL**，HLS 无法保证（§3.4）；
rejection sampling 的变长执行时间是 ML-DSA 的已知难点。

---

**第 ⑨ 步：PKCS#11 跑在硬件上 + 协议栈对接**（Phase 9，约 2–3 周）

把 §3.3 已经写好并用 SoftHSMv2 对比验证过的 PKCS#11 前端接到硬件后端上，
`pkcs11-tool` 全命令回归；再用 oqs-provider（OpenSSL 3）走本机 PKCS#11 做
**TLS 1.3 混合密钥交换**演示。产出整机性能报告：Encaps/s、Sign/s、单次延迟、与纯软件基线对比。

*为什么放在这么后面*：接口层早在无板阶段就写好并验证过了，这里只是换后端——
把它排在硬化之后，是为了让性能数字反映的是最终形态。

---

**第 ⑩ 步：对标合规做一轮完整自查**（持续）

按 §10.3 的清单逐条过：

- **算法级**：FIPS 203/204 接口一致、全部 KAT 通过、参数集切换正确、TVLA 通过、AXI 寄存器映射文档；
- **模块级（对标 FIPS 140-3 的原型版）**：角色分权、zeroize 可验证、明文密钥边界、
  备份恢复演练含全套负测试、审计链可验证、**上电自检（POST）——KAT 自测失败则拒绝进入工作态**
  （这一条现在还没做，属于硬件阶段新增）、PKCS#11 行为与 SoftHSMv2 对比无歧义。

正式认证的话，FIPS 140-3 走 CMVP（算法要先过 ACVT），国内对应 **GM/T 0028**（密码模块安全技术要求）
与 GM/T 0030（密码模块检测）。个人 / 原型项目做到上面清单全绿，已经是很强的成果口径。

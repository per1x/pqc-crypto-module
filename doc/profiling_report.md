> 平台：Apple M 系列（arm64），macOS 27.0，liboqs 0.16.0，clang -O2

**结论先行**

1. **算法级基线已拿到**（下表），这是将来对比硬件加速效果的唯一参照系。

   走的是**手写 aarch64 汇编**，没有帧指针可回溯，统计采样无法穿透。

3. **切分决策的工具已就位**（`tools/amdahl.py`），当前用路线图的文献占比跑出
   与 §5.2.3 完全一致的结论；换成实测占比即可重跑。

## 2. 符号级归因：失败的排查过程（如实记录）

§5.2 想要的是"Keccak 占多少、NTT 占多少"。本机排查了三轮，都没能拿到可信数字：

**第 1 轮：直接对 homebrew 的 liboqs 采样**
`sample(1)` 的叶子样本 **97% 落在 `run_op`**（我们自己的 benchmark 函数），
Keccak 只有 1.4%。这个数字与路线图的 ~55% 差了一个数量级 ——
**不是发现，是归因失败**：预编译的 `.a` 里 ML-KEM/ML-DSA 内部符号是 static，
栈回溯走不进去，全部记在了最近一个可解析的帧上。

**第 2 轮：从源码重编 liboqs（RelWithDebInfo，带 `-g`）**
符号确实出来了（能看到 `PQCP_MLKEM_NATIVE_MLKEM768_AARCH64_keypair`），
但叶子仍有 **88% 落在 `run_op`**，且样本行显示的是调用点
`run_op (in bench_sym) + 372 [...] bench.c:60` —— 说明**栈没有被展开**。

**第 3 轮：加 `-fno-omit-frame-pointer` 重编，再试通用 C 目标**
仍然 89% 落在 `run_op`。查符号表发现根因：

```
$ nm -a b3/lib/liboqs.a | grep -c aarch64_asm
65
```

liboqs 0.16 的 ML-KEM/ML-DSA 用的是 **mlkem-native / mldsa-native 的手写
aarch64 汇编**（`..._ntt_aarch64_asm`、`..._rej_uniform_aarch64_asm` 等），
即使 `OQS_DIST_BUILD=OFF -DOQS_OPT_TARGET=generic` 也照样编进去。
手写汇编不建立帧指针，基于帧指针的统计采样**在原理上就穿不过去**。

**结论**：这台机器上拿不到可信的符号级占比。硬凑一个数字去做硬件决策，
比没有数字更危险，所以这里不给。

### 怎么才能拿到真数字（下一步的具体做法）

§5.2 本来就要求在**目标平台**上测（Cortex-A53/A9），而不是在开发机上：

1. **交叉编译到 aarch64 Linux**（对应 §3.10 已经打通的交叉编译链路），
   liboqs 配 `-DOQS_DIST_BUILD=OFF`，并显式关掉 native 加速
   （必要时直接删掉 `mlkem-native`/`mldsa-native` 的 asm 路径，
   或改用 PQClean 的纯 C 实现 —— 反正 PS 侧要不要 NEON 汇编本身就是个决策点）。
2. 用 **`perf record -g --call-graph dwarf`**：DWARF 展开不依赖帧指针，
   能穿过没有帧指针的汇编（代价是采样开销大）。这是 Linux 上的正解，
   macOS 的 `sample` 没有等价能力。
3. 或者用**确定性计数**：给 Keccak 置换加一个计数器，数出每次 KeyGen/Sign
   调用多少次置换，再单独微基准一次置换的耗时，相乘即得占比。
   这比统计采样更精确、可复现，代价是要改 liboqs 源码。
4. 拿到占比后：`tools/amdahl.py --measured --keccak X --ntt Y` 重跑决策表。

## 3. 切分决策表（当前用文献占比）

`tools/amdahl.py` 的输出，占比取路线图 §5.2.3 的 SHAKE 55% / NTT 30%：

| 方案 | 剩余时间 | 端到端加速比 |
|------|--------:|-----------:|
| ① 全软件（基线） | 1.000 | 1.00× |
| ② 只做 NTT 硬件（10×） | 0.730 | **1.37×** |
| ③ 只做 Keccak 硬件（20×） | 0.477 | **2.09×** |
| ④ 两个核都做 | 0.207 | **4.82×** |
| ⑤ 两个都做 + 10% 传输开销 | 0.307 | 3.25× |
| ⑥ 两个都做 + 20% 传输开销 | 0.407 | **2.45×** |
| ⑦ 整条流程进 PL（无搬运） | 0.150 | 6.67× |

（②③④⑥ 与路线图 §5.2.3 正文的 1.37/2.09/4.82/2.45 逐项吻合，
说明工具的计算是对的 —— 不确定的只是占比输入。）

**三条可直接用的结论**

1. **只做 NTT 的端到端收益只有 1.37×。** 如果目标是性能，
   它不该是第一个做的核；如果目标是学 RTL 与格密码结构，先做 NTT 仍然合理。
   ——**这是两个不同的目标，不要混着谈。**
2. **若目标是端到端性能，Keccak 是第一顺位投资**（单独做就有 2.09×）。
3. **PS-PL 搬运开销能吃掉一半收益**（4.82× → 2.45×）。
   接口设计（DMA、批处理粒度、是否把整条 KeyGen 都放进 PL）必须在
   **架构阶段**决策，不能等 RTL 写完再补救。

⚠️ 这三条结论建立在**文献占比**上。在换成目标平台实测值之前，
它们是"合理的默认判断"，不是本项目的实测结论。

### 这一步验证掉的三个非平凡结论

1. **liboqs 的 `keypair_derand` coins 就是 `d‖z`**（FIPS 203 KeyGen 的两个输入按序拼接）
   —— 75 条 keyGen 向量逐字节相符，顺序猜错的话一条都过不了。
2. **ML-DSA 可以用注入随机源做到完全确定性**：liboqs 没有 `keypair_derand`，
   本项目用 `OQS_randombytes_custom_algorithm` 脚本化喂入 ξ / rnd，
   keyGen 75 条 + sigGen 90 条全部相符，且实测消费字节数恰为 32 —— 模型正确。
   这条同时给路线图 §7.6 的**种子存储优化**扫清了障碍。
3. **签名的 `rnd` 语义可控**：deterministic 组（rnd=0³²）与 hedged 组（ACVP 给定 rnd）
   都能复现出与向量一致的签名，说明 `pqc_sign` 的 rnd 参数确实透传到了算法内部
   （`test_pqc_roundtrip` 里还有一条"换 rnd 必须换签名"的反向断言兜底）。

### 关键决策

1. **状态机写成显式转移表 + 纯函数**（`src/slot/fsm.c`），非法转移是"表里没有"而不是
   "某个 if 忘了写"。测试里的期望表是**照 §7.1 的图独立写第二遍**的，不是从实现抄的 ——
   否则只是在证明"表等于它自己"。45 组合中 30 组非法，这个数字本身也被断言，
   将来谁放宽了限制会立刻暴露。
2. **SO 解锁后恢复到锁定前的状态，而不是一律回"已装载"**。§7.1 的图写的是回已装载，
   但锁定也可能发生在空槽位上，那时回"已装载"等于谎报槽位里有密钥。这是对图的有意偏离。
3. **User PIN 失败锁槽位，SO PIN 失败只计数不锁**。§7.3 说"超限锁定槽位，仅 SO 可解锁" ——
   如果 SO 自己也被锁死，就没人能解锁，设备直接变砖。SO 凭证的兜底恢复归 §8.4 的
   Shamir M-of-N 仪式管（第 4 步）。**这条是安全性与可用性的权衡，值得复核。**
4. **句柄带 generation**：`handle = (generation << 32) | (slot_id + 1)`，
   destroy / zeroize 递增 generation，旧句柄立刻变 `HSM_ERR_BAD_HANDLE`。
5. **生成与由种子装载走同一条代码路径**（都先有种子再展开）。这样 §7.6 的种子存储策略
   不会变成一条没人走的旁路。SEED_STORAGE 槽位在装载时**立即销毁刚算出的私钥**，
   只留 64/32 B 种子，签名/解封装时现场重展开、用后即清 —— 测试里连续两次解封装
   都得到与主机一致的共享秘密，证明确实是重展开而不是留了副本。
6. **PIN 验证值 = KMAC256(pin_key, slot_id ‖ role ‖ salt ‖ pin)**，`pin_key` 是每槽位随机的
   32 字节、只存在于 KEK/BEK 包裹内 —— 不存明文也不存可离线爆破的哈希。
   比较走 `pqc_ct_equal` 常量时间。（**注**：初版直接用 KDR 派生，第 4 步的跨设备恢复
   测试证明那样会让恢复出来的 token 永远登录不上，已改成现在这样，见第 4 步。）
7. **元数据 KMAC 标签绑定 slot_id**，所以把 slot 3 的记录整条搬到 slot 5 也会被检出；
   同时绑定 KDR，换一台"设备"旧标签立刻失效（§8.3 sealing 的雏形，已有测试）。
8. **KDR 是桩**（`src/crypto/kdr.c` 里的固定假根密钥，源码里写明"Phase 7 这段必须消失"），
   符合 §5.7.2「设备绑定只能设计与桩实现，真实绑定必须有板」。

### 本步发现并修掉的两个问题

- `test_slot_meta` 里"把 PIN 失败计数改成 0"的篡改测试，因为基准值本来就是 0，
  等于什么都没改 —— 测试自己暴露了自己是假的，已改为非零起点。
- `hsm_slot_load_seed` 原先先动状态机再校验种子长度（虽有回滚）。已把便宜的参数校验
  提到状态机之前：不该因为一个长度写错的调用就去动槽位状态。

### 收尾：并发（§7.4）

每槽位一把互斥锁 + 一把会话表锁，**锁序恒为 tlock → slot->lock**；会话表访问返回
拷贝而非指针，避免跨锁持有。`test_slot_concurrent` 覆盖"多线程分用槽位""多线程抢
同一槽位""会话表开关竞争"，断言使用计数无丢失更新、且**任何时刻都读不到半更新的
元数据**（即 KMAC 校验失败次数恒为 0）。

TSan 验证：加锁后 0 race；**反证**——临时去掉槽位锁重编一遍，TSan 报 9 处 race，
说明检测确实有效，不是"没测到"。

### 已知边界（不要当成已完成）

- 每槽位一个密钥对象（对应 §7.6 的 8 KB/槽预算），不是 PKCS#11 的任意多对象。

## 第 3 步：KEK 包裹与密文密钥库 ✅

| 模块 | 文件 | 要点 |
|------|------|------|
| 包裹 | `src/store/wrap.c` | AES-256-GCM；blob = `magic‖ver‖alg‖aad_len‖ct_len‖nonce‖ct‖tag`；**元数据进 AAD** |
| 单槽位持久化 | `src/slot/persist.c` | blob = 明文元数据 ‖ wrap(密钥材料 + PIN 材料)，元数据同时是 AAD |
| 密钥库文件 | `src/store/keystore.c` | 全文件 KMAC + 原子写 `tmp→fsync→rename→fsync(dir)` |

**关键决策**

1. **nonce 走 SP 800-38D §8.2.2 的 RBG 构造**（每次 `RAND_bytes` 现取 96 bit，无状态）。
   计数器方案跨重启会重置导致复用，随机方案没有这个坑；代价是同一 KEK 上限 2^32 次，
   本项目量级远达不到。`test_wrap` 里有一条**可执行的红线演示**：同 KEK 同 nonce 加密
   两条明文，两条密文的异或恰好等于两条明文的异或 —— 密钥流被完全抵消。这条测试
   同时断言正常路径（随机 nonce）不具备该性质。
2. **元数据放在包裹外、同时进 AAD**：密钥库要能不解密就列出槽位状态，
   而改一个字节就会让 GCM 校验失败。两全。
3. **每次 save 换一把新 KEK**（新随机 salt → 新派生），于是 §8.1 的"KEK 轮换"
   成了默认行为，nonce 空间也随之刷新。
4. 全文件 KMAC 是必需的：**删一条记录、调换两条记录、截断文件**这些攻击
   单看每条记录都合法，只有全文件 MAC 能发现。

**测试**：`test_wrap` 330 断言（含对 blob **每一个字节**做翻转扫描，全部检出）；
`test_keystore` 71 断言（往返可用、120 处篡改全检出、**穷举 save 的每个写点注入断电**
后旧文件仍完好且密钥可用、崩溃残留的 `.tmp` 不影响下次保存）。

## 第 4 步：备份与恢复 ✅

**密钥层级（§8.1/§8.3 的两条路径）**

```
KDR（设备根，桩）─KDF→ KEK ─wrap→ 密钥库文件   （绑定设备，拷走打不开）
RMK（导出时现生成）─KDF→ BEK ─wrap→ 备份文件   （不绑定设备，可跨机恢复）
                    └─ Shamir M-of-N → N 份分片，离线保管
```

**关键决策**

1. **RMK 从不落盘、从不返回调用方**：导出结束时进程内已清零，此后世上只剩分片。
2. **分片不足 M 份时 Shamir 不会报错**（它算出一个错误的 RMK，这是信息论安全的
   固有表现）。本设计**特意依赖 GCM tag 作兜底**：错 RMK → 错 BEK → tag 校验失败
   → `HSM_ERR_INTEGRITY`。头文件里写明了这条依赖链。
3. **只有带 `SLOT_POLICY_BACKUPABLE` 的槽位进备份**；其余是"纯 sealed 槽位"
   （如设备身份钥），设备损坏即密钥消失 —— 这是 §8.3 的取舍，不是遗漏。
4. **恢复是设备级操作，不要求会话**：典型场景就是一台空白新设备，上面没有任何
   SO 凭证可登录。Phase 7 起必须由物理"恢复模式"信号门控。

**本步抓到并修掉的设计缺陷**：PIN 验证值原先直接由 KDR 派生，导致**跨设备恢复出来的
token 永远登录不上**（新设备 KDR 不同 → 验证值对不上）。改为每槽位一把随机 `pin_key`，
PIN 验证值由它派生，`pin_key` 本身放在 KEK/BEK 包裹内。离线拿到密钥库文件仍无法
爆破 PIN，安全性不降，可移植性解决。**这是端到端测试抓出来的，单元测试抓不到。**

**测试**：`test_audit` 177 断言（测试里**按公式独立重算整条链**再与文件逐条比对，
而不是只验自洽）；`test_audit_integration` 48 断言（接线正确、失败也落链、红线扫描）。
`test_shamir` 846 断言（GF(256) 常量时间乘法、3-of-5 穷举、篡改检测）；
`test_backup` 65 断言，主线是 Phase 6 的验收演练 —— 建库 → 导出 → **整机清零** →
用 M 份分片恢复 → 原公钥能验证恢复后签出的签名，且**穷举 C(5,3)=10 种分片组合全部成功**。
负测试（不足 M 份、篡改分片、他人分片、篡改/截断备份文件）全部在恢复成功之前先跑，
确认它们真的挡住了。

## 第 5 步：审计哈希链与 zeroize 验证 ✅

**审计**（`src/audit/audit.c`，§8.6）：append-only，`H_i = SHA3-256(H_{i-1} ‖ entry_i)`。
文件头存 `count` 与链头并就地更新，于是恒有 `文件大小 == 64 + 96*count` ——
这个恒等式让**尾部截断**和**朴素的尾部伪造追加**当场现形（纯"一条接一条"的格式
砍掉尾巴后前缀仍自洽，发现不了）。

**诚实的局限（写在 audit.h 里，并有反向断言把它跑出来）**：纯哈希链**挡不住能重写
整个文件的攻击者** —— 算法公开、链头就在文件头里，从任意一点重算整条链再把
`count`/`head` 改自洽即可。`test_audit` 里专门留了一条用例构造这种伪造并
**断言 verify 返回 0**，让这个洞一直可见。真正的防线是 §8.6 的"用设备 ML-DSA
身份钥对链头签名固化"，把 `(count, head, 时间)` 送到本机改不到的地方 —— 本模块
只负责提供随时可被签的链头（`audit_head`），签名固化本身未做，列在遗留项。
已接入槽位管理器 —— `hsm_token_attach_audit()` 挂上之后，init/login/登录失败/锁定/
生成/装载/签名/解封装/销毁/清零/解锁/备份导出/恢复/KEK 轮换全部自动落链，**失败也落**。

**zeroize 验证**（`tests/unit/test_zeroize.c`）：直接 include 私有头窥视槽位结构，
断言清零真的落到内存 —— 指针归零、`seed`/`pin_key`/salt/verifier 全 0、
整个结构体里搜不到原私钥的任何片段；从全部 5 个状态各清零一次都干净。
红线检查：密钥库文件、备份文件、Shamir 分片、审计日志里都搜不到明文私钥/PIN/验证值。

**诚实的界限**：本测试能证明"结构体内秘密字段被清零"和"落盘文件里搜不到明文"。
它**不能**证明已释放的堆页、CPU 寄存器、swap 分区没有残留 —— 那属于 Phase 7 的
"断电即失"与介质残留验证，**必须有板子**（§5.7.2）。

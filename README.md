# pqc-crypto-module

A post-quantum + SM-series **hardware security module prototype** running in the
programmable logic of a Xilinx Zynq UltraScale+ **XCZU3EG**. The cryptographic
cores, the noise source, the key vault and the access boundary all live in FPGA
fabric; Linux on the ARM cores is only the side that issues commands.

Every number in this repository comes from **the real device**, not simulation.

> **Status: research prototype.** Not certified, not hardened, not for
> production. See [Status and limitations](#status-and-limitations) — the gaps
> are listed, not hidden.

---

## What it does

| | |
|---|---|
| **Post-quantum KEM** | ML-KEM-512 / 768 / 1024 (FIPS 203), full KeyGen / Encaps / Decaps in RTL — byte-exact against NIST ACVP vectors **on silicon** |
| **Post-quantum signature** | ML-DSA-44 / 65 / 87 (FIPS 204), KeyGen / Sign / Verify in RTL, one bitstream covering all three parameter sets — byte-exact against ACVP **on silicon** |
| **Symmetric & SM-series** | AES-128/256, SM4, SM3 — checked against FIPS 197, GB/T 32907, GB/T 32905 |
| **True random source** | 8-ring-oscillator entropy source, SP 800-90B health tests (RCT/APT), SHA-3 sponge conditioning. Measured min-entropy **H = 0.871 bit/sample** |
| **Keys managed in the TEE** | Every key is generated by the OP-TEE TA from OP-TEE PRNG ⊕ PL TRNG entropy; only KEK-wrapped blobs (AES-256-GCM) are ever stored. Post-quantum private keys exist only as seeds, expanded inside the PL for each operation and wiped by hardware afterwards |
| **Hardware key vault** | Symmetric keys can be **loaded only by the TA through the secure world** (the load port accepts `AxPROT[1]=0` only; normal-world writes are dropped and counted) and leave only over a private wire to the cipher cores. There is **no read path in the RTL**; the vault is wiped when the session ends |
| **Security boundary** | AXI firewall gating on `AxPROT[1]`, proven in both directions on the board: the secure world reads a `SECURE_ONLY=1` core, the normal world is refused at the bus |
| **Standard front end** | SDF-style (GM/T 0018) C library, PKCS#11 v3.2 module, `hsmctl` CLI and an HTTP (JSON) gateway, so an application never sees a register |

Current default bitstream (with ML-DSA), post-route: 55,366 LUT (78.5 %), 199 DSP,
85 BRAM, WNS +1.615 ns @ 75 MHz.

## Architecture

```
 ┌──────────────────────────── PS · Cortex-A53 ─────────────────────────────┐
 │ application ─▶ libsdfe / hsmctl / hsm_httpd ─▶ pqchsm_fpgad (daemon)     │
 │                                   op sequences │          │ key blobs    │
 │ ···························· normal world ·····│··········│··············│
 │                                     /dev/secmmio     OP-TEE TA (S-EL0)   │
 │                                                │     gen / wrap / unwrap │
 │                                                │     PTA (S-EL1)         │
 │                                                ▼          ▼              │
 │              BL31 SiP (EL3): whitelisted MMIO · seed / sym-key loading   │
 └────────────────────────────────────────┬─────────────────────────────────┘
                 M_AXI_HPM0_LPD  (AXI4-Lite, AxPROT[1] = security bit)
                                          ▼
 ┌──────────────────────────── PL · FPGA fabric ────────────────────────────┐
 │                axi4lite_xbar  (full decode, one address per reg)         │
 │ ┌───────┬──────────┬─────────┬──────────┬─────────┬─────────┬─────────┐  │
 │ │ slot0 │  slot1   │  slot2  │  slot3   │  slot4  │  slot5  │  slot6  │  │
 │ │ trng  │key_vault │   sym   │  mlkem   │ canary  │   fan   │  mldsa  │  │
 │ │       │          │AES/SM4/ │ 512/768/ │ same as │ observe │44/65/87 │  │
 │ │       │          │   SM3   │   1024   │ slot 1  │  only   │         │  │
 │ └───────┴────┬─────┴────▲────┴──────────┴─────────┴─────────┴─────────┘  │
 │              └──────────┘  use_key: private wire, not the bus            │
 │  every slot sits behind axi4lite_firewall (AxPROT gate);                 │
 │  SECURE_ONLY=1 on all but the fan (slot 5) in the default build          │
 └──────────────────────────────────────────────────────────────────────────┘
```

Each slot is 64 KB at `0x8000_0000 + slot × 0x1_0000`.

**In the default build all five functional slaves (slots 0/1/2/3/6) are
`SECURE_ONLY=1`** — the normal world cannot reach any of them. Every core access
the daemon makes goes through `/dev/secmmio` to a BL31 SiP, which issues it from
EL3 against a whitelist; key material (post-quantum seeds, symmetric keys) travels
only TA → PTA → SiP, and those ports are not on the normal-world whitelist. Slot 4 remains a second key-vault
instance; under this configuration it is a like-for-like control that shows a
refusal is the gate's doing and not a broken core. The fan (slot 5) stays 0: it
is not inside the cryptographic boundary and should not be.

A second configuration exists for development — `PQC_DEV_OPEN=1` sets the
functional slaves to `SECURE_ONLY=0` so Linux can drive them directly, and its
product is named `zu3eg_hsm_dev.bit`. Same RTL, one parameter apart.

> ⚠️ **A refused access reads back 0; it does not raise an error.** The
> firewall and the address decoder are RAZ/WI, so no user-space program can
> take the board down with a bad address — deliberate, and verified on silicon
> (36,000 refused accesses, board still up). The flip side is that a mistyped
> address is silent; check `VERSION`
> (`0x0001_0000` on every core) rather than looking for an error code. Details
> in [docs/REGISTERS.md](docs/REGISTERS.md).

Full detail: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) ·
register-level contract: [docs/REGISTERS.md](docs/REGISTERS.md).

## Quick start

No board is needed for anything in this section.

```bash
git clone https://github.com/per1x/pqc-crypto-module
cd pqc-crypto-module

python3 -m venv .venv-rtl && ./.venv-rtl/bin/pip install cocotb
brew install icarus-verilog verilator      # or your distro's packages

./tools/rtl_sim_fast.sh     # iteration: per-module, Verilator, seconds to minutes
./tools/rtl_sim.sh          # full suite, 272 cocotb tests on Icarus (~40 min, run before merging)
./tools/rtl_lint.sh         # Verilator -Wall + Icarus, every module under hardware/rtl, zero warnings
./tools/rtl_synth_check.sh  # Yosys synthesisability
```

To build the host software and its PKCS#11 module (CMake ≥ 3.20, OpenSSL 3):

> The PQC algorithms come from the vendored mlkem-native / mldsa-native in
> `third_party/pqc-native/` — the same source tree the OP-TEE TA compiles.
> **liboqs is no longer a dependency.**

```bash
./tools/fetch_vectors.sh && cmake -S . -B build && cmake --build build -j
ctest --test-dir build --output-on-failure
```

Bitstream (Vivado 2020.1, ~35 min, target `xazu3eg-sfvc784-1-i`):

```bash
vivado -mode batch -source hardware/syn/impl_bitstream.tcl
```

### Calling it like a crypto module

`service/` gives an application the interface a real HSM exposes. The demo links
**no cryptographic algorithm library** — the OpenSSL it links serves the remote
port's TLS transport only — so any correct answer it prints
can only have come from the FPGA.

```c
#include "sdfe.h"

SDFE_HANDLE dev, ses;
uint8_t ek[1600], ct[1600], ss[32];
uint8_t blob[SDFE_SYMKEY_BLOB_MAX], pt[16], out[16];
uint32_t ek_len = sizeof ek, ct_len = sizeof ct, ss_len = sizeof ss, kh, blen = sizeof blob;

SDFE_OpenDevice(&dev);
SDFE_OpenSession(dev, &ses);

SDFE_GenerateRandom(ses, 32, ss);                    /* ring-oscillator TRNG  */
SDFE_GenerateKeyPair_MLKEM(ses, SDFE_MLKEM_768,      /* dk never reaches here */
                           ek, &ek_len, &kh);
SDFE_Encapsulate_MLKEM(ses, SDFE_MLKEM_768, ek, ek_len,
                       ss, &ss_len, ct, &ct_len);
SDFE_Decapsulate_MLKEM(ses, kh, ct, ct_len, ss, &ss_len);   /* by handle */

SDFE_GenerateKey(ses, /*slot*/ 3, 16, blob, &blen);  /* TA makes an SM4 key, loads it, returns the blob */
SDFE_Encrypt(ses, SDFE_ALG_SM4, 3, pt, out);         /* one block, computed in the FPGA          */
SDFE_LoadKey(ses, 3, blob, blen);                    /* next session: load the same key again    */
```

Plaintext import (`SDFE_ImportKey`) is still in the interface but always returns
`SDR_NOTSUPPORT`: plaintext keys never pass through the normal world.

Build and run: `make -C service && ./service/sdf_demo`.
Interface reference: [docs/API.md](docs/API.md).

From another machine, the full demo over the remote port (TCP 9797, **mTLS**):

```bash
./demo/remote/run.sh                           # asks for the address; ships demo credentials
./tools/demo_remote.sh <board-ip> --provision  # use your own PKI instead (once)
```

### Command line and HTTP

- **`hsmctl`** — one business action per command (`keygen`, `encrypt`, `sign`,
  `encap`, `backup`/`restore`, …), a thin shell over `service/hsmops.c`. Keys are
  stored as public key + TA-wrapped blob, never in plaintext.
- **`hsm_httpd`** — the same operations as JSON over HTTP: `127.0.0.1:8080`
  (plain, loopback only, for on-board apps) and `:8443` (HTTPS, mutual TLS).

Command and route reference: [service/README.md](service/README.md) (full manual in
Chinese in [README.zh-CN.md](README.zh-CN.md)). The on-board business demo
(`sh /media/sd-mmcblk1p2/demo/run.sh`) runs the whole flow and shows which layer —
TEE, TEE→PL, PL, daemon — did each step; a captured run is in
[docs/demo/business_demo.html](docs/demo/business_demo.html).

## Status and limitations

Accurate statements about what this does **not** do.

- **The ACVP KeyGen path still hands out the private key.** On the product path
  the private key never leaves the PL: the TA generates and wraps the seed, writes
  it into the PL staging port through the secure world, and each operation
  (`MODE.CHAIN`) expands it and has the hardware wipe it afterwards. But the
  KeyGen that takes `d‖z` from software is still there — ACVP has to reproduce and
  check the private key from a given seed — and its `dk` is read from `OUT_DATA`.
  `CTRL.SEED_LOCK` forces KeyGen onto the staging port, but it is a latch, not a
  fuse: a power cycle clears it, and the daemon does not set it by default.
- **root can still make the hardware compute.** The daemon assembles operation
  sequences in the normal world and issues them through the EL3 SiP whitelist.
  Key *loading* has moved into the secure world (the symmetric load port accepts
  secure transactions only, and the whitelist excludes it), so the normal world
  can neither read nor inject key material — but it can use keys that are already
  loaded, and any process able to open a TA session as `LOGIN_USER` can have the
  TA load a key from **its own** blob. Per-caller authorisation is not done yet.
- **The KEK root is derivable.** The TA's HUK is SHA-256(Device DNA), with no
  eFUSE burned; DNA is readable, so to someone holding both the DNA and a blob,
  the blob is not real ciphertext. A real HUK sits behind authenticated boot (see
  the encrypted-boot item below). On the host side, `src/crypto/kdr.c` is a stub
  constant in the DEV profile (compiled out in PRODUCTION, which fails closed with
  no provider); `PQCHSM_KDR=device-dna` switches to a root bound to Device DNA.
  ⚠️ **DNA is not a secret** — it buys anti-cloning, not confidentiality.
- **No SM2 core.** SM4 and SM3 are present; the SM2 asymmetric algorithm is not.
- **This is a security prototype, not a fast one.** Throughput figures include
  per-byte software AXI traffic and are published for the 1 : 1.5 : 2.1 ratio
  across parameter sets, not as a performance claim.
- **Power and EM side channels are out of scope, deliberately.** Constant-time
  work covers timing only. Masking cannot be validated without a side-channel
  bench, and shipping unvalidated masking is worse than shipping none.
- **There is no encrypted boot.** BBRAM is blocked by board hardware (no cell on
  `VCC_BATT`) and the PUF black key is rejected by the BootROM before the PUF is
  ever reached. RSA authenticated boot does work with zero eFUSEs, but it is not a
  trust root — `bh_auth_enable` is defined as skipping the eFUSE PPK hash check. A
  replacement-resistant trust root requires burning eFUSE, which is this project's
  permanent red line. Evidence and the full argument:
  [docs/SECURITY.md](docs/SECURITY.md).
- **PS-side XMPU/XPPU cannot reach the PL window.** UG1085 settles it: no PS
  protection unit covers `0x8000_0000`. The firewall in the PL is the only
  enforcement point on this path — which is why the address decode is one-to-one
  with no mirrors.
- **DDR-side XMPU blocks reads, not use.** The XMPU does not gate transactions; it
  poisons them and the endpoint gates (XAPP1320 v3.0 p.10). BL31 configures it at
  boot, so a normal-world read of OP-TEE's secure memory is a bus error with no
  manual step. That is all it stops — root can still ask the hardware to compute,
  since the SiP does not check the caller.

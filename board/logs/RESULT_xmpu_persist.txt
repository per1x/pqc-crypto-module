=== XMPU 按属性毒化：**开机自动生效**（2026-08-17 收尾会话）===

这份和 RESULT_xmpu_poison.txt 的区别只有一条，但那是最要紧的一条：
那一份的毒化是**跑起来之后用 JTAG 手动打开的**，重启就没了；
这一份是 **BL31 在 EL3 里开机就写好的**，全程没有任何 JTAG 步骤、没有任何手工动作。

镜像：BOOT.BIN = 0ea6e4437698abc7b44b3a235b49ce78
      （BL31 = LOG_LEVEL=20；bl31.elf 离板副本 312a8c09…，
        在构建机 /home/build/keep/，已置只读）
CSU_MULTI_BOOT = 0x00000000  ← 默认上电路径，不是靠 multiboot 指到某个非 golden 槽

----------------------------------------------------------------------
一、开机后直接读（没有做任何事，就是等它起来）
----------------------------------------------------------------------
  0x60000000 = Bus error (SIGBUS, 退出码 135)
  0x60100000 = Bus error (SIGBUS, 退出码 135)
  0x60200000 = Bus error (SIGBUS, 退出码 135)
  0x6FFFF000 = Bus error (SIGBUS, 退出码 135)     ← 区域末端

--- 对照：区域外与共享内存，应当不受影响 ---
  0x10000000 = 0xEDFE0DD0                        ← 设备树魔数，照常
  0x70000000 = 0x00000000                        ← OP-TEE 共享内存，故意不圈，照常

----------------------------------------------------------------------
二、同一次启动内的关/开对照（判据只认同址前后对照）
----------------------------------------------------------------------
用 JTAG 把六个实例的 POISON 清零（**仅为取对照证据**），再从 Linux 读同一个地址：

  毒化关闭（POISON=0）      0x60000000 = 0xAA0003F3   ← OP-TEE 的一条 AArch64 指令
  毒化开启（ATTRIB=1）      0x60000000 = Bus error

也就是说：**这块板上的 root 在毒化关闭时确实读得到 OP-TEE 的安全内存**，
开启之后读不到了。这条是反证，不是推论。

----------------------------------------------------------------------
三、"重启之后自己回来"——这才是这份日志的重点
----------------------------------------------------------------------
接着上面那步（此刻毒化是**关**的、0x60000000 读得出 0xAA0003F3），
直接 sysrq 重启，什么都不做：

  重启后 uptime = up 0 min
  CSU_MULTI_BOOT = 0x00000000
  0x60000000 = Bus error          ← BL31 自己又把它写回去了

----------------------------------------------------------------------
四、寄存器实配（JTAG 读，六个实例）
----------------------------------------------------------------------
  inst  CTRL        POISON      R15_STRT    R15_END     R15_MSTR    R15_CFG
  DDR0  0x0000000B  0x00100000  0x00060000  0x0006FFFF  0x00000000  0x00000017
  DDR1  0x0000000B  0x00100000  0x00060000  0x0006FFFF  0x00000000  0x00000017
  DDR2  0x0000000B  0x00100000  0x00060000  0x0006FFFF  0x00000000  0x00000017
  DDR3  0x0000000B  0x00100000  0x00060000  0x0006FFFF  0x00000000  0x00000017
  DDR4  0x0000000B  0x00100000  0x00060000  0x0006FFFF  0x00000000  0x00000017
  DDR5  0x0000000B  0x00100000  0x00060000  0x0006FFFF  0x00000000  0x00000017

  CTRL 保持 0x0B（DEFRDALWD|DEFWRALWD|ALIGNCFG）—— **没有动 POISONCFG**，
  理由见 patch_atf_secmmio.py 里的长注释（BASE=0 时置它会把违规写打进物理地址 0）。

protunit_probe（经 EL3 只读窗口读实配）另外显示：
  DDR1 ERR_ADDR=0006002e ERR_MASTER=000000a0(APU) ISR=00000008[SECURTYVIO]
  DDR2 ERR_ADDR=0006000d ERR_MASTER=000000a0(APU) ISR=00000008[SECURTYVIO]
  → DDR1/DDR2 就是 XAPP1320 图 3 里 APU 到 DDR 的两个 CCI 端口。
    它们把 APU 的非安全访问判成安全违规并锁存 —— 检测和拦截现在都成立了。

----------------------------------------------------------------------
五、EL3 那一笔写到底有没有进去 —— 用采样点夹死（诊断版镜像）
----------------------------------------------------------------------
旧结论说"POISON 回读恒 0，分不清是没写进去还是写进去又被清掉"。
这次用**三个采样点**把它切开。采样值写进被禁用区域 R14 的三个寄存器
（R14_CONFIG 的 EN=0，这三个字不参与任何判定，纯当草稿纸；
 而 0xFD00_0000 段本来就在 SiP 的只读白名单上，所以普通世界读得到，
 **不需要串口、也不需要 JTAG**）：

  采样①  R14_START (+0x1E0)  早期那次写完，紧接着回读
  采样②  R14_MASTER(+0x1E8)  BL31 交接前读一次（早期那次还在不在）
  采样③  R14_END   (+0x1E4)  交接前再读一次

两个诊断版镜像，六个实例，**十二个采样点全部读到 0x00100000**：

  3771d140…（带"交接前再写一次"）  ①=②=③=0x00100000
  8a290f42…（去掉那次重写）        ①=②=③=0x00100000

结论：**EL3 那一笔写从来就是成功的，也从来没有被谁清掉。**
"交接前再写一次"是多余的，已经去掉（patch_atf_secmmio.py 里
PQCHSM_XMPU_LATE 默认 0）。生产版镜像不带任何诊断写 —— 上面第四节
那次 JTAG 读里 R14 三个字全是 0，就是这一点的自检。

⚠️ 那么旧的"回读恒 0"是怎么来的？**那份带 POISON 写的镜像根本没跑起来。**
   它被 FSBL 的 100 秒看门狗打掉、multiboot 自增到 7，实际跑的是槽 7 里
   另一份不含这段代码的 BL31 —— 读的是那一份的 POISON。详见
   RESULT_slot_boot_wdt.txt。

----------------------------------------------------------------------
七、这条**没有**验证
----------------------------------------------------------------------
· **没做真 POR 复验。** board/scripts/jtag_por.tcl 要求 PMU 的 CSU_ROM 错误位
  是置着的才能触发，而这轮收尾时 ERROR_STATUS_1/2 都是 0（本轮没有任何一次
  BootROM 失败）。为了凑一个 POR 触发源去故意搞坏一次启动，风险大于收益，
  所以没做。
  已验证的是**等价的冷路径**：CSU_MULTI_BOOT=0、从 BOOT.BIN 起、
  BootROM→FSBL→BL31→OP-TEE→U-Boot→Linux 整条链与上电完全相同。
  真 POR 相比它只多"清 POR-only 闩锁"，而 XMPU 的配置是 BL31 每次启动都重写的，
  不依赖任何 POR-only 状态。
· 万一新 BOOT.BIN 在某次真上电时起不来：FSBL 会 multiboot++ 落到
  BOOT0001.BIN（bb3402ea，已知 10/10 能启动）——板子仍然起得来，
  只是那一份**不带**开机毒化。

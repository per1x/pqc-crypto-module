# 常量时间与内存清零

本文档记录审计了什么、用什么方法审计、审计发现了什么，以及结论到哪里为止。所涉及
的分层参见 [architecture.zh-CN.md](architecture.zh-CN.md)。

覆盖两条性质：

- **常量时间** —— 接触密钥材料的代码，其执行时间不得依赖该材料的取值。
- **清零** —— 密钥材料不得在不再需要之后仍留在内存里。

这两条都不是靠"写的时候小心"能维持住的性质，而且在功能测试里完全看不出来：对 MAC
标签用一次 `memcmp`、中途加一条跳过清零的 `return`、用秘密字节做表下标，全都能通过
整套正确性测试。所以两条都被写成每次回归都要跑的检查。

## 范围

| 在范围内 | 不在范围内 |
|---|---|
| `src/` 下的全部代码 | liboqs 内部 |
| 比较原语 `pqc_ct_equal` | OpenSSL 内部 |
| `src/backup/shamir.c` 的 GF(256) 运算 | `hardware/` 的 RTL 与 Python 参考模型 |
| `src/` 与 `include/` 里密钥材料的生命周期 | `cli/`、`tests/`、`demo/` |

排除项各有各的理由，如实写明：

- **liboqs 与 OpenSSL** 实现了活路径上的每一个密码原语。它们的时序特性是那两个项目
  的性质，不是本项目的性质；本项目对此不作任何断言，也无法从外部验证。liboqs 在部分
  平台上用手写汇编，源码级审计在那里本来也没有意义。
- **`hardware/`** 是寄存器传输级逻辑，那里该问的是周期数而不是指令时序。`ntt_core`
  与 `keccak_f1600` 每次变换的周期数固定（分别是 3457 与 24）、与数据无关 —— 但这一点
  由 cocotb 回归保证，不由这里的工具保证。

  RTL 里唯一一处**真正的**常量时间要求在 `mlkem_decaps`：解封装最后要比对
  重加密出来的密文 c′ 与送进来的 c，比对一旦提前退出，就能从"解封装用了多久"
  读出两者从第几个字节开始不同 —— 而 c′ 是攻击者送进来的 c 解密再加密的结果，
  这条时序信道足以逐字节恢复明文（Fujisaki-Okamoto 变换里最经典的一个坑）。
  该核的做法是：比对固定跑满整条密文、只累积一个 `cmp_diff`、隐式拒绝值
  J(z‖c) 无条件先算好、最后用位掩码而不是 `if` 选。
  `test_decaps_constant_time` 直接测这条性质（同一 dk 下三种密文拍数必须相同），
  并且**验过它会咬人**：把比对改成一发现不同就跳出，只有这一条用例会挂。

  > 同一个 param_set 下换一把密钥，拍数会差约 0.1%。那来自封装里矩阵 A 的
  > 拒绝采样，只取决于**公开的** ek，与密文和私钥都无关。
- **`cli/` 与 `tests/`** 不持有长期密钥材料；daemon 把 PIN 直接透给槽位管理器，并清掉
  自己的栈缓冲。

## 方法

### 源码级审计 —— `tools/ct_audit.py`

工具先剥掉注释与字符串字面量，再对剩下的部分套四条规则：

| 规则 | 命中什么 |
|---|---|
| R1 比较 | `memcmp` / `strcmp` / `strncmp` / `bcmp` 作用于秘密数据 |
| R2 分支 | `if` / `while` / `switch` / `?:` 的判据里读取了秘密数据 |
| R3 下标 | 数组下标表达式由秘密数据派生 |
| R4 除法 | 除数由秘密数据派生 |

"秘密"按标识符命名判定（`sk`、`seed`、`pin`、`kek`、`bek`、`rmk`、`cek`、`ss`、
`verifier`、`tag` 等），另有一张排除表挡住名字里带同样词根的公开量（`sk_len`、
`key_type`、`pin_flags` 等）。按命名判定会多报而不会少报，对审计工具来说这是正确的
偏向。

两处细化让输出可操作而不是一堆噪声：

- **把秘密传进函数，不等于按它分支。** `if (pqc_wrap(kek, …) != 0)` 分支的是返回码。
  工具在分析判据前先把函数调用整体折叠掉，只有直接在判据里被读取的值才算数。
- **访问链按链尾分类。** `g_secrets[i].in_use` 取到的是 `in_use` 而不是 `g_secrets`；
  `s->sk` 取到的是 `sk`。

指针有效性判断（`if (!sk)`、`sk == NULL`）不是数据相关分支，不予上报。

### 白名单

可疑点可以用注释标记声明为"已审阅"，写在同一行或紧贴上方的注释块里：

```c
/* tag 在这里是 TLV 的类型字段，不是 MAC 或摘要。帧结构在解析阶段
 * 本来就是攻击者可见的。
 * 常量时间：判据是公开的协议标签，与任何密钥材料无关 */
if (t == tag) {
```

标记后面必须给出理由。带标记的条目会单列在报告的白名单一节，而不是静默消失 ——
每一条"这里没问题"都必须带着看得见的依据。

### 统计式时序测试 —— `tests/unit/test_ct_timing.c`

源码级审计说明不了编译器与流水线实际跑成什么样。时序测试按 dudect 的思路直接量：
构造两类输入 —— 一类固定、一类随机 —— 以随机交错的顺序采样，再对两组样本做 Welch
t 检验。执行时间与数据无关时，两组样本同分布，|t| 留在噪声范围内。

这个测试被写成不可能"空过"：

- **反证。** 同一套采样与检验会再跑一遍 `leaky_equal()` —— 一个提前退出的比较。它
  **必须**被判为有数据依赖；判不出来就说明这套装置没有区分能力，此时用例失败，而不是
  报告通过。
- **空对照。** 两类输入都取随机。这时连 `leaky_equal()` 都不该被判出差异。它排除的是
  反向失效：一套对任何输入都报"有差异"的装置。

在负载重的机器上保持稳定靠三件事：门限取得保守（|t| ≤ 25，dudect 常用值是 10）、每轮
裁掉最慢的 10%（长尾来自调度而不是被测代码）、跑 7 轮取中位数。

### 清零检查 —— `tools/check_zeroize.py`

两条结构性检查，与审计工具共用同一套秘密命名判定 —— 两份报告对"什么算密钥材料"
必须给出同一个答案：

| 检查 | 要求 |
|---|---|
| A 结构体覆盖 | 结构体的每一个密钥字段都要在其销毁函数里被清零 |
| B 返回路径 | 局部密钥缓冲在写入之后的每一条 `return` 上都必须已清零 |

检查 A 会做传递闭包：`slot_wipe_key_material()` 与 `slot_wipe_pins()` 合起来覆盖
`slot_t`，而整体清零 `pqc_secure_zero(x, sizeof(*x))` 一次算作覆盖全部字段。**类型名
本身就表示秘密**的结构体（`p11_secret_t`）被要求整体清零而不是逐字段清 —— 否则将来
新增一个字段就会悄悄漏掉。

检查 B 是线性近似：它按文本顺序推进函数体，不做控制流分析，因此对"写入分支与提前
返回互斥"的写法会多报。两条检查都用 `无需清零：` 标记加必填理由，写在缓冲的声明处
（整条豁免）或某一条 `return` 上。

### 清零测试 —— `tests/unit/test_zeroize.c`

五组运行期断言，其中三组值得单说：

- **结构性覆盖。** 槽位清零之后，测试把整个 `slot_t` 抄一份，挖掉少数几个合法非零的
  字段（互斥量、元数据、元数据的 KMAC 标签、解锁目标状态），断言剩下的每一个字节都是
  0。将来新增的字段默认落在"剩下的字节"里，忘了清零会在这里当场失败，而不是从一串
  逐字段断言的缝里溜过去。
- **死存储消除。** `pqc_secure_zero` 只有在那条存储扛过优化时才有意义。一个 `noinline`
  函数在自己的栈帧里填满哨兵、清零、通过 `volatile` 指针把帧地址留出来，然后返回；
  调用方再把这段已经死掉的栈读回来。这个 TU 专门编在 `-O2`，好让编译器有动机去消除
  那条存储。反证是同一套探针但完全不清零 —— 它必须找得到哨兵；找不到就说明探针根本
  没读到那段内存，"清零后找不到"这个结论也就一文不值。
- **释放后残留。** 一批块填上哨兵后释放，再用普通 `malloc` 申请一批同样大小的块来扫。
  这条检查由它自己的反证把关：普通 `malloc`/`free` 必须让哨兵仍然可见，否则说明分配器
  在释放时自己就清了块内容，这套观察手段在该平台没有分辨力。反证不成立时测试如实说明
  并跳过，而不是记成通过。

## 审计发现

对 `src/` 跑一遍审计，得到四条真实问题，均已修复。

### `src/hal/accel_stub.c` —— 按签名随机化输入分支

寄存器接口里没法传空指针，所以约定 `rnd` 全 0 表示"让后端自取随机数"。哨兵判定
写成了逐字节分支：

```c
int all_zero = 1;
for (int z = 0; z < 32; z++) {
    if (rnd[z]) {
        all_zero = 0;
    }
}
```

`rnd` 是 ML-DSA 的签名随机化输入，属于秘密数据。这条分支会泄漏"哪一个字节先非零"。
改成固定 32 轮的按位或累加，无分支。

### `src/hal/accel_stub.c` —— 错误路径上私钥留在缓冲里

签名路径先把私钥拷进本地缓冲，之后才校验上下文长度。校验失败时直接返回、没有清零，
于是一份完整的 ML-DSA 私钥会在一个 `static` 缓冲里留到进程结束。该路径已补上
`pqc_secure_zero`。

### `src/store/keystore.c` —— 派生失败时留下半截密钥

`keystore_save_impl()` 在同一个条件里派生 KEK 与全文件 MAC 密钥。第二次派生失败时，
第一次已经把一把完整的 KEK 写进了缓冲，而函数就这么返回了。现在这条路径会把两个缓冲
连同盐一起清掉。

### `src/crypto/kdr.c`、`src/hal/pqc_accel.c`、`src/slot/slot.c` —— 失败路径未清缓冲

另有三条路径在 KDF 或 `RAND_bytes` 失败后直接返回，而那次失败可能已经往种子或根密钥
缓冲里写进了半截数据。三处现在都先清零再返回。

### 属于命名撞车而不是缺陷的条目

有四处上报是通用命名造成的误报。这些名字本身确实有误导性，所以在源头改名而不是加
白名单：

- `accel_stub.c` 用 `rnd` 当 Keccak 的轮计数器，与同一文件里表示签名随机化输入的
  `rnd` 撞车。改名为 `round`。
- `p11_module.c` 用 `want` 表示请求的对象类别、`slot.c` 用 `want` 表示请求的状态，与
  密码学源文件里表示"重算出来的期望标签"的 `want` 撞车。分别改名为 `want_class` 与
  `want_state`。

只有一处进了白名单：`src/proto/proto.c` 的 `tlv_find()` 按 `tag` 分支，而这里的 `tag`
是 TLV 的类型字段 —— 属于帧结构，任何看得到线路的人都看得到，与任何 MAC 无关。

## 清零检查里的豁免

共八条豁免，都写了理由，分两类。

**公开的完整性标签。** `keystore_save_impl().tag`、`hsm_keystore_load().want`、
`slot_meta_verify().want`、`slot_t.meta_tag`，以及 `audit_verify_file()` 与
`audit_read()` 里的审计链哈希，都是会写进文件或随锚点公布出去的 MAC 与哈希。去清零一个
模块自己要公布的值只是做样子；真正要清的是算出它的那把密钥，而那把密钥是清了的。
`meta_tag` 还额外**不能**清：清零会把元数据复位并重新盖章，槽位在被清空之后仍然是可验
完整性的。

**对象句柄。** `p11_session_t.sign_key` 与 `.verify_key` 是 PKCS#11 的对象句柄 ——
槽位号加代数。它们指向的密钥材料从不离开槽位。

## 已经就位的常量时间构造

审计确认了下面这些，而不是引入了它们。之所以列出来，是因为它们的理由从代码本身看不
出来：

- **`pqc_ct_equal`**（`src/util/util.c`）把整段长度上的 XOR 差异累加起来，最后只比一
  次。仓库里每一处 PIN 验证值、包裹标签、元数据标签、分片校验和、备份 MAC 与审计链哈希
  的比较都走它。审计确认 `src/` 下没有任何一处用 `memcmp` 比较秘密数据：现存的六处
  `memcmp` 比的全是文件格式魔数。
- **GF(256) 乘法**（`src/backup/shamir.c`）用位运算的俄罗斯农民乘法，而不是 log/antilog
  查表。查表要用秘密数据当下标，会在 D-cache 上留下痕迹。这里的循环固定八轮、无数据相关
  内存访问，系数选择全部靠 0x00/0xFF 掩码完成。
- **GF(256) 求逆**用固定加法链算 `a^254`，而不是扩展欧几里得，链长与 `a` 无关。
- **拉格朗日插值**在 x=0 处只与公开的分片索引有关；逐字节累加就是 XOR，没有分支。

## 不作断言的部分

- **对 liboqs 与 OpenSSL 不作任何断言。** 活路径上每一次 ML-KEM 与 ML-DSA 运算都在
  liboqs 内部完成。liboqs 若有时序侧信道，本模块就有，而这里的任何检查都发现不了。
- **审计是源码级的词法分析，不是编译器级的。** 它看不见编译器引入的分支、看不见编译器
  拒绝生成的 `cmov`、也看不见被溢出到栈槽之后又被重新装载的秘密。时序测试从经验上覆盖了
  比较原语，代码库的其余部分只有源码审计覆盖。
- **清零检查是静态近似。** 检查 B 没有控制流分析，缓冲在一条分支里写入、从另一条分支
  返回，且形状超出线性扫描的模型时，它会漏掉。
- **对进程地址空间之外的内存不作任何断言。** CPU 寄存器、已换出的页、掉电之后的 DRAM
  都不在覆盖范围内。密钥缓冲会尽力 `mlock`，但那是 best-effort，在内存压力下的行为未经
  验证。
- **释放后残留的观察与平台有关。** 在 glibc 上，反证能在 32 个重新申请的块里全部找到
  哨兵，因此这条检查在 Linux 回归上是带完整分辨力运行的。macOS 的系统分配器在释放时就
  清掉了块内容；反证会检测到这一点，测试如实报告跳过，而不是记成通过。

## 复现

```bash
# 源码级审计。先跑自检：一个什么都扫不出来的扫描器，报"没问题"说明不了任何事。
python3 tools/ct_audit.py --self-test
python3 tools/ct_audit.py

# 清零结构性检查，顺序同上。
python3 tools/check_zeroize.py --self-test
python3 tools/check_zeroize.py

# 运行期检查。
cmake --build build --target test_ct_timing test_zeroize
./build/test_ct_timing
./build/test_zeroize

# 五项都接进了 ctest。
ctest --test-dir build -R 'ct_audit|ct_timing|zeroize'
```

两个工具在存在未标注条目时都以非零退出码结束，因此它们会让构建失败，而不是打印一条
没人看的警告。

时序测试在开发机（Apple M 系列，macOS，Apple clang）上的实测输出：

```
    比较长度 4096 字节，每类每轮 20000 次采样，7 轮取中位数，裁掉最慢的 10%
    反证   leaky_equal（提前退出）     |t| =   1444.4  门限 25
    被测   pqc_ct_equal                |t| =      0.7  门限 25
    空对照 两类均随机：leaky |t| =    0.0   ct |t| =    0.4
```

在 aarch64 Linux 容器（Debian，GCC 12，glibc）上：

```
    反证   leaky_equal（提前退出）     |t| =    366.8  门限 25
    被测   pqc_ct_equal                |t| =      1.5  门限 25
    空对照 两类均随机：leaky |t| =    1.0   ct |t| =    1.1
```

反证与被测之间隔着两到三个数量级，这正是重点：这套装置确实能把有数据依赖的比较与
常量时间的比较分开，`pqc_ct_equal` 落在常量时间那一侧，而且在两套工具链上距离门限
都留着足够的余量，调度噪声不足以改变判定。

`test_zeroize` 在 GCC 12 / glibc 上报 110 条断言，在 macOS 上报 108 条：多出来的两条正是
释放后残留检查 —— 它在那里的反证成立，所以真正跑了起来。两套工具链都观察到同一位置上
的普通 `memset` 被当成死存储消除，而 `pqc_secure_zero` 扛了下来 —— 这正是
`pqc_secure_zero` 存在的理由。

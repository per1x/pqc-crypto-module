## 一、这台密码机现在是什么

**密码边界是 FPGA fabric。** ML-KEM 核、ML-DSA 核、对称核（AES-128/256、SM4、SM3）、
环形振荡器熵源、片内密钥金库与访问门控全部在 PL 里。主机侧的 PKCS#11 / SDF 库、
keystore、槽位元数据跑在它**之外**。

### 能力清单

| 类别 | 能力 | 证据 |
|---|---|---|
| KEM | ML-KEM-512/768/1024 KeyGen / Encaps / Decaps | 真硅上逐字节对 NIST ACVP（20/20） |
| 签名 | ML-DSA-44/65/87 KeyGen / Sign / Verify | 真硅上逐字节对 ACVP（32/0，见下方 ⚠️） |
| 对称 | AES-128/256、SM4，ECB/CBC/CTR/CFB/OFB | 对 SP 800-38A / GB/T 32907 |
| 杂凑 | SM3 | 对 GB/T 32905 A.1 |
| 熵源 | PL 环振 + SP 800-90B 健康检测 | 调理前 H = 0.871 bit/sample；PL 重配重启矩阵 H = 0.507 ≥ 0.436 |
| 私钥保护 | 片内金库：`dk`/`sk` 不出总线，按槽号使用 | 读游标 seek 到 sk 段读回全 0，而按槽签出的 σ 与自送 sk 逐字节相同 |
| 接口 | GM/T 0018 风格 SDF、PKCS#11 v3.2 | `sdf_demo` 九节全绿；p11 演示 |
| 设备绑定 | 密钥派生根可绑 Device DNA（默认关） | 板上与远端主机两条路都跑通 |

⚠️ **ML-DSA 的 32/0 是在 SK_LOCK 闩上之前取的。** 闩上之后 KeyGen 只吐 `pk`，
ACVP 的 KeyGen 向量比对不了私钥 —— 那 6 条**必然**失败，**那是闩锁在正常工作**。
`mldsa_hwtest` 现在会把这句话直接打出来。要重取 KeyGen 证据：先重配 PL 清掉闩锁，
且别让 daemon 先起来。

### 明确**没有**的东西

* **没有安全启动**（BBRAM 那条见第四节；不烧 eFUSE = 没有防替换的信任根）
* **没有 SM2**
* **没有算法证书**（ACVP 向量是本地跑的，那是正确性证据，不是证书）
* **root 仍然能"用"密钥**（读不到私钥，但能命令硬件做运算 —— SiP 不校验调用来源）
* **root 仍然读得到 OP-TEE 的安全内存**（见第三节 XMPU）
* **没有功耗/电磁侧信道对策**（刻意排除，理由见 SECURITY）

## 四、被卡住的两件

### ⛔ BBRAM 加密启动 —— **受阻：板级硬件限制（`VCC_BATT` 没接电池）**

**这不是"没做对"，是这块板上两个必要条件互斥。** 2026-08-17 用两次物理断电
把它验到底了。

**证据链（闭合的）**

| 环节 | 结论 | 怎么证的 |
|---|---|---|
| 镜像的密码学 | **对** | 线下解密：nky `Key 0` + 启动头 IV，在 `fsbl_sourceoffset=0x2800` 处 **48 字节安全头 + 16 字节 GCM tag 校验通过**，明文正是 ZynqMP 安全头该有的样子（32 字节全 0 = 不换钥、12 字节 = `IV 1`、4 字节 = 字数，对上 pmufw 长度） |
| bif 结构 | **对** | 与 `bootgen -bif_help keysrc_encryption` 的官方示例逐字一致 |
| nky 格式 | **对** | 直接用 bootgen 自己生成的那份（`Device xczu3eg`，两对 Key/IV） |
| 钥匙进了 BBRAM | **是** | XilSKey 返回 `Status=0`；`BBRAM_STS` 读到 `CRC_DONE=1 / CRC_PASS=1` |
| 启动头声明 BBRAM | **是** | `0x3A5C3C5A`，由对照编译定死（同一份 bif 只改 `[keysrc_encryption]`） |
| 多重启动通路 | **通** | 同一个槽放**与 golden 逐字节相同**的明文孪生镜像，能起 |
| `PGM_MODE` 锁存 | **只有 POR 能清** | 软件四种复位全试过（XilSKey `PrgrmDisable`、JTAG 直写、JTAG `rst -system`、Linux 走 PMU system 域复位），POR 后实测由 `1` 变 `0` |
| POR 之后启动 | **仍失败** | **两轮**，其中第二轮是"烧完立刻断电、上电第一件事就启动"，排掉了"中间那些 JTAG 复位干扰了 BBRAM"这个干扰 |

**唯一能同时解释全部现象的解释**：这块 AXU3EG 的 `VCC_BATT` **没有接电池**，
POR 在清掉 `PGM_MODE` 的同时把 BBRAM 里的钥匙也清了。于是：

* 烧钥匙 → 钥匙在，但 `PGM_MODE=1`，**CSU 不把它交给 BootROM**
* 断电清锁存 → 锁存清了，**钥匙也没了**

**两个条件在这块板上永远不可能同时成立。**

**要让它成立需要什么**：给 `VCC_BATT` 接一颗电池（板级硬件改动）。
这不是配置问题，也不是代码问题，**不是软件能绕过去的**。

⚠️ 即便将来接上电池跑通了，口径也只能是**机密性 + 可恢复**：不烧 eFUSE 就没有
`ENC_ONLY`，攻击者换一份声明为"不加密"的镜像，BootROM 照启不误 ——
**加密挡不住替换，不是防替换的信任根。**

**留下的可复用资产**（接上电池就能直接用）：

* `boot/persist/build_bbram_boot.sh` —— 生成加密 BOOT.BIN，两道自检
  （前段无明文串、启动头密钥来源位 = `0x3A5C3C5A`），`ENC=0` 出明文孪生对照组
* 加密镜像成品：板上 `/media/sd-mmcblk1p2/hsm/BOOT_ENC2.BIN`（**不在任何启动槽**）
* 烧写程序：构建机 `/home/build/bbram_ws/bbapp/Debug/bbapp.elf`
* 密钥：构建机 `/home/build/nkytest/gen.nky` 的 `Key 0`

⚠️ **两个把人骗住的坑，写在这里省下别人的时间**：
① ZynqMP 的安全头是 **48 字节**不是 64（权威在
`xilsecure_v4_0/src/zynqmp/xsecure_aes.h` 的 `XSECURE_SECURE_HDR_SIZE`）——
我按 64 空跑了好几轮线下解密。
② `0x3A5C3C5A` 是 BBRAM、`0xA5C3C5A3` 是 eFUSE，**极容易记反**。

**板子现在是安全的**：golden `BOOT.BIN` 是明文头、`ENC_ONLY` 没烧，
BootROM 根本不看 BBRAM，随时断电都能起来；起不来的加密镜像不在任何启动槽里。

### 🔶 PUF + 黑钥放启动头 —— **走到了"BootROM 拒收"，比 BBRAM 远，但还没通**

**已经做成的（都不用烧 eFUSE）：**

* PUF 注册跑通：`xilskey_puf_registration`（`XSK_PUF_PROGRAM_EFUSE=FALSE`、
  `XSK_PUF_INFO_ON_UART=TRUE`、4K 模式），裸机经 JTAG 跑。
* 串口当时正好进了那个"枚举正常但控制端点全废"的坏状态，**改为用 JTAG 直接读
  `PufInstance` 结构** —— 偏移靠"读 `RedKey` 和 `BlackKeyIV` 与配进去的值逐字节对上"
  验证（第一版算多了 4 字节，就是这么发现的）。拿到：

  ```
  CHASH        = 0x5D5FBDBC
  AUX          = 0x00864FE2
  辅助数据      = 386 字（1544 字节）
  BlackKeyIV   = A1B2C3D4E5F60718293A4B5C   （与配置逐字节相同 → 偏移正确）
  BlackKey     = B905C759 48FB929D 74CCC353 82A62581 09A01D5B E8769714 6D7AB7A3 6F594F8A
  ```

* bootgen 接受了这份数据并出了镜像。**辅助数据文件必须正好 386 字、且不带
  CHASH/AUX** —— 带上就报 `Invalid no. of data bytes for PUF Helper Data`。
* 启动头自检通过：密钥来源位 = `0xA35C7C53`（启动头黑钥），
  头里 `0x4c` 处的黑钥与 PUF 产出的**逐字节相同**。

**没做成的：BootROM 拒收这份镜像 —— 两轮，能核对的字段已全部核对过。**

第二轮修了辅助数据的布局（第一轮塞了 386 字**纯**辅助数据；bootgen 要的是
**384 字辅助数据 + CHASH + AUX**。判据是搜镜像：第一轮 `AUX` 在整个镜像里
一次都没出现，修完之后 CHASH 在 `0xeb8`、AUX 在 `0xebc`）。**结果不变。**

到此为止能核对的字段全部核对过，**没有一项不对**：

| 字段 | 值 | 判定 |
|---|---|---|
| 密钥来源位（`0x28`） | `0xA35C7C53` | ✅ 启动头黑钥 |
| 启动头里的黑钥（`0x4c`） | `b905c759…6f594f8a` | ✅ 与 PUF 产出逐字节相同 |
| PUF_BH 属性位（`0x44` 的 [7:6]） | `3` | ✅ 声明"辅助数据在启动头"（对照：BBRAM 那份是 0） |
| 辅助数据 | 384 字 + CHASH + AUX | ✅ bootgen 接受 |
| CHASH / AUX 位置 | `0xeb8` / `0xebc` | ✅ 紧跟辅助数据 |

那个属性位掩码不是猜的，来自 FSBL 源码
`zynqmp_fsbl/src/xfsbl_image_header.h` 的 `XIH_BH_IMAGE_ATTRB_PUF_BH_MASK (0x00C0U)`。

⚠️ 但**失败方式与 BBRAM 那次不同，这个差别有信息量**：

| | BBRAM 那次 | PUF 这次 |
|---|---|---|
| BootROM 行为 | **直接停住**，APU 一直在 Reset，`MULTI_BOOT` 停在 6 | **继续往下搜**，`MULTI_BOOT` 自增到 7 并启动了槽 7 |
| 说明什么 | 解密失败被锁死 | 更像"镜像头/格式不被接受"，还没到解密那一步 |

**剩下的嫌疑（都需要手上没有的资料，因此停）**：

* BootROM 在启动头模式下再生 PUF，是否还要求 eFUSE 的 PUF 安全位处于某个状态
  （XilSKey 里有 `XSK_PUF_PROGRAM_SECUREBITS` / `SYN_INVALID` / `REGISTER_DISABLE`
  这一组，我全部保持默认没动）。
* BootROM 从黑钥导出 KEK 的方式，是否与 XilSKey 注册时用的完全一致。

两条都要 UG1085 / UG1283 里 PUF 启动流程的确切描述才能定。**没有依据就不再试**
—— 今天在 XMPU 位定义、BBRAM 密钥来源常数、安全头 48/64 字节上，

### 其余可选手段（未做）

BBRAM 死在"钥匙靠电池、锁存靠断电"这对矛盾上。**PUF 两样都不需要**，
所以它绕开了整堵墙。已确认工具链支持（不是设想）：

```
[fsbl_config] pufhd_bh          ← PUF 辅助数据放**启动头**，不进 eFUSE
[puf_file]    pufhelperdata.txt
[bh_keyfile]  black_key.txt     ← AES 钥匙用 PUF 派生的 KEK 加密后放启动头
[bh_key_iv]   bhkeyiv.txt
[bootloader, destination_cpu=a53-0, encryption=aes] fsbl.elf
```

* **PUF 是芯片的物理指纹**，每次上电现场再生密钥 —— 不需要电池，不需要 eFUSE。
* 密钥**任何地方都不以明文存在**：启动头里是黑钥（密文），只有这颗芯片解得开。
* 换一块板，同一份 BOOT.BIN 解不开 → **真正的设备绑定，比 BBRAM 强**。
* 一次性 PUF 注册用现成例程
  `xilskey_v6_9/examples/xilskey_puf_registration.c`，关键宏默认就不烧 eFUSE：

  ```c
  #define XSK_PUF_PROGRAM_EFUSE   FALSE   /* 默认不烧 */
  #define XSK_PUF_INFO_ON_UART    FALSE   /* 改 TRUE：辅助数据+黑钥打到串口 */
  ```

  改成 `INFO_ON_UART=TRUE`，串口收下辅助数据与黑钥，直接喂给上面那份 bif。

**次选：灰钥（`bh_gry_key`）放启动头。** 也不用 eFUSE 不用电池，但它是用
Xilinx 的**家族密钥**混淆的，而家族密钥**所有 ZU+ 芯片共用一把** ——
**那是混淆，不是保护**。拿它把加密通路跑通有意义，当成安全措施是夸大。

**两条纯软件的（不依赖硅上任何密钥）：**

* **U-Boot 验证启动（FIT 签名）**：给 `image.ub` 签名，U-Boot 验完再引导内核。
  **挡不住换 BOOT.BIN**，但从 U-Boot 往上是一条真的完整性链。
* **装位流前校验**：`hsm-boot.sh` 在 `fpgautil` 之前先验 `.bit` 的哈希/签名。
  挡不住 root 绕过，但把"随便换个位流就换掉整个密码边界"抬高一档。

⚠️ **共同的天花板**：不烧 eFUSE 就没有 `ENC_ONLY` / `RSA_EN`，BootROM **不强制**
加密或认证 —— 换一份"声明为不加密"的镜像照启不误。**以上任何一条都挡不住替换**，
买到的是机密性与设备绑定，不是防替换的信任根。那一条只有烧 eFUSE 才有，
而 eFUSE 不可逆 + 只有一块板 = 本项目已永久排除。

### ⚠️ J1（位流固化进 BOOT.BIN）—— **能启动，但那个形态掉网**

镜像用当前 BL31 重建、放槽 7 启动：四个 A53 都是 `Running`，**内核起来了**，
但板子网络够不着、串口也不给提示符。已按纪律恢复到 golden。

不再往下追的理由：**它唯一的消费者是安全启动，而安全启动本身被上面那条卡着**。
演示形态在运行时装位流，网络和演示都正常 —— J1 不是必需项。

## 六、怎么演示

**上电，等 35 秒。** 不需要任何操作 —— `fpga_manager` 报 `operating`、daemon 起好、
eth1 在 `192.168.50.175`。

```bash
# 本机（板子上）
/media/sd-mmcblk1p2/hsm/sdf_demo

# 远程（另一台机器，先从板子取一次性口令）
TOK=$(ssh root@192.168.50.175 cat /media/sd-mmcblk1p2/hsm/hsm_token)
./sdf_demo 192.168.50.175 "$TOK"
```

九节内容：PING / ML-KEM-768 三步 / SM4 密钥进硬件 / **ML-DSA 三个参数集** /
四种分组模式 / SM3 / 以及一条**反证**——断开重连后旧句柄必须失效。

配套单项工具（都在 `/media/sd-mmcblk1p2/hsm/`）：

| 工具 | 演示什么 |
|---|---|
| `dna_probe -w` | 设备绑定：读 DNA，并**正面验证写会被 EL3 拒绝** |
| `protunit_probe` | 保护单元实配（XPPU 关着、XMPU 区域、六实例状态） |
| `mldsa_hwtest` | ML-DSA 对 ACVP（注意 SK_LOCK，见第一节 ⚠️） |
| `dna-bind-check`（主机侧） | 远端主机把 keystore 绑到这块板 |

**掉网了怎么办**：先用串口**只读**看状态（`board/scripts/serial_console.py --watch N`），
别用串口打命令。再不行用 JTAG 清 `CSU_MULTI_BOOT` 加系统复位 —— 本轮用了六次，
六次都成，**一次电都没断**。

> ## ✅ 板子是好的，在演示形态运行中 —— 而且「硬停必须断电」这个结论**是错的**
>
> **2026-08-17 收尾更正。** 本文档一度写着"BootROM 认证失败硬停之后 JTAG 救不回来、
> 只能断电"。**错了。真正的原因是启动模式被改成了 JTAG，而这个可以用 JTAG 改回去。**
>
> `CRL_APB_BOOT_MODE_USER`（`0xFF5E0200`）的位定义（PMUFW `crl_apb.h:1990-2002`）：
>
> ```
> [3:0]   BOOT_MODE       POR 采样的引脚值
> [8]     USE_ALT         = 1 时改用下面的 ALT_BOOT_MODE
> [15:12] ALT_BOOT_MODE   0 = JTAG
> ```
>
> 硬停时读出 **`0x00000100`** = `USE_ALT=1` 且 `ALT_BOOT_MODE=0` → **芯片被强制成
> JTAG 启动模式**。BootROM 于是老老实实等调试器喂代码、不去读 SD、也不放 APU。
> 这**根本不是什么"安全锁定"**，是启动模式被改掉了。
> （板子健康时这个寄存器是 `0x40`；把它写 0 之后读回 `0x5` = SD1，正是引脚本来的值。）
>
> **验证过的救板动作（2026-08-17 实测，把 D 那次硬停从 APU Reset 一路救回演示形态，
> 一次电都没断）**：
>
> ```tcl
> connect -url tcp:127.0.0.1:3121
> targets -set -filter {name =~ "PSU"}
> mwr -force 0xFF5E0200 0x0      ;# ★ 清 USE_ALT → 回到引脚采样的 SD1 启动模式
> mwr -force 0xFFCA0010 0        ;# CSU_MULTI_BOOT = 0 → 回 golden
> rst -system
> after 8000
> targets -set -filter {name =~ "Cortex-A53 #0"}
> catch {con}                    ;# 会停在 Reset Catch，必须 con
> ```
>
> 状态会依次走 `APU Reset` → `Reset Catch, EL3(S)/A64` → `Running`，
> 约 20 秒后 eth1 就通了。
>
> ⚠️ **强烈怀疑那一行 `mwr 0xFF5E0200 0x0` 才是此前六次成功救板的隐含前提没被记下来
> 的原因** —— 之前的救板配方里没有它，所以遇到这次这种情况就以为"救不回来了"。

## 一、这台密码机现在是什么

**密码边界是 FPGA fabric。** ML-KEM 核、ML-DSA 核、对称核（AES-128/256、SM4、SM3）、
环形振荡器熵源、片内密钥金库与访问门控全部在 PL 里。主机侧的 PKCS#11 / SDF 库、
keystore、槽位元数据跑在它**之外**。

### 能力清单

| 类别 | 能力 | 证据 |
|---|---|---|
| KEM | ML-KEM-512/768/1024 KeyGen / Encaps / Decaps | 真硅上逐字节对 NIST ACVP（20/20） |
| 签名 | ML-DSA-44/65/87 KeyGen / Sign / Verify | 真硅上逐字节对 ACVP（32/0，见下方 ⚠️） |
| 对称 | AES-128/256、SM4，ECB/CBC/CTR/CFB/OFB | 对 SP 800-38A / GB/T 32907 |
| 杂凑 | SM3 | 对 GB/T 32905 A.1 |
| 熵源 | PL 环振 + SP 800-90B 健康检测 | 调理前 H = 0.871 bit/sample；PL 重配重启矩阵 H = 0.507 ≥ 0.436 |
| 私钥保护 | 片内金库：`dk`/`sk` 不出总线，按槽号使用 | 读游标 seek 到 sk 段读回全 0，而按槽签出的 σ 与自送 sk 逐字节相同 |
| 接口 | GM/T 0018 风格 SDF、PKCS#11 v3.2 | `sdf_demo` 九节全绿；p11 演示 |
| 设备绑定 | 密钥派生根可绑 Device DNA（默认关） | 板上与远端主机两条路都跑通 |

⚠️ **ML-DSA 的 32/0 是在 SK_LOCK 闩上之前取的。** 闩上之后 KeyGen 只吐 `pk`，
ACVP 的 KeyGen 向量比对不了私钥 —— 那 6 条**必然**失败，**那是闩锁在正常工作**。
`mldsa_hwtest` 现在会把这句话直接打出来。要重取 KeyGen 证据：先重配 PL 清掉闩锁，
且别让 daemon 先起来。

### 明确**没有**的东西

* **没有加密启动**（第四节：BBRAM 死在没电池；PUF 六个变体全被 BootROM 拒，
  失败点已夹到 BootROM 内部无公开资料的那一步）。
  **但 RSA 认证启动是通的、零 eFUSE**（变体 G 上板验过）——
  它不是信任根，别把它说成信任根
* **没有 SM2**
* **没有算法证书**（ACVP 向量是本地跑的，那是正确性证据，不是证书）
* **root 仍然能"用"密钥**（读不到私钥，但能命令硬件做运算 —— SiP 不校验调用来源）
* **root 读 OP-TEE 安全内存 —— 已能堵上，但只在运行时**（第三节 ②-c：开毒化后是 Bus error；②-d：开机自动生效还差一步）
* **没有功耗/电磁侧信道对策**（刻意排除，理由见 SECURITY）

### ② XMPU / XPPU —— **根因定了，缺口在运行时堵上了；差开机自动生效**

第一会话的状态是"挡得住非安全 DMA 主控、挡不住 APU，**为什么需要 UG1085 才能定**"。
**这句话本身有两处错，见下面 ②-b —— 那两个"DMA 主控"其实是 APU，而且它什么都没挡住。**

**定下来了，而且答案与 DDR 通路架构无关 —— 是 XMPU 的工作方式被理解错了。**

权威出处：**XAPP1320《Isolation Methods in Zynq UltraScale+ MPSoCs》v3.0
（2020-04-30）第 10 页**：

> "If an illegal transaction is attempted, the XMPU asserts AxUser[10] but the
> transaction **is passed to the memory controller**. This mechanism is referred to
> as poison by attribute. **The transaction is gated by the end point, not the XMPU
> itself.**"

**XMPU 只负责"检测 + 打毒标记"，真正掐掉事务的是终点（DDR 控制器）。**
而我们这份配置里毒化根本没开：

```
DDR0..5  CTRL   = 0x0000000b   → bit2 POISONCFG = 0
DDR0..5  POISON = 0x00000000   → ATTRIB(bit20) = 0，BASE = 0
```

现象因此完全自洽：**区域是对的、检测是活的（违规确实被锁存了），
但没有任何东西去 gate，所以数据照样返回。**

**顺带排掉了三个假设**（都去查了 Xilinx 自己的定义，不是猜）：

| 曾经的怀疑 | 结论 | 出处 |
|---|---|---|
| `cfg=0x17` 的位定义抄错了 | **没抄错**，语义正确 | `xddr_xmpu0_cfg.h`；QEMU `hw/misc/xlnx-xmpu.c:205-228` 严格模式判据 `sec != regionns` |
| `ALIGNCFG=1` 让 START/END 变成 MB 单位，于是区域压根没覆盖 | **不是**。字段恒为 `addr>>12`，ALIGNCFG 只把区域**对齐**到 1 MB | QEMU `xlnx-zynqmp-xmpu.c:283-292`（`xr->start <<= 12`）与 327-328（`&= ~addr_mask`）。实测印证：`ERR_ADDR=0x0006002a` → `0x6002a000`，正落在区域内 |
| `MASTER=0` 被硬件当成"不匹配任何主控" | **不是**，掩码 0 即匹配所有主控 | QEMU 同文件 330 行 `(mask & id) == (mask & master_id)` |

### ②-b 断电后跑判决实验：**结论比预想的更糟，而且推翻了上一轮的一句话**

POR 之后跑 `verify_after_por.sh`，同时把 `protunit_probe` 的**寄存器映射错误**
修掉（见下），拿到的实配是：

```
DDR0  CTRL=0000000b  ERR_ADDR=00000000  ERR_MASTER=00000000(RPU0)  ISR=00000000
DDR1  CTRL=0000000b  ERR_ADDR=0006002e  ERR_MASTER=000000ac(APU)   ISR=00000008[SECURTYVIO]
DDR2  CTRL=0000000b  ERR_ADDR=00060039  ERR_MASTER=000000a4(APU)   ISR=00000008[SECURTYVIO]
DDR3..5                        全 0
```

**两处必须更正的旧结论：**

**① 上一轮说"挡住了非安全 DMA 主控 `0xa0`/`0xac`"——那两个主控号是 APU 自己。**
主控 ID 表抄自 PMUFW 自己的 LUT（`xpfw_xpu.c:71`）：`{ 0x80U, 0xBFU, "APU" }`。
`0xa0` / `0xa4` / `0xac` **全部落在 APU 段内**。
于是"流氓外设 DMA 这条路堵上了、那是净收益"这句话**不成立** ——
**XMPU 到目前为止什么都没挡住。**

**② `protunit_probe` 把 `+0x10` 当成 LOCK 打了出来，其实那是 ISR。**
权威偏移（`xddr_xmpu0_cfg.h`）：`+0x10 ISR`、`+0x20 LOCK`。
所以历史日志里那一列 `LOCK=0x00000008` 根本不是"锁上了"，而是
**`ISR.SECURTYVIO`（bit3）= 发生过安全违规**。真正的 LOCK 读出来是 **0**
（没锁，BL31 仍可改配置 —— 这对下一步是好消息）。工具已修正并重新上板取证。

**修正之后，全部证据第一次自洽了：**

* DDR1 / DDR2 正是 XAPP1320 图 3 里那两个 **CCI AXI** 端口
  （六个实例的端口分别是 `0:LPD AXI  1:CCI AXI  2:CCI AXI  3:HP0/DP  4:HP1,HP2  5:HP3,FPD_DMA`），
  **CCI 就是 APU 到 DDR 的路**。
* 这两个实例**确实检测到了 APU**，违规类型正是 `SECURTYVIO` —— 我们配的
  REGNNS=0 + 严格 NS 检查**完全按预期在工作**。
* 违规地址 `0x6002e000` / `0x60039000` 都落在 OP-TEE core 段内。
* 而 `devmem` **照样读回真实数据**。
* DDR0/3/4/5 是 0 不是"APU 没到达"，而是那四个端口（LPD、HP0-3、FPD_DMA）
  本来就没有往这段地址的流量。

> **所以答案定死了：XMPU 看得见 APU、也正确判定为安全违规，就是不拦。**
> 因为拦截本来就不是它的职责（XAPP1320：由终点 gate），而毒化没开。
> 这与 XAPP1320 的描述**完全吻合**，不再有第二种解释。

### ②-c 开毒化 —— **做通了，板上验过；但只在运行时，重启就没了**

`LOCK=0` 说明 XMPU 配置寄存器没锁，于是**不用重建 BL31 就能直接验**：JTAG 把六个
实例的 `POISON.ATTRIB`（bit20）置上，再从 Linux 同址读一次。

```
毒化关闭   devmem 0x60000000 → 0xAA0003F3     ← OP-TEE 的一条 AArch64 指令
毒化开启   devmem 0x60000000 → Bus error（退出码 135 = SIGBUS）
对照       devmem 0x10000000 → 0xEDFE0DD0     ← 区域外，照常
对照       devmem 0x70000000 → 0x00000000     ← OP-TEE 共享内存，故意不圈，照常
```

**功能零影响**：`sdf_demo` 九节全绿（ML-KEM / ML-DSA 三参数集 / 四种分组模式 /
SM3 / 句柄失效反证），`READY=yes`、PL `operating`、daemon 与网络都正常。

> **所以"root 读得到 OP-TEE 安全内存"这条，在开了毒化之后是真的堵上了。**

工具：`board/scripts/xmpu_poison_on.tcl`（构建机上 `xsct` 跑，幂等）。
证据：`board/logs/RESULT_xmpu_poison.txt`（关/开同址对照 + 区域外对照）。

⚠️ **只动 `POISON.ATTRIB`，不动 `CTRL`**，两条理由都不能省：
① `CTRL` 现在是 `0x0b`，其中 `DEFRDALWD`/`DEFWRALWD` 管的是"不匹配任何区域的
访问"——清掉等于把整个 DDR 都拒了，板子起不来。
② `CTRL.POISONCFG` 在 Xilinx QEMU 模型里走的是**按地址**重定向（打到
`POISON.BASE`），而 BASE 现在是 0 —— 一次违规的**写**就会打进物理地址 0。
在把 BASE 指到安全去处之前绝不能置它。

## 四、安全启动：能不能在铁律内做成

**铁律**：绝不烧 eFUSE；不装电池就没有 BBRAM。问题是——在这两条之下还剩什么。

### 先把天花板写死（这一条与做不做得成无关）

不烧 eFUSE 就没有 `ENC_ONLY` 和 `RSA_EN`，**BootROM 不强制加密、也不强制认证**。
攻击者换一份"声明为不加密"的镜像，BootROM 照启不误。

> **所以本项目在任何配置下都拿不到"防替换的信任根"。**
> 能拿到的上限是**机密性 + 设备绑定**。这一条**不是本轮的失败，是芯片的规则**。

### ⛔ BBRAM —— **受阻：板级硬件（`VCC_BATT` 没接电池）**

两个必要条件互斥，已用**两次物理断电**验到底（第一会话）：

* 烧钥匙 → 钥匙在，但 `BBRAM_STS.PGM_MODE` 锁成 1，**CSU 不把钥匙交给 BootROM**
* 断电清锁存 → 锁存清了，**钥匙也一起没了**

**要让它成立需要给 `VCC_BATT` 接一颗电池 —— 板级硬件改动，软件绕不过去。**

留下的可复用资产：`boot/persist/build_bbram_boot.sh`；加密镜像
`/media/sd-mmcblk1p2/hsm/BOOT_ENC2.BIN`（**不在任何启动槽**）。

### 🔶 PUF 黑钥 —— **根因定位到具体一字，修正镜像已构建，板上未验**

**先纠正一条此前文档里的错误**：`docs/SECURITY.zh-CN.md` 原来写着
"PUF 黑密钥依赖烧 eFUSE，已永久排除"。**这是错的。**
`bootgen -bif_help fsbl_config` 对 `bh_auth_enable` 的原文是
"RSA authentication … **excluding the verification of PPK hash and SPK ID**"，
AMD 的 Embedded Design Tutorial 也写明 PUF boot header 模式
"**does not require programming of eFUSEs**"。**这条路在铁律内是成立的。**

**上一轮被拒收的三个缺陷，全部有权威出处**：

| # | 缺陷 | 权威依据 | 旧镜像实测 |
|---|---|---|---|
| ① | bif 缺 `puf4kmode`（bootgen **默认 12K**，注册却是 4K） | `bootgen -bif_help fsbl_config` 原文 "(Default is 12k bit)"；注册端 `xilskey_puf_registration.h:148` = `XSK_PUF_MODE4K` | 启动头 `0x44` 的 `[17:16]` = **0**（应为 3） |
| ② | bif 缺 `shutter=0x0100005E` | 注册端 `xilskey_eps_zynqmp_puf.h:72` `XSK_ZYNQMP_PUF_SHUTTER_VALUE = 0x0100005e` | 启动头 `0x6c` = **`0x01000020`**（bootgen 默认值） |
| ③ | **辅助数据最后一字被上一轮"修"坏了** | `xilskey_eps_zynqmp_puf.c` 注册尾部：`Aux = (PufStatus & AUX_MASK) >> 4` 而 `SyndromeData[385] = (PufStatus & AUX_MASK) << 4` —— **差 8 位移位** | 写的是 `0x00864FE2`，正确值 **`0x864FE200`** |

**③ 是一次"修复"造成的回归，值得完整记下来**：

* 第一版把 `PufInstance.SyndromeData[]` 的 386 字**原样**写进 `puf_file` —— **那是对的**。
  库自己就会把 CHASH 放进 `[384]`、`AUX<<4` 放进 `[385]`。
* 然后在镜像里搜 `0x00864FE2` 搜不到，判定"AUX 没进去"，于是改成
  "384 字 + CHASH + AUX"。**搜不到是必然的** —— 真正该在那里的是 `0x864FE200`。
  **这个假阴性把一份正确的数据改坏了。**
* 佐证：文件里 `word[383]` 与 `word[384]` **都是 CHASH**。这不是错位，正是库的行为
  —— 4K 模式读数循环停在 `Index=383`，最后读到的那字就是 CHASH，随后又复制到 `[384]`。
  **说明只有最后一字是坏的。**

**本轮两次上板（都在非 golden 槽，golden 全程未动）**：

| 变体 | 配置 | BootROM 行为 | 代价 |
|---|---|---|---|
| A | `pufhd_bh, puf4kmode, shutter=…`，辅助数据仍坏 | `MULTI_BOOT` 6 → **7**，继续往下搜 | 无。槽 7 事先换成 `BOOT.BIN` 副本当安全网，板子自己回到可用 |
| B | A + `bh_auth_enable` + 全分区 RSA-4096 | **停住**，`MULTI_BOOT` 停在 6，APU 一直 Reset | 当时以为要 POR，**事后证明不用**：清 `BOOT_MODE_USER.USE_ALT` 即可救回（见第〇节） |
| C | A + **修正后的辅助数据** | `MULTI_BOOT` 6 → **7**，与 A 相同 | 无，板子自己回来 |
| D | C + `bh_auth_enable` + 全分区 RSA-4096 | **停住**，与 B 相同 | **JTAG 救回，没断电** |
| E | C + `opt_key`（官方参考 bif 的最后一处差异） | `MULTI_BOOT` 6 → **7**，与 A/C 相同 | 无 |
| **G** | **只签名、不加密、不碰 PUF** | **`MULTI_BOOT` 停在 6 —— 起来了，网络通** | 无 |

**四次实测排出来的规律（这是本轮最硬的一块事实）**：

| | 辅助数据坏 | 辅助数据对 |
|---|---|---|
| **不带 RSA** | A：自增往下搜 | C：自增往下搜 |
| **带 RSA** | B：硬停 | D：硬停 |

**结论：失败方式只由"带不带 RSA"决定，与辅助数据对不对无关。**
换句话说 —— **辅助数据那三个缺陷是真的、修得也对，但它们不是拦路的那一个。**
BootROM 在更早的地方就把这份镜像否掉了，根本没走到用辅助数据再生 PUF 那一步。

### ★ 变体 G：**RSA 认证启动是通的，零 eFUSE**

G 是"只签名、不加密、不碰 PUF"的镜像，**从槽 6 正常启动、网络通**。
（`HSM_STATUS` 显示 `DAEMON=nosock / READY=no` 正是预期 —— G 故意用了
`atf_build_v50` 那份没有 secmmio SiP 的 BL31，这反而证明跑的确实是 G。）

**于是 B/D 的硬停不是 RSA 失败**，是过了认证、在 PUF/解密那一步挂的。

> **顺带得到一个实打实的正面能力：`bh_auth_enable` 的 RSA 认证启动在这块板上是
> 通的，一颗 eFUSE 都没烧。** 它**不是**信任根（PPK 摘要不与 eFUSE 比对，
> 攻击者换一份自己签的镜像照样过），但认证通路本身活着、可复现。
> 产物 `/home/build/pufboot/BOOT_PUF_G.BIN`，bif 同目录 `p_G.bif`。

### ★ 离线判据：镜像的密码学是对的，问题只可能在 BootROM 里

用**已知的红钥**（`XSK_PUF_AES_KEY` = `gen.nky` 的 `Key 0`）加启动头 `0xa0` 处的
IV，离线解变体 C 的 FSBL 段：

```
fsbl_sourceoffset = 0x2e00
GCM 校验：**通过**
  明文前 32 字节 = 全 0        （不换钥，正确）
  接下来 12 字节 = 7c301006…   （= nky 的 IV 1，正确）
  最后 4 字节    = 0x7eb8 字   （= 129760 字节 = pmufw 长度，正确）
```

**镜像的加密、密钥、IV、结构全部正确。** 唯一没被独立验证过的环节，就是
BootROM 能不能从启动头那 32 字节黑钥反推出这把红钥。

### 结论：**卡在 BootROM 内部，没有公开资料可查**

把上面几条并起来，失败点被唯一地夹住了：

| 环节 | 状态 |
|---|---|
| 启动头各字段（密钥来源 / PUF_HD / PUF 模式 / shutter / 黑钥 / 黑钥 IV） | ✅ 逐字对过 Xilinx 自己的定义 |
| 辅助数据 386 字 | ✅ 与 XilSKey 的 `SyndromeData[]` 逐字一致 |
| 镜像的 AES-GCM 加密 | ✅ **离线解密 + tag 校验通过** |
| RSA 认证通路 | ✅ **变体 G 上板证明是通的** |
| bif 配置 | ✅ 官方参考 bif 的每一处差异都试过了（含 `opt_key`） |
| **BootROM：黑钥 → KEK → 解密** | ❌ **唯一没验证过的一环，也是唯一还能出错的一环** |

这一步在 BootROM 里，**不开源，UG1085 只有框图级描述**。
前面那三个缺陷全是靠读 Xilinx 源码定位的，**这一条没有源码可读**。
按项目纪律「没有依据就不再猜着上板」，**到此为止，不硬凑**。

⚠️ `opt_key` 这条已经试过了（变体 E）：给全部 nky 补上 `Key Opt` 之后 bootgen
接受、启动头 `opt_key` 位也置上了，结果与 A/C 一模一样。
* eFUSE 的 PUF 安全位（`XSK_PUF_SYN_INVALID` / `REGISTER_DISABLE` 那一组）
  是否必须处于某个状态 —— 全部保持默认未烧，且**按铁律不会去烧**。

**变体 C 已构建并通过全部可离线核对的自检**
（`boot/persist/build_puf_boot.sh`，产物 `/home/build/pufboot/BOOT_PUF_C.BIN`，

⚠️ **口径（本轮结束时的真实状态）**：**PUF 加密启动没有做通。**

## 六、怎么演示

**上电，等 35 秒。** 不需要任何操作 —— `fpga_manager` 报 `operating`、daemon 起好、
eth1 在 `192.168.50.175`。

```bash
# 本机（板子上）
/media/sd-mmcblk1p2/hsm/sdf_demo

# 远程（另一台机器，先从板子取一次性口令）
TOK=$(ssh root@192.168.50.175 cat /media/sd-mmcblk1p2/hsm/hsm_token)
./sdf_demo 192.168.50.175 "$TOK"
```

九节内容：PING / ML-KEM-768 三步 / SM4 密钥进硬件 / **ML-DSA 三个参数集** /
四种分组模式 / SM3 / 以及一条**反证**——断开重连后旧句柄必须失效。

配套单项工具（都在 `/media/sd-mmcblk1p2/hsm/`）：

| 工具 | 演示什么 |
|---|---|
| `dna_probe -w` | 设备绑定：读 DNA，并**正面验证写会被 EL3 拒绝** |
| `protunit_probe` | 保护单元实配（XPPU 关着、XMPU 区域、六实例状态） |
| `mldsa_hwtest` | ML-DSA 对 ACVP（注意 SK_LOCK，见第一节 ⚠️） |
| `dna-bind-check`（主机侧） | 远端主机把 keystore 绑到这块板 |
| `verify_after_por.sh` | **断电之后第一件事**：XMPU 的判决性只读实验（在仓库 `board/scripts/`，尚未进板，传法见第〇节） |

**掉网了怎么办**：先用串口**只读**看状态（`board/scripts/serial_console.py --watch N`），
别用串口打命令。再不行用 JTAG 清 `CSU_MULTI_BOOT` 加系统复位。
⚠️ "BootROM 认证失败"那种硬停也能用 JTAG 救回，**但标准配方里必须加一行
`mwr -force 0xFF5E0200 0x0`**（清 `USE_ALT`），否则怎么复位 APU 都不放。见第〇节。

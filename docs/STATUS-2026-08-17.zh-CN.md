## 〇、先看这一节：**板子是好的；还剩两件要人动手**

> ## ✅✅ 又一条被推翻：**软件能触发真 POR,"只能物理断电"是错的**
>
> **2026-08-17 实测。** 此前反复记录"这颗芯片没有软件 POR 通路"，依据是 xsct 的
> `rst -por` / `-srst` / `-ps` 在这块板上都不支持。**但那只说明 JTAG 线没引出 POR
> 引脚，不等于芯片没有软件 POR 通路。**
>
> UG1085 第 6 章（PMU）：每个错误源都能配成触发 **"Generation of a power-on-reset
> (POR)"**，掩码由 `PMU_GLOBAL.ERROR_POR_EN_{1,2}` 写 1 解除。于是只要有一个错误源
> **当前是置位的**，给它解掩码，PMU 立刻发 POR：
>
> ```tcl
> targets -set -filter {name =~ "PSU"}
> mwr -force 0xFFD80560 0x04000000    ;# ERROR_POR_EN_2 bit26 = CSU_ROM
> ```
>
> `ERROR_STATUS_2` 的 bit26 是 `CSU_ROM`，只要上次启动 BootROM 报过错就是置着的
> —— 试加密启动失败之后必然满足。脚本：`board/scripts/jtag_por.tcl`。
>
> **怎么证明真是 POR**：往 `PERS_GLOB_GEN_STORAGE7`（`0xFFD8006C`，UG1085 明写
> "only reset by the power-on reset"）写 `0xDEADBEEF`，触发后读回 `0x00000000`。
> 实测就是这样，板子 35 秒回演示形态。
>
> ⚠️ **别用 XMPU 的 `ERR_ADDR`/ISR 当 POR 探针** —— 它们虽是 POR-only，但每次开机
> 都会被重新锁存成同样的值，看着像"没清"。我先上过一次当。`CSU_BR_ERROR` 同理不适合。
>
> ⚠️ 这是 **PS 的 POR，不掉电源轨**。对 multiboot、安全态、POR-only 闩锁等价；
> 对"掉电才丢"的东西（没电池的 BBRAM）**不一定**等价 —— 那条值得用这个新手段重验。
>
> **这条的意义**：它把"必须有人去拔电源"从关键路径上拿掉了，
> 也意味着**加密启动那个有效测法（镜像放 `BOOT.BIN` + 冷启动）现在可以远程做**。

> ## ✅ 板子是好的，在演示形态运行中 —— 而且「硬停必须断电」这个结论**是错的**
>
> **2026-08-17 收尾更正。** 本文档一度写着"BootROM 认证失败硬停之后 JTAG 救不回来、
> 只能断电"。**错了。真正的原因是启动模式被改成了 JTAG，而这个可以用 JTAG 改回去。**
>
> `CRL_APB_BOOT_MODE_USER`（`0xFF5E0200`）的位定义（PMUFW `crl_apb.h:1990-2002`）：
>
> ```
> [3:0]   BOOT_MODE       POR 采样的引脚值
> [8]     USE_ALT         = 1 时改用下面的 ALT_BOOT_MODE
> [15:12] ALT_BOOT_MODE   0 = JTAG
> ```
>
> 硬停时读出 **`0x00000100`** = `USE_ALT=1` 且 `ALT_BOOT_MODE=0` → **芯片被强制成
> JTAG 启动模式**。BootROM 于是老老实实等调试器喂代码、不去读 SD、也不放 APU。
> 这**根本不是什么"安全锁定"**，是启动模式被改掉了。
> （板子健康时这个寄存器是 `0x40`；把它写 0 之后读回 `0x5` = SD1，正是引脚本来的值。）
>
> **验证过的救板动作（2026-08-17 实测，把 D 那次硬停从 APU Reset 一路救回演示形态，
> 一次电都没断）**：
>
> ```tcl
> connect -url tcp:127.0.0.1:3121
> targets -set -filter {name =~ "PSU"}
> mwr -force 0xFF5E0200 0x0      ;# ★ 清 USE_ALT → 回到引脚采样的 SD1 启动模式
> mwr -force 0xFFCA0010 0        ;# CSU_MULTI_BOOT = 0 → 回 golden
> rst -system
> after 8000
> targets -set -filter {name =~ "Cortex-A53 #0"}
> catch {con}                    ;# 会停在 Reset Catch，必须 con
> ```
>
> 状态会依次走 `APU Reset` → `Reset Catch, EL3(S)/A64` → `Running`，
> 约 20 秒后 eth1 就通了。
>
> ⚠️ **强烈怀疑那一行 `mwr 0xFF5E0200 0x0` 才是此前六次成功救板的隐含前提没被记下来
> 的原因** —— 之前的救板配方里没有它，所以遇到这次这种情况就以为"救不回来了"。

## 一、这台密码机现在是什么

**密码边界是 FPGA fabric。** ML-KEM 核、ML-DSA 核、对称核（AES-128/256、SM4、SM3）、
环形振荡器熵源、片内密钥金库与访问门控全部在 PL 里。主机侧的 PKCS#11 / SDF 库、
keystore、槽位元数据跑在它**之外**。

### 能力清单

| 类别 | 能力 | 证据 |
|---|---|---|
| KEM | ML-KEM-512/768/1024 KeyGen / Encaps / Decaps | 真硅上逐字节对 NIST ACVP（20/20） |
| 签名 | ML-DSA-44/65/87 KeyGen / Sign / Verify | 真硅上逐字节对 ACVP（32/0，见下方 ⚠️） |
| 对称 | AES-128/256、SM4，ECB/CBC/CTR/CFB/OFB | 对 SP 800-38A / GB/T 32907 |
| 杂凑 | SM3 | 对 GB/T 32905 A.1 |
| 熵源 | PL 环振 + SP 800-90B 健康检测 | 调理前 H = 0.871 bit/sample；PL 重配重启矩阵 H = 0.507 ≥ 0.436 |
| 私钥保护 | 片内金库：`dk`/`sk` 不出总线，按槽号使用 | 读游标 seek 到 sk 段读回全 0，而按槽签出的 σ 与自送 sk 逐字节相同 |
| 接口 | GM/T 0018 风格 SDF、PKCS#11 v3.2 | `sdf_demo` 九节全绿；p11 演示 |
| 设备绑定 | 密钥派生根可绑 Device DNA（默认关） | 板上与远端主机两条路都跑通 |

⚠️ **ML-DSA 的 32/0 是在 SK_LOCK 闩上之前取的。** 闩上之后 KeyGen 只吐 `pk`，
ACVP 的 KeyGen 向量比对不了私钥 —— 那 6 条**必然**失败，**那是闩锁在正常工作**。
`mldsa_hwtest` 现在会把这句话直接打出来。要重取 KeyGen 证据：先重配 PL 清掉闩锁，
且别让 daemon 先起来。

### 明确**没有**的东西

* **没有加密启动**（第四节：BBRAM 死在没电池；PUF 用**有效测法**（POR 冷启动）
  也跑过了，仍是硬停）。
  **但 RSA 认证启动是通的、零 eFUSE**（变体 G 上板验过）——
  它不是信任根，别把它说成信任根
* **没有 SM2**
* **没有算法证书**（ACVP 向量是本地跑的，那是正确性证据，不是证书）
* **root 仍然能"用"密钥**（读不到私钥，但能命令硬件做运算 —— SiP 不校验调用来源）
* ~~**root 读 OP-TEE 安全内存 —— 已能堵上，但只在运行时**~~ →
  **收尾会话已做成开机自动生效，见第八节。** 第三节 ②-c/②-d 是当时的记录，已被第八节取代
* **没有功耗/电磁侧信道对策**（刻意排除，理由见 SECURITY）

### ② XMPU / XPPU —— **根因定了，缺口在运行时堵上了；差开机自动生效**

第一会话的状态是"挡得住非安全 DMA 主控、挡不住 APU，**为什么需要 UG1085 才能定**"。
**这句话本身有两处错，见下面 ②-b —— 那两个"DMA 主控"其实是 APU，而且它什么都没挡住。**

**定下来了，而且答案与 DDR 通路架构无关 —— 是 XMPU 的工作方式被理解错了。**

权威出处：**XAPP1320《Isolation Methods in Zynq UltraScale+ MPSoCs》v3.0
（2020-04-30）第 10 页**：

> "If an illegal transaction is attempted, the XMPU asserts AxUser[10] but the
> transaction **is passed to the memory controller**. This mechanism is referred to
> as poison by attribute. **The transaction is gated by the end point, not the XMPU
> itself.**"

**XMPU 只负责"检测 + 打毒标记"，真正掐掉事务的是终点（DDR 控制器）。**
而我们这份配置里毒化根本没开：

```
DDR0..5  CTRL   = 0x0000000b   → bit2 POISONCFG = 0
DDR0..5  POISON = 0x00000000   → ATTRIB(bit20) = 0，BASE = 0
```

现象因此完全自洽：**区域是对的、检测是活的（违规确实被锁存了），
但没有任何东西去 gate，所以数据照样返回。**

**顺带排掉了三个假设**（都去查了 Xilinx 自己的定义，不是猜）：

| 曾经的怀疑 | 结论 | 出处 |
|---|---|---|
| `cfg=0x17` 的位定义抄错了 | **没抄错**，语义正确 | `xddr_xmpu0_cfg.h`；QEMU `hw/misc/xlnx-xmpu.c:205-228` 严格模式判据 `sec != regionns` |
| `ALIGNCFG=1` 让 START/END 变成 MB 单位，于是区域压根没覆盖 | **不是**。字段恒为 `addr>>12`，ALIGNCFG 只把区域**对齐**到 1 MB | QEMU `xlnx-zynqmp-xmpu.c:283-292`（`xr->start <<= 12`）与 327-328（`&= ~addr_mask`）。实测印证：`ERR_ADDR=0x0006002a` → `0x6002a000`，正落在区域内 |
| `MASTER=0` 被硬件当成"不匹配任何主控" | **不是**，掩码 0 即匹配所有主控 | QEMU 同文件 330 行 `(mask & id) == (mask & master_id)` |

### ②-b 断电后跑判决实验：**结论比预想的更糟，而且推翻了上一轮的一句话**

POR 之后跑 `verify_after_por.sh`，同时把 `protunit_probe` 的**寄存器映射错误**
修掉（见下），拿到的实配是：

```
DDR0  CTRL=0000000b  ERR_ADDR=00000000  ERR_MASTER=00000000(RPU0)  ISR=00000000
DDR1  CTRL=0000000b  ERR_ADDR=0006002e  ERR_MASTER=000000ac(APU)   ISR=00000008[SECURTYVIO]
DDR2  CTRL=0000000b  ERR_ADDR=00060039  ERR_MASTER=000000a4(APU)   ISR=00000008[SECURTYVIO]
DDR3..5                        全 0
```

**两处必须更正的旧结论：**

**① 上一轮说"挡住了非安全 DMA 主控 `0xa0`/`0xac`"——那两个主控号是 APU 自己。**
主控 ID 表抄自 PMUFW 自己的 LUT（`xpfw_xpu.c:71`）：`{ 0x80U, 0xBFU, "APU" }`。
`0xa0` / `0xa4` / `0xac` **全部落在 APU 段内**。
于是"流氓外设 DMA 这条路堵上了、那是净收益"这句话**不成立** ——
**XMPU 到目前为止什么都没挡住。**

**② `protunit_probe` 把 `+0x10` 当成 LOCK 打了出来，其实那是 ISR。**
权威偏移（`xddr_xmpu0_cfg.h`）：`+0x10 ISR`、`+0x20 LOCK`。
所以历史日志里那一列 `LOCK=0x00000008` 根本不是"锁上了"，而是
**`ISR.SECURTYVIO`（bit3）= 发生过安全违规**。真正的 LOCK 读出来是 **0**
（没锁，BL31 仍可改配置 —— 这对下一步是好消息）。工具已修正并重新上板取证。

**修正之后，全部证据第一次自洽了：**

* DDR1 / DDR2 正是 XAPP1320 图 3 里那两个 **CCI AXI** 端口
  （六个实例的端口分别是 `0:LPD AXI  1:CCI AXI  2:CCI AXI  3:HP0/DP  4:HP1,HP2  5:HP3,FPD_DMA`），
  **CCI 就是 APU 到 DDR 的路**。
* 这两个实例**确实检测到了 APU**，违规类型正是 `SECURTYVIO` —— 我们配的
  REGNNS=0 + 严格 NS 检查**完全按预期在工作**。
* 违规地址 `0x6002e000` / `0x60039000` 都落在 OP-TEE core 段内。
* 而 `devmem` **照样读回真实数据**。
* DDR0/3/4/5 是 0 不是"APU 没到达"，而是那四个端口（LPD、HP0-3、FPD_DMA）
  本来就没有往这段地址的流量。

> **所以答案定死了：XMPU 看得见 APU、也正确判定为安全违规，就是不拦。**
> 因为拦截本来就不是它的职责（XAPP1320：由终点 gate），而毒化没开。
> 这与 XAPP1320 的描述**完全吻合**，不再有第二种解释。

`LOCK=0` 说明 XMPU 配置寄存器没锁，于是**不用重建 BL31 就能直接验**：JTAG 把六个

## 四、安全启动：能不能在铁律内做成

**铁律**：绝不烧 eFUSE；不装电池就没有 BBRAM。问题是——在这两条之下还剩什么。

### 先把天花板写死（这一条与做不做得成无关）

不烧 eFUSE 就没有 `ENC_ONLY` 和 `RSA_EN`，**BootROM 不强制加密、也不强制认证**。
攻击者换一份"声明为不加密"的镜像，BootROM 照启不误。

> **所以本项目在任何配置下都拿不到"防替换的信任根"。**
> 能拿到的上限是**机密性 + 设备绑定**。这一条**不是本轮的失败，是芯片的规则**。

### ⛔ BBRAM —— **受阻：板级硬件（`VCC_BATT` 没接电池）**

两个必要条件互斥，已用**两次物理断电**验到底（第一会话）：

* 烧钥匙 → 钥匙在，但 `BBRAM_STS.PGM_MODE` 锁成 1，**CSU 不把钥匙交给 BootROM**
* 断电清锁存 → 锁存清了，**钥匙也一起没了**

**要让它成立需要给 `VCC_BATT` 接一颗电池 —— 板级硬件改动，软件绕不过去。**

留下的可复用资产：`boot/persist/build_bbram_boot.sh`；加密镜像
`/media/sd-mmcblk1p2/hsm/BOOT_ENC2.BIN`（**不在任何启动槽**）。

### 🔶 PUF 黑钥 —— **根因定位到具体一字，修正镜像已构建，板上未验**

**先纠正一条此前文档里的错误**：`docs/SECURITY.zh-CN.md` 原来写着
"PUF 黑密钥依赖烧 eFUSE，已永久排除"。**这是错的。**
`bootgen -bif_help fsbl_config` 对 `bh_auth_enable` 的原文是
"RSA authentication … **excluding the verification of PPK hash and SPK ID**"，
AMD 的 Embedded Design Tutorial 也写明 PUF boot header 模式
"**does not require programming of eFUSEs**"。**这条路在铁律内是成立的。**

**上一轮被拒收的三个缺陷，全部有权威出处**：

| # | 缺陷 | 权威依据 | 旧镜像实测 |
|---|---|---|---|
| ① | bif 缺 `puf4kmode`（bootgen **默认 12K**，注册却是 4K） | `bootgen -bif_help fsbl_config` 原文 "(Default is 12k bit)"；注册端 `xilskey_puf_registration.h:148` = `XSK_PUF_MODE4K` | 启动头 `0x44` 的 `[17:16]` = **0**（应为 3） |
| ② | bif 缺 `shutter=0x0100005E` | 注册端 `xilskey_eps_zynqmp_puf.h:72` `XSK_ZYNQMP_PUF_SHUTTER_VALUE = 0x0100005e` | 启动头 `0x6c` = **`0x01000020`**（bootgen 默认值） |
| ③ | **辅助数据最后一字被上一轮"修"坏了** | `xilskey_eps_zynqmp_puf.c` 注册尾部：`Aux = (PufStatus & AUX_MASK) >> 4` 而 `SyndromeData[385] = (PufStatus & AUX_MASK) << 4` —— **差 8 位移位** | 写的是 `0x00864FE2`，正确值 **`0x864FE200`** |

**③ 是一次"修复"造成的回归，值得完整记下来**：

* 第一版把 `PufInstance.SyndromeData[]` 的 386 字**原样**写进 `puf_file` —— **那是对的**。
  库自己就会把 CHASH 放进 `[384]`、`AUX<<4` 放进 `[385]`。
* 然后在镜像里搜 `0x00864FE2` 搜不到，判定"AUX 没进去"，于是改成
  "384 字 + CHASH + AUX"。**搜不到是必然的** —— 真正该在那里的是 `0x864FE200`。
  **这个假阴性把一份正确的数据改坏了。**
* 佐证：文件里 `word[383]` 与 `word[384]` **都是 CHASH**。这不是错位，正是库的行为
  —— 4K 模式读数循环停在 `Index=383`，最后读到的那字就是 CHASH，随后又复制到 `[384]`。
  **说明只有最后一字是坏的。**

**本轮两次上板（都在非 golden 槽，golden 全程未动）**：

| 变体 | 配置 | BootROM 行为 | 代价 |
|---|---|---|---|
| A | `pufhd_bh, puf4kmode, shutter=…`，辅助数据仍坏 | `MULTI_BOOT` 6 → **7**，继续往下搜 | 无。槽 7 事先换成 `BOOT.BIN` 副本当安全网，板子自己回到可用 |
| B | A + `bh_auth_enable` + 全分区 RSA-4096 | **停住**，`MULTI_BOOT` 停在 6，APU 一直 Reset | 当时以为要 POR，**事后证明不用**：清 `BOOT_MODE_USER.USE_ALT` 即可救回（见第〇节） |
| C | A + **修正后的辅助数据** | `MULTI_BOOT` 6 → **7**，与 A 相同 | 无，板子自己回来 |
| D | C + `bh_auth_enable` + 全分区 RSA-4096 | **停住**，与 B 相同 | **JTAG 救回，没断电** |
| E | C + `opt_key`（官方参考 bif 的最后一处差异） | `MULTI_BOOT` 6 → **7**，与 A/C 相同 | 无 |
| **G** | **只签名、不加密、不碰 PUF** | **`MULTI_BOOT` 停在 6 —— 起来了，网络通** | 无 |

**四次实测排出来的规律（这是本轮最硬的一块事实）**：

| | 辅助数据坏 | 辅助数据对 |
|---|---|---|
| **不带 RSA** | A：自增往下搜 | C：自增往下搜 |
| **带 RSA** | B：硬停 | D：硬停 |

**结论：失败方式只由"带不带 RSA"决定，与辅助数据对不对无关。**
换句话说 —— **辅助数据那三个缺陷是真的、修得也对，但它们不是拦路的那一个。**
BootROM 在更早的地方就把这份镜像否掉了，根本没走到用辅助数据再生 PUF 那一步。

### ★ 变体 G：**RSA 认证启动是通的，零 eFUSE**

G 是"只签名、不加密、不碰 PUF"的镜像，**从槽 6 正常启动、网络通**。
（`HSM_STATUS` 显示 `DAEMON=nosock / READY=no` 正是预期 —— G 故意用了
`atf_build_v50` 那份没有 secmmio SiP 的 BL31，这反而证明跑的确实是 G。）

**于是 B/D 的硬停不是 RSA 失败**，是过了认证、在 PUF/解密那一步挂的。

> **顺带得到一个实打实的正面能力：`bh_auth_enable` 的 RSA 认证启动在这块板上是
> 通的，一颗 eFUSE 都没烧。** 它**不是**信任根（PPK 摘要不与 eFUSE 比对，
> 攻击者换一份自己签的镜像照样过），但认证通路本身活着、可复现。
> 产物 `/home/build/pufboot/BOOT_PUF_G.BIN`，bif 同目录 `p_G.bif`。

### ★ 离线判据：镜像的密码学是对的，问题只可能在 BootROM 里

用**已知的红钥**（`XSK_PUF_AES_KEY` = `gen.nky` 的 `Key 0`）加启动头 `0xa0` 处的
IV，离线解变体 C 的 FSBL 段：

```
fsbl_sourceoffset = 0x2e00
GCM 校验：**通过**
  明文前 32 字节 = 全 0        （不换钥，正确）
  接下来 12 字节 = 7c301006…   （= nky 的 IV 1，正确）
  最后 4 字节    = 0x7eb8 字   （= 129760 字节 = pmufw 长度，正确）
```

**镜像的加密、密钥、IV、结构全部正确。** 唯一没被独立验证过的环节，就是
BootROM 能不能从启动头那 32 字节黑钥反推出这把红钥。

### ⛔⛔ 推翻上面全部结论：**BootROM 会报错误码，读出来发现我们六次测试全是无效的**

**我之前说"没有公开资料"是错的。** UG1085 第 11 章有一整张 BootROM 错误码表
（表 11-9），而且错误码是**可读的**：`PMU_GLOBAL.CSU_BR_ERROR`（**`0xFFD80528`**）。
表 11-8 说它同时保存**第一个镜像的错误码（bits 15:8）**和**最近镜像的（bits 7:0）**，
所以即使 BootROM 已经 fall-through 到别的槽，那一次失败的原因照样读得到。

清零之后逐个复现，读到的是：

| 变体 | 配置 | 错误码 |
|---|---|---|
| C | 黑钥加密，**不带** RSA | **`0x39`** |
| D | 黑钥加密 **+ RSA** | **`0x53`** |

**`0x53` 在 UG1085 表 11-9 里写得清清楚楚：**

> **0x53 — "Changing the state from non-secure to secure is not allowed."**
> Solution: "Ensure the key source is the same across multiple images used for boot
> in **POR and SRST**."

相邻的 0x51 把规则说全了：

> **0x51 — "Changing the state of the device from secure to non-secure is not allowed.
> **After POR, if first image is secure then subsequent images are secure.**"

**也就是说：ZynqMP 的安全状态由 POR 之后启动的​第一个镜像​锁定，
热复位（SRST）不能把它从"非安全"改成"安全"。**

而我们六次测试的做法**全都是**：板子已经用明文 `BOOT.BIN` 起来了（非安全状态）→
`set_multiboot=6` → **热重启** → BootROM 去读槽 6 里的加密镜像。
**这在 BootROM 看来就是"非安全 → 安全"，按规则直接拒绝。**

> **所以：PUF 加密启动到底行不行，我们​从来没有真正测过​。**
> 六次"失败"里，至少带 RSA 的那两次（B/D）失败的原因是**测试方法本身**，
> 与 PUF、辅助数据、shutter、`opt_key` 都没有关系。

`0x39` 未见于 UG1085 v2.2（表从 0x38 直接跳到 0x3A）。但从它的位置
（紧挨着 0x3A "authentication only is selected, but no authentication is selected
in eFUSE or the boot header"）加上 UG1085 那句
**"PUF regeneration can only be performed when authentication is enabled"**，
最合理的解释是 **`0x39` ≈ "选了黑钥/PUF 密钥源，但没有开认证"**。
这也与实测吻合：不带 RSA 的 A/C/E 全是 `0x39`，带 RSA 的 B/D 越过了这一关、
改报 `0x53`。

### ✅✅ 有效测法已执行（远程 POR）：**仍然失败，而且这次是干净的负面结论**

有了软件 POR（见第〇节）之后，这个测法不再需要人去拔电源。2026-08-17 执行：

**先做了降风险验证**（把安全网整条走通，零风险）：
把 `BOOT.BIN` 换成一个**故意损坏启动头**的镜像（`0x24` 的 `XLNX` 改掉）——
它不可能锁定安全态。结果：BootROM 拒收 → **`MULTI_BOOT` 自增到 1** →
起 `BOOT0001.BIN` → 20 秒网络就通 → 再从网络把 `BOOT.BIN` 写回 → 演示形态恢复。
**兜底路径与恢复路径都验证过了。**

**然后跑正式的**：`BOOT_PUF_D.BIN`（带 RSA 的那版）→ `BOOT.BIN` → 触发 POR。

| 观测 | 值 |
|---|---|
| POR 探针 `PERS7` | `0x00000000` → **确实发生了真 POR** |
| `CSU_MULTI_BOOT` | **`0x0`** → BootROM **没有**自增，是**硬停** |
| A53 #0 | `APU Reset` |

> **所以：`0x53`（非安全→安全）这条已经被绕开了，加密镜像作为 POR 后的第一个镜像
> 仍然起不来。** 这次是一个**干净的负面结论** —— 之前六次是测法无效，这一次不是。

**附带确认了一条对风险模型很要紧的事实**：救板时把 multiboot 指到槽 1（明文）
就正常启动了 —— **失败的加密镜像不会把安全态锁成 secure**，
所以"加密镜像失败 → 明文兜底也被拒 → 变砖"那个最坏场景**不成立**。

### ★★ 用 JTAG 读 CSU 内部状态：**BootROM 根本没碰过 PUF**

不需要串口 —— 其实串口在这里本来就没用（BootROM 阶段失败**不往串口吐任何东西**，
BBRAM 那次也是"串口零字节、连 FSBL 横幅都没有"）。真正有信息量的是
**CSU 里 PUF 自己的寄存器**，APU 停着也能用 JTAG 读。

硬停之后读到的（CSU 基址 `0xFFCA0000`）：

| 寄存器 | 值 | 含义 |
|---|---|---|
| `CSU_PUF_CMD` (`0xFFCA4000`) | `0x00000000` | **BootROM 从没发过 PUF 命令** |
| `CSU_PUF_CFG1` (`0xFFCA4008`) | `0x00080080` | 复位默认；4K 模式应是 `0x0c230090` |
| `CSU_PUF_SHUT` (`0xFFCA400C`) | `0x01000020` | 复位默认；我们启动头里写的是 `0x0100005E` |
| `CSU_PUF_STATUS` (`0xFFCA4010`) | `0x00000002` | `KEY_RDY = 0`，**从没再生出密钥** |
| `CSU_ISR` PUF_ACC_ERROR | `0` | 连一次 PUF 访问都没发生 |
| OCM `0xFFFC0000` | 全 `DEADBEEF` | OCM 的初始化填充 —— **FSBL 压根没被装载** |

> **结论：BootROM 在碰 PUF 之前就把镜像否掉了。**
> 失败不在 PUF 再生、不在黑钥解密、不在辅助数据、不在 shutter ——
> **它们从头到尾就没被用到过。** 卡点在更早的**启动头校验**。

**顺着这条又排掉一个假设。** UG1085 表 11-5 写明镜像属性 **[31:16] 是 Reserved、
默认 0**，而 `puf4kmode` 恰好写在 bit[17:16] —— 错误码 `0x33` 正是
"Reserved fields in image attributes are not zero"。于是做了**变体 H**：
去掉 `puf4kmode`（属性高 16 位归零），其余与 D 相同，POR 冷启动。
**结果一模一样** —— PUF 寄存器仍是复位值、OCM 仍是 `DEADBEEF`、仍然硬停。
**保留位这条也排除了。**

### 现在的结论：**这块硅上"启动头黑钥"这条通路不成立**

把所有证据摆在一起，失败点被夹到了一个很窄的地方：

| 环节 | 状态 |
|---|---|
| 启动头各字段（含密钥来源 `0xA35C7C53`） | ✅ 逐字对过 UG1085 表 11-4 / 11-5 |
| 镜像的 AES-GCM 加密 | ✅ 离线用红钥解 FSBL 段，tag 校验通过 |
| RSA 认证通路 | ✅ 变体 G 上板正常启动（零 eFUSE） |
| 安全态规则（`0x53`） | ✅ 用 POR 冷启动绕开了 |
| 镜像属性保留位（`0x33`） | ✅ 变体 H 归零后无变化 |
| **BootROM 接受 `bh_blk_key` 这个密钥来源** | ❌ **没走到 PUF 就被否，PUF 全程未被触碰** |

**能做的都做了：** 六个配置变体 + 有效的 POR 测法 + 逐寄存器的 JTAG 内窥。
剩下的解释只有两种，而两种都不是我们这边能动的：
① 这颗硅/这版 BootROM 不接受启动头黑钥；
② 还有一个未公开的前置条件（最可能是 eFUSE 里的 PUF 位 —— 注意 XilSKey 自己的
`XilSKey_Puf_Regeneration()` 开头就拒绝 eFUSE CHASH 为 0 的情况，
理由写着"PUF regeneration is not allowed, as PUF data is not stored in eFuse"，
**这与 UG1085 表 12-6 说的"CHASH 未编程时可用启动头黑钥"自相矛盾**）。

**两条都指向 eFUSE，而 eFUSE 是本项目的永久红线。到此为止，不再猜着上板。**

### 原来写的"唯一有效的测法"（已执行，见上）

安全状态只有 POR 能重置，而 `CSU_MULTI_BOOT` 也由 POR 清零 —— 两条合起来意味着：
**加密镜像必须放在 `BOOT.BIN`（多重启动槽 0），然后断电冷启动。**
放非 golden 槽 + 热重启的那套流程，**在原理上永远测不了加密启动**。

正确步骤（**要人在板子旁边**）：

1. 先把 `BOOT.BIN` 备份好（离板已有 `c4c99e2e…`；板上 `BOOT0002.BIN` 是兜底 golden）。
2. `cp BOOT_PUF_D.BIN → /media/sd-mmcblk1p1/BOOT.BIN`（**D，带 RSA 的那版** ——
   因为不带 RSA 的会撞 `0x39`）。
3. **断电冷启动。**
4. 起来了 → PUF 加密启动成立；起不来 → 读 `0xFFD80528` 拿新的错误码。

**失败时怎么救**：POR 之后 multiboot=0 走 `BOOT.BIN`，失败会自增去搜
`BOOT0001/0002…`，槽 1、槽 2 都是能启动的明文镜像，**多半会自己落回去**；
落不回去就用第〇节那套 JTAG 动作（清 `USE_ALT` + `multiboot=0`）。
⚠️ 但要注意：一旦第一个镜像是"安全"的，后续镜像也必须是安全的（0x51），
所以 fall-through 到明文槽**可能同样被拒**。这是这次实验的真实风险，
**必须有人在旁边、并且准备好用 JTAG 把 `BOOT.BIN` 换回去**。

## 八、收尾会话（2026-08-17 晚）：两件遗留事都做完了

接手时的两件遗留事：① XMPU 持久化；② 查清槽启动不稳定性。
**结果：两件是同一个根因，查清 ② 直接把 ① 解开了。**

结论文档在 [FINAL-REPORT](FINAL-REPORT-2026-08-17.zh-CN.md) 第四节，
原始证据在 `board/logs/RESULT_slot_boot_wdt.txt` 与 `RESULT_xmpu_persist.txt`。
这里只记过程与被推翻的东西。

### ①-a 先做对照实验，把"槽机制坏"和"镜像坏"分开

这一步是整轮的关键，而且它便宜。安全网：先把槽 7 换成已知能启动的镜像
（原 J1 镜像 `2d7799a3` 构建机上有备份，事后已还原），槽 6 失败时板子自己落回好镜像。

* 槽 6 放**已知能启动**的镜像（`c4c99e2e`）→ 20 秒回来、`MULTI_BOOT` **停在 6**。
  → **槽机制本身是好的。**
* 槽 6 放上一轮那份被拒的重建镜像（`12c3fc8e`）→ **138 秒**才回来、
  `MULTI_BOOT` **变成 7**。→ **复现了。**

### ①-b 排除 BootROM：它根本没报错

```
CSU_MULTI_BOOT   0xFFCA0010 = 0x00000007
CSU_BR_ERROR     0xFFD80528 = 0x00000000   ← BootROM 没报任何错
RESET_REASON     0xFF5E0220 = 0x00000025   ← 含 SRST 位
```

离线逐字节比两份镜像：**启动头 14 个字段、六个分区头全部逐字相同**，
46845 字节差异**全部**落在 BL31 那个分区内部（`0x47256c..0x484ca9`，
而分区 #2 是 `0x472540 + 0x127C0`）。
BootROM 只校验启动头 + 装载 FSBL，这两样两份完全一样 —— 它不可能拒。
分区头里 checksum word offset = 0，**FSBL 也不校验分区内容**。

> 那"谁"把 `MULTI_BOOT` 从 6 加到 7 的？——**本项目自己的 FSBL 补丁。**

### ①-c 真凶：`make_wdt_patch.py` 第 4 行就写着

```
# and fall back (multiboot++) on any WDT-induced reset.
```

* FSBL 交接给 ATF **之前**武装 PS SWDT0，`XFSBL_WDT_EXPIRE_TIME = 100` 秒
  （`xfsbl_misc_drivers.h:42`）；
* **故意不在 handoff 时停掉它**（`xfsbl_handoff.c` 补丁原文：*"the WDT is
  intentionally NOT stopped at handoff … It keeps guarding the ATF/OP-TEE/U-Boot
  phase"*）；
* 停狗在 **U-Boot 的 `boot.scr`** 里（带 `0xABC` 钥匙写 ZMR，`WDEN=0`）；
* 于是「FSBL 交接」到「U-Boot 跑到 `boot.scr`」之间有一条**硬的 100 秒线**；
* 超了 → SWDT 整机复位 → 下一次 FSBL 认出是 WDT 复位 → **`multiboot++`**
  （`xfsbl_initialization.c` 那段补丁）。

`LOG_LEVEL=50` 把整张页表（2888 行）打到 115200 串口，**把 ATF 那段推到 100 秒线附近**。
赶上了就起来，没赶上就 6→7。**"时灵时不灵"是在跟一条 100 秒的死线赛跑。**

138 ≈ 100（看门狗）+ 38（落到槽 7 的一次正常启动），对得上。

### ② XMPU 持久化：把 `LOG_LEVEL` 降到 20，它自己就成了

只改 `LOG_LEVEL` 50→20，其余构建参数逐字不动（`PLAT=zynqmp SPD=opteed DEBUG=1`）。

| 镜像 | 槽 6 | 网络回来 | `MULTI_BOOT` |
|---|---|---|---|
| `c4c99e2e`（对照） | 成功 | 20 秒 | 6 |
| `12c3fc8e`（L50，复现旧失败） | **失败** | 138 秒 | **7** |
| `3771d140`（L20 + 诊断 + 交接前重写） | 成功 | 23 秒 | 6 |
| `8a290f42`（L20 + 诊断，去掉重写） | 成功 | 41 秒 | 6 |
| `0ea6e443`（L20 生产版） | 成功 | 35 秒 | 6 |

三份 L20 镜像**零失败**。

### ②-a 诊断不走串口 —— 因为串口正是失败原因，用它诊断是自指的

接手时串口又回到那个坏状态（`stty` 与 pyserial 都是 `tcsetattr: Invalid argument`，
`cu.`/`tty.` 两个节点都是）。**但就算串口是好的，也不该用它** ——
上一轮想用 `NOTICE()` 打回读值，而"打串口"恰恰就是把启动拖过 100 秒线的那件事。

改成把回读值写进**被禁用区域 R14** 的三个寄存器当草稿纸
（`R14_CONFIG` 的 `EN=0`，这三个字不参与任何判定；而 `0xFD00_0000` 段本来就在
SiP 的**只读**白名单上，普通世界经 `/dev/secmmio` 就读得到）——
**不用串口，也不用 JTAG。**

三个采样点：① 早期写完立刻回读 → `R14_START`；② BL31 交接前（早期那次还在不在）
→ `R14_MASTER`；③ 交接前再读 → `R14_END`。加上 Linux 起来后的 POISON 现值，共四点。

**两个诊断版镜像 × 六个实例 × 三个采样点，十二个点全是 `0x00100000`。**

### ②-b 于是推翻上一轮那条"回读恒 0"

> **那是个假观测。那份带 `POISON` 写的镜像根本没跑起来。**

它被 100 秒看门狗打掉、`multiboot++` 落到槽 7，实际跑的是槽 7 里另一份
**不含这段代码**的 BL31 —— 读到 0 理所当然。
「EL3 写没进去」和「写进去又被清掉」**两个都不是**。

顺带证明"交接前再写一次"是多余的：去掉它的对照版四个采样点一模一样。
生产版因此**不带**任何重写、也不带任何诊断写
（`patch_atf_secmmio.py` 里 `PQCHSM_XMPU_LATE` 默认 0），
JTAG 读回 R14 三个字全 0 就是这一点的自检。

### ②-c 提升成默认形态

`multiboot` 由 POR 清零，所以只放在槽 6 等于下次上电就没了。
把验证过的镜像提升成 `BOOT.BIN`（旧的留在卡上 `BOOT_PRE_XMPU.BIN`，
离板副本 `/home/build/BOOT_WORKING_REF.BIN`），`multiboot=0` 重启后：

```
CSU_MULTI_BOOT = 0        ← 默认上电路径
devmem 0x60000000 → Bus error
devmem 0x10000000 → 0xEDFE0DD0
sdf_demo 九节全绿，dna_probe -w 正常，eth1 通，PL operating
```

再补一条最直接的持久化反证：**JTAG 把 POISON 清零 → `0x60000000` 读回
`0xAA0003F3`；直接重启、什么都不做 → 又变回 Bus error。**

### ②-d 这轮**没有**做的

* **没做真 POR 复验。** `jtag_por.tcl` 要求 PMU 的 CSU_ROM 错误位置着才能触发，
  而本轮 `ERROR_STATUS_1/2` 都是 0（没有任何一次 BootROM 失败）。
  为凑触发源去**故意搞坏一次启动**，风险大于收益，所以没做。
  已验证的是等价冷路径（`MULTI_BOOT=0`、从 `BOOT.BIN` 起，整条链与上电相同）；
  XMPU 配置由 BL31 每次启动重写，不依赖任何 POR-only 状态。
* 万一新 `BOOT.BIN` 某次上电起不来：FSBL 会 `multiboot++` 落到 `BOOT0001.BIN`
  （`bb3402ea`，已知 10/10 能启动）—— 板子仍起得来，但**那一份不带开机毒化**。

### ②-e 顺手修掉的两个坑

* **产物不再就地覆盖。** 上一轮把当前 `BOOT.BIN` 所用的 `bl31.elf` 覆盖掉且没备份，
  永久丢失。现在 `build-bl31-secmmio.sh` 每次用**新的 `BUILD_BASE` 和新的输出名**，
  成品另存 `/home/build/keep/` 并置只读。
  「重建镜像与在跑的这份不一致」这个遗留问题也随之消失 ——
  现在在跑的就是从当前 ATF 树重建出来的，脚本/源码/产物三者对得上。
* **旧文档里"`BOOT_SECMMIO.BIN` 是在跑的 `BOOT.BIN` 的离板副本"已失效**：
  它在上一轮又被重建覆盖了（现为 `12c3fc8e`）。真正的副本是
  `/home/build/BOOT_WORKING_REF.BIN`。

### ②-f 记一笔与本轮无关的既有状态

`p1/use_backup` 这个标记文件存在，于是 `boot.scr` 一直走 `image_backup.ub`
而不是 `image.ub`（两者同尺寸同日期）。演示不受影响，
但**要换内核就得同时换 `image_backup.ub`，或者先删掉 `use_backup`**。

# 安全策略（草稿）

> **本文是针对研究原型撰写的草稿。** 它采用 FIPS 140-3（ISO/IEC 19790:2012）
> 非专有安全策略的结构，并映射到 GM/T 0028-2014 的相应条款，目的是把"现状"
> 与"送检所需"之间的差距显式列出来，而不是留给读者去推断。第 13 节即为差距
> 清单。本模块未申请也未取得任何认证，且下文若干节描述的是模块当前**尚未**
> 满足的要求。

## 1. 概述

| 项目 | 取值 |
|---|---|
| 模块名称 | pqc-crypto-module |
| 模块类型 | 单芯片硬件模块：密码引擎是 Xilinx XCZU3EG 的可编程逻辑，主机软件作为边界之外的控制面 |
| 目标安全等级 | 硬件边界已存在并生效；要主张 3 级还需物理防拆响应、设备绑定的密钥派生根与算法证书——见 §10 |
| 形态 | XCZU3EG（AXU3EGB 板）上的 FPGA bitstream，由跑 Linux 的 Cortex-A53 经 AXI4 驱动；主机侧是共享库（`pqchsm-pkcs11`）加守护进程与命令行工具 |
| 密码边界 | 可编程逻辑：ML-KEM 512/768/1024、AES-128/256、SM4、SM3、环形振荡器 TRNG、密钥仓，以及把它们围起来的按 AxPROT 门控的 AXI 防火墙 |
| 边界如何生效 | `axi4lite_firewall` 对 `SECURE_ONLY=1` 的从机拒绝任何 `AxPROT[1]=1` 的事务（DECERR）。已在真硅上双向证明——见下方证据 |
| 已测试的运行环境 | XCZU3EG（`xazu3eg-sfvc784-1-i`）@75 MHz，Cortex-A53 上 Linux 5.4；主机侧工具在 macOS arm64 与 Debian aarch64（GCC 12） |

**边界生效的证据。** 板上实测，同一次运行、同一份 bitstream、同一个地址：

| | `0x8004_0000`（`SECURE_ONLY=1`） | `0x8003_0000`（`SECURE_ONLY=0`） |
|---|---|---|
| 安全世界 EL3（`AxPROT[1]=0`） | 读到 `0x00010000` | 读到 `0x00010000` |
| 普通世界 EL1-NS（`AxPROT[1]=1`） | **被拒 —— SIGBUS / DECERR** | 读到 `0x00010000` |

右边一列是对照：同一个普通世界能成功读到未设门控的核，所以左边那格的拒绝来自
门控，而不是地址不可达。安全世界那一侧是一个最小的 EL3 负载——给 BL31 加的一个
SiP 调用，只做一次读并把值返回。原始日志与完整方法见
[密码机原型-说明文档.md](密码机原型-说明文档.md) §3.6。

另有一项针对密钥仓的实测：扫两个从机各 256 字节（48 个读得到、80 个被防火墙拒），
密钥的四个字一个都没出现，而这些密钥算出的密文是正确的。

模块提供后量子密钥封装与数字签名服务、密钥存储、槽位与会话管理、M-of-N 备份
与恢复，以及防篡改审计日志，经 PKCS#11 v3.2 接口对外暴露。

## 2. 密码模块规格

模块由 `src/` 与 `include/pqchsm/` 下的源码定义，构建为 `libpqchsm` 与 PKCS#11
共享库。它链接 OpenSSL 3 与 liboqs；按此处划定的边界，两者位于边界之外，
其算法实现原样使用。

核准算法、参数集及各自的支撑证据见 [algorithms.zh-CN.md](algorithms.zh-CN.md)。

模块只有一种工作模式，不存在非核准模式：需要非核准算法的服务一概不提供。

加速器抽象层（`include/pqchsm/accel.h`）允许把算术运算交给可编程逻辑执行。
四种 transport 以完全相同的方式实现它——软件桩、仿真 RTL 后端、经 AXI4-Lite 与
AXI4-Stream 驱动同一批 RTL 的后端，以及面向真实设备的内存映射 transport——
它们共用的寄存器契约见 [register-map.zh-CN.md](register-map.zh-CN.md)。
在已测试的运行环境上只跑软件路径。

## 3. 密码模块接口

| 逻辑接口 | 实现方式 |
|---|---|
| 数据输入 | PKCS#11 函数参数；TLV 命令协议（`src/proto`） |
| 数据输出 | PKCS#11 返回缓冲；TLV 响应 |
| 控制输入 | PKCS#11 函数选择；命令行与管理工具命令 |
| 状态输出 | PKCS#11 返回码；`hsm_status_t`；审计日志 |
| 电源接口 | 软件模块不适用 |

没有任何接口返回私钥材料。`include/pqchsm/` 中的每个 API 都基于不透明句柄工作；
`tools/check_no_readback.py` 在结构上强制这一点：一旦有人往密钥派生根的头文件里
加入读回函数，检查即失败。

## 4. 角色、服务与鉴别

定义三种角色（`hsm_role_t`）：

| 角色 | 鉴别方式 | 服务 |
|---|---|---|
| 公共 | 无 | 读取公开的令牌信息、读取公钥、验签 |
| 用户 | 用户 PIN | 密钥生成、签名、封装、解封装、槽位内的对象管理 |
| 安全管理员 | 管理员 PIN | 令牌初始化、PIN 重置与解锁、清零、备份与恢复 |

鉴别基于 PIN。PIN 以带槽位盐值的 KMAC256 摘要存储，比较使用常量时间原语。
用户 PIN 连续失败会累加计数并在达到上限时锁定槽位，只有安全管理员可解锁。

角色由每个服务入口都要过的显式访问控制表强制，而不是散落各处的条件判断；
槽位状态机（`src/slot/fsm.c`）同样是一张显式转移表。两者都由
`tests/unit/test_slot_fsm.c` 直接覆盖。

## 5. 软件安全

模块以源码交付，由集成方构建。构建产物的完整性由运行环境负责，模块自身不对
自己做签名校验。送检需要对模块映像采用核准的完整性技术，本模块尚无此机制。

密钥库文件带整文件 KMAC256 标签，因此记录的删除、调换与截断都会在装载时被拦住。
审计日志是 SHA3-256 哈希链，链头由 ML-DSA 设备身份密钥签名。

## 6. 运行环境

可修改型。模块以库的形式运行在通用操作系统上的任意宿主进程内。按 FIPS 140-3
这对应安全 1 级，进程隔离由操作系统负责。

敏感缓冲在平台允许时 `mlock`，使用后清零。两者都不能防御能读取进程地址空间的
攻击者；审计覆盖与不覆盖的范围见 [constant-time.zh-CN.md](constant-time.zh-CN.md)。

## 7. 物理安全

当前形态的软件模块不适用。设计上预期部署为 Zynq 级 SoC 上的多芯片独立模块、
算法核落在可编程逻辑里，届时物理安全要求（防篡改证据、篡改响应、环境失效保护）
才会适用。这些目前都不存在。

## 8. 非入侵式安全

不作声明。常量时间审计（`tools/ct_audit.py`）验证模块自身源码中不存在秘密相关的
分支、内存下标与除数，`tests/unit/test_ct_timing.c` 以统计方式验证常量时间比较
原语与数据无关。两者都不构成 ISO/IEC 19790 附录 F 意义上的非入侵式攻击缓解声明：
liboqs 与 OpenSSL 内部的算法实现不在分析范围内，也没有做过任何功耗或电磁分析。

## 9. 敏感安全参数管理

密钥层次、各敏感安全参数的生成、存储与清零见
[algorithms.zh-CN.md](algorithms.zh-CN.md#密钥与参数清单)。

密钥与随机数的熵来自由操作系统播种的 OpenSSL DRBG，模块自身不含熵源。
带 SP 800-90B 连续健康检测的环形振荡器噪声源已有 RTL
（`hardware/rtl/trng/trng_health.v`）并在仿真中验证，但尚未接入软件路径。

清零是结构性的而不是零散的：`tools/check_zeroize.py` 验证每个密钥材料字段都被
其销毁函数抹掉、每个局部密钥缓冲在每条返回路径上都被抹掉，否则构建失败。
`tests/unit/test_zeroize.c` 另在 `-O2` 下验证清零原语没有被当作死存储消除，
并配对照确认同一位置上的普通 `memset` **确实**会被消除。

边界之内（可编程逻辑里）的清零分两种，形态不同，都不是"清指针"：

- **密钥仓**用寄存器阵列，`zeroize` / `tamper` 在**一个时钟沿**清完全部槽位，
  不存在"擦了一半"的窗口。选寄存器而不是 BRAM，这是理由之一。
- **ML-KEM 的两块 8 KB 缓冲**是 BRAM，只能逐地址写 0（8192 拍），"擦了一半"
  的窗口一定存在。设计上的处理是把这个窗口**明确暴露成一个状态位**
  （`STATUS[4] = WIPING`），期间拒绝一切读写、拒绝启动、写回 SLVERR 而不是
  静默丢弃 —— 静默丢弃会让软件按错误的长度启动，出一个安静的错误结果。
  判据是仿真里**读回两块 BRAM 的全部 16384 个字节确认为 0**，
  不是"`OUT_LEN` 变成 0"；后者只证明软件读不到，正文还在不在它答不了。

  ⚠️ 这一条**在板上证不了，而这正是设计对的表现**：软件本来就没有任何一条
  路径能读到那些字节（有的话才是漏洞）。板上能证的是 `WIPING` 的行为与时长。

## 10. 自测试

上电自测在第一次密码服务之前运行，也可显式重跑（`pqc_self_test()`）。
每一项都是已知答案测试，期望值来自模块之外：

| 测试项 | 期望值来源 |
|---|---|
| SHA3-256 | FIPS 202 公开示例 |
| KMAC256 | SP 800-185 官方示例 Sample #4 |
| AES-256-GCM | GCM 规范测试用例 14 |
| ML-KEM-768 密钥生成 | NIST ACVP ML-KEM-keyGen-FIPS203 向量 |
| ML-DSA-65 密钥生成 | NIST ACVP ML-DSA-keyGen-FIPS204 向量 |

任一项失败即置模块为错误状态，此后每个密码服务都返回 `PQC_ERR_SELF_TEST`
且不产生任何输出，恢复需要重跑并通过。`tests/unit/test_selftest.c` 不止断言
"五项都过"，还断言错误状态确实拦下每一个入口，包括参数本身非法时也不得先行
返回参数错误而绕过闸门。

FIPS 140-3 要求但**尚未实现**的条件自测试：新生成密钥对的配对一致性测试，
以及随机数发生器的连续测试。两者都列在第 13 节。

## 11. 生命周期保障

开发全程版本控制，每次改动都带上对应的测试。测试套件在 macOS/arm64 与
Debian/aarch64 上通过 `ctest` 运行，并在 AddressSanitizer、UndefinedBehaviorSanitizer
下运行，并发路径另在 ThreadSanitizer 下运行。算法路径的正确性钉在 NIST ACVP
向量上，`tools/kat_evidence.sh` 通过实际运行重新生成证据表。

RTL 由 `tools/rtl_lint.sh` 检查（Verilator `-Wall`，每个模块各自作为顶层跑一遍，
外加一道 Icarus Verilog），并由 cocotb 回归对着独立预言机验证。豁免条目连同理由
列在 `hardware/rtl/lint_waivers.vlt` 中，按文件与信号名精确匹配，因此同类告警的
新增实例不会被顺带遮住。

交付形态为源码。没有签名的发布产物，没有正式的配置管理记录，除仓库文档之外
也没有单独的操作员指南。

## 13. 与送检要求之间的差距

下列每一条都足以单独阻断送检。列在这里是为了避免把本文读成"已经就绪"。

1. **没有设备绑定。** 密钥派生根是编译进去的常量，其字面文本本身就写明了这一点。
   真实设备应从 eFUSE、BBRAM 或 PUF 取得该值。
2. **~~边界内没有熵源。~~ 已关闭。** 边界内有一个带 SP 800-90B 连续健康检测的环形
   振荡器噪声源，实测最小熵 0.871234 比特/样本。**主机**软件仍从 OpenSSL 取种子。
3. **没有模块完整性校验。** 使用前没有任何机制校验模块映像。
4. **缺少条件自测试。** 没有新生成密钥对的配对一致性测试，也没有随机数连续测试。
5. **没有物理安全。** 边界靠逻辑（AxPROT 门控）生效，不是靠物理。没有防拆外壳、
   没有防拆响应、没有环境失效防护。RTL 里有一根 `tamper` 输入，拉高会擦除密钥仓，
   但目前没有任何东西接到它上面。
6. **没有算法证书。** ACVP 向量是本地跑的，这是正确性证据，不是证书。
7. **审计日志假定单写者。** 审计模块不对文件加锁。
8. **Shamir 分片校验和不带密钥。** 只能发现损坏，不能发现篡改。
9. **管理员 PIN 未强制锁定。** 失败会计数但不锁定槽位，因为锁定等于把设备变砖，
   兜底手段是 M-of-N 恢复。
10. **ML-DSA 没有完整算法的硬件实现。** ML-KEM 512/768/1024 的
    KeyGen/Encaps/Decaps 已在 PL 里实现，并在真硅上对 NIST ACVP 向量逐字节
    一致；对称核（AES-128/256、SM4、SM3）同样在 PL 里并对标准向量一致。
    ML-DSA 只有算子（13 个模块，对参考模型验证过），没有串成整核。

## 与 GM/T 0028-2014 的对应

GM/T 0028-2014 与 ISO/IEC 19790:2012 对齐，因此章节结构高度对应。下表记录每条
要求在本文中的落点。

| GM/T 0028 条款 | 主题 | 本文对应 |
|---|---|---|
| 7.1 | 密码模块规格 | §1、§2 |
| 7.2 | 密码模块接口 | §3 |
| 7.3 | 角色、服务和鉴别 | §4 |
| 7.4 | 软件/固件安全 | §5 |
| 7.5 | 运行环境 | §6 |
| 7.6 | 物理安全 | §7 |
| 7.7 | 非入侵式安全 | §8 |
| 7.8 | 敏感安全参数管理 | §9 |
| 7.9 | 自测试 | §10 |
| 7.10 | 生命周期保障 | §11 |
| 7.11 | 对其他攻击的缓解 | §12 |

有两处差异专门影响 GM/T 0028 送检，且本模块并未处理：该标准的核准算法清单是
商用密码算法体系（SM2、SM3、SM4、ZUC），本模块一个都没有实现；随机性要求引用的是
GM/T 0005 而非 SP 800-90B，因此 `hardware/rtl/trng/` 里的噪声源健康检测阈值
需要按该文件重新推导。

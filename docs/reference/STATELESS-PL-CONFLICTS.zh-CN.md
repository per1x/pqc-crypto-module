# 「PL 完全无状态 + 密钥全归 PS-TEE」冲突清单

> **基准模型**（本文的判定尺）：① PL 完全无状态，只存多项式/公开参数、只做计算，运算结束不得残留秘密；
> ② 所有密钥与种子归 PS-TEE 权威保管；③ 每次运算由 TEE 送种子进 PL 展开、算完即弃。
> 凡与这三条抵触的，本文都列为冲突。**只做分析，未改任何代码，未碰开发板。**
>
> **前提假设：量产形态有真信任根。** 烧 `PPK0_HASH + RSA_EN`（认证根）+ `FUSE_AES` 或 PUF 注册
> （秘密根），CSU AUTH 位置起，HUK 走 CSU AES-GCM + device key 的真实路径。
> **这块 AXU3EGB 只是原型载体，它没烧 eFUSE 是原型阶段的流程选择，不是架构能力边界。**
> 本文按"有信任根"判定；凡结论依赖"根是公开 DNA"的，一律标为原型形态特有并单独说明（见 §8.1）。

## 0. 两条先看（会改变决策）

### 0.1 ⚠️ 一条被拦下的错误主张

分析过程中出现过一个很有诱惑力的结论："PL 侧的种子暂存口（`SEED_STAGED` / `SEED_DATA` / `SEED_LOCK`）
已经实现了，最贵的一半已经付过钱，批 1 只剩几十行 EL3"。

**这是假的，我逐条核过**：全仓 `grep` `SEED_STAGED`/`SEED_DATA`/`SEED_STAT`/`SEED_LOCK` **零命中**，
daemon 里 `SEED` 相关代码 0 处。`mlkem_axi` 的寄存器实际到 `0x34 KEYPSET` 为止，没有 `0x38`。
**PL 侧的安全种子通路一行都还没有写**，它是批 1 的真实工作量，不是已完成项。

### 0.2 ✅ 一条独立于模型变更、今天就成立的实缺陷

**「算完即弃」在 RTL 层目前是零覆盖**——这条我也逐条核过，是真的：

| 事实 | 核验方式 |
|---|---|
| ML-DSA 三个核（`sign.v`/`keygen.v`/`verify.v`）**没有任何 `zeroize` 端口** | `grep -c zeroize` = **0 / 0 / 0** |
| `mldsa_engine.v:57-63` 自己写明只擦 engine 的输入缓冲，核内 s1/s2/t0、y、z、c 是"已知缺口" | 源码注释 |
| ML-KEM 三个核把 `sha3_core.zeroize` **接死为 `1'b0`** | `keygen.v:155`、`decaps.v:210` |
| `ram_dp.v` 无复位口 → 核内 BRAM 靠复位也擦不掉 | 源码 |
| 对称核的 zeroize 能力**RTL 里有**，但 daemon 从未定义 `SY_CTRL`，**从来没发过一次** | daemon 无该偏移 |

**这意味着：无论采不采用新模型，今天每跑完一次 ML-DSA 签名，展开态私钥（s1/s2/t0）与签名中间量
都原样留在 PL 里，任何 `ZEROIZE` 都碰不到。** 这是本次扫描里最有价值的发现，建议批 1 优先处理。

## 3. B 组 —— 算完即弃在 RTL 层未实现（**建议批 1 优先**）

| ID | 冲突点 | 怎么打架 | 严重度 | 消解 | 批次 |
|---|---|---|---|---|---|
| **Z-01** | ML-DSA 三核无 zeroize 端口（`mldsa_engine.v:59-63` 自陈） | 违基准①③：签名完成后展开态私钥原样留在核内 BRAM | 硬冲突 | **一台共享擦除机**（见下） | **批1** |
| **Z-02** | `sign.v` 的 `key_out`(=K)、`tr_out`、`mu`、`rhopp`、`ctilde` 明文寄存器只在 `!rst_n` 清 | `ZEROIZE` 对它们零作用，连"靠复位充数"都不成立（`mldsa_axi.v:354-356` 特意改回纯复位） | 硬冲突 | 核复位改 `rst_n && !wipe`，一拍带走 | **批1** |
| **Z-03** | ML-KEM 核内 BRAM（`u_bank`/`u_ekbuf`/`u_cbuf`）无擦除 | ŝ/ê/t̂ 与 dk/c 缓冲留在 PL。`mlkem_axi` 文件头自己论证过"只清指针不擦 BRAM 是把目录页撕了正文还在"，但没延伸到核内 | 硬冲突 | 同一台擦除机广播 | **批1** |
| **Z-04** | `sha3_core.zeroize` 在 ML-KEM 三处接 `1'b0` | 海绵状态过过 d/z/σ/dk；与 `mldsa_axi.v:371-376` 的处理**自相矛盾**（那边接了真 zeroize） | 需重构 | 三行改接 | **批1** |
| **Z-05** | 对称核 zeroize 有能力但 daemon 无 `SY_CTRL`，从未发过 | 展开轮密钥表跨运算跨会话驻留，软件栈没有任何一条路擦它 | 需重构 | daemon 补 `SY_CTRL`(S_SYM+0x04)，`session_end()` 一并发 | **批1** |

**推荐实现（比逐核加机器省八成工作量）**：不做三台擦除机,在 `mldsa_engine` 里做**一台**——
共享 wipe 计数器 + `wipe_en` 广播给三个核，每块 `ram_dp` 的 B 口在 wiping 期强制成 `(addr=cnt, we=1, din=0)`。
**关键数字：所有 BRAM 并行擦，总拍数 = 最大 AW 而非各块相加 → 2^13 = 8192 拍 ≈ 109 µs @75 MHz**，
与 `mlkem_axi` 现有缓冲擦除同量级，不是灾难。同一台机器一并解决 Z-03/Z-04。

## 7. 我的反驳：四处我认为不该照做

### 7.1 对称密钥金库（V-03）—— 建议**保留**，只改归属与寿命

> 注：本节结论不变，但论据已按"有信任根"前提重写——早期版本用的"掉电即失、无持久密文"那条理由，
> 在有真 HUK 之后不再成立（见 §8.1）。

保留它的理由现在只剩两条，但都够硬：

1. **性能。** `sym_axi` 是单分组变换，每块约 10 次寄存器访问，每次是 `ioctl → SMC → EL3 → mmio`
   一个来回（约 0.3–0.5 µs），今天分组路径已只有 3–4 MB/s 量级。若改成**每分组重送密钥**，
   再加 8 次 KEY 写 + `LOAD_KEY` + 密钥扩展等待，访问数近乎翻倍、吞吐腰斩。
   若是**每段送一次**则代价可忽略（8 次写摊到成千上万块上）。
   ⚠️ **基准第 3 条里"每次运算"的粒度没有定义**——这正是需要拍板的地方，见 §7.2。
2. **它是仓库里唯一一条可证伪、已实测的结构性质**：密钥寄存器到 `s_axi_rdata` 之间**根本没有导线**
   （不是门控，是没有连线），`test_key_vault` 逐地址扫描验证过；且因为是 2048 个 FF 而非 BRAM，
   擦除一个时钟沿完成、**没有"擦了一半"的窗口**。删掉它，README 证据表、security-policy §1 送检证据、
   `hsm_hwtest` 边界扫描三处一并失去对象——**这在送检语境下是净损失**。

**注意这不是给 PL 开保管权**：正本仍在 TEE，基准②的实质（权威归属）成立，
放宽的只是基准①③的**寿命粒度**。

**替代方案（便宜且都有现成写法）**：① 装载口只认安全事务（`AxPROT[1]==0`）；
② **EL3 白名单必须排除该偏移**——否则 root 经 SiP 转一手照样能写（两边缺一等于白做）；
③ daemon 补 `SY_CTRL`，段末与 `session_end` 发 ZEROIZE。
对外口径改成"权威副本在 TEE，PL 侧是**单段使用容器**、段末即擦"。这样基准①③实质成立、②的权威归属
也成立，而唯一那条硬证据保住了。

### 7.2 基准①建议放宽到"不得残留**跨操作**的秘密"

"不得残留任何秘密"在 BRAM 上**字面不可实现**——`ram_dp` 无复位口，擦除必然有 8192 拍窗口。
所以可实现形式本来就是"操作结束即擦、窗口暴露成状态位"。

放宽边界（四条缺一不可）：① 擦除由**硬件在 S_FIN/DONE 无条件触发**，不由任何软件（包括 TA）决定；
② 展开区不带 valid 位、不带跨请求可引用的槽号语义；③ 擦除中 `WIPING=1` 且拒绝下一笔；
④ 逐地址真写零，不靠复位充数、不靠"下次覆盖"。

**但不放宽到会话级**：TA 只能经 SiP 发写事务，TA 崩溃/被拒服务/掉电时**清除动作根本发不出去**，
残留时长不由 TA 决定。"TA 门控生命周期"改变的只是谁来清，不改变秘密在 PL 过夜这个事实。

### 7.3 ACVP 可测性：方向要反过来说

严格模型下 ACVP **更好做，不是更难**。ACVP 的 KeyGen 本就要求外部喂确定性种子并逐字节比对 pk‖sk
——这正是基准模型下唯一正当的调用形状。**今天在花钱的反而是现状**：`dk_lock`/`sk_lock` 把导出封死，
逼 ACVP 绕开调用链去 `board/src/mldsa_hwtest.c` 直连寄存器，**测的不是产品路径**；交付形态一闩上，
认证证据与交付形态就对不上号。

做法：保留 `IN_DATA` 那条路（`mlkem_axi` 文件头第 115 行自己已定此口径），
软件侧加**可选载荷**而**不是 test-mode 寄存器位**（后者会引入"置上就能读私钥"的新攻击面）。
**谁能用它由门禁决定，不由模式位决定。**

### 7.4 批 2 应设硬门槛；PKCS#11 进程模型重写推后

批 2 全部依赖一件**从未成功过**的事（OP-TEE 在这块板跑通，卡 BL32 入口）。
**建议设硬门槛：先让一个最小 TA（hello world + `TEE_GenerateRandom`）真跑通并留下串口证据，
在那之前不动 `src/` 一行。** 同时把批 2 里**不依赖 TEE 的那一半**提前到批 1——
EL3 侧种子暂存、SiP 门禁、PL 擦除覆盖，**这三件事无论 TEE 最终成不成都成立**。

## 8. 在有信任根的前提下，这个模型买到了什么

**前提（本文基准假设）**：量产形态有真信任根——烧 `PPK0_HASH + RSA_EN`（认证根）+ `FUSE_AES` 或 PUF
注册（秘密根），CSU AUTH 位置起，OP-TEE 的 HUK 走 `SHA-256(DNA + USER eFUSE)` → CSU AES-GCM 用
device key 加密的真实路径。**这块 AXU3EGB 只是原型载体，不是能力边界。**

**结论：在这个前提下，TEE 主线严格优于"私钥常驻 PL 金库"。** 三条理由：

1. **持久化从负债变成资产。** 有真 HUK 后，keystore 密文的根是真秘密，拿到 SD 卡解不开。
   于是"秘密以密文持久化"不再是弱点——**这正是所有商用 HSM 的标准做法**（密钥必须跨重启存活、
   必须能备份、必须能迁移）。反过来，PL 金库"掉电即失"在量产语境下是**功能缺陷**而非安全优势：
   密钥活不过一次重启，也无法备份。
2. **安全启动闭合了镜像替换。** 认证根一旦锚在 eFUSE，"把 SD 上的 OP-TEE 换成恶意 BL32"这条路被堵死，
   TEE 的隔离才真正可依赖。
3. **对运行时 root 的改善仍然成立且更彻底**：root 既读不到 TEE 内的种子，也（在门禁落地后）不能自己
   灌种子——堵掉那条最阴险的攻击：换掉种子后这块板生成的每把密钥攻击者都算得出来，而板子照常工作、
   ACVP 照常过、没有任何一处报错。

### 8.1 ⚠️ 一条本文早期版本的结论，现予撤回

本文早期版本有一条判断："新模型对离线攻击者严格更弱，因为 PL 里的秘密掉电即失、无持久密文可攻，
而 TEE 模型把秘密变成由可读 DNA 派生的 KEK 保护的持久密文。"

**在有信任根的前提下这条不成立，撤回。** 它的全部成立条件是"KEK 的根是公开的 Device DNA"——
而那是**未供给形态**的特征，不是架构特征。信任根一旦供给，该论证自动失效。
保留这段记录只为说明：**"离线更弱"是供给状态的函数，不是 TEE 主线的固有属性。**

### 8.2 信任根前提下，本文哪些结论不变

需要强调的是，本清单的**绝大部分结论与信任根无关**，不因这条前提而改变：

| 组 | 是否受信任根影响 | 说明 |
|---|---|---|
| **B 组（擦除覆盖 Z-01…Z-05）** | ❌ 完全不受影响 | RTL 里没有擦除端口，与密钥根在哪毫无关系。**这是最该先做的一批** |
| **A 组（金库与槽位 ABI）** | ❌ 不受影响 | 纯粹是"PL 有状态 vs 模型要求无状态"的结构冲突 |
| **C 组（软件密钥栈在普通世界）** | ⬆️ **变得更重要** | 有真根之后，秘密才真的值钱；`sk`/`seed`/`pin_key` 留在普通世界、PKCS#11 在第三方进程内链接 slot 层（PS-13），都从"反正 DNA 也是公开的"升级为真实缺陷 |
| **TA 两颗地雷（PS-22/24）** | ⬆️⬆️ **严重度显著上升** | `TEEC_LOGIN_PUBLIC` + `CMD_KDF_DERIVE` 接受任意 label：**今天它泄的是一个由公开 DNA 派生的值，有真 HUK 之后它泄的是真正的存储 KEK**。必须在 TA 接上产品路径之前修掉 |
| **门禁（PS-11/12）** | ❌ 不受影响 | EL3 按调用者世界分级，与信任根正交；且它是 TEE 主线兑现的前提 |
| **PS-03（KDR 来自可读 DNA）** | ✅ **由此解决** | 不再是"软件消解不了"，而是**量产供给项**：接一个从真 HUK 取根的 provider |

### 8.3 对外口径

- **量产形态**：可以正常宣称"密钥由 TEE 保管、私钥不出安全世界"——前提是烧写与供给真的做了，
  且 CSU AUTH 位确实置起（否则上游 `zynqmp_huk.c` 会**静默降级**成 development HUK，
  失败形态是"看起来跑通了"，这条要写进产线自检）。
- **原型形态（这块 AXU3EGB）**：演示与评测材料需标注"信任根未供给的原型形态"，
  不要把原型上的测量结果直接当作量产安全性质的证据。这是**标注问题，不是能力问题**。

## 9. 收敛建议

**批 1（不依赖 OP-TEE，全部可独立成立）**
1. PL 擦除覆盖：一台共享擦除机（Z-01…Z-04）+ daemon 补 `SY_CTRL`（Z-05）
2. EL3 侧种子生成与暂存 + SiP 按调用者世界门禁 + 白名单排除种子/装载偏移（PS-11/12，即 CODE-1）
3. 软件三条收口：禁 `SEED_STORAGE`、删 KDR 自动回退到桩、随机源判定改 `is_hardware`（PS-04/07/25）
4. TA 两颗地雷（PS-22/24）——虽是死代码，几乎免费
5. 三处"PL 会话缓存"表述同时降级为单次操作（PLAN-01/05/06）
6. 文档只在文首加形态标注，**正文一字不动**（避免承诺未交付能力）

**批 2（硬门槛：最小 TA 先在板上跑通并留证据）**
KEK/wrap 上移（PS-01）→ KDR provider（PS-02）→ 槽位秘密与 pin_key（PS-06）→ 句柄表上移（D-01）
→ 金库降级/删除（V-01/02/04/05/06）→ 备份与注入链（PS-16/17）

**量产供给项（不是"补不了"，是排产工作）**：烧写计划（认证根 `PPK0_HASH+RSA_EN` + 秘密根
`FUSE_AES` 或 PUF，**两套独立**）、OP-TEE HUK 供给（含产线自检 CSU AUTH 位确实置起，
否则静默降级成 development HUK）、`pqc_kdr_provider_optee()`（PS-03）、产线密钥保管
（Bootgen HSM 模式，PPK 私钥不落构建机）。

**其余产品化前置**：物理防篡改（需新增 BOM + 机械 + 台架验证）、认证资质（下游于前两项）。

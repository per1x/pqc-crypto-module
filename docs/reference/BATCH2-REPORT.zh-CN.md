## 1. 前置死结：查明不成立

`ARCHITECTURE-TARGET §9`、`FINAL-PLAN §4`、`STATELESS-PL-CONFLICTS §7.4` 三处都写着
**"OP-TEE TA 从未上板跑通（卡在 BL32 入口），在这解决之前整条主线是空中楼阁"**。

实测**不成立**。那是打包漏 24 字节 `boot_embdata` 那个坑还没修时的状态，修好之后就通了，
只是结论文档没跟着更新。三处已改（保留原文并注明当时的判断依据）。

⚠️ **"驱动起来了"不是 TA 跑通的证据。** `optee: initialized driver` 与 `/dev/tee0`
都不检查 TA 能不能加载。`tee/host/ta_probe.c` 的判据分两半：

| | 判据 | 结果 |
|---|---|---|
| [2a] | 匿名登录被拒，**且 origin = TA** | ✅ `ACCESS_DENIED` |
| [2b] | `LOGIN_USER` 会话建立 | ✅ |
| [3] | `CMD_GET_INFO` 版本与 host 一致 | ✅ `0x00010000` |

`origin = TA` 才是要害：它意味着 TA **已被找到、加载、执行到自己的入口**，是它主动拒的。
只测"能开会话"不够 —— 一个把门拆掉的 TA 也能通过。

## 2. 种子保管上移 TA，EL3 退成纯通路

批 1 的形态是"EL3 自己取熵自己写"。种子明文确实没经过普通世界，但**触发权**还在：
有 root 的人可以随时让板子换一份种子。批 2 把这条收掉。

| 层 | 改动 |
|---|---|
| **EL3** | `PQCHSM_SEED_NS_ALLOWED` → **0**；新增 `PQC_SEED_WORD`（`0x8200ff15`），只把一个字写进 PL 暂存口，自己不产生、不保存、不回读。**无条件只认安全世界，没有过渡开关** |
| **OP-TEE** | 新增极窄伪 TA（`boot/optee/patch_optee_seedpta.py`）。TA 在 S-EL0 发不了 SMC，必须 S-EL1 中转。两道门：调用方为空拒、非用户 TA 拒 |
| **TA** | `CMD_SEED_NEW` / `CMD_SEED_REPLAY` / `CMD_SEED_TO_PL` |

**为什么 `PQC_SEED_WORD` 不给过渡开关**：这条路上流的是**种子明文**（批 1 那条只是触发），
放行普通世界等于把 CODE-1 原样搬回来。

**为什么 PTA 不做成通用 SMC 转发口**：那等于把 EL3 的整个 SiP 表暴露给任何 TA。

**`CMD_SEED_REPLAY` 不是解包谕言机**：它解开 blob 之后**只往 PL 的暂存口写**，
没有任何把明文交回调用方的路径 —— 这正是批 1 删掉 `CMD_UNWRAP` 的理由。

板上自检**两面都验**（反面那条成功反而是故障）：

```
自检：普通世界触发 EL3 种子装载已被拒（errno=5）—— 这是批 2 期望的形态
自检通过：TA → PTA → EL3 → PL 这条种子路通了（world=1）
```

## 3. A 组：PL 退成无状态计算引擎

按 `FINAL-PLAN` §7 登记表 V-01/V-02/V-04/V-05/V-06、D-01/D-02 与 §7.2 的四条。

| 项 | 原状 | 现状 |
|---|---|---|
| V-01 | ML-KEM 16 槽 × 4 KB dk 金库 | **匿名 4 KB 单操作展开区** |
| V-02 | ML-DSA 8 槽 × 8 KB sk 金库 | **匿名 8 KB 单操作展开区** |
| V-04 | `dk_lock` / `sk_lock` 一次性闩 | **删除** |
| V-05 | `MODE` 的 `*_TO_SLOT`/`*_FROM_SLOT`/`SLOT[9:6]` | **删除**；`[4]` 改为 `CHAIN` |
| V-06 | `KEYSTAT` 槽有效位 + `KEYPSET` 每槽 pset | **只剩健康位**；`KEYPSET` 恒 0 |
| D-01 | 句柄"就是"金库槽号 | 句柄是本进程表下标，表里放 **TA 包好的种子密文** |
| D-02 | `-lock` 启动参数 | **删除**（参数保留但忽略） |

§7.2 的四条，逐条落地：

1. **擦除由硬件在 `S_FIN` 无条件触发** —— 软件没有任何"不擦"的选项；
2. **展开区没有 valid 位、没有跨请求可引用的槽号** —— 寄存器面上**根本没有能引用它的
   名字**。这比"擦干净了"更强：即便擦除有 bug 也引用不到；
3. **擦除期间拒绝下一笔**，且**不静默**（置 `PARAM_ERR` 并作废上一次结果）；
4. **逐地址真写零**，不靠复位、不靠"下次覆盖"。

### `CHAIN`：无状态的落点

一条命令里**先从暂存种子展开私钥、再做本次运算、算完无条件擦**。
它替代的正是"按槽引用上一次的 dk/sk" —— 差别在于私钥是这条命令自己现展开的。

- **两相位**：Decaps / Sign（需要私钥）；
- **单相位**：KeyGen（`hide_sk` —— 只交出 pk，私钥进展开区随即擦掉）。

**CHAIN 必须有一份备好的暂存种子**（`chain_gate_ok`）。少了这道门，展开相位会退回
"从 `IN_DATA` 读种子"，而那几十个字节是残留 —— 结果是**静默展开出另一把密钥**，
签出来的 σ / 解出来的 K 完全合法，只是对不上任何人的公钥。

### 顺带的好处

金库从 64 KB 降到 4/8 KB 之后，`zeroize` 的擦除计数器从 16 位收回 13 位：
**65536 拍（874 µs）→ 8192 拍（109 µs）**。这不只是好处，是必须的 ——
展开区现在每次运算后都要擦。

## 4. C 组：软件密钥栈接到 TA 托管

PL 无状态之后，"这把私钥"的载体只能是**种子**，保管方是 TA。

```
KeyGen ：daemon → TA CMD_SEED_NEW → TA 生成种子、送进 PL、**把种子包成 PWRP blob 交回**
         → daemon 发 CHAIN|SEED_STAGED 的 KeyGen → 拿到 pk（OUT_LEN 恰好 = pk 长度）
Decaps ：daemon → TA CMD_SEED_REPLAY(blob) → TA 解开、同一份种子再送进 PL
/Sign    → daemon 发 CHAIN|SEED_STAGED 的命令 → PL 现展开、算完即擦
```

**daemon 从头到尾没有一个能放种子或私钥明文的缓冲区**，句柄表里只有 TA 包好的密文
（本进程解不开 —— KEK 由 TA 内的 KDR 派生，没有出口）。

新增 `wait_exp_idle`：擦除期间 START 会被拒并作废上一次结果，软件必须真的去等。
**用读来等** —— 写在擦除期间被拒，而被拒的写从 EL3 回来是 SError（丢板子）。

## 6. 真正受阻 / 需产品化前置

| 项 | 状态 | 根因与代价 |
|---|---|---|
| **安全启动 / 镜像认证** | 受阻，**不做** | 认证根要锚在 eFUSE，而烧 eFUSE 是一次性不可逆。**能改 SD 的人可以把 BL32 换成"打印密钥"的恶意 OP-TEE，板子照跑** —— "密钥在 TEE"对能改镜像的人**不提供任何保密**。 |

| **RPMB 防回滚** | 能力边界，可做 | 密钥已找回、可正常用（读 / bump），但 `src/` 未接。接它**不需要**任何不可逆动作。 |

⚠️ **前两条合起来决定了这套东西的上限**：批 2 之后"种子/私钥由安全世界保管"在
**软件与总线层面**是真的（普通世界拿不到、触发不了、PL 里也不过夜），
但它**挡不住能改镜像的人**，而且**KEK 的根是公开可推导的**。
这个区别必须一直说清楚，别让"TEE 保管"升级成"硬件保护"。

## 7. 这一轮抓到的自身错误

写下来是因为它们各自代表一类**不会报错**的失败：

1. **`S_FIN` 无条件擦之后，紧接着的 START 被外层守卫静默丢弃**，而上一次的
   `DONE`/`OUT_LEN` 还留着 —— 软件读到的是上一次的结果。改走 `PARAM_ERR`
   那条**吵闹**的拒绝路径。（一个 bug 造成两处测试失败。）
2. **`S_KICK` 选核用 `mode` 而不是 `mode_eff`** —— 链式的展开相位会去启动
   Decaps 核。症状是"链式一直不完成"或"K 对不上"，都不指向那一行。
3. **用例把 Encaps 的 `K‖ct` 切反了**，表现成"链式 K 对不上"而指向 RTL。
4. **`CHAIN` 只做了 Decaps，KeyGen 漏了** —— 于是交付路径上的 KeyGen 走了
   ACVP 那条（`ek‖dk` 一起出来），dk 越过了 AXI 边界。
   **是 daemon 的 `n == eklen` 断言在板上抓到的** —— 那条断言正是为此存在的。
5. **`iopack_bench` 没等擦除窗口**，被拒之后死等 `DONE`，把 harness 的 480 秒
   看门狗喂饱了，表现成"板子挂了"，而实际只是少等了 55 µs。
6. **`res(-1, ...)` 把跳过打成了通过** —— 判据是 `good ? "✅" : "❌"`，而 -1 是真值。
   一个"跳过被当成通过"的报告比没有报告更危险。

另有一处**文档互相矛盾**：`ARCHITECTURE-TARGET §2` 说 `dk_lock`/`sk_lock`
"仍应保留"，与 `FINAL-PLAN §7` 的 V-04（随 V-01/02 删）冲突。
FINAL-PLAN 是唯一权威源，按它做，并把那处改掉、说明"软件侧自证"没有丢
（`n == eklen`/`pklen` 本来就不依赖闩锁）。

## 8. 板子最终状态与怎么演示

- 槽 6 = `BOOT_B2.BIN`（`f045a64b…`），multiboot = 6，重启后仍是 6
- 演示位流 `zu3eg_hsm_dev.bit` = `e76a2321…`；送检位流 `zu3eg_hsm.bit` = `425abaec…`
- daemon = `2d7d2468…`；TA = `1c9cbcfb…`（开机由 `hsm-boot.sh` 从 SD 复制到 `/lib/optee_armtz/`）
- golden 三份：`0ea6e443…` / `bb3402ea…` / `8d42d1a5…`，槽 7 仍是已知能启动的安全网

**演示**：上电约 35 秒自动就绪，从够得着 eth1 的机器上
`./demo/remote/run.sh <板子IP> --smoke`。

⚠️ 两个会咬人的：

- 板子**没有 RTC**，重启后时钟回到镜像里那个日期，客户端证书会"尚未生效"、
  TLS 报 `bad certificate` —— **先 `date -u -s` 对表，再查凭据**。
- **掉电会把 multiboot 清零、自动回 golden**，那时跑的是没有批 2 那套的旧 BL31，
  daemon 会 fail-closed 不启动。回到批 2 形态：
  `insmod pmsec.ko set_multiboot=6` + `hsmreboot.sh`。
- 跑完任何 `plharness.sh` 之后 PL 是**厂家位流**（harness 无条件恢复），
  要回演示形态就重启一次。

# S1 硬件 TRNG（2026-08-12，完成，未上板）

## 做了什么

仓库里原本只有 `trng_health.v`（SP 800-90B §4.4 的 RCT + APT，阈值参数化、
告警锁存，质量很好）—— 但**缺噪声源本身**，也缺调理和总线接口。补齐成完整熵源：

```
环振阵列 ──采样/抽取──> 原始比特 ──┬──> 连续健康检测（RCT + APT）
                                    └──> Keccak 海绵调理 ──> FIFO ──> AXI ──> 安全世界
```

| 文件 | 作用 |
|---|---|
| `hardware/rtl/trng/ring_osc.v` | 单条环振。综合走真反相器环，仿真走抖动行为模型 |
| `hardware/rtl/trng/trng_source.v` | 8 条环振（13/15/…/27 级）+ 两级同步器 + 抽取 |
| `hardware/rtl/trng/trng_cond.v` | Keccak 海绵调理器，复用已有的 `keccak_f1600` |
| `hardware/rtl/trng/trng_top.v` | 启动健康检测、告警处置、zeroize 策略 |
| `hardware/rtl/trng/trng_axi.v` | AXI4-Lite 从机 + **AxPROT 安全门控** + tamper 引脚 |
| `hardware/rtl/common/sync_fifo.v` | 可擦除 FIFO（flush 逐地址覆零，不是只挪指针） |
| `hardware/model/trng_cond_model.py` | 调理器的 Python 黄金模型 |
| `docs/trng-register-map.zh-CN.md` | 寄存器表与驱动契约 |

## 几个有意的设计选择

**调理用 Keccak 海绵，不是自己发明的白化。**
SP 800-90B §3.1.5.1.2 给了一份 vetted conditioning 清单（HMAC/CMAC/CBC-MAC/
Hash_df/哈希函数），用清单里的构件，输出熵可以直接按 `min(输出长度, 输入熵)` 计；
自己发明的白化（von Neumann、LFSR 打散）要另行论证。
选 Keccak 还顺带证明了 `keccak_f1600` 是可复用的 IP，而不是只能给
`pqc_accel_axi` 用的一次性件 —— **零增量面积拿到一个 vetted 构件**。

**健康检测吃的是抽取之后的样本流**，也就是调理器实际消费的那一条。
检测的对象必须和被使用的对象是同一个，否则检测没有意义。

**告警之后连熵池一起清。**
标准只要求"停止输出并上报"，动作留给使用方。这里选最保守的：
告警 → ready 拉低 → FIFO 擦除 → **调理器连同海绵状态一起复位** → 启动检测重跑。
理由是告警意味着噪声源可能已经失效了一段时间，池子里可能混进了低熵输入，
留着比丢掉风险大。代价只是重新暖机。

**AxPROT 门控：被拒的读绝不弹 FIFO。**
`AxPROT[1]=1`（non-secure）的读写一律 DECERR，且不产生任何副作用。
返回 DECERR 而不是 OKAY+0 是有意的 —— 静默返回 0 会让普通世界以为拿到了
随机数，而 0 是最糟的"随机数"。
"被拒的读不弹 FIFO"单独测一条：如果被拒的读仍然弹出，普通世界虽然拿不到数，
却获得了一个"反复读把熵池抽干"的手段。让安全世界拿不到随机数，
和自己拿到随机数，是两个不同的攻击，后者一样致命。

**这一层不是唯一一层。** AxPROT 是纵深防御的最内层，完整隔离还要靠
XMPU/XPPU（在 master 那端就挡掉）和地址映射（不出现在普通世界设备树里）。
三层的分工写在 `docs/trng-register-map.zh-CN.md`。

## 环振被优化掉是最危险的失效模式，脚本里专门防了

反相器环违反了综合工具的两条基本假设（组合逻辑无环、逻辑可化简）。
不做三件事，环就会被优化掉：

1. RTL 里 `DONT_TOUCH`（在 `ring_osc.v` 的 `chain` 声明上）；
2. `ALLOW_COMBINATORIAL_LOOPS TRUE`（在 `trng_ooc.tcl` 里对环网络设置）；
3. `LUTLP-1` DRC 降级为 Warning，否则 `write_bitstream` 直接失败。

**环被吃掉之后，综合日志里不会有任何报错** —— 采样器采到常量，TRNG 静默变成
常数发生器。所以 `trng_ooc.tcl` 在**综合后和布线后各数一次** ring_osc 层次下的
LUT 数量，少于 120 就直接 `error` 退出。实测两次都是 **160 个 LUT**
（8 条环 × 平均 20 级 = 160），与设计值精确吻合。

> 顺带一个坑：XDC **不是完整的 Tcl**。`if`、`for`、`remove_from_collection`
> 都会报 `[Designutils 20-1307]` 并**静默忽略那一条约束**，脚本还继续跑完。
> 第一版把条件判断写进 XDC，三条约束全被吞了。带判断的部分必须放在 `.tcl` 里。

## ⚠️ 尚未成立的事（不要在任何报告里写成结论）

**1. 最小熵完全没有实测。**
RTL 仿真里环振跑的是 `ring_osc.v` 的行为模型，**抖动量是编的**，比真实器件

因此：

> **任何最小熵数字都不能从仿真里得出。**
> 测试里"看起来很随机"的断言（1 的比例 0.507、最长游程 10）
> **只是在防低级错误**（采样器接反、异或写成或、抽取计数器差一），
> 不构成任何熵评估。

当前假设 **H = 0.5 bit/样本**，健康检测阈值（RCT C=41、APT W=1024 C=793）和
调理比例（1088 比特进 → 256 比特出）都是照它算的。上板之后必须：
1. 导出 ≥1M 个原始比特（`DECIM` 可调）；
2. 跑 NIST EntropyAssessment（SP 800-90B 官方工具）；
3. 按实测的 H 反过来定 `DECIM`、`RCT_CUTOFF`、`APT_CUTOFF`、`ABSORB_BLOCKS`。

**2. 环振的物理布局没有约束。**
真实设计要用 `LOC`/`pblock` 把各条环分散摆放，避免互锁（injection locking）

**3. 没上过板。** 以上全部是仿真 + 综合结果。

**4. 软件通路只到"驱动写完并通过契约测试"，没有跑在真硬件上。**
见下面 S1b。真板上还要做地址分配、决定 SECURE_ONLY 的取值、并把选择
transport 这一步接进 pqchsmd / TA 的初始化。

# S1b 软件侧：熵源驱动，替掉软件 RNG（2026-08-12，完成，未上板）

RTL 做完只是一半。用户要的是"作为熵源，让安全世界软件从它取随机、替掉软件
RNG" —— 这一半在软件树里。

## 做法：照抄 accel 那条接缝

仓库里已经有一套成熟的做法（`include/pqchsm/accel.h`）：**先把 AXI 寄存器表
定死，再写一个 C 实现的"假外设"**，暴露与真 PL 完全相同的寄存器语义，
真板到手后换成 `/dev/mem` + mmap，上层一行不改。熵源照搬这条接缝：

| 文件 | 作用 |
|---|---|
| `include/pqchsm/hwrng.h` | 寄存器偏移、状态位、错误码、`hwrng_transport_t` |
| `src/hal/hwrng.c` | 驱动本体：自检、取字节、告警处置 |
| `src/hal/hwrng_stub.c` | `trng_axi` 寄存器语义的软件模型（FIFO 由 OpenSSL 填） |
| `src/hal/hwrng_mmap.c` | `/dev/mem` + mmap，基址由 `PQCHSM_HWRNG_MMAP_BASE` 给出 |
| `tests/unit/test_hwrng.c` | 契约测试，41 条断言 |

**熵源单开一条接缝，没有并进 `accel.h` 的操作码**，与 RTL 侧分成两个 AXI 从机
是同一组理由：生命周期不同（加速器是发命令等完成，TRNG 常开自由运行）、
访问权限不同、故障域不同（TRNG 告警要能独立上报，不该被加速器的忙闲挡住）。

## 驱动里三条不能省的纪律

1. **读 RDATA 之前必须先查 `STATUS.DATA_VALID`。** 空读返回 0，而 0 是最糟的
   "随机数"。契约里那个锁存的 `UNDERRUN` 位就是用来事后抓住不查就读的驱动的。
2. **取完一批之后复查 `UNDERRUN` 与 `ALARM`，任一置位则整批清零作废。**
   不是"把出错之后的部分丢掉" —— 告警是**锁存的电平**，只说明"这段时间里发生
   过"，定位不到是第几个字。既然定位不了，就只能全丢。
3. **绝不回退到软件随机源。** `pqc_random_bytes()` 装了 transport 就走硬件，
   取不到就返回 -1；liboqs 的随机源回调签名是 `void`，没有返回值可用，
   所以那边直接 `abort()`。静默回退会让"熵来自硬件"恰好在最要紧的时刻悄悄
   变成假话，而调用方无从知道。

第 2 条是最容易写漏的一条，所以单独做了**变异测试**验证它真的在起作用：
把复查那几行换成 `(void)s;` 重新编译，`test_hwrng` 立刻在"取到最后才告警"
那条上失败（返回 0 而不是 -3，且缓冲区里留着数据）。测试确实咬得住这行代码，
不是摆设。

## 验证

`tests/unit/test_hwrng.c`，41 条断言，`ctest -R hwrng` 通过。验的是
`docs/trng-register-map.zh-CN.md` 那份契约的**软件侧** —— RTL 侧由
`test_trng_axi.py` 验同一份契约。两边对着同一张表各写各的，接口层面的分歧
在无板阶段就会暴露，这正是先定寄存器表再写假外设的收益。

覆盖到的：没装 transport 时如实报不可用、启动检测没过时 READY 不拉高、
非 4 倍数长度的尾部处理、告警早退与告警复查两条路径都整批清零、空池超时
（而不是死等、也不是硬读 RDATA 把 0 当随机数）、ZEROIZE 重跑启动检测、
`pqc_random_bytes()` 确实弹了硬件的字（读 `WORDS` 计数验证：32 字节正好 8 个
字）、故障时确实不回退。

> **这里一个字都没测熵。** transport 是软件模型，FIFO 由 OpenSSL 填 ——
> 测出来的"随机性"只反映 OpenSSL。软件模型也如实把 `is_hardware` 报成 0，
> 审计里"熵来自硬件"这句话的依据就是这一位。

模型还有一处刻意的不保真：软件里没有时钟，所以拿"读了几次 STATUS"当时间
基准（每次推进 64 个启动样本，暖机需轮询 16 次）。它证明了驱动确实在轮询、
确实等到 READY 才读；**没有**证明任何与时延、吞吐、熵率有关的东西。

## 还差什么（都要等板子）

- 地址分配：`PQCHSM_HWRNG_MMAP_BASE` 现在没有取值，`hwrng_transport_mmap()`
  返回 NULL。
- `hwrng_mmap.c` 走 `/dev/mem`，也就是跑在普通世界。而 `trng_axi` 默认
  `SECURE_ONLY=1`，**这条路在默认配置下本来就打不通**（AxPROT[1]=1 → DECERR）。
  这不是 bug：它的正当用途是综合成 `SECURE_ONLY=0` 的调试位流做通路验证和
  熵采集，以及当作 OP-TEE TA 侧驱动的原型（TA 里换成安全世界的映射，寄存器
  时序完全一样）。生产配置下取熵必须走安全世界。
- 把"选哪个 transport"接进 pqchsmd / TA 的初始化 —— 那要等 OP-TEE 主线的 TA
  稳定后再合过来。

# S2 SHA-3 / SHAKE 海绵进 PL（2026-08-12，核完成，未接总线）

## 做了什么

仓库里原本只有 `keccak_f1600` 置换核，海绵的 framing 全在 C 里
（`src/hal/pqc_accel.c` 的 `accel_shake`）。那个分工在当时是对的 —— 核更小，
SHAKE128/256 与 SHA3-256/512 共用同一个置换。代价是**每置换一次就要过一次
总线**：PS 写 200 字节状态 → 触发 → 读回 200 字节。一次 SHAKE256 吸收 32 字节
要搬 400 字节总线数据，去做 24 个周期的运算。

`hardware/rtl/keccak/sha3_core.v` 把 padding / 吸收 / 挤压整个搬进 PL。
除了省掉那些搬运，还有一条更要紧的：**中间状态不再离开密码边界**。
SHAKE 的中间状态在 ML-KEM 里就是 ρ/σ 展开的上下文，让它反复出入普通世界
可寻址的缓冲区，在真密码机里是说不过去的。

接口是**两端都带背压的字节流**：`in_valid/in_ready/in_data` 喂消息，
`in_flush` 宣告结束，`out_valid/out_ready/out_data` 按需挤压。
挤压**不设长度寄存器** —— SHAKE 的输出长度本来就是任意的，设了等于凭空
加一个上限，还多一个要校验的参数。消费方读够了停下即可。

## 两个刻意的简化

**吸收按字节做，不攒 lane。** `keccak_f1600` 的读口是组合的、写口在空闲时
接受写入，于是"读出 lane → 异或进一个字节 → 写回"整个是一条组合路径，
一个周期就能做完。攒 lane 的写法要处理"不足 8 字节的尾巴怎么对齐"，
按字节做连这个问题都不存在，pad 的位置计算也跟着消失。

**padding 只要两次读-改-写。** pad10*1 中间那串 0 异或进去是空操作，可以整个
跳过，只剩：① 当前位置异或 suffix；② `rate-1` 处异或 `0x80`。两笔顺序执行，
所以 suffix 恰好落在 `rate-1` 时（消息长 ≡ rate-1）自然合并成 `suffix^0x80`，
不需要单独判这个边角。

## 这一步踩的两个坑，都值得记下来

**坑一：`start` 只在空闲时才认，于是第二次操作永远发不动。**
挤压是没有自然终点的（SHAKE 输出长度任意，核心无从知道消费方何时读够），
所以挤完也不会自己回空闲。第一版把 `start` 写在 `S_IDLE` 分支里，结果第一次
操作之后核心永远停在 `S_SQUEEZE`。表现是**驱动写了 start 之后 `in_ready`
永远不来** —— 不报错，只挂死。现在 `start` 的语义改成"丢掉手头的一切，
从干净海绵重新开始"，从任何状态都生效。

**坑二：`kec_done` 是电平，会保持到下一次 `start`，于是判完成判到了上一次。**
进入等待状态的头一拍，`start` 才刚发出去、置换还没开始，而 `done` 上挂着的
还是**上一次**置换留下的 1，于是当场判定"已完成"，在置换进行当中就开始挤压。

这个 bug 的表现极具迷惑性：A 阵列在 24 轮里每拍都在变，挤出来的**头十几个
字节取自中间轮的状态，后面的字节等置换跑完才取、反而是对的**。于是摘要
"前面错、后面对"，看着像位序或对齐问题，其实是时序问题。而且**第一次操作
恰好是对的**（复位后 `done=0`，没有陈旧值），非要连算两次才暴露 ——
所以"连算两次"那条用例不是锦上添花，它是唯一能抓住这个 bug 的用例。

> 有意思的是 `trng_cond.v` 里早就用 `!kick_busy && kec_done` 处理过同一个坑，
> 注释也写了。同一个人隔几天在同一个置换核上又踩了一遍 —— 说明这类"电平型
> done"的接口本身就容易误用。真要根治应该让 `keccak_f1600` 直接输出 `busy`。

**还有一条是测试台自己的教训**：第一版等 `in_ready` 用的是裸 `while True`，
核心一停住，仿真就闷头跑了一千六百万个周期直到被外面杀掉，什么信息都没留下。
换成带上限的等待之后，同一个 bug 变成一条指出 `state` 的失败信息，
整套用例也从"十分钟跑不完"变成 **2.6 秒**。

# S2b 接总线：软件 PQC 真的在调硬件 SHAKE（2026-08-12，完成，未上板）

## 做了什么

S2 留下的窟窿是 `sha3_core` 是个裸核，PS 够不到它。这一步把它接进
`pqc_accel_axi`，加操作码 **10（SHAKE / SHA3）**，并让 `accel_shake()`
优先整条委托给 PL。

```
软件                          PL
accel_shake()
  └─ 模式 10 ──AXI4-Lite/Stream──▶ pqc_accel_axi
                                     └─ sha3_core（海绵）
                                          └─ keccak_f1600（置换）
  └─ 退回路径：模式 9 ─────────────▶ 同一个 keccak_f1600（走直通口）
```

`PARAM` 打包三个字段：`[7:0]` 域分隔后缀、`[15:8]` rate、`[31:16]` 输出字节数。
放 `PARAM` 而不是新加寄存器，是为了不动 `docs/register-map.md` 那张已经定死的
表 —— `PARAM` 本来就是"参数集"字段，此前没有任何硬件操作码用过它。

## 只用一个置换核

模式 9（裸置换，给对拍用）与模式 10（海绵）**共用同一个 `keccak_f1600`**。

各占一个的话，光这一块就要多花约 3500 LUT；ZU3EG 一共 70560 LUT，后面 S4 的
ML-KEM 核还要再要一个。所以给 `sha3_core` 开了一个直通口：海绵空闲时，
上层可以直接读写底下那 25 个 lane、直接踢置换。`pqc_accel_axi` 里模式 9 的
状态机因此**一行没改** —— 端口名与语义与当初直接例化 `keccak_f1600` 时完全一致。

直通口有两条纪律，都不是防御性编程：

- **非空闲时读口回 0，不透传。** `ext_rd_data` 若无条件接出置换核的读口，
  上层在挤压途中读一下就拿到了海绵的中间状态 —— 而挤压中的海绵状态在 ML-KEM
  里就是 ρ/σ 展开的上下文。这是"状态不出密码边界"这句话的实际落点，
  有一条专门的用例盯着（把条件去掉，那条用例立刻失败）。
- **`ext_start` 组合打进置换核，不多寄存一拍。** 上层判完成普遍写成"踢的那一拍
  跳过、下一拍起看 `done`"，中间多一级寄存会让上层在置换真正开始前就看到上一次
  遗留的 `done` —— 又是 S2 那个坑，只是换了个地方发作。

## 命令收尾要擦海绵

模式 10 在报 `DONE` 之前给 `sha3_core` 打一拍 `zeroize` 并**等它清完**。

这不是可选的卫生动作。挤压没有自然终点（SHAKE 的输出长度任意，核心无从知道
消费方何时读够），所以挤完最后一块海绵不会自己回空闲，也就再不肯把置换核借
出去 —— 紧接着的一条模式 9 命令会永远等不到 `DONE`。**把 `zeroize` 那一行删掉，
整套 SHAKE 用例直接挂死到超时**（试过了）。顺带把上一条消息的海绵状态清掉，
两件事一次做完。

必须等 `busy` 落下才报 `DONE`：否则软件看到 `DONE` 立刻发下一条模式 9 命令时，
海绵还在写那 25 个 0，会把刚装进去的 lane 冲掉。

## 软件侧：优先硬件，但只在"没实现"时回落

`accel_shake()` 先试模式 10；消息或输出超过 512 字节（PL 侧缓冲区尺寸），
或该 transport 回 `ERRCODE=3`（该模式没实现）时，退回原来"C 侧做 framing、
模式 9 只做置换"的路。结果逐字节相同。

**回落只认 `ERRCODE=3`。** 其他任何失败都如实向上报错 —— 一块坏了的加速器
如果每次都被软件兜住，就再也没人会发现它坏了。

**这个回落与熵源那条"绝不回落"不是一回事**，值得说清楚：SHAKE 是公开函数，
退回软件 framing 不损失任何机密性保证，损失的只是"中间状态留在 PL 里"这条纵深；
而熵源回落到软件 RNG 会直接改变安全根基。所以一个允许回落、一个宁可失败。

软件桩（`accel_stub.c`）也实现了模式 10，参数校验的边界与 `ERRCODE` 与 PL 侧
一模一样。这样"上层调模式 10"的代码在没有 PL 的机器上走的是同一条分支，
参数编码写错这类 bug 不必等板子到手才暴露。

这一步第一次把 `pqc_accel_axi` **整个顶层**做了 OOC 综合 + 布局布线
（此前 `ooc_synth.tcl` 只读 `rtl/mlkem` 与 `rtl/keccak` 两个目录，
根本读不到 `rtl/bus`，所以这个顶层从来没被综合过）。结果不好看：

| 顶层 | LUT | 占比 | WNS @100 MHz | Fmax |
|---|---|---|---|---|
| `pqc_accel_axi`（S2b 后） | 62718 | **88.89%** | **−2.492 ns（不收敛）** | 80.1 MHz |
| `pqc_accel_axi`（S2b 前） | 57799 | 81.91% | **−2.372 ns（不收敛）** | 80.8 MHz |
| `ntt_core` 单独 | 28494 | 40.38% | **−2.679 ns（不收敛）** | 78.9 MHz |
| `sha3_core` 单独 | 3932 | 5.57% | +4.873 ns | 195.0 MHz |

（器件 `xazu3eg-sfvc784-1-i`，BRAM 0，DSP 13，功耗 1.053 W）

**先把账算清楚，别把锅甩错地方。**

- **时序不收敛不是这一步造成的。** S2b 之前就是 −2.372 ns，之后 −2.492 ns，
  差 0.12 ns；而 `ntt_core` 自己单独跑就是 −2.679 ns。关键路径在 NTT 里，
  和 SHAKE 没关系 —— `sha3_core` 单独有 +4.873 ns 的余量，是全场最宽松的一块。
- **面积也主要不是这一步。** S2b 加了 4919 LUT（7 个百分点），这个数不小，
  下面单说；但基数 57799 是它接手时就有的。
- **两个大头都是同一个毛病：用寄存器阵列当存储。** `ntt_core` 的 256 个系数、
  `pqc_accel_axi` 的 128 字缓冲区都是 `reg` 数组，而且都有多个读口。
  报告里 `LUT as Memory = 0` —— **Vivado 一个都没映射成分布式 RAM**，
  全摊成了组合选择树（F7 Muxes 5434、F8 Muxes 2462）。
  `pqc_accel_axi.v` 文件头那句"映射成分布式 RAM 只占几十个 LUT"是想当然，
  实测不成立，已就地改正。

**S2b 那 4919 LUT 花在哪。** 直通口本身很便宜（`sha3_core` 从 3824 涨到 3932，
+108）。贵的是模式 10 要**按字节**读写那块 128 字的缓冲区：原来只有按字的读写口，
现在多了一套字节粒度的读口与读-改-写口，而缓冲区是寄存器阵列 —— 每加一个口，
选择树就整套复制一遍。同样的账，换成真 BRAM 就是加一个读口的事。

**结论：S3 的范围要扩。** 原计划只是"NTT 核改 BRAM 存储版"，现在看
`pqc_accel_axi` 的数据缓冲区得一起改成同步读的单口 BRAM 结构 ——
它自己就占了约 30000 LUT，比 NTT 核还多。这两处一起换掉之前，
**整颗片子塞不进 S4 的 ML-KEM 核**（S1 的 TRNG 另占约 6%）。

这个数字是这一步最有价值的产出：它不是"跑通了"，是"跑通了但按现在的写法
装不下"，而且指明了下一步该动哪里。若不是把顶层真的综合一遍，
这件事会一直拖到 S4 拼装的时候才炸。

# S3 换成 BRAM：整个加速器从 88.89% 的 LUT 掉到 6.76%（2026-08-12，完成，未上板）

## 做了什么

S2b 的综合报告指出两处"用寄存器阵列当存储"的写法吃掉了大半颗片子。这一步
把它们都换成真双口块 RAM：

- 新增 `hardware/rtl/common/ram_dp.v` —— 按 UG901 的推断模板写的参数化 TDP
  同步 RAM（两个口各一个 `always`、各自 `dout <= mem[addr]`、读优先、**不带复位**）。
- `hardware/rtl/mlkem/ntt_core.v` 的 256×16 系数存储换成一块 `ram_dp`。
  组合读没了，一个蝶形从 1 拍变 2 拍：`S_RD` 发地址、`S_WB` 拿数算完写回；
  缩放同样拆成 `S_SC_RD` / `S_SC_WB`。一次变换从约 1160 cycles 变成 2305 cycles。
- `hardware/rtl/bus/pqc_accel_axi.v` 的 128×32 数据缓冲区换成一块 `ram_dp`：
  A 口分时给输入流写入 / 装载读出 / 结果写回，B 口专给输出流读。

## 三处时序要跟着改，每一处都不是形式上的

**1. 读地址要提前几拍，要数清楚。** `ntt_core` 的读口现在是同步读，
而 `pqc_accel_axi` 给它的地址本身还过了一级寄存器，所以 `S_STORE` 里
地址要**提前两拍**（`ntt_rd_addr <= cnt + 2`），并且在进 `S_STORE` 之前
插一个 `S_NTT_PRE` 把第 0 个地址先发出去。缓冲区那边地址只过一级 BRAM，
提前一拍即可（`S_LOAD_PRE` + `bufa_addr = cnt+1`）。
第一版按"提前一拍"写，`test_ntt_datapath` 当场挂 —— 这种差一拍的错
靠肉眼看不出来，只能让测试说话。

**2. 输出流要"读超前一拍"。** `m_axis_tdata` 原来是 `bufmem[rd_ptr]` 的组合读。
换成 BRAM 之后 B 口的地址给的是 **下一拍的** `rd_ptr`（没握手时就等于当前值），
这样本拍 `bufb_dout` 恰好是本拍 `rd_ptr` 指的那个字。这是 BRAM 做 FIFO 读口的
标准写法；写成 `rd_ptr` 会让 15 个用例里挂掉 8 个（试过）。

**3. 模式 10 的挤压不能再"按字节读-改-写"。** BRAM 没法同一拍读了再写回同一个字。
改成字节攒进 `sq_acc`、凑满 4 个（或到输出末尾）才整字写回，读口直接消失 ——
而这条按字节的读口正是 S2b 多花 4919 LUT 的主因。
顺带一个好副作用：最后那个不满 4 字节的字，多出来的字节现在是 0，
而不是残留的**输入消息字节**。

## 一条被测试盖住的隐患，补了用例

去掉 `S_LOAD_PRE` 之后 16 个用例**全部照过**。原因是正常收包时输入流的写指针
在 TLAST 之后归零，于是 `S_IDLE` 里摆在 A 口地址上的 `wr_ptr` 恰好是 0，
装载第一个字碰巧读对了 —— 正确性依赖了一个"碰巧"。

一旦软件漏发 TLAST（传输被截断、DMA 描述符写错），写指针停在包尾，
第一个字就会读错，而命令照样报 DONE、不报错。给密码加速器留这种失效模式不行。
补了 `test_load_start_is_independent_of_write_pointer`：不带 TLAST 送完 50 个字
再发命令，结果必须与带 TLAST 时逐字节相同。用变异验证过 —— 去掉 `S_LOAD_PRE`
时**只有这一条**失败。

## 综合结果（`xazu3eg-sfvc784-1-i`，OOC，含布局布线）

| 顶层 | LUT | 占比 | 寄存器 | BRAM | DSP | WNS @100 MHz | 功耗 |
|---|---|---|---|---|---|---|---|
| `ntt_core`（S3 后） | **258** | **0.37%** | 55 | 0.5 | 13 | **+0.077 ns（收敛）** | 0.236 W |
| `ntt_core`（S3 前） | 28494 | 40.38% | — | 0 | 13 | −2.679 ns | — |
| `pqc_accel_axi`（S3 后） | **4768** | **6.76%** | 2188 | 1.5 | 13 | **−0.047 ns** | 0.297 W |
| `pqc_accel_axi`（S3 前） | 62718 | 88.89% | 10736 | 0 | 13 | −2.492 ns | 1.053 W |

`ntt_core` 少了 **110 倍**的 LUT，整个加速器顶层少了 **13 倍**，功耗掉到三分之一。
`LUT as Memory` 仍然是 0，但这次是对的：存储全在 `RAMB18E2` / `RAMB36E2` 里
（映射报告确认 `u_mem/mem_reg` 是 `256 x 16 (READ_FIRST)` 双口）。

**S4 的空间到手了。** 之前是"整颗片子塞不进 ML-KEM 核"，现在加速器顶层只占 6.76%，
加上 S1 的 TRNG 约 6%，还有八成多的 LUT 和 214 片 BRAM 留给 S4。

## 时序还差 0.047 ns，说清楚差在哪

`pqc_accel_axi` 的 WNS 是 **−0.047 ns**（6190 条路径里 2 条不过），
折算 Fmax 99.5 MHz。关键路径不在存储，在蝶形的乘法链：

```
u_ntt/u_mem BRAM B 口输出 → LUT2 → DSP × 3 级（zeta 乘、Montgomery 归约的两次乘）
→ CARRY8 → BRAM A 口输入        共 22 级逻辑，9.693 ns
```

其中 BRAM 的 clk→out 就占了 0.998 ns。两条可行的修法：

1. 打开 BRAM 的可选输出寄存器（`DO_REG=1`）—— Vivado 自己在综合日志里提示了。
   clk→out 降到 0.4 ns 上下，够收敛，代价是读延迟再加一拍，
   前面那三处"提前几拍"的算法要跟着全改一遍。
2. 在蝶形内部插一级流水，把三级串起来的 DSP 乘法拆开。代价是
   `butterfly_ct` / `butterfly_gs` 要带时钟，它们现在是纯组合模块、
   有独立的 cocotb 组合用例。

**这一步没做，是有意的。** 本项目的目标是原型验证，99.5 MHz 与 100 MHz
对"能不能放进去"没有区别；而 S4 把 ML-KEM 状态机拼进来时这块一定要重新做时序，
现在为 0.047 ns 去动一个刚验证完的数据通路不划算。
真要跑满 100 MHz 时按上面第 1 条改，工作量是确定的。

## 验证

- cocotb：`ntt_core` 5 个用例、`pqc_accel_axi` **16** 个用例（新增 1 个），全通。
- C 侧：`ctest -R accel` 两个用例全通 —— 软件桩、Verilator 后端、OpenSSL 三方逐字节一致。
- 变异验证两处：把输出流的"读超前一拍"改回 `rd_ptr`（16 挂 8），
  去掉 `S_LOAD_PRE`（只挂新加的那一条）。
- 全量 `ctest`：46 个里 6 个 `kat_*` 失败，与本步无关 ——
  它们要 `vectors/` 下的向量文件（未入库，`tools/fetch_vectors.sh` 拉取），
  改动前后一样红。

# S3b：把剩下的寄存器阵列扫干净

S3 只动了 `ntt_core` 和加速器顶层的缓冲区。`tools/rtl_synth_check.sh` 的
"摊成寄存器"清单里还剩几条，这一步逐条过了一遍 —— **该换的换，不该换的
把理由写进脚本**，免得下一个人再追一遍。

## 该换的三块

| 模块 | 存储 | 原来的读口 | 改法 |
|---|---|---|---|
| `mldsa_ntt_core` | 256 × 32 bit | 组合，且蝶形一拍读两个 | `ram_dp`，蝶形拆 `S_RD`/`S_WB` 两拍 |
| `mlkem_rej_uniform` | 256 × 12 bit | 组合读 + **两个写口** | `ram_dp`，A 口写候选 1、B 口写候选 2 |
| `mldsa_rej_uniform_buf` | 256 × 23 bit | 组合读，单写 | `ram_dp`，B 口常年挂读地址 |

`mlkem_rej_uniform` 那块值得单说：它一拍最多收下**两个**候选（`mlkem_rej_pair`
从 3 个字节里取两个 12 位数），所以原来是两个写口加一个读口的寄存器阵列 ——
真双口 BRAM 正好对得上。A 口写第一个候选（地址 `count`），B 口写第二个
（地址 `slot2 = count + take1`）。两个槽位恒差 1，永远不同址，不会踩到
`ram_dp` 那条"两口同写一址"的断言。收集结束（`!busy`）之后 B 口改接外部读口。

## 综合结果（`xazu3eg-sfvc784-1-i`，OOC，含布局布线）

| 设计 | CLB LUT | 占比 | 寄存器 | BRAM | DSP | WNS | Fmax |
|---|---|---|---|---|---|---|---|
| `mldsa_ntt_core`（S3b 后） | **1027** | **1.46%** | 57 | 1 | 20 | −2.525 ns | 79.8 MHz |
| `mldsa_ntt_core`（S3b 前） | 56602 | 80.22% | 8552 | 0 | 20 | −6.149 ns | 61.9 MHz |
| `mldsa_rej_uniform_buf`（S3b 后） | **18** | **0.03%** | 11 | 0.5 | 0 | +8.363 ns | 610.9 MHz |
| `mldsa_rej_uniform_buf`（S3b 前） | 1860 | 2.64% | 5904 | 0 | 0 | — | — |

**55 倍。** 一个 ML-DSA 的 NTT 核原来要吃掉 80% 的片子 —— 也就是说
S2 那版 RTL 里，ML-KEM 和 ML-DSA 的 NTT 核**放不进同一颗 ZU3EG**。
现在两个加起来占 1.8%。

采样缓冲那一条更干净：**LUT 从 1860 到 18（103 倍），寄存器从 5904 到 11
（537 倍）**，代价是半块 RAMB18。5904 = 256 × 23 + 16 —— 那 5888 个触发器
就是逐字摊开的多项式缓冲，1860 个 LUT 是给它配的读出多路选择树。
换成 `ram_dp` 之后两样都没了。

## 这里要如实说一句：`mldsa_ntt_core` 仍然不满足 100 MHz

WNS −2.525 ns，折算 79.8 MHz。原因和 ML-KEM 侧那条路径同源，只是更严重：
ML-DSA 的模数是 23 位、系数按 32 位承载，Montgomery 归约里那两次乘法都是
32×32，串在一条组合路径上比 ML-KEM 的 16 位版长得多。

**为什么现在不修**：`mldsa_ntt_core` 目前**没有被 `pqc_accel_axi` 例化** ——
加速器顶层只走 ML-KEM 的 NTT。它是为将来的 ML-DSA 通路准备的独立模块，
接进总线的那一天必然要重新做时序（多半是在蝶形里插一到两级流水）。
现在为它单独改一遍数据通路，等接总线时还要再改一遍。
**它现在的作用是证明"面积放得下"，这一点已经成立了。**

## 故意不换的两块

这两条会一直留在 `rtl_synth_check.sh` 的清单里，脚本现在会把它们标成
"预期之内"：

- **`keccak_f1600` 的 `A`**：1600 bit 的置换状态，一轮里 25 条 lane 要同时读、
  同时写。BRAM 只有两个口，装不下这种全并行访问 —— 它本来就该是触发器。
  同一份清单里的 `B`/`C`/`D`/`Ath`/`Anext` 是轮内的组合中间量，Yosys 把数组
  一律当 memory 报，综合出来是纯组合线网，不占存储。
- **`sync_fifo` 的 `mem`**：只有 TRNG 一个实例，32 bit × `FIFO_DEPTH`，
  一共 1 Kbit 上下。更要紧的是它是 **FWFT（首字直通）**：`rd_valid` 拉高的
  同一拍 `rd_data` 就得有效，因为 AXI4-Lite 要在同一次读事务里返回数据。
  换成同步读的 BRAM 就得加一拍，那要连着动 `trng_top` 和 AXI 读通路 ——
  为 1 Kbit 付这个代价不划算。

判断标准写在 `hardware/rtl/common/ram_dp.v` 的注释里：**组合读的存储永远
变不成 BRAM**，但"该不该是 BRAM"要看访问模式和位宽，不是看它长得像数组。

## 验证

cocotb 113 个用例全通（`mldsa_ntt_core` 5 个、`mlkem_rej_uniform` 2 个、
`mldsa_rej_uniform_buf` 1 个都在里面，三处读口的一拍延迟由测试台补上升沿覆盖）。

# S4：完整的 ML-KEM 密钥生成核（纯 RTL）

S1 到 S3 放进 PL 的都是**算子**：TRNG、Keccak/SHA-3 海绵、NTT、基乘、压缩、
两种采样、12 位编解码。密钥生成的**编排**——谁先谁后、ρ/σ 怎么展开、矩阵怎么
累加、字节怎么打包——一直还在普通世界的 C 里。

S4 把编排也搬进去。现在的接口是：

```
普通世界  →  d（32 字节）、z（32 字节）、param_set
普通世界  ←  ek、dk 两串字节
```

**中间的 ŝ、ê、Â、σ 一个都不出芯片。** 这是"密钥不出边界"那句话第一次
在这个项目里有了硬件形态 —— 私钥的每一个中间量都只在 PL 的 BRAM 里存在过，
普通世界的地址空间里从来没有它们。

## 数据通路

```
d‖k ──SHA3-512(G)──→ ρ ‖ σ
                      │
  σ‖N ──SHAKE256──→ CBD ──→ NTT ──→ ŝ[0..k-1]（槽 0..3）
                                    ê[0..k-1]（槽 4..7）
  ρ‖j‖i ──SHAKE128──→ 拒绝采样 ──→ Â[i][j]
                                    │
                        Â[i][j] ∘ ŝ[j] 累加 ──→ t̂[i]（槽 8..11）
                                    │
                        × f、加 ê[i]、barrett
                                    │
              ByteEncode12 ──→ ek = t̂‖ρ ──→ SHA3-256 ──→ H(ek)
                          ──→ dk = ŝ‖ek‖H(ek)‖z
```

多项式存储是一块 16 槽 × 256 系数 × 16 bit 的真双口 BRAM（64 Kbit，约 2 块
RAMB36）。`param_set` 在**运行时**选 512 / 768 / 1024，三套共用同一份数据通路 ——
为三个参数集各综合一份，在真密码机里是说不通的：同一块板要同时支持多套参数。

## 一个 sha3_core 走完全程

G（SHA3-512）、PRF（SHAKE256）、XOF（SHAKE128）、H（SHA3-256）四种用法在时间上
互不重叠，共用同一个海绵核。四种只差 `rate` 和 `suffix` 两个字节，`start`
那一拍锁存即可。多例化一个置换核要 ~7000 LUT，这颗片子上不划算。

代价是每换一种用法要单独走一个 start 状态 —— 状态机因此多了四个状态，
但这是显式的、看得见的。

## 三处值得记下来的地方

**① 累加为什么可以每一步都 barrett。** 参考实现是把 k 个基乘全加完再 barrett
一次，这里是每加一个就 barrett。两者**逐系数完全相同**：`barrett_reduce` 给的是
同余类里唯一的代表元，同余 ⇒ 输出相同。好处是累加器恒定在 ±1664，加上一个基乘
输出（范围 (−q, q)）也就 ±4993，稳稳落在 16 位有符号里 —— 不必为 k=4 的最坏
情况把累加器加宽。

**② `Â[i][j]` 的 XOF 头是 ρ‖j‖i，j 在前。** 写成 ρ‖i‖j 照样能跑出合法的
多项式、合法的 ek/dk，只是不是 ML-KEM 的那一个。这类错误不会崩、不会越界，
只会让密钥对不上 —— 所以对拍必须锚在外部向量上，见下面的验证一节。

**③ `out_valid` 必须带上"H 的海绵收不收得下"这个条件。** ek 那两段字节要同时
交给下游和 H 的海绵，而海绵每吸满 136 字节要停 24 拍做置换。第一版把这个条件
只写进了内部的推进条件、`out_valid` 一直挂着 —— AXI4-Stream 的规矩是 valid 与
ready 同时为高就必须完成一次传输，于是下游把同一个字节收了好几遍。
**实测多出 233 字节**（≈9 次置换 × 26 拍），正好对上 1184 字节的 ek 要过
8.7 次置换。这个 bug 在"只看最终字节是否相等"的测试里表现为长度不对，
定位很快；但如果输出没接背压、下游又恰好每拍都 ready，它可以一直藏着。

## 验证：锚在 ACVP 向量上，分两层查

黄金模型是 `hardware/model/mlkem_oracle.py` 的 `mlkem_keygen` —— 那份实现是拿
**NIST ACVP 向量**验过的（`oracle_d`），所以这里的比对不是"自己和自己比"。

- **第一层，中间量**：ŝ、ê、t̂ 逐系数比对。这三个量都在多项式存储里，
  `DEBUG_BANK=1` 时把存储读口引出来看。有这一层是因为 ek/dk 一旦对不上，
  光看三千多个字节完全定位不到是哪一步错的。
- **第二层，最终字节**：三个参数集的 `ek‖dk` 全部逐字节一致。
  512 是 1632 字节、768 是 3584、1024 是 6208。

> ⚠️ `DEBUG_BANK` 是**仿真专用参数，综合时必须是 0**。那个口直连私钥系数，
> 引出来等于在密码边界上开一个洞。综合脚本不传这个参数，默认就是 0。

**变异验证**：把 XOF 头改成 ρ‖i‖j（矩阵转置），`t̂[0]` 那一条立刻挂 ——
说明中间量那一层不是摆设，它在最终字节之前就把错误拦下来了。

**背压用例与常规用例走同一段采样代码**。写成两段的话，"背压下也一致"验证的
就只是两段测试代码碰巧写法不同，而不是 RTL 的行为。

cocotb 全量 **117 个用例**（新增 4 个）全通。

## 综合结果（`xazu3eg-sfvc784-1-i`，OOC，含布局布线）

| `mlkem_keygen` | **6032** | **8.55%** | 3327 | 3 (1.39%) | 29 (8.06%) | 0.245 W | **+0.420 ns** | **104.4 MHz** |
| `mlkem_cbd_stream` | 143 | 0.20% | 75 | 0 | 0 | 0.222 W | +8.167 ns | 545.6 MHz |

一个**完整的 ML-KEM 密钥生成**（三个参数集运行时可选，自带 Keccak 海绵）
占这颗片子 **8.55% 的 LUT、1.4% 的 BRAM、8% 的 DSP**，四分之一瓦。
片子还剩九成，后面的 Encaps/Decaps、对称核、密钥仓都还有地方。

慢，但这是原型验证要的东西：**能实现、放得下、跑得到时钟**。

## 时序：第一版差了 10.7 ns，切两刀就过了

第一版 `mlkem_keygen` 的 **WNS 是 −10.722 ns（48.3 MHz）** —— 差一倍还多，
不是四舍五入的事。布线报告给的关键路径起点是 `b1_r_reg[6]/Q`，
经 `u_bm/smul_return`（DSP48E2_X2Y11）→ `u_bm/u_a1b1/m`（DSP48E2_X2Y10）→
后面还串着几级 DSP —— **整条路径都在基乘里**。

数一下就明白了。`mont_reduce` 内部本身是两次乘法（`m = a·QINV`、`m·Q`），
所以 r0 这条路上串着：

```
smul(a1,b1) → mont ×2 → smul(·,ζ) → mont ×2   = 6 级
                                    ↓ 状态机里还接着
                              barrett          = 2 级
                                                 ─────
                                                 8 级串行乘法
```

一级 DSP 乘加在这颗片子上约 2.4 ns，8 级就是 19 ns 出头 —— 和实测的
20.7 ns 对得上。**问题不在综合工具，在数据通路本身写得太深。**

切两刀，把 8 级分成 3 + 3 + 2：

1. 在 `t_a1b1` 处切开 `mlkem_basemul`，拆成 `_head`（a1·b1 那一次 fqmul）
   和 `_tail`（其余四次 + 两个加法）。四次 fqmul 之间互相独立，深度仍是 3 级。
2. 在 `barrett_reduce` 之前再切一刀。

`tomont`（`acc0 × 2³² mod q` 再加 ê 再 barrett）是同一个毛病的小号版本，
3 + 2 = 5 级，同样在中间打一拍。

**组合版 `mlkem_basemul` 保留**，由 `_head` + `_tail` 直接拼出来，接口和原有
的 cocotb 用例一个字没动 —— 这样"基乘"这段数学**仍然只有一份实现**，
和 `mont_reduce` 的规矩一致。要流水的核例化两半自己插寄存器，
不需要流水的（和读代码的人）看组合版。

代价与收益：

| | 第一版 | 切完 |
|---|---|---|
| 每对系数 | 5 拍 | 7 拍 |
| `tomont` 每系数 | 3 拍 | 4 拍 |
| LUT | 5883 | 6032（+149） |
| 寄存器 | 3274 | 3327（+53） |
| WNS | **−10.722 ns** | **+0.420 ns** |
| Fmax | 48.3 MHz | **104.4 MHz** |

多花 149 个 LUT、慢三成拍数，换 100 MHz 收敛。

**新的关键路径不在基乘了**：`u_ntt/u_mem`（NTT 的系数存储）出来经 22 级逻辑、
其中 3 组 DSP 乘加，9.205 ns 回到同一块 BRAM 的 DIN —— 也就是 NTT 蝶形本身。
它只剩 0.42 ns 余量，接总线、加时钟树之后大概率还要再动一次。
这一点先记在这里，等 Encaps/Decaps 接进来一起看。

# S4b：完整的 ML-KEM 封装核（纯 RTL，2026-08-12，完成，未上板）

KeyGen 之后把 Encaps 也做成纯 RTL。接口：

```
普通世界  →  ek（384k+32 字节，字节流）、m（32 字节）、param_set
普通世界  ←  K（32 字节）‖ c（768/1088/1568 字节），一条字节流
```

**r̂、e₁、e₂、Â、以及 G 出来的那半截随机种子，一个都不出芯片。**
共享密钥 K 是唯一出去的秘密，而它本来就要交给上层。

## 数据通路

```
ek ──┬─→ ByteDecode12 ──→ t̂[0..k-1]（槽 8..11）
     └─→ SHA3-256(H) ──→ H(ek)
                          │
m ‖ H(ek) ──SHA3-512(G)──→ K ‖ r
                                │
  r‖N ──SHAKE256──→ CBD_η1 ──→ NTT ──→ r̂[0..k-1]（槽 0..3）
  r‖N ──SHAKE256──→ CBD_2  ─────────→ e₁[0..k-1]（槽 4..7）
                                       e₂        （槽 12）
  ρ‖i‖j ──SHAKE128──→ 拒绝采样 ──→ Â[i][j]
                                       │
             Â[i][j] ∘ r̂[j] 累加 → 逆 NTT → + e₁[i] → Compress_du → c₁
             t̂[i]   ∘ r̂[i] 累加 → 逆 NTT → + e₂ + Decompress₁(m) → Compress_dv → c₂
```

槽位分配与 KeyGen 一致（16 槽 × 256 × 16 bit 的同一块双口 BRAM），
只是住的东西换了：0..3 是 r̂、4..7 是 e₁、8..11 是从 ek 解出来的 t̂、12 是 e₂。

## 三处取舍

**① `du`/`dv` 做成运行时输入，不是 parameter。** 512/768 用 du=10 dv=4，
1024 用 du=11 dv=5。同一块板要同时支持三套参数集，所以新写的 `mlkem_bitpack`
的 `d` 是**端口**而不是参数。代价是移位量变成变量 —— 但累加器只有 20 位，
变量移位综合出来是几十个 LUT，比"为三个参数集各例化一份打包器"便宜得多。

顺带一提，`mlkem_bitpack` **不需要 flush**：ML-KEM 每个多项式 256 个系数，
256·d 比特 = 32d 字节，**总是整字节**，比特累加器跑完一个多项式必然回到空。

**② 累加器借 `ntt_core` 的存储，不另开 BRAM。** t̂ᵀr̂ 的中间和要占一整个
多项式。MAC 阶段 `ntt_core` 本来就闲着，于是让累加直接写进它的系数存储，
算完原地做逆 NTT —— 既省一块 BRAM，也省掉一次 256 系数的搬运。
代价是 MAC 阶段要同时用到四个读口：`ntt_core` 存储（累加器）、bank 的 A 口
（t̂）、bank 的 B 口（r̂）、拒绝采样缓冲（Â）。四个口刚好够，没有冲突。

**③ XOF 头是 ρ‖i‖j，i 在前 —— 与 KeyGen 正好相反。** Encaps 要的是 **A 的
转置**（û = Aᵀr̂）。写反了照样跑出合法的密文，只是解不开。和 KeyGen 那处
一样，这类错误必须靠外部向量才看得见。

## 两个位宽陷阱

都是在写完之后靠算数发现的，不是靠测试：

**`tbytes` = 384k。** 384 = 256 + 128，是**两项**移位和。第一版写成四项
（128+64+32+16 = 240），于是 ek 只吃进 k·240+32 字节就卡死 —— 768 是 752
字节、512 是 512 字节，数字精确对得上，一看就知道是常数拆错了。

**`se_n` 要数到 2k。** k=4 时 2k = 8，三位装不下会绕回 0，ML-KEM-1024 的
e₂ 永远采不到。这与 KeyGen 里 `se_n` 那个溢出是**同一类**错误 ——
在这份代码里，"某个计数器的上界随 k 变"是最容易写窄的地方。

## 验证：同样锚在 ACVP 向量上，分两层查

黄金模型是 `mlkem_oracle.py` 的 `mlkem_encaps`，拿 NIST ACVP 的 encapDecap
向量验过（`oracle_e`）。

- **第一层，中间量**：r̂、e₁、e₂，以及从 ek 解出来的 t̂，逐系数比对。
- **第二层，最终字节**：三个参数集的 `K‖c` 全部逐字节一致
  （512 是 32+768、768 是 32+1088、1024 是 32+1568 字节）。

**背压用例与常规用例走同一段采样代码**。ek 那一路三拍给两拍、密文那一路
五拍收两拍，两头的停顿再叠上海绵每 136 字节停 24 拍 —— 512 从 26777 拍变
28329 拍（**+5.8%**），输出逐字节不变。

> ⚠️ `DEBUG_BANK` 同样是**仿真专用，综合时必须是 0**。那个口直连 r̂，
> 引出来等于在密码边界上开一个洞。综合脚本不传，默认就是 0。

cocotb 全量 **122 个用例**（新增 3 个）全通。

## 拍数（仿真实测，@100 MHz）

| 参数集 | 拍数 | 时间 |
|---|---|---|
| ML-KEM-512 | 26 777 | 268 µs |
| ML-KEM-768 | 42 489 | 425 µs |
| ML-KEM-1024 | 61 172 | 612 µs |

与 KeyGen 同一个量级（768 是 43.3 k）—— 两者的主要开销都是 k² 次 XOF
拒绝采样，Encaps 多一次逆 NTT、少一次 `tomont`，正好抵掉一点。

## 综合结果（`xazu3eg-sfvc784-1-i`，OOC，含布局布线）

| 设计 | CLB LUT | 占比 | 寄存器 | BRAM | DSP | 功耗 | WNS | Fmax |
|---|---|---|---|---|---|---|---|---|
| `mlkem_encaps` | **5388** | **7.64%** | 3315 | 3 (1.39%) | 40 (11.11%) | 0.257 W | **+0.068 ns** | **100.7 MHz** |
| `mlkem_keygen` | 6032 | 8.55% | 3327 | 3 (1.39%) | 29 (8.06%) | 0.245 W | +0.420 ns | 104.4 MHz |

Encaps 比 KeyGen **还小一点**（LUT 少 11%），但 DSP 多了 11 个 ——
多出来的是四个 `mlkem_compress`（du/dv 各两种）和输出那条 barrett，
而省下的是 KeyGen 的 `tomont` 与 `encode12` 那一整套打包。

两个核加起来占这颗片子约 **16% 的 LUT、2.8% 的 BRAM、19% 的 DSP**，半瓦。
按现在的速度，Decaps（要复用 Encaps 的数据通路做重加密）之后大概三成，
密钥仓与总线边界还有地方。

## 时序：输出那条尾巴要切一刀

第一版布线后 **WNS = −1.987 ns（83.4 MHz）**。关键路径是整条输出尾巴挤在一拍：

```
bank BRAM 读出 ──→ barrett_reduce ──→ mlkem_compress ──→ 打包器累加器
                    (2 级 DSP)        (1 级 DSP)         (LUT)
     1.14 ns          ~5.4 ns           ~2.5 ns          ~1.5 ns     = 11.924 ns
```

数一下就明白：`barrett_reduce` 内部是两次乘法（`v·a >> 26`、`a − t·q`），
`mlkem_compress` 又是一次（乘 `⌈2³³/q⌉` 再移位），**三级 DSP 串在一起**，
前面还挂着一次同步存储读出。这跟 S4 里基乘那条路是同一类问题，
只是这次串的是"约减 + 压缩"而不是五次 Montgomery 乘。

切在 barrett 与 compress 之间（`outc_r`），两边正好各剩一半：

| | 第一版 | 切完 |
|---|---|---|
| 每系数拍数 | 2（RD→FEED） | 3（RD→CMP→FEED） |
| ML-KEM-768 总拍数 | 41 654 | 42 489（+2.0%） |
| LUT | 5372 | 5388（+16） |
| 寄存器 | 3313 | 3315（+2） |
| WNS | **−1.987 ns** | **+0.068 ns** |
| Fmax | 83.4 MHz | **100.7 MHz** |

**十六个 LUT、两个寄存器、2% 的拍数，换 17 MHz。** 这一刀便宜得没有争议 ——
之所以第一版没切，是因为写的时候把"读存储 → 算 → 打包"当成了一件事，
而它在硅上是三件事。

**新的关键路径又回到了 NTT 蝶形**：`u_ntt/u_mem` 出来经 22 级逻辑、
其中 3 组 DSP 乘加，9.578 ns 回到同一块 BRAM 的 DIN。
与 S4 里 KeyGen 收完时序之后的关键路径是同一条 —— 也就是说，
**ML-KEM 数据通路的时序天花板现在由 `ntt_core` 的蝶形决定**，
余量只有 0.068 ns。后面接总线、加时钟树，这条路一定要再动一次；
届时该改的是 `ntt_core` 本身，而不是每个调用它的核各切各的。

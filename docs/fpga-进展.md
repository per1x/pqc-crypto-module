# S1 硬件 TRNG（2026-08-12，完成，未上板）

## 做了什么

仓库里原本只有 `trng_health.v`（SP 800-90B §4.4 的 RCT + APT，阈值参数化、
告警锁存，质量很好）—— 但**缺噪声源本身**，也缺调理和总线接口。补齐成完整熵源：

```
环振阵列 ──采样/抽取──> 原始比特 ──┬──> 连续健康检测（RCT + APT）
                                    └──> Keccak 海绵调理 ──> FIFO ──> AXI ──> 安全世界
```

| 文件 | 作用 |
|---|---|
| `hardware/rtl/trng/ring_osc.v` | 单条环振。综合走真反相器环，仿真走抖动行为模型 |
| `hardware/rtl/trng/trng_source.v` | 8 条环振（13/15/…/27 级）+ 两级同步器 + 抽取 |
| `hardware/rtl/trng/trng_cond.v` | Keccak 海绵调理器，复用已有的 `keccak_f1600` |
| `hardware/rtl/trng/trng_top.v` | 启动健康检测、告警处置、zeroize 策略 |
| `hardware/rtl/trng/trng_axi.v` | AXI4-Lite 从机 + **AxPROT 安全门控** + tamper 引脚 |
| `hardware/rtl/common/sync_fifo.v` | 可擦除 FIFO（flush 逐地址覆零，不是只挪指针） |
| `hardware/model/trng_cond_model.py` | 调理器的 Python 黄金模型 |
| `docs/trng-register-map.zh-CN.md` | 寄存器表与驱动契约 |

## 几个有意的设计选择

**调理用 Keccak 海绵，不是自己发明的白化。**
SP 800-90B §3.1.5.1.2 给了一份 vetted conditioning 清单（HMAC/CMAC/CBC-MAC/
Hash_df/哈希函数），用清单里的构件，输出熵可以直接按 `min(输出长度, 输入熵)` 计；
自己发明的白化（von Neumann、LFSR 打散）要另行论证。
选 Keccak 还顺带证明了 `keccak_f1600` 是可复用的 IP，而不是只能给
`pqc_accel_axi` 用的一次性件 —— **零增量面积拿到一个 vetted 构件**。

**健康检测吃的是抽取之后的样本流**，也就是调理器实际消费的那一条。
检测的对象必须和被使用的对象是同一个，否则检测没有意义。

**告警之后连熵池一起清。**
标准只要求"停止输出并上报"，动作留给使用方。这里选最保守的：
告警 → ready 拉低 → FIFO 擦除 → **调理器连同海绵状态一起复位** → 启动检测重跑。
理由是告警意味着噪声源可能已经失效了一段时间，池子里可能混进了低熵输入，
留着比丢掉风险大。代价只是重新暖机。

**AxPROT 门控：被拒的读绝不弹 FIFO。**
`AxPROT[1]=1`（non-secure）的读写一律 DECERR，且不产生任何副作用。
返回 DECERR 而不是 OKAY+0 是有意的 —— 静默返回 0 会让普通世界以为拿到了
随机数，而 0 是最糟的"随机数"。
"被拒的读不弹 FIFO"单独测一条：如果被拒的读仍然弹出，普通世界虽然拿不到数，
却获得了一个"反复读把熵池抽干"的手段。让安全世界拿不到随机数，
和自己拿到随机数，是两个不同的攻击，后者一样致命。

**这一层不是唯一一层。** AxPROT 是纵深防御的最内层，完整隔离还要靠
XMPU/XPPU（在 master 那端就挡掉）和地址映射（不出现在普通世界设备树里）。
三层的分工写在 `docs/trng-register-map.zh-CN.md`。

## 环振被优化掉是最危险的失效模式，脚本里专门防了

反相器环违反了综合工具的两条基本假设（组合逻辑无环、逻辑可化简）。
不做三件事，环就会被优化掉：

1. RTL 里 `DONT_TOUCH`（在 `ring_osc.v` 的 `chain` 声明上）；
2. `ALLOW_COMBINATORIAL_LOOPS TRUE`（在 `trng_ooc.tcl` 里对环网络设置）；
3. `LUTLP-1` DRC 降级为 Warning，否则 `write_bitstream` 直接失败。

**环被吃掉之后，综合日志里不会有任何报错** —— 采样器采到常量，TRNG 静默变成
常数发生器。所以 `trng_ooc.tcl` 在**综合后和布线后各数一次** ring_osc 层次下的
LUT 数量，少于 120 就直接 `error` 退出。实测两次都是 **160 个 LUT**
（8 条环 × 平均 20 级 = 160），与设计值精确吻合。

> 顺带一个坑：XDC **不是完整的 Tcl**。`if`、`for`、`remove_from_collection`
> 都会报 `[Designutils 20-1307]` 并**静默忽略那一条约束**，脚本还继续跑完。
> 第一版把条件判断写进 XDC，三条约束全被吞了。带判断的部分必须放在 `.tcl` 里。

# S1b 软件侧：熵源驱动，替掉软件 RNG（2026-08-12，完成，未上板）

RTL 做完只是一半。用户要的是"作为熵源，让安全世界软件从它取随机、替掉软件
RNG" —— 这一半在软件树里。

## 做法：照抄 accel 那条接缝

仓库里已经有一套成熟的做法（`include/pqchsm/accel.h`）：**先把 AXI 寄存器表
定死，再写一个 C 实现的"假外设"**，暴露与真 PL 完全相同的寄存器语义，
真板到手后换成 `/dev/mem` + mmap，上层一行不改。熵源照搬这条接缝：

| 文件 | 作用 |
|---|---|
| `include/pqchsm/hwrng.h` | 寄存器偏移、状态位、错误码、`hwrng_transport_t` |
| `src/hal/hwrng.c` | 驱动本体：自检、取字节、告警处置 |
| `src/hal/hwrng_stub.c` | `trng_axi` 寄存器语义的软件模型（FIFO 由 OpenSSL 填） |
| `src/hal/hwrng_mmap.c` | `/dev/mem` + mmap，基址由 `PQCHSM_HWRNG_MMAP_BASE` 给出 |
| `tests/unit/test_hwrng.c` | 契约测试，41 条断言 |

**熵源单开一条接缝，没有并进 `accel.h` 的操作码**，与 RTL 侧分成两个 AXI 从机
是同一组理由：生命周期不同（加速器是发命令等完成，TRNG 常开自由运行）、
访问权限不同、故障域不同（TRNG 告警要能独立上报，不该被加速器的忙闲挡住）。

## 驱动里三条不能省的纪律

1. **读 RDATA 之前必须先查 `STATUS.DATA_VALID`。** 空读返回 0，而 0 是最糟的
   "随机数"。契约里那个锁存的 `UNDERRUN` 位就是用来事后抓住不查就读的驱动的。
2. **取完一批之后复查 `UNDERRUN` 与 `ALARM`，任一置位则整批清零作废。**
   不是"把出错之后的部分丢掉" —— 告警是**锁存的电平**，只说明"这段时间里发生
   过"，定位不到是第几个字。既然定位不了，就只能全丢。
3. **绝不回退到软件随机源。** `pqc_random_bytes()` 装了 transport 就走硬件，
   取不到就返回 -1；liboqs 的随机源回调签名是 `void`，没有返回值可用，
   所以那边直接 `abort()`。静默回退会让"熵来自硬件"恰好在最要紧的时刻悄悄
   变成假话，而调用方无从知道。

第 2 条是最容易写漏的一条，所以单独做了**变异测试**验证它真的在起作用：
把复查那几行换成 `(void)s;` 重新编译，`test_hwrng` 立刻在"取到最后才告警"
那条上失败（返回 0 而不是 -3，且缓冲区里留着数据）。测试确实咬得住这行代码，
不是摆设。

## 验证

`tests/unit/test_hwrng.c`，41 条断言，`ctest -R hwrng` 通过。验的是
`docs/trng-register-map.zh-CN.md` 那份契约的**软件侧** —— RTL 侧由
`test_trng_axi.py` 验同一份契约。两边对着同一张表各写各的，接口层面的分歧
在无板阶段就会暴露，这正是先定寄存器表再写假外设的收益。

覆盖到的：没装 transport 时如实报不可用、启动检测没过时 READY 不拉高、
非 4 倍数长度的尾部处理、告警早退与告警复查两条路径都整批清零、空池超时
（而不是死等、也不是硬读 RDATA 把 0 当随机数）、ZEROIZE 重跑启动检测、
`pqc_random_bytes()` 确实弹了硬件的字（读 `WORDS` 计数验证：32 字节正好 8 个
字）、故障时确实不回退。

> **这里一个字都没测熵。** transport 是软件模型，FIFO 由 OpenSSL 填 ——
> 测出来的"随机性"只反映 OpenSSL。软件模型也如实把 `is_hardware` 报成 0，
> 审计里"熵来自硬件"这句话的依据就是这一位。

模型还有一处刻意的不保真：软件里没有时钟，所以拿"读了几次 STATUS"当时间
基准（每次推进 64 个启动样本，暖机需轮询 16 次）。它证明了驱动确实在轮询、
确实等到 READY 才读；**没有**证明任何与时延、吞吐、熵率有关的东西。

## 还差什么（都要等板子）

- 地址分配：`PQCHSM_HWRNG_MMAP_BASE` 现在没有取值，`hwrng_transport_mmap()`
  返回 NULL。
- `hwrng_mmap.c` 走 `/dev/mem`，也就是跑在普通世界。而 `trng_axi` 默认
  `SECURE_ONLY=1`，**这条路在默认配置下本来就打不通**（AxPROT[1]=1 → DECERR）。
  这不是 bug：它的正当用途是综合成 `SECURE_ONLY=0` 的调试位流做通路验证和
  熵采集，以及当作安全世界侧驱动的原型（换成安全世界的映射，寄存器时序完全
  一样）。生产配置下取熵必须走安全世界。
- 把"选哪个 transport"接进 pqchsmd 的初始化 —— 尚未做。板上取熵目前走的是
  `board/trngraw.c` 那条直接 mmap 的路。

# S2 SHA-3 / SHAKE 海绵进 PL（2026-08-12，核完成，未接总线）

## 做了什么

仓库里原本只有 `keccak_f1600` 置换核，海绵的 framing 全在 C 里
（`src/hal/pqc_accel.c` 的 `accel_shake`）。那个分工在当时是对的 —— 核更小，
SHAKE128/256 与 SHA3-256/512 共用同一个置换。代价是**每置换一次就要过一次
总线**：PS 写 200 字节状态 → 触发 → 读回 200 字节。一次 SHAKE256 吸收 32 字节
要搬 400 字节总线数据，去做 24 个周期的运算。

`hardware/rtl/keccak/sha3_core.v` 把 padding / 吸收 / 挤压整个搬进 PL。
除了省掉那些搬运，还有一条更要紧的：**中间状态不再离开密码边界**。
SHAKE 的中间状态在 ML-KEM 里就是 ρ/σ 展开的上下文，让它反复出入普通世界
可寻址的缓冲区，在真密码机里是说不过去的。

接口是**两端都带背压的字节流**：`in_valid/in_ready/in_data` 喂消息，
`in_flush` 宣告结束，`out_valid/out_ready/out_data` 按需挤压。
挤压**不设长度寄存器** —— SHAKE 的输出长度本来就是任意的，设了等于凭空
加一个上限，还多一个要校验的参数。消费方读够了停下即可。

## 两个刻意的简化

**吸收按字节做，不攒 lane。** `keccak_f1600` 的读口是组合的、写口在空闲时
接受写入，于是"读出 lane → 异或进一个字节 → 写回"整个是一条组合路径，
一个周期就能做完。攒 lane 的写法要处理"不足 8 字节的尾巴怎么对齐"，
按字节做连这个问题都不存在，pad 的位置计算也跟着消失。

**padding 只要两次读-改-写。** pad10*1 中间那串 0 异或进去是空操作，可以整个
跳过，只剩：① 当前位置异或 suffix；② `rate-1` 处异或 `0x80`。两笔顺序执行，
所以 suffix 恰好落在 `rate-1` 时（消息长 ≡ rate-1）自然合并成 `suffix^0x80`，
不需要单独判这个边角。

## 这一步踩的两个坑，都值得记下来

**坑一：`start` 只在空闲时才认，于是第二次操作永远发不动。**
挤压是没有自然终点的（SHAKE 输出长度任意，核心无从知道消费方何时读够），
所以挤完也不会自己回空闲。第一版把 `start` 写在 `S_IDLE` 分支里，结果第一次
操作之后核心永远停在 `S_SQUEEZE`。表现是**驱动写了 start 之后 `in_ready`
永远不来** —— 不报错，只挂死。现在 `start` 的语义改成"丢掉手头的一切，
从干净海绵重新开始"，从任何状态都生效。

**坑二：`kec_done` 是电平，会保持到下一次 `start`，于是判完成判到了上一次。**
进入等待状态的头一拍，`start` 才刚发出去、置换还没开始，而 `done` 上挂着的
还是**上一次**置换留下的 1，于是当场判定"已完成"，在置换进行当中就开始挤压。

这个 bug 的表现极具迷惑性：A 阵列在 24 轮里每拍都在变，挤出来的**头十几个
字节取自中间轮的状态，后面的字节等置换跑完才取、反而是对的**。于是摘要
"前面错、后面对"，看着像位序或对齐问题，其实是时序问题。而且**第一次操作
恰好是对的**（复位后 `done=0`，没有陈旧值），非要连算两次才暴露 ——
所以"连算两次"那条用例不是锦上添花，它是唯一能抓住这个 bug 的用例。

> 有意思的是 `trng_cond.v` 里早就用 `!kick_busy && kec_done` 处理过同一个坑，
> 注释也写了。同一个人隔几天在同一个置换核上又踩了一遍 —— 说明这类"电平型
> done"的接口本身就容易误用。真要根治应该让 `keccak_f1600` 直接输出 `busy`。

**还有一条是测试台自己的教训**：第一版等 `in_ready` 用的是裸 `while True`，
核心一停住，仿真就闷头跑了一千六百万个周期直到被外面杀掉，什么信息都没留下。
换成带上限的等待之后，同一个 bug 变成一条指出 `state` 的失败信息，
整套用例也从"十分钟跑不完"变成 **2.6 秒**。

# S2b 接总线：软件 PQC 真的在调硬件 SHAKE（2026-08-12，完成，未上板）

## 做了什么

S2 留下的窟窿是 `sha3_core` 是个裸核，PS 够不到它。这一步把它接进
`pqc_accel_axi`，加操作码 **10（SHAKE / SHA3）**，并让 `accel_shake()`
优先整条委托给 PL。

```
软件                          PL
accel_shake()
  └─ 模式 10 ──AXI4-Lite/Stream──▶ pqc_accel_axi
                                     └─ sha3_core（海绵）
                                          └─ keccak_f1600（置换）
  └─ 退回路径：模式 9 ─────────────▶ 同一个 keccak_f1600（走直通口）
```

`PARAM` 打包三个字段：`[7:0]` 域分隔后缀、`[15:8]` rate、`[31:16]` 输出字节数。
放 `PARAM` 而不是新加寄存器，是为了不动 `docs/register-map.md` 那张已经定死的
表 —— `PARAM` 本来就是"参数集"字段，此前没有任何硬件操作码用过它。

## 只用一个置换核

模式 9（裸置换，给对拍用）与模式 10（海绵）**共用同一个 `keccak_f1600`**。

各占一个的话，光这一块就要多花约 3500 LUT；ZU3EG 一共 70560 LUT，后面 S4 的
ML-KEM 核还要再要一个。所以给 `sha3_core` 开了一个直通口：海绵空闲时，
上层可以直接读写底下那 25 个 lane、直接踢置换。`pqc_accel_axi` 里模式 9 的
状态机因此**一行没改** —— 端口名与语义与当初直接例化 `keccak_f1600` 时完全一致。

直通口有两条纪律，都不是防御性编程：

- **非空闲时读口回 0，不透传。** `ext_rd_data` 若无条件接出置换核的读口，
  上层在挤压途中读一下就拿到了海绵的中间状态 —— 而挤压中的海绵状态在 ML-KEM
  里就是 ρ/σ 展开的上下文。这是"状态不出密码边界"这句话的实际落点，
  有一条专门的用例盯着（把条件去掉，那条用例立刻失败）。
- **`ext_start` 组合打进置换核，不多寄存一拍。** 上层判完成普遍写成"踢的那一拍
  跳过、下一拍起看 `done`"，中间多一级寄存会让上层在置换真正开始前就看到上一次
  遗留的 `done` —— 又是 S2 那个坑，只是换了个地方发作。

## 命令收尾要擦海绵

模式 10 在报 `DONE` 之前给 `sha3_core` 打一拍 `zeroize` 并**等它清完**。

这不是可选的卫生动作。挤压没有自然终点（SHAKE 的输出长度任意，核心无从知道
消费方何时读够），所以挤完最后一块海绵不会自己回空闲，也就再不肯把置换核借
出去 —— 紧接着的一条模式 9 命令会永远等不到 `DONE`。**把 `zeroize` 那一行删掉，
整套 SHAKE 用例直接挂死到超时**（试过了）。顺带把上一条消息的海绵状态清掉，
两件事一次做完。

必须等 `busy` 落下才报 `DONE`：否则软件看到 `DONE` 立刻发下一条模式 9 命令时，
海绵还在写那 25 个 0，会把刚装进去的 lane 冲掉。

## 软件侧：优先硬件，但只在"没实现"时回落

`accel_shake()` 先试模式 10；消息或输出超过 512 字节（PL 侧缓冲区尺寸），
或该 transport 回 `ERRCODE=3`（该模式没实现）时，退回原来"C 侧做 framing、
模式 9 只做置换"的路。结果逐字节相同。

**回落只认 `ERRCODE=3`。** 其他任何失败都如实向上报错 —— 一块坏了的加速器
如果每次都被软件兜住，就再也没人会发现它坏了。

**这个回落与熵源那条"绝不回落"不是一回事**，值得说清楚：SHAKE 是公开函数，
退回软件 framing 不损失任何机密性保证，损失的只是"中间状态留在 PL 里"这条纵深；
而熵源回落到软件 RNG 会直接改变安全根基。所以一个允许回落、一个宁可失败。

软件桩（`accel_stub.c`）也实现了模式 10，参数校验的边界与 `ERRCODE` 与 PL 侧
一模一样。这样"上层调模式 10"的代码在没有 PL 的机器上走的是同一条分支，
参数编码写错这类 bug 不必等板子到手才暴露。

这一步第一次把 `pqc_accel_axi` **整个顶层**做了 OOC 综合 + 布局布线
（此前 `ooc_synth.tcl` 只读 `rtl/mlkem` 与 `rtl/keccak` 两个目录，
根本读不到 `rtl/bus`，所以这个顶层从来没被综合过）。结果不好看：

| 顶层 | LUT | 占比 | WNS @100 MHz | Fmax |
|---|---|---|---|---|
| `pqc_accel_axi`（S2b 后） | 62718 | **88.89%** | **−2.492 ns（不收敛）** | 80.1 MHz |
| `pqc_accel_axi`（S2b 前） | 57799 | 81.91% | **−2.372 ns（不收敛）** | 80.8 MHz |
| `ntt_core` 单独 | 28494 | 40.38% | **−2.679 ns（不收敛）** | 78.9 MHz |
| `sha3_core` 单独 | 3932 | 5.57% | +4.873 ns | 195.0 MHz |

（器件 `xazu3eg-sfvc784-1-i`，BRAM 0，DSP 13，功耗 1.053 W）

**先把账算清楚，别把锅甩错地方。**

- **时序不收敛不是这一步造成的。** S2b 之前就是 −2.372 ns，之后 −2.492 ns，
  差 0.12 ns；而 `ntt_core` 自己单独跑就是 −2.679 ns。关键路径在 NTT 里，
  和 SHAKE 没关系 —— `sha3_core` 单独有 +4.873 ns 的余量，是全场最宽松的一块。
- **面积也主要不是这一步。** S2b 加了 4919 LUT（7 个百分点），这个数不小，
  下面单说；但基数 57799 是它接手时就有的。
- **两个大头都是同一个毛病：用寄存器阵列当存储。** `ntt_core` 的 256 个系数、
  `pqc_accel_axi` 的 128 字缓冲区都是 `reg` 数组，而且都有多个读口。
  报告里 `LUT as Memory = 0` —— **Vivado 一个都没映射成分布式 RAM**，
  全摊成了组合选择树（F7 Muxes 5434、F8 Muxes 2462）。
  `pqc_accel_axi.v` 文件头那句"映射成分布式 RAM 只占几十个 LUT"是想当然，
  实测不成立，已就地改正。

**S2b 那 4919 LUT 花在哪。** 直通口本身很便宜（`sha3_core` 从 3824 涨到 3932，
+108）。贵的是模式 10 要**按字节**读写那块 128 字的缓冲区：原来只有按字的读写口，
现在多了一套字节粒度的读口与读-改-写口，而缓冲区是寄存器阵列 —— 每加一个口，
选择树就整套复制一遍。同样的账，换成真 BRAM 就是加一个读口的事。

**结论：S3 的范围要扩。** 原计划只是"NTT 核改 BRAM 存储版"，现在看
`pqc_accel_axi` 的数据缓冲区得一起改成同步读的单口 BRAM 结构 ——
它自己就占了约 30000 LUT，比 NTT 核还多。这两处一起换掉之前，
**整颗片子塞不进 S4 的 ML-KEM 核**（S1 的 TRNG 另占约 6%）。

这个数字是这一步最有价值的产出：它不是"跑通了"，是"跑通了但按现在的写法
装不下"，而且指明了下一步该动哪里。若不是把顶层真的综合一遍，
这件事会一直拖到 S4 拼装的时候才炸。

# S3 换成 BRAM：整个加速器从 88.89% 的 LUT 掉到 6.76%（2026-08-12，完成，未上板）

## 做了什么

S2b 的综合报告指出两处"用寄存器阵列当存储"的写法吃掉了大半颗片子。这一步
把它们都换成真双口块 RAM：

- 新增 `hardware/rtl/common/ram_dp.v` —— 按 UG901 的推断模板写的参数化 TDP
  同步 RAM（两个口各一个 `always`、各自 `dout <= mem[addr]`、读优先、**不带复位**）。
- `hardware/rtl/mlkem/ntt_core.v` 的 256×16 系数存储换成一块 `ram_dp`。
  组合读没了，一个蝶形从 1 拍变 2 拍：`S_RD` 发地址、`S_WB` 拿数算完写回；
  缩放同样拆成 `S_SC_RD` / `S_SC_WB`。一次变换从约 1160 cycles 变成 2305 cycles。
- `hardware/rtl/bus/pqc_accel_axi.v` 的 128×32 数据缓冲区换成一块 `ram_dp`：
  A 口分时给输入流写入 / 装载读出 / 结果写回，B 口专给输出流读。

## 三处时序要跟着改，每一处都不是形式上的

**1. 读地址要提前几拍，要数清楚。** `ntt_core` 的读口现在是同步读，
而 `pqc_accel_axi` 给它的地址本身还过了一级寄存器，所以 `S_STORE` 里
地址要**提前两拍**（`ntt_rd_addr <= cnt + 2`），并且在进 `S_STORE` 之前
插一个 `S_NTT_PRE` 把第 0 个地址先发出去。缓冲区那边地址只过一级 BRAM，
提前一拍即可（`S_LOAD_PRE` + `bufa_addr = cnt+1`）。
第一版按"提前一拍"写，`test_ntt_datapath` 当场挂 —— 这种差一拍的错
靠肉眼看不出来，只能让测试说话。

**2. 输出流要"读超前一拍"。** `m_axis_tdata` 原来是 `bufmem[rd_ptr]` 的组合读。
换成 BRAM 之后 B 口的地址给的是 **下一拍的** `rd_ptr`（没握手时就等于当前值），
这样本拍 `bufb_dout` 恰好是本拍 `rd_ptr` 指的那个字。这是 BRAM 做 FIFO 读口的
标准写法；写成 `rd_ptr` 会让 15 个用例里挂掉 8 个（试过）。

**3. 模式 10 的挤压不能再"按字节读-改-写"。** BRAM 没法同一拍读了再写回同一个字。
改成字节攒进 `sq_acc`、凑满 4 个（或到输出末尾）才整字写回，读口直接消失 ——
而这条按字节的读口正是 S2b 多花 4919 LUT 的主因。
顺带一个好副作用：最后那个不满 4 字节的字，多出来的字节现在是 0，
而不是残留的**输入消息字节**。

## 一条被测试盖住的隐患，补了用例

去掉 `S_LOAD_PRE` 之后 16 个用例**全部照过**。原因是正常收包时输入流的写指针
在 TLAST 之后归零，于是 `S_IDLE` 里摆在 A 口地址上的 `wr_ptr` 恰好是 0，
装载第一个字碰巧读对了 —— 正确性依赖了一个"碰巧"。

一旦软件漏发 TLAST（传输被截断、DMA 描述符写错），写指针停在包尾，
第一个字就会读错，而命令照样报 DONE、不报错。给密码加速器留这种失效模式不行。
补了 `test_load_start_is_independent_of_write_pointer`：不带 TLAST 送完 50 个字
再发命令，结果必须与带 TLAST 时逐字节相同。用变异验证过 —— 去掉 `S_LOAD_PRE`
时**只有这一条**失败。

## 综合结果（`xazu3eg-sfvc784-1-i`，OOC，含布局布线）

| 顶层 | LUT | 占比 | 寄存器 | BRAM | DSP | WNS @100 MHz | 功耗 |
|---|---|---|---|---|---|---|---|
| `ntt_core`（S3 后） | **258** | **0.37%** | 55 | 0.5 | 13 | **+0.077 ns（收敛）** | 0.236 W |
| `ntt_core`（S3 前） | 28494 | 40.38% | — | 0 | 13 | −2.679 ns | — |
| `pqc_accel_axi`（S3 后） | **4768** | **6.76%** | 2188 | 1.5 | 13 | **−0.047 ns** | 0.297 W |
| `pqc_accel_axi`（S3 前） | 62718 | 88.89% | 10736 | 0 | 13 | −2.492 ns | 1.053 W |

`ntt_core` 少了 **110 倍**的 LUT，整个加速器顶层少了 **13 倍**，功耗掉到三分之一。
`LUT as Memory` 仍然是 0，但这次是对的：存储全在 `RAMB18E2` / `RAMB36E2` 里
（映射报告确认 `u_mem/mem_reg` 是 `256 x 16 (READ_FIRST)` 双口）。

**S4 的空间到手了。** 之前是"整颗片子塞不进 ML-KEM 核"，现在加速器顶层只占 6.76%，
加上 S1 的 TRNG 约 6%，还有八成多的 LUT 和 214 片 BRAM 留给 S4。

## 时序还差 0.047 ns，说清楚差在哪

`pqc_accel_axi` 的 WNS 是 **−0.047 ns**（6190 条路径里 2 条不过），
折算 Fmax 99.5 MHz。关键路径不在存储，在蝶形的乘法链：

```
u_ntt/u_mem BRAM B 口输出 → LUT2 → DSP × 3 级（zeta 乘、Montgomery 归约的两次乘）
→ CARRY8 → BRAM A 口输入        共 22 级逻辑，9.693 ns
```

其中 BRAM 的 clk→out 就占了 0.998 ns。两条可行的修法：

1. 打开 BRAM 的可选输出寄存器（`DO_REG=1`）—— Vivado 自己在综合日志里提示了。
   clk→out 降到 0.4 ns 上下，够收敛，代价是读延迟再加一拍，
   前面那三处"提前几拍"的算法要跟着全改一遍。
2. 在蝶形内部插一级流水，把三级串起来的 DSP 乘法拆开。代价是
   `butterfly_ct` / `butterfly_gs` 要带时钟，它们现在是纯组合模块、
   有独立的 cocotb 组合用例。

**这一步没做，是有意的。** 本项目的目标是原型验证，99.5 MHz 与 100 MHz
对"能不能放进去"没有区别；而 S4 把 ML-KEM 状态机拼进来时这块一定要重新做时序，
现在为 0.047 ns 去动一个刚验证完的数据通路不划算。
真要跑满 100 MHz 时按上面第 1 条改，工作量是确定的。

## 验证

- cocotb：`ntt_core` 5 个用例、`pqc_accel_axi` **16** 个用例（新增 1 个），全通。
- C 侧：`ctest -R accel` 两个用例全通 —— 软件桩、Verilator 后端、OpenSSL 三方逐字节一致。
- 变异验证两处：把输出流的"读超前一拍"改回 `rd_ptr`（16 挂 8），
  去掉 `S_LOAD_PRE`（只挂新加的那一条）。
- 全量 `ctest`：46 个里 6 个 `kat_*` 失败，与本步无关 ——
  它们要 `vectors/` 下的向量文件（未入库，`tools/fetch_vectors.sh` 拉取），
  改动前后一样红。

# S3b：把剩下的寄存器阵列扫干净

S3 只动了 `ntt_core` 和加速器顶层的缓冲区。`tools/rtl_synth_check.sh` 的
"摊成寄存器"清单里还剩几条，这一步逐条过了一遍 —— **该换的换，不该换的
把理由写进脚本**，免得下一个人再追一遍。

## 该换的三块

| 模块 | 存储 | 原来的读口 | 改法 |
|---|---|---|---|
| `mldsa_ntt_core` | 256 × 32 bit | 组合，且蝶形一拍读两个 | `ram_dp`，蝶形拆 `S_RD`/`S_WB` 两拍 |
| `mlkem_rej_uniform` | 256 × 12 bit | 组合读 + **两个写口** | `ram_dp`，A 口写候选 1、B 口写候选 2 |
| `mldsa_rej_uniform_buf` | 256 × 23 bit | 组合读，单写 | `ram_dp`，B 口常年挂读地址 |

`mlkem_rej_uniform` 那块值得单说：它一拍最多收下**两个**候选（`mlkem_rej_pair`
从 3 个字节里取两个 12 位数），所以原来是两个写口加一个读口的寄存器阵列 ——
真双口 BRAM 正好对得上。A 口写第一个候选（地址 `count`），B 口写第二个
（地址 `slot2 = count + take1`）。两个槽位恒差 1，永远不同址，不会踩到
`ram_dp` 那条"两口同写一址"的断言。收集结束（`!busy`）之后 B 口改接外部读口。

## 综合结果（`xazu3eg-sfvc784-1-i`，OOC，含布局布线）

| 设计 | CLB LUT | 占比 | 寄存器 | BRAM | DSP | WNS | Fmax |
|---|---|---|---|---|---|---|---|
| `mldsa_ntt_core`（S3b 后） | **1027** | **1.46%** | 57 | 1 | 20 | −2.525 ns | 79.8 MHz |
| `mldsa_ntt_core`（S3b 前） | 56602 | 80.22% | 8552 | 0 | 20 | −6.149 ns | 61.9 MHz |
| `mldsa_rej_uniform_buf`（S3b 后） | **18** | **0.03%** | 11 | 0.5 | 0 | +8.363 ns | 610.9 MHz |
| `mldsa_rej_uniform_buf`（S3b 前） | 1860 | 2.64% | 5904 | 0 | 0 | — | — |

**55 倍。** 一个 ML-DSA 的 NTT 核原来要吃掉 80% 的片子 —— 也就是说
S2 那版 RTL 里，ML-KEM 和 ML-DSA 的 NTT 核**放不进同一颗 ZU3EG**。
现在两个加起来占 1.8%。

采样缓冲那一条更干净：**LUT 从 1860 到 18（103 倍），寄存器从 5904 到 11
（537 倍）**，代价是半块 RAMB18。5904 = 256 × 23 + 16 —— 那 5888 个触发器
就是逐字摊开的多项式缓冲，1860 个 LUT 是给它配的读出多路选择树。
换成 `ram_dp` 之后两样都没了。

## 这里要如实说一句：`mldsa_ntt_core` 仍然不满足 100 MHz

WNS −2.525 ns，折算 79.8 MHz。原因和 ML-KEM 侧那条路径同源，只是更严重：
ML-DSA 的模数是 23 位、系数按 32 位承载，Montgomery 归约里那两次乘法都是
32×32，串在一条组合路径上比 ML-KEM 的 16 位版长得多。

**为什么现在不修**：`mldsa_ntt_core` 目前**没有被 `pqc_accel_axi` 例化** ——
加速器顶层只走 ML-KEM 的 NTT。它是为将来的 ML-DSA 通路准备的独立模块，
接进总线的那一天必然要重新做时序（多半是在蝶形里插一到两级流水）。
现在为它单独改一遍数据通路，等接总线时还要再改一遍。
**它现在的作用是证明"面积放得下"，这一点已经成立了。**

## 故意不换的两块

这两条会一直留在 `rtl_synth_check.sh` 的清单里，脚本现在会把它们标成
"预期之内"：

- **`keccak_f1600` 的 `A`**：1600 bit 的置换状态，一轮里 25 条 lane 要同时读、
  同时写。BRAM 只有两个口，装不下这种全并行访问 —— 它本来就该是触发器。
  同一份清单里的 `B`/`C`/`D`/`Ath`/`Anext` 是轮内的组合中间量，Yosys 把数组
  一律当 memory 报，综合出来是纯组合线网，不占存储。
- **`sync_fifo` 的 `mem`**：只有 TRNG 一个实例，32 bit × `FIFO_DEPTH`，
  一共 1 Kbit 上下。更要紧的是它是 **FWFT（首字直通）**：`rd_valid` 拉高的
  同一拍 `rd_data` 就得有效，因为 AXI4-Lite 要在同一次读事务里返回数据。
  换成同步读的 BRAM 就得加一拍，那要连着动 `trng_top` 和 AXI 读通路 ——
  为 1 Kbit 付这个代价不划算。

判断标准写在 `hardware/rtl/common/ram_dp.v` 的注释里：**组合读的存储永远
变不成 BRAM**，但"该不该是 BRAM"要看访问模式和位宽，不是看它长得像数组。

## 验证

cocotb 113 个用例全通（`mldsa_ntt_core` 5 个、`mlkem_rej_uniform` 2 个、
`mldsa_rej_uniform_buf` 1 个都在里面，三处读口的一拍延迟由测试台补上升沿覆盖）。

# S4：完整的 ML-KEM 密钥生成核（纯 RTL）

S1 到 S3 放进 PL 的都是**算子**：TRNG、Keccak/SHA-3 海绵、NTT、基乘、压缩、
两种采样、12 位编解码。密钥生成的**编排**——谁先谁后、ρ/σ 怎么展开、矩阵怎么
累加、字节怎么打包——一直还在普通世界的 C 里。

S4 把编排也搬进去。现在的接口是：

```
普通世界  →  d（32 字节）、z（32 字节）、param_set
普通世界  ←  ek、dk 两串字节
```

**中间的 ŝ、ê、Â、σ 一个都不出芯片。** 这是"密钥不出边界"那句话第一次
在这个项目里有了硬件形态 —— 私钥的每一个中间量都只在 PL 的 BRAM 里存在过，
普通世界的地址空间里从来没有它们。

## 数据通路

```
d‖k ──SHA3-512(G)──→ ρ ‖ σ
                      │
  σ‖N ──SHAKE256──→ CBD ──→ NTT ──→ ŝ[0..k-1]（槽 0..3）
                                    ê[0..k-1]（槽 4..7）
  ρ‖j‖i ──SHAKE128──→ 拒绝采样 ──→ Â[i][j]
                                    │
                        Â[i][j] ∘ ŝ[j] 累加 ──→ t̂[i]（槽 8..11）
                                    │
                        × f、加 ê[i]、barrett
                                    │
              ByteEncode12 ──→ ek = t̂‖ρ ──→ SHA3-256 ──→ H(ek)
                          ──→ dk = ŝ‖ek‖H(ek)‖z
```

多项式存储是一块 16 槽 × 256 系数 × 16 bit 的真双口 BRAM（64 Kbit，约 2 块
RAMB36）。`param_set` 在**运行时**选 512 / 768 / 1024，三套共用同一份数据通路 ——
为三个参数集各综合一份，在真密码机里是说不通的：同一块板要同时支持多套参数。

## 一个 sha3_core 走完全程

G（SHA3-512）、PRF（SHAKE256）、XOF（SHAKE128）、H（SHA3-256）四种用法在时间上
互不重叠，共用同一个海绵核。四种只差 `rate` 和 `suffix` 两个字节，`start`
那一拍锁存即可。多例化一个置换核要 ~7000 LUT，这颗片子上不划算。

代价是每换一种用法要单独走一个 start 状态 —— 状态机因此多了四个状态，
但这是显式的、看得见的。

## 三处值得记下来的地方

**① 累加为什么可以每一步都 barrett。** 参考实现是把 k 个基乘全加完再 barrett
一次，这里是每加一个就 barrett。两者**逐系数完全相同**：`barrett_reduce` 给的是
同余类里唯一的代表元，同余 ⇒ 输出相同。好处是累加器恒定在 ±1664，加上一个基乘
输出（范围 (−q, q)）也就 ±4993，稳稳落在 16 位有符号里 —— 不必为 k=4 的最坏
情况把累加器加宽。

**② `Â[i][j]` 的 XOF 头是 ρ‖j‖i，j 在前。** 写成 ρ‖i‖j 照样能跑出合法的
多项式、合法的 ek/dk，只是不是 ML-KEM 的那一个。这类错误不会崩、不会越界，
只会让密钥对不上 —— 所以对拍必须锚在外部向量上，见下面的验证一节。

**③ `out_valid` 必须带上"H 的海绵收不收得下"这个条件。** ek 那两段字节要同时
交给下游和 H 的海绵，而海绵每吸满 136 字节要停 24 拍做置换。第一版把这个条件
只写进了内部的推进条件、`out_valid` 一直挂着 —— AXI4-Stream 的规矩是 valid 与
ready 同时为高就必须完成一次传输，于是下游把同一个字节收了好几遍。
**实测多出 233 字节**（≈9 次置换 × 26 拍），正好对上 1184 字节的 ek 要过
8.7 次置换。这个 bug 在"只看最终字节是否相等"的测试里表现为长度不对，
定位很快；但如果输出没接背压、下游又恰好每拍都 ready，它可以一直藏着。

## 验证：锚在 ACVP 向量上，分两层查

黄金模型是 `hardware/model/mlkem_oracle.py` 的 `mlkem_keygen` —— 那份实现是拿
**NIST ACVP 向量**验过的（`oracle_d`），所以这里的比对不是"自己和自己比"。

- **第一层，中间量**：ŝ、ê、t̂ 逐系数比对。这三个量都在多项式存储里，
  `DEBUG_BANK=1` 时把存储读口引出来看。有这一层是因为 ek/dk 一旦对不上，
  光看三千多个字节完全定位不到是哪一步错的。
- **第二层，最终字节**：三个参数集的 `ek‖dk` 全部逐字节一致。
  512 是 1632 字节、768 是 3584、1024 是 6208。

> ⚠️ `DEBUG_BANK` 是**仿真专用参数，综合时必须是 0**。那个口直连私钥系数，
> 引出来等于在密码边界上开一个洞。综合脚本不传这个参数，默认就是 0。

**变异验证**：把 XOF 头改成 ρ‖i‖j（矩阵转置），`t̂[0]` 那一条立刻挂 ——
说明中间量那一层不是摆设，它在最终字节之前就把错误拦下来了。

**背压用例与常规用例走同一段采样代码**。写成两段的话，"背压下也一致"验证的
就只是两段测试代码碰巧写法不同，而不是 RTL 的行为。

cocotb 全量 **117 个用例**（新增 4 个）全通。

## 综合结果（`xazu3eg-sfvc784-1-i`，OOC，含布局布线）

| `mlkem_keygen` | **6032** | **8.55%** | 3327 | 3 (1.39%) | 29 (8.06%) | 0.245 W | **+0.420 ns** | **104.4 MHz** |
| `mlkem_cbd_stream` | 143 | 0.20% | 75 | 0 | 0 | 0.222 W | +8.167 ns | 545.6 MHz |

一个**完整的 ML-KEM 密钥生成**（三个参数集运行时可选，自带 Keccak 海绵）
占这颗片子 **8.55% 的 LUT、1.4% 的 BRAM、8% 的 DSP**，四分之一瓦。
片子还剩九成，后面的 Encaps/Decaps、对称核、密钥仓都还有地方。

慢，但这是原型验证要的东西：**能实现、放得下、跑得到时钟**。

## 时序：第一版差了 10.7 ns，切两刀就过了

第一版 `mlkem_keygen` 的 **WNS 是 −10.722 ns（48.3 MHz）** —— 差一倍还多，
不是四舍五入的事。布线报告给的关键路径起点是 `b1_r_reg[6]/Q`，
经 `u_bm/smul_return`（DSP48E2_X2Y11）→ `u_bm/u_a1b1/m`（DSP48E2_X2Y10）→
后面还串着几级 DSP —— **整条路径都在基乘里**。

数一下就明白了。`mont_reduce` 内部本身是两次乘法（`m = a·QINV`、`m·Q`），
所以 r0 这条路上串着：

```
smul(a1,b1) → mont ×2 → smul(·,ζ) → mont ×2   = 6 级
                                    ↓ 状态机里还接着
                              barrett          = 2 级
                                                 ─────
                                                 8 级串行乘法
```

一级 DSP 乘加在这颗片子上约 2.4 ns，8 级就是 19 ns 出头 —— 和实测的
20.7 ns 对得上。**问题不在综合工具，在数据通路本身写得太深。**

切两刀，把 8 级分成 3 + 3 + 2：

1. 在 `t_a1b1` 处切开 `mlkem_basemul`，拆成 `_head`（a1·b1 那一次 fqmul）
   和 `_tail`（其余四次 + 两个加法）。四次 fqmul 之间互相独立，深度仍是 3 级。
2. 在 `barrett_reduce` 之前再切一刀。

`tomont`（`acc0 × 2³² mod q` 再加 ê 再 barrett）是同一个毛病的小号版本，
3 + 2 = 5 级，同样在中间打一拍。

**组合版 `mlkem_basemul` 保留**，由 `_head` + `_tail` 直接拼出来，接口和原有
的 cocotb 用例一个字没动 —— 这样"基乘"这段数学**仍然只有一份实现**，
和 `mont_reduce` 的规矩一致。要流水的核例化两半自己插寄存器，
不需要流水的（和读代码的人）看组合版。

代价与收益：

| | 第一版 | 切完 |
|---|---|---|
| 每对系数 | 5 拍 | 7 拍 |
| `tomont` 每系数 | 3 拍 | 4 拍 |
| LUT | 5883 | 6032（+149） |
| 寄存器 | 3274 | 3327（+53） |
| WNS | **−10.722 ns** | **+0.420 ns** |
| Fmax | 48.3 MHz | **104.4 MHz** |

多花 149 个 LUT、慢三成拍数，换 100 MHz 收敛。

**新的关键路径不在基乘了**：`u_ntt/u_mem`（NTT 的系数存储）出来经 22 级逻辑、
其中 3 组 DSP 乘加，9.205 ns 回到同一块 BRAM 的 DIN —— 也就是 NTT 蝶形本身。
它只剩 0.42 ns 余量，接总线、加时钟树之后大概率还要再动一次。
这一点先记在这里，等 Encaps/Decaps 接进来一起看。

# S4b：完整的 ML-KEM 封装核（纯 RTL，2026-08-12，完成，未上板）

KeyGen 之后把 Encaps 也做成纯 RTL。接口：

```
普通世界  →  ek（384k+32 字节，字节流）、m（32 字节）、param_set
普通世界  ←  K（32 字节）‖ c（768/1088/1568 字节），一条字节流
```

**r̂、e₁、e₂、Â、以及 G 出来的那半截随机种子，一个都不出芯片。**
共享密钥 K 是唯一出去的秘密，而它本来就要交给上层。

## 数据通路

```
ek ──┬─→ ByteDecode12 ──→ t̂[0..k-1]（槽 8..11）
     └─→ SHA3-256(H) ──→ H(ek)
                          │
m ‖ H(ek) ──SHA3-512(G)──→ K ‖ r
                                │
  r‖N ──SHAKE256──→ CBD_η1 ──→ NTT ──→ r̂[0..k-1]（槽 0..3）
  r‖N ──SHAKE256──→ CBD_2  ─────────→ e₁[0..k-1]（槽 4..7）
                                       e₂        （槽 12）
  ρ‖i‖j ──SHAKE128──→ 拒绝采样 ──→ Â[i][j]
                                       │
             Â[i][j] ∘ r̂[j] 累加 → 逆 NTT → + e₁[i] → Compress_du → c₁
             t̂[i]   ∘ r̂[i] 累加 → 逆 NTT → + e₂ + Decompress₁(m) → Compress_dv → c₂
```

槽位分配与 KeyGen 一致（16 槽 × 256 × 16 bit 的同一块双口 BRAM），
只是住的东西换了：0..3 是 r̂、4..7 是 e₁、8..11 是从 ek 解出来的 t̂、12 是 e₂。

## 三处取舍

**① `du`/`dv` 做成运行时输入，不是 parameter。** 512/768 用 du=10 dv=4，
1024 用 du=11 dv=5。同一块板要同时支持三套参数集，所以新写的 `mlkem_bitpack`
的 `d` 是**端口**而不是参数。代价是移位量变成变量 —— 但累加器只有 20 位，
变量移位综合出来是几十个 LUT，比"为三个参数集各例化一份打包器"便宜得多。

顺带一提，`mlkem_bitpack` **不需要 flush**：ML-KEM 每个多项式 256 个系数，
256·d 比特 = 32d 字节，**总是整字节**，比特累加器跑完一个多项式必然回到空。

**② 累加器借 `ntt_core` 的存储，不另开 BRAM。** t̂ᵀr̂ 的中间和要占一整个
多项式。MAC 阶段 `ntt_core` 本来就闲着，于是让累加直接写进它的系数存储，
算完原地做逆 NTT —— 既省一块 BRAM，也省掉一次 256 系数的搬运。
代价是 MAC 阶段要同时用到四个读口：`ntt_core` 存储（累加器）、bank 的 A 口
（t̂）、bank 的 B 口（r̂）、拒绝采样缓冲（Â）。四个口刚好够，没有冲突。

**③ XOF 头是 ρ‖i‖j，i 在前 —— 与 KeyGen 正好相反。** Encaps 要的是 **A 的
转置**（û = Aᵀr̂）。写反了照样跑出合法的密文，只是解不开。和 KeyGen 那处
一样，这类错误必须靠外部向量才看得见。

## 两个位宽陷阱

都是在写完之后靠算数发现的，不是靠测试：

**`tbytes` = 384k。** 384 = 256 + 128，是**两项**移位和。第一版写成四项
（128+64+32+16 = 240），于是 ek 只吃进 k·240+32 字节就卡死 —— 768 是 752
字节、512 是 512 字节，数字精确对得上，一看就知道是常数拆错了。

**`se_n` 要数到 2k。** k=4 时 2k = 8，三位装不下会绕回 0，ML-KEM-1024 的
e₂ 永远采不到。这与 KeyGen 里 `se_n` 那个溢出是**同一类**错误 ——
在这份代码里，"某个计数器的上界随 k 变"是最容易写窄的地方。

## 验证：同样锚在 ACVP 向量上，分两层查

黄金模型是 `mlkem_oracle.py` 的 `mlkem_encaps`，拿 NIST ACVP 的 encapDecap
向量验过（`oracle_e`）。

- **第一层，中间量**：r̂、e₁、e₂，以及从 ek 解出来的 t̂，逐系数比对。
- **第二层，最终字节**：三个参数集的 `K‖c` 全部逐字节一致
  （512 是 32+768、768 是 32+1088、1024 是 32+1568 字节）。

**背压用例与常规用例走同一段采样代码**。ek 那一路三拍给两拍、密文那一路
五拍收两拍，两头的停顿再叠上海绵每 136 字节停 24 拍 —— 512 从 26777 拍变
28329 拍（**+5.8%**），输出逐字节不变。

> ⚠️ `DEBUG_BANK` 同样是**仿真专用，综合时必须是 0**。那个口直连 r̂，
> 引出来等于在密码边界上开一个洞。综合脚本不传，默认就是 0。

cocotb 全量 **122 个用例**（新增 3 个）全通。

## 综合结果（`xazu3eg-sfvc784-1-i`，OOC，含布局布线）

| 设计 | CLB LUT | 占比 | 寄存器 | BRAM | DSP | 功耗 | WNS | Fmax |
|---|---|---|---|---|---|---|---|---|
| `mlkem_encaps` | **5388** | **7.64%** | 3315 | 3 (1.39%) | 40 (11.11%) | 0.257 W | **+0.068 ns** | **100.7 MHz** |
| `mlkem_keygen` | 6032 | 8.55% | 3327 | 3 (1.39%) | 29 (8.06%) | 0.245 W | +0.420 ns | 104.4 MHz |

Encaps 比 KeyGen **还小一点**（LUT 少 11%），但 DSP 多了 11 个 ——
多出来的是四个 `mlkem_compress`（du/dv 各两种）和输出那条 barrett，
而省下的是 KeyGen 的 `tomont` 与 `encode12` 那一整套打包。

两个核加起来占这颗片子约 **16% 的 LUT、2.8% 的 BRAM、19% 的 DSP**，半瓦。
按现在的速度，Decaps（要复用 Encaps 的数据通路做重加密）之后大概三成，
密钥仓与总线边界还有地方。

## 时序：输出那条尾巴要切一刀

第一版布线后 **WNS = −1.987 ns（83.4 MHz）**。关键路径是整条输出尾巴挤在一拍：

```
bank BRAM 读出 ──→ barrett_reduce ──→ mlkem_compress ──→ 打包器累加器
                    (2 级 DSP)        (1 级 DSP)         (LUT)
     1.14 ns          ~5.4 ns           ~2.5 ns          ~1.5 ns     = 11.924 ns
```

数一下就明白：`barrett_reduce` 内部是两次乘法（`v·a >> 26`、`a − t·q`），
`mlkem_compress` 又是一次（乘 `⌈2³³/q⌉` 再移位），**三级 DSP 串在一起**，
前面还挂着一次同步存储读出。这跟 S4 里基乘那条路是同一类问题，
只是这次串的是"约减 + 压缩"而不是五次 Montgomery 乘。

切在 barrett 与 compress 之间（`outc_r`），两边正好各剩一半：

| | 第一版 | 切完 |
|---|---|---|
| 每系数拍数 | 2（RD→FEED） | 3（RD→CMP→FEED） |
| ML-KEM-768 总拍数 | 41 654 | 42 489（+2.0%） |
| LUT | 5372 | 5388（+16） |
| 寄存器 | 3313 | 3315（+2） |
| WNS | **−1.987 ns** | **+0.068 ns** |
| Fmax | 83.4 MHz | **100.7 MHz** |

**十六个 LUT、两个寄存器、2% 的拍数，换 17 MHz。** 这一刀便宜得没有争议 ——
之所以第一版没切，是因为写的时候把"读存储 → 算 → 打包"当成了一件事，
而它在硅上是三件事。

**新的关键路径又回到了 NTT 蝶形**：`u_ntt/u_mem` 出来经 22 级逻辑、
其中 3 组 DSP 乘加，9.578 ns 回到同一块 BRAM 的 DIN。
与 S4 里 KeyGen 收完时序之后的关键路径是同一条 —— 也就是说，
**ML-KEM 数据通路的时序天花板现在由 `ntt_core` 的蝶形决定**，
余量只有 0.068 ns。后面接总线、加时钟树，这条路一定要再动一次；
届时该改的是 `ntt_core` 本身，而不是每个调用它的核各切各的。

# S4c：完整的 ML-KEM 解封装核（纯 RTL，2026-08-12，完成，未上板）

至此 ML-KEM 的三个操作全部是纯 RTL。接口：

```
普通世界  →  dk（768k+96 字节，字节流）、c（32(du·k+dv) 字节，字节流）、param_set
普通世界  ←  K（32 字节）
```

**ŝ、m′、以及重加密出来的 c′，一个都不出芯片。** 出去的只有 K。

## 重加密直接例化封装核 —— 这不是取巧，是标准的定义本身

FIPS 203 的 `Decaps_internal` 第 3~5 步是

```
(K′, r′) = G(m′ ‖ h)          c′ = K-PKE.Encrypt(ek, m′, r′)
```

而 `Encaps_internal(ek, m′)` 第 1~2 步是

```
(K,  r)  = G(m′ ‖ H(ek))      c  = K-PKE.Encrypt(ek, m′, r)
```

只要 `h == H(ek)`（合法 dk 的定义），两者**逐比特相同**。所以"重加密"就是
原样跑一遍 `mlkem_encaps`。再写一份 Encrypt 的唯一效果，是多出一个能和
Encaps 各错各的地方 —— 而这类错误不会崩，只会让密钥对不上。

代价是 decaps 里有两个 `sha3_core`、两个 `ntt_core`（一个在解密前端、一个在
封装核里）。它们在时间上不重叠，理论上可以共享，但共享要加仲裁，而这颗片子
的 LUT 还剩八成 —— **共用的是源码，不是硅上那块逻辑**，这个取舍在原型阶段
明显划算。

### 顺带做了 FIPS 203 §7.3 的 dk 自洽性检查

标准里 G 的第二个输入取自 dk 里存的 `h`；本核取的是**从 ek 重新算出来的
H(ek)**（因为它在封装核内部）。对任何合法 dk 这两者相等，不等则说明 dk 自身
不自洽 —— 而标准本来就要求解封装前做这项检查。本核顺手做了，结果由
`dk_hash_ok` 给出。**这里比照字面实现更严，不是更松**：字面实现直接信 dk 里
的 h。

## 常量时间：本模块唯一不能妥协的地方

密文比对一旦提前退出，就能从"解封装用了多久"读出 c′ 与 c 从第几个字节开始
不同 —— 而 c′ 是攻击者送进来的 c 解密再加密的结果，这条时序信道足以逐字节
恢复明文。这是 Fujisaki-Okamoto 变换里最经典的一个坑。

RTL 里的四条做法：

- `cmp_diff` 只做**累积或**，状态机的任何跳转都不看它；
- 比对固定跑满 `clen` 个字节，**没有任何 early-out 分支**；
- J(z‖c) = SHAKE256(z‖c, 32) **无条件先算好**，不是"发现不同了才去算"；
- 最后用位掩码在 K′ 与 J(z‖c) 之间选，不是 `if`。

`test_decaps_constant_time` 直接测这条性质：同一个 dk 下，正常密文、首字节被
改、末字节被改，三次拍数必须完全相同。

**这条用例验过它会咬人。** 把比对改成"一发现不同就跳出"（只改这一处，功能
仍然全对），六个用例里**只有它**挂，报出：

```
拍数随密文内容变了：正常 43578、首字节改 31324、末字节改 43578 —— 密文比对提前退出了
```

28% 的拍数差 —— 一条功能测试永远看不见、而它一眼就看见的信道。

> 同一个 param_set 下换一把密钥，拍数会差约 0.1%。那来自封装里矩阵 A 的
> 拒绝采样，只取决于**公开的** ek，与密文和私钥都无关。

## 三处取舍

**① c 先整条缓冲，再按自己的节奏解包。** c 那一路要同时喂三个去处（J 的海绵、
c 缓冲、位解包器），而位解包的下游还要停下来跑 NTT。三者的背压耦在一起会让
`c_ready` 的条件变成一团。多花 1568 拍换一个说得清的时序，值。

**② 累加器放多项式存储、û 留在 NTT 核里 —— 与 Encaps 正好相反。** 这里基乘的
a 取自 ŝ（多项式存储 A 口）、b 取自刚变换完的 û（NTT 核存储），让 û 留在原地
省一趟搬运；累加值就只能放多项式存储的 B 口。Encaps 那边 a/b 都在多项式存储
里，所以累加值反过来放 NTT 核。**两边的"谁放哪"都是被"三个独立读口"这一条
逼出来的**，不是随手安排。

**③ `w = v − su` 拆成三级流水。** decompress 一次乘法、barrett 两次、
compress₁ 又一次 —— 四级 DSP 串一拍在这颗片子上跑不到 100 MHz。Encaps 的输出
尾巴就是这么栽的（S4b）。

## 一个位宽陷阱

ek 回放给封装核时，`ekpos` 清零那一拍同步读还没跟上，第一个字节会读到上一次
停在读口上的值（地址还停在 `eklen`）。表现很有迷惑性：**ŝ 解码对、J(z‖c) 对、
三个"改密文"用例全过，只有"正常密文"用例挂** —— 因为 H(ek) 错了以后
K′ 与 c′ 全错，每一次都走隐式拒绝。`ekb_wait` 起手置 1 补这一拍。

## 验证

黄金模型是 `mlkem_oracle.py` 的 `mlkem_decaps`，拿 NIST ACVP 的 encapDecap
向量验过（`oracle_f`）。六个用例分三类：

- **正常密文**：ŝ 逐系数比对 + K 逐字节等于封装时的 K（三个参数集）。
- **被改过的密文**：K 必须逐字节等于黄金模型的 J(z‖c)。只验"不等于正确的 K"
  是不够的 —— 拒绝值写成全零、写成常量、或者错用了 z‖c 之外的输入，都能让
  "不等于正确值"成立。改动位置取首、中、末三处：只改第一个字节的话，
  "比到第一个不同就停"的实现照样能过。
- **拍数与密文内容无关**（见上）。

另有 dk 哈希自检用例（把 dk 里的 h 改一个比特，`dk_hash_ok` 必须掉下来）
和背压用例。

cocotb 全量 **128 个用例**（新增 6 个）全通；C 侧 46 个 ctest 也全通。

# S4d：把时序天花板从三个核里搬到一处 —— `ntt_core` 的蝶形流水

## 症状：每个核都在同一条路上碰壁

三个核收时序的过程连起来看很清楚：

| 核 | 第一版 WNS | 关键路径 | 怎么修的 |
|---|---|---|---|
| `mlkem_keygen`（S4） | −10.722 ns | 基乘：8 级 DSP 串一拍 | 把 `mlkem_basemul` 切成 `_head`/`_tail` |
| `mlkem_encaps`（S4b） | −1.987 ns | 输出尾巴：barrett + compress + 打包 | 在 barrett 与 compress 之间加一级寄存器 |
| `mlkem_decaps`（S4c） | −0.127 ns | **`u_enc/u_ntt/u_mem` 的自环** | 见下 |

前两次修完，关键路径**都**落到了同一个地方：`ntt_core` 的蝶形。
S4b 那一节末尾已经写下这句话 ——

> ML-KEM 数据通路的时序天花板现在由 `ntt_core` 的蝶形决定，余量 0.068 ns。
> 接总线之后要动的是 `ntt_core` 本身，不是每个核各切各的。

Decaps 就是那个"接下来"。它单独综合 98.7 MHz，差的不是逻辑深度变了，而是
设计变大以后布线更挤：同一条路在 Encaps 里是 +0.068 ns，在 Decaps 里是
−0.127 ns，**0.195 ns 全是绕线**。这种余量撑不到接总线、加密钥仓那一步。

## 修法：切在乘积之后、Montgomery 归约之前

蝶形这条路是

```
BRAM 读出 → 一次乘法（ζ·b）→ mont_reduce（内部 m=a·QINV、m·Q 两次）→ BRAM 写入
  1.14 ns        2.4 ns                   4.8 ns                        ≈ 9.7 ns
```

**三级 DSP 串在一起**。切在乘积之后：前半 1 级、后半 2 级。切法与
`mlkem_basemul` 的 `_head`/`_tail` 完全一样，组合版 `butterfly_ct` /
`butterfly_gs` 仍由两半拼出来 —— 接口和原有的 cocotb 用例都不变，
**同一段数学只有一份实现**。

GS 的前半多算一件事：`a′ = barrett(a+b)` 这条路是 2 级乘法，放前半正好和后半
的 mont（2 级）配平；放后半的话后半变成"2 级并 2 级"、前半只剩 1 级。

缩放那一路（逆变换末尾乘 `f = mont²/128`）同样是三级乘法，照样切一刀。

FSM 因此从 `S_RD → S_WB` 变成 `S_RD → S_MU → S_WB`，一次变换
**2305 拍 → 3457 拍**。

## 结果：一处改动，四个设计一起收敛

| 设计 | LUT | 占比 | 寄存器 | BRAM | DSP | 功耗 | WNS | Fmax |
|---|---|---|---|---|---|---|---|---|
| `ntt_core` | 290 | 0.41% | 73 | 0.5 (0.23%) | 10 (2.78%) | 0.235 W | **+2.130 ns** | **127.1 MHz** |
| `mlkem_keygen` | 6047 | 8.57% | 3335 | 3 (1.39%) | 29 (8.06%) | 0.247 W | **+0.931 ns** | **110.3 MHz** |
| `mlkem_encaps` | 5447 | 7.72% | 3333 | 3 (1.39%) | 37 (10.28%) | 0.257 W | **+1.204 ns** | **113.7 MHz** |
| `mlkem_decaps` | **10802** | **15.31%** | 6910 | 5.5 (2.55%) | 72 (20.00%) | 0.331 W | **+0.785 ns** | **108.5 MHz** |

前后对比：

| | 切之前 | 切之后 |
|---|---|---|
| `mlkem_keygen` Fmax | 104.4 MHz | **110.3 MHz** |
| `mlkem_encaps` Fmax | 100.7 MHz | **113.7 MHz** |
| `mlkem_decaps` Fmax | 98.7 MHz ✗ | **108.5 MHz** |
| LUT（keygen / encaps / decaps） | 6032 / 5388 / 10752 | 6047 / 5447 / 10802 |
| DSP（keygen / encaps / decaps） | 29 / 40 / 78 | 29 / **37** / **72** |
| 一次 NTT | 2305 拍 | 3457 拍 |
| ML-KEM-768 KeyGen | 42 489 拍 | 50 229 拍（+18%） |

**DSP 反而少了。** 乘积进了寄存器之后，Vivado 能用上 DSP48E2 内部的流水寄存器，
原来要外挂逻辑凑的地方现在收进了 DSP 里 —— encaps 40→37、decaps 78→72。
LUT 只多了几十个。代价基本只有拍数：**+18% 的时间，换 8~14 MHz 和一处而非三处
的收敛点。**

## 这件事本身的教训

三个核各自撞墙时，每一次都可以"就地切一刀"把自己救回来。前两次是对的 ——
那两条路（基乘、输出尾巴）确实是各核自己的。第三次不是：`ntt_core` 是三个核
共用的，就地切只会让 decaps 好看，keygen 和 encaps 的余量原封不动，
而下一个例化它的模块还要再撞一次。

**判断标准是"这条路属于谁"**：属于调用方的，调用方切；属于被调用模块的，
改被调用模块。前者切三次是三份实现，后者切一次是一份。

# S5：密码边界 —— PL 内密钥仓 + AXI 防火墙（2026-08-12，完成，未上板）

前面四节做的是**算法**：把 ML-KEM 整套搬进 PL，让中间量不出芯片。
这一节做的是**边界**：让"密钥不出密码边界"从一条纪律变成一个电路事实。

```
        s_axi ──▶ axi4lite_firewall ──▶ 元数据寄存器组 ──▶ key_vault
                    AxPROT / 地址窗口 / tamper                  │
                                                     use 口 ────┘──▶ PL 内的算法核
```

三段的分工是刻意分开的：

- **防火墙**决定"这笔访问该不该存在"；
- **寄存器组**决定"这笔访问是什么意思"，它只碰元数据；
- **仓**决定"密钥怎么存"，它的密钥寄存器与总线之间没有导线。

## 核心不变量：不是"读不出来"，是"没有路径"

普通做法是把密钥放在内存里，靠软件不去读。那要求每一处访问都记得判权限，
**漏判一处就是一个安静的洞**。这里的做法是：密钥寄存器与 `s_axi_rdata` 之间
根本没有导线。软件能做的只有写进去、锁定、擦掉、问一句"这槽有没有装"。

这条在 `test_key_never_readable` 里是**逐字扫描整个 256 字节地址空间**验证的：
八个槽全装上互不相同的密钥，扫完所有可读地址，断言 64 个密钥字一个都不出现。

**验过它会咬人**：把读多路选择器里的 `ZERO_CNT` 那一支改成
`u_vault.keys[0]`，用例立刻报出

```
密钥字出现在总线读回值里：0x24→0xa5010001
```

## "拦下来"和"到了但被忽略"是两回事

`trng_axi`（S2）里已经有一份内联的 AxPROT 门控：判 NS 位，不合规回 DECERR
且不产生副作用。那份是对的，但它是"事务进到从机内部、效果被门控信号掐掉"
—— 掐得对不对，取决于从机里**每一处**副作用都记得判那个信号。

`axi4lite_firewall` 把边界前移：**不合规的事务连下游的握手都不会发生**。
下游从机看到的每一笔访问都是已经放行过的，从机里不必再判一次，也就没有
可漏判的东西。边界是一根导线的位置，不是一段代码的自觉。

`test_nonsecure_blocked_without_side_effects` 用最狠的那个操作直接测这件事：
**non-secure 反复写 `CTRL.ZEROIZE`**。这条也验过会咬人 —— 把防火墙改成
"照样转发到下游、只是回 DECERR"，六个用例挂了五个。

**策略全是编译期 parameter。** 可写的策略寄存器意味着"改策略"本身成了攻击面：
谁能写它、写它的那条路又归谁管，是个会无限套娃的问题。唯一的运行时输入是
`tamper`，而它只能把门关得更紧。

## tamper 只进不出

| 触发 | 效果 | 能否恢复 |
|---|---|---|
| `CTRL.ZEROIZE` | 一拍清空全部槽位、VALID、LOCK；`ZERO_CNT` 加一 | 可以 |
| `tamper` 引脚 | 同上，**并锁存** | **只有 `rst_n`** |

`tamper` 拉高之后，防火墙转为 fail-closed —— 连读 `STATUS` 都返回 DECERR，
软件没有任何一条路能把它清掉。这是有意的：真密码机检测到物理攻击之后本来
就要重新灌装，而"软件可以宣布警报解除"恰恰是被攻陷的软件最想要的能力。

### 擦除为什么是一拍完成的

密钥存在寄存器阵列里而不是 BRAM。BRAM 只能逐地址写零，擦除过程中存在一个
**"擦了一半"的窗口** —— 掉电或复位卡在那个窗口里，残留就还在片上。
寄存器阵列一个时钟沿全清，没有这个窗口。

代价是 2048 个触发器。`tools/rtl_synth_check.sh` 会把 `keys` 列进"摊成寄存器
的存储"清单里 —— 那是**故意的**，不是 S3 那个 16 KiB 缓冲的重演。
判断标准仍然是规模：这里 2048 bit 付得起，那里 16 KiB 付不起。脚本里的说明
已经补上，免得这条看起来像个没处理的警告。

## 两条容易写漏的规则

**① 半把密钥不算密钥。** `COMMIT` 只在整把密钥都写齐时才置 VALID。
写了 7 个字就 COMMIT，槽位仍然无效并置 `DENY`。半把密钥比没有密钥更危险 ——
它看起来可用，实际后半段是零。

**② 锁定挡得住误改，挡不住销毁。** `LOCK` 之后写不进、擦不掉，但
`CTRL.ZEROIZE` 清得掉。否则一把锁死的密钥会永远占着仓位，连重新灌装都做不到。

## 违规留痕

拦下来只是第一步。拦下来这件事本身必须留痕，否则**"没被攻击"和"被攻击了但
没人知道"长得一模一样**。`VIOL_CNT` 是饱和计数，`VIOL_INFO` 记的是**第一次**
违规的现场（地址 / 读写 / NS 位）—— 取第一次而不是最后一次，因为第一次通常
是探测，最后一次往往已经是扫描噪声。

# S6：对称与国密核 —— AES / SM4 / SM3，密钥走密钥仓（2026-08-12，完成，未上板）

S4 做的是后量子算法，S5 做的是边界。这一节把常规对称算法补齐，并且**用它们
把 S5 那条边界真正用起来**：算法核的密钥不是软件写进来的，是从密钥仓的
使用口直接进来的。

```
    vault_s_axi ─▶ key_vault_axi ──use 口(256 bit)──▶ sym_axi ─▶ AES/SM4/SM3
    sym_s_axi   ────────────────────────────────────▶┘
                              ▲
                       tamper 一根线通到两边
```

## 黄金模型先行：三个算法都钉在标准正文的向量上

`hardware/model/sym_oracle.py` 照 FIPS 197、GB/T 32907-2016、GB/T 32905-2016
的正文写三份参考实现，**不调用任何密码库**，各自钉在标准附录的测试向量上，
并各配一条反证：

| 反证 | 必须失败的检查 |
|---|---|
| AES S 盒的仿射常数改一位 | FIPS 197 C.1 的密文 |
| SM4 的 L 少一项旋转 | GB/T 32907 A.1 的密文 |
| SM3 的 T_j 分界挪一格 | GB/T 32905 A.1 的摘要 |
| AES 换一把钥匙 | 解不开原来的密文 |

四条都验过会失败。

### S 盒：RTL 放表，模型放代数

`sbox.v` 是 `sym_oracle.py --emit-sbox` 生成的，而模型里的 AES S 盒是**从
GF(2⁸) 求逆 + 仿射变换算出来的**，不是抄表。于是"两边抄错同一格"这件事
不可能发生 —— `test_aes` 把 256 个输入逐值过一遍正向表与逆向表与代数定义
比对，并验两表互逆。

SM4 的 S 盒标准正文只给表（代数参数要反推），所以模型那边也是表；
把它钉住的是 GB/T 的密文 —— 表错一格，附录 A 的密文立刻不对。

## 三个核的设计取舍

**① 接口是两条命令，不是一条。**

```
key_start → 装载并展开密钥
blk_start → 处理一个分组
```

真密码机是"装一次密钥、过很多个分组"。合成一条要么每个分组重跑一遍密钥
扩展、吞吐掉四分之三，要么得引入"密钥没变就跳过扩展"的缓存 —— 而那个判断
的耗时依赖于"这次的密钥是不是上次那把"。**拆成两条命令，这条信道根本不出现。**

**② SM4 的解密就是加密，只把轮密钥倒过来用。** 这是 Feistel 结构自带的性质，
所以 `sm4_core` 没有逆向数据通路。两个核并排放着正好把结构性差别摆出来：
AES 的逆变换是另一套逻辑（InvSubBytes / InvMixColumns），面积差不多翻倍；
SM4 一分钱不用多花 —— 1014 LUT 对 3520 LUT。

**③ SM3 的填充在核内做。** 填充是"看起来简单、实际最常写错"的一段，
放进硬件写一次、用跨块边界的用例钉住，比让每个调用方各写一遍强。

**④ SM3 的消息扩展窗口往前看，不是往后看。** 标准的递推式要保留过去 16 个字，
但压缩那边还要 W′[j] = W[j] ^ W[j+4] —— 那是**未来**的字，于是扩展得比压缩
快 4 步、两个进度分别管。换成窗口装 W[j..j+15] 就没这个问题：
W[j] = w[0]、W[j+4] = w[4] 当场就有，新字 W[j+16] 由同一个窗口算出。
一拍一轮、一套进度。

## 写 SM3 踩的三个坑

都记在 RTL 注释里，因为它们都是"下一个人也会踩"的那类：

**① 轮号差一。** j 从 1 数到 64（j==0 那拍用来装载 A..H 与窗口），所以标准
正文里的轮号是 **j−1**。T_j 的分界、T_j 的循环左移量、FF/GG 的分界三处都得用
j−1 —— 照着 j 写就整体差一轮，摘要**完全不对**而不是差一点。

**② `in_last` 表达不了空消息。** 用"和最后一个字节同拍"的 `in_last`，
空消息就没有那一拍可用，核永远停在等字节上。改成 `in_flush`
（与 `sha3_core` 同一个约定）。

**③ `can_len` 在块边界没有重新置 1。** "0x80 落在第 55 字节之后"那条分支
进到下一块还以为放不下长度域，于是一路补零补下去 —— **长度 56~63 的消息
永远算不完**。这正是 `test_sm3` 里那条 56 字节用例存在的理由：
填充里最容易写错的就是"剩余空间放不下 8 字节长度、要再补一整块"这个分支，
而随手测几个短消息碰不到。

## 关于常量时间，把话说准

软件 AES 的经典问题是 S 盒查表走 cache，访问时间依赖于查的是哪一格。
**硬件里没有这个问题**：查表就是一片组合逻辑，任何输入都走同一条路径。

但这是"**这类攻击面在硬件上不存在**"，不是"我们做了防护"。两件事分清：

- 三个核的拍数都只由参数（密钥长度 / 消息长度）决定，与密钥、明文、消息
  内容的取值完全无关 —— `test_aes` / `test_sm4` / `test_sm3` 里各有一条用例
  真的量了一遍；
- 三个核**都没有**做功耗/电磁侧信道防护（掩码、随机化）。DPA 是另一回事，
  真要防得在数据通路上加掩码，那是一次独立的改造。**这里不做，也不假装做了。**

## 密钥走密钥仓：总线上没有 KEY 寄存器

常见做法是让软件把密钥写进一组 KEY 寄存器，加密核再从那里读 —— 密钥于是在
总线上走过一遍、又在寄存器里躺着，谁能读那段地址谁就有密钥。

`sym_axi` **没有 KEY 寄存器**。软件能写的只有 `KEY_SLOT`（一个 3 位槽号），
密钥本体从 `key_vault` 的 use 口直接进算法核，那 256 根线不出 PL。
软件说的是"用第 3 号槽的那把钥匙"，而不是"这把钥匙是 0x…"。

于是"读密钥"这件事在总线上**没有对应的地址**，而不是"有地址但被门控了"。

`test_key_never_on_either_bus` 把这句话变成一条会失败的检查：

- 往槽 3 装 FIPS 197 的官方密钥，让 AES-128 加密官方明文；
- **密文必须与 FIPS 197 一致**（说明密钥确实到了核里）；
- 同时把**两个从机各 256 字节的地址窗口逐字扫一遍**，断言密钥的字一个都不出现。

两条同时成立才算数：只验前者，把密钥抄到某个可读寄存器也能过；
只验后者，一个"把密钥全擦了"的实现也能过。

顺带修掉一个不会报错的错：密钥仓 use 口的字序原本是"先写的字在低位"，
而算法核按大端拿高位 —— **密文全错，但没有任何一处会报错**。改成"先写的字
在最高位"，与仓库里其它地方（`block_in[127:120]` 是第 0 个字节）一致。

# S7：上板 —— 在 ZU3EG 真硅上跑通官方向量（2026-08-12，24/24 通过）

前面六节末尾都写着"未上板"。这一节把那句话去掉了。

**在此之前，本条线一个 bitstream 都没有过。** 所有"综合通过、时序收敛"都是
`synth_design -mode out_of_context` 的模块级结果 —— OOC 设计没有顶层、没有 PS、
没有 I/O，**根本产不出 bitstream**。这一点当时每节都写了"未上板"，但没说透。

## 补齐的三层

| 模块 | 作用 |
|---|---|
| `mlkem_axi` | ML-KEM 三个整核的 AXI4-Lite 从机 |
| `axi4lite_xbar` | 一主多从的地址译码 |
| `zu3eg_hsm_top` + `impl_bitstream.tcl` | 板级顶层与完整实现流程（非工程模式，全进 git） |

**三个核的输入形状完全不同**（KeyGen 要两个并行 256 位种子，Encaps 要 m 加一条
ek 字节流，Decaps 要 dk 与 c 两条流），`mlkem_axi` 统一成"一切都往 `IN_DATA` 灌，
顺序就是标准里的顺序"，长度由 `param_set` 算 —— **软件不用报长度，也就报不错**。

地址译码自己写而不用 Xilinx 的互联 IP：本设计单主、单时钟、全 AXI4-Lite，
那个 IP 带来的全是用不上的东西；更要紧的是**它进不了 cocotb 回归**，
译码这一段就会成为整条链上唯一没被对拍覆盖的地方。

## 真机结果

```
[ML-KEM-512  NIST ACVP]  KeyGen/Encaps/Decaps 各三组，逐字节一致
[对称与国密]             AES-128/256（FIPS 197 C.1/C.3）、SM4（GB/T 32907 A.1）、

[密码边界]               两个从机各 256 字节扫完（48 读得到 / 80 被防火墙拒）：

[AxPROT]                 金丝雀（SECURE_ONLY=1）被 DECERR 拒；

[TRNG]                   启动健康检测通过（1023 样本）、无 RCT/APT 告警、
```

**AxPROT 那一条是仿真给不了的**：板上的 Linux 跑在非安全世界，它发出的每一笔

## 三个只在真硅上现形的 bug

**仿真、综合、时序、bitstream 生成全部正常**，载进板子也显示 `operating`，
但 CPU 卡死在第一笔读上 —— 串口日志里是 RCU 报某个 CPU 死在用户进程里、
其它 CPU 还活着。

**① 顶层引用了后面才声明的 wire。**
`.maxihpm0_lpd_aclk(clk_sys)` 写在 `wire clk_sys;` 之前。**Vivado 不报错**，
而是给那个端口新建一条同名的**无驱动**网络。查布线后 checkpoint 才看见：

```
u_ps/inst/maxihpm0_lpd_aclk → net u_ps/maxihpm0_lpd_aclk → driver = （空）
BUFGCE_DIV: O → net clk_sys，扇出 26 个引脚（我的逻辑），不含 PS
```

PS 的 AXI 主口没有时钟。**Icarus 对同样的写法直接报 `Unable to bind wire`**
（本会话前面已经被它抓过好几次）—— Vivado 的静默才是危险的那个。

**② `M_AXI_HPM0_LPD` 是 AXI4，不是 AXI4-Lite。**
`bid` / `rid` / **`rlast`** 这三个由 PL 驱动、送回 PS 的响应信号全部悬空。
**PS 在等 `rlast` 结束读突发，永远等不到。** 这是真凶。
AXI4-Lite 本质是"突发长度恒为 1 的 AXI4"，所以 `rlast = rvalid`、
`bid`/`rid` 回显即可。

**③ `mlkem_axi` 的 start 是非阻塞赋值**（下一拍才有效），而三个核的 `done`
是**电平**、保持到下次 start。一进 `S_RUN` 就查 `core_dn` 会读到上一次残留的
`done`，当场结束、`OUT_LEN` 为 0。表现是**每个核第一次跑永远对、第二次必错**
（真机上 tc0 通过、tc1 报"输出 0 字节"）。

仿真抓不到 ③，是因为链式用例里每个核只跑一次，而"跑两次"那条中间隔着一次
zeroize —— zeroize 会复位核，正好把 `done` 清掉。补了
`test_repeat_same_core` 堵这个缺口。

### 挡住 ① 与 ②

`impl_bitstream.tcl` 加了综合后断言：PS 的 `maxihpm0_lpd_aclk` / `maxigp2_rlast`
/ `maxigp2_bid` / `maxigp2_rid` 只要没有驱动就**中止实现**。

```
断言通过：maxihpm0_lpd_aclk <- u_div/O
断言通过：maxigp2_rlast <- u_xbar/s_rvalid_reg/Q
断言通过：maxigp2_bid <- awid_r_reg[15]/Q
断言通过：maxigp2_rid <- arid_r_reg[15]/Q
```

**这条断言是拿两次断电换来的。**

## 上板方法：不需要新 BOOT.BIN

从 `system.xsa` 里确认过厂家 psu_init 已经开好 `PSU__USE__M_AXI_GP2=1`
（M_AXI_HPM0_LPD，32 位）与 `PSU__FPGA_PL0_ENABLE=1`（150 MHz，实测 147.456）。
所以运行时 `fpgautil -b xxx.bit -f Full` 就够，**golden BOOT.BIN 全程不动**。

PL0 经 `BUFGCE_DIV` 二分频到 **75 MHz** 给密码核 —— 最慢的 `mlkem_decaps`
单独综合 108.5 MHz，留 45% 余量给"接上总线、加了时钟树"那部分。
用 `BUFGCE_DIV` 而不是 MMCM：没有 lock 要等、没有复位时序要排。

顶层**没有任何外部管脚**（一切经 PS 进出），因此一条 XDC 管脚约束都不需要，
也就没有"管脚号写错"这一整类问题。

## 一个流程上的教训：eth0 在 PL 里

板上 `eth0` 是 `80000000.ethernet` —— **网卡在厂家 PL 里面**。刷 PL 的那一刻
SSH 必断，而 rootfs 是 initramfs。我为此断了三次网、要了三次断电，
每次都是同一个错：**把解绑网卡的命令放在前台 SSH 里跑**，第一个被解绑的就是
eth0，SSH 当场断，后面的恢复步骤再也不会执行。

修的不是某一条命令，是方法。`board/plharness.sh`：

```
setsid 脱离终端 → 解绑 PL 驱动 → 跑 payload
              → 收尾**必定**装回 factory.bit、rebind 驱动、恢复 IP
              → 网络自己回来，不用重启（重启会冲掉 initramfs 里的东西）
```

配套还有两条：**日志逐行 `sync`**（硬挂时 SD 卡的写回缓存会把没落盘的全丢掉
—— 前两次挂死之所以"日志全空"就是这个），以及看门狗。

## 排障顺序：先做能证伪的实验

三次挂死之后，先做的不是继续改设计，而是一个**用已知能工作的设计**做的对照
实验：解绑全部 PL 驱动 → 运行时重载**厂家**的 bitstream → 读厂家的寄存器。

一次同时证伪了两个假设：

| 假设 | 结果 |
|---|---|
| 解绑 PL 驱动会关掉 PL 时钟（引用计数归零） | **证伪** —— 持有 `pl0_ref` 的是 `xilinx_fclk`，一直绑着；解绑 9 个 PL 驱动后计数不变 |
| PCAP 运行时重配后 PS-PL 隔离没解除 | **证伪** —— 驱动全解绑后读 `0x80080000 = 0x00000001` 成功 |

两条都排除之后，剩下的只能是我的设计 —— 于是回去读顶层，找到了 `rlast`。

## 综合结果（完整实现，含布局布线）

|---|---|

| 寄存器 | 25519（18.1%） |
| BRAM | 15.5 / 216（7.2%） |
| DSP | 138 / 360（38.3%） |

整机（TRNG + 密钥仓 + AES/SM4/SM3 + ML-KEM 三核 + 金丝雀 + 译码 + PS）

## 还没做的，照旧说清楚

- **最小熵**：TRNG 只做了通过/不通过的健康检测与粗统计。真实最小熵必须导出
  原始比特跑 SP 800-90B 的 EntropyAssessment —— 仿真里的抖动是编的，

- **XMPU/XPPU 与设备树**：PS 侧的隔离还没配。

# P6：风扇温控 —— 一个「答得上却答错」的传感器（2026-08-13）

板子出厂把风扇脚 AA11 钉死在低电平，也就是常转满速，很吵。任务是按结温调速。

代码放在 `fpga/fan_ctrl/`，与 `hardware/rtl/` 下的密码逻辑**目录分开** ——
风扇不碰密码的任何信号，密码也不碰风扇的，两边只共用时钟和复位。但它们进
**同一个 bitstream**：PL 只有一份，运行时载进去的那一个就是全部，分成两个
"设计"没有意义。

## 温度为什么必须从 PL 自己读

风扇是**散热**，不是外设。它得在没有 Linux 的时候也工作 —— 开机那几十秒、
U-Boot 里停着的时候、内核挂死的时候、以及任何"软件本该更新占空比却没更新"
的时刻。把温度源放在 PS 侧、让 Linux 读了写寄存器，等于让散热依赖软件活着。

所以结温直接从 PL 的 SYSMONE4 经 DRP 读，整条链路只依赖 PL 时钟。
AXI 那一路（槽 5，`0x8005_0000`）**只是观测口**，拔掉它风扇照转。

那为什么还要这个观测口？因为要**证明**温控在工作。要在板上看到"空载低占空
比、加负载结温上去占空比跟上"，没有能读温度和占空比的口，就只能靠耳朵判断，
那不算验证。

## 四道安全，方向永远是「多吹」

| # | 条件 | 动作 |
|---|---|---|
| ① | 最低档 | 25% 而不是 0 —— 把风扇停死不是省电是赌运气 |
| ② | ≥80°C | 强制 100%，降到 74°C 才解除（进得早、出得晚） |
| ③ | 长时间拿不到有效温度 | 强制 100% —— 温度未知时唯一安全的假设是"可能很热" |
| ④ | **读数长时间一个比特不变** | 强制 100% —— 见下一节，这条是上板后补的 |

手动覆盖（调试用）盖不过 ② ③ ④。调试口不能让人把芯片烤了。

四条各有一条 cocotb 用例。③ 和 ④ 在正常路径下永远走不到，最容易漏。

## 上板第一轮：数值完全合理，但那是个死值

第一版载进去，看着一切正常：占空比 25%、档位 0、`forced_full=0`、超时位 0、
温度 32.5°C。风扇确实安静了。

**唯一不对的是那个温度码在 5 分钟、60 次采样里一个比特都没变过。**

对照组说明了一切：同期 PS 侧 AMS（`in_temp0_ps_temp_raw`，走的是**完全不同
的通路**）报的结温在 24.9~29.1°C 之间正常抖动；而 PS 侧读到的 PL 温度
（`in_temp2_pl_temp_raw`）自始至终是 0。ADC 根本没在转换，DRP 读回来的是
寄存器里那个从没被写过的值。

**当初在验证载荷里记一路 PS 侧温度做对照，就是为了这种情况。** 拿自己的读数
证明自己没有意义 —— 状态机读错寄存器、换算系数写错，读数照样"看起来像温度"。
32.5°C 这个数落在完全合理的位置，只看它是永远发现不了的。

两个 SYSMON 配置字都错了，而且**错得没有症状**：

- `INIT_41=0x20F0` 把 SEQ 设成"连续序列模式"。序列模式要另外配 `SEQ_CHSEL`
  （0x48/0x49）指定扫哪些通道 —— 一个都没配，序列里空空如也，ADC 无事可做。
  改回**默认模式（SEQ=0）**：ADC 自己循环采温度和几路电源，一个通道不用配，
  正是文件头原本就想要的东西。
- `INIT_42=0x0400` 让 ADCCLK = DCLK/4，75 MHz 下是 18.75 MHz，
  **超过 SYSMONE4 约 5.2 MHz 的上限 3.6 倍**。分频比改成参数：
  75 MHz 版用 16，200 MHz 版用 40 —— 两版 bitstream 时钟不同，写死必错一个。

## 比修 bug 更要紧的是第 ④ 条

原来只有"**读不到**就满速"。这次的坏法它完全挡不住：DRP 照样应答、寄存器
照样有个看着很合理的温度，只是那个数是死的。"读不到"永远不成立，风扇就
心安理得停在最低档，而**没有任何人会发现**。

所以补上：连续 30000 次采样（约 30 秒）读数一个比特不变，也当传感器故障。
真实结温永远在抖，"完全不变"本身就是故障信号。误判的方向是风扇多吹，
可以接受。

计数单位是"采样次数"不是时钟拍数 —— 换时钟频率不用重算。

## 顺带开的 DRP 窗口

第一轮定位这个 bug 是靠猜 + 三十多分钟一轮 bitstream。所以补了个软件可用的
DRP 读窗口（`0x10` 写地址、`0x14` 读数据），能直接读：

- `0x3F` 标志、`0x40/0x41/0x42` 配置（确认 INIT 真的生效）
- **`0x20` 最高温 / `0x24` 最低温记录** —— 这两个是决定性的：复位值是
  `0x0000` / `0xFFFF`，ADC 只要转换过一次就会变。它们要是还停在复位值，
  就直接证明 ADC 一次都没转过，不经过我的换算、不经过我的状态机、
  也不用判断数值合不合理。

窗口的读**绝不拉 `value_valid`**：配置寄存器当成温度是几百度，不能让人在
shell 里读一下寄存器就把风扇带偏。这一条单独一个用例。

## 测试台也跟着改真实了

量占空比时必须喂**带 ±1 LSB 抖动**的温度。原来喂恒定值，加了第 ④ 条之后
会被判成传感器卡死 —— 那不是误报，是测试台不够像真硬件：真 SYSMON 每 1 ms
出一个数，而且读数一直在抖。

## 持久化：为什么是 boot.scr 而不是 BOOT.BIN

要"开机就静"，得让启动链在起 Linux 之前就装上带温控的 bitstream。两条路：

**改 BOOT.BIN 放非 golden 槽 —— 在这块板上既危险又无效。**
危险是因为板子没有 JTAG，写坏了没有任何补救手段。无效是因为 multiboot
寄存器**由 POR 清零**，BootROM 冷启动永远从偏移 0（也就是 `BOOT.BIN`）起，
放进非 golden 槽的镜像**根本轮不到**，除非有人先把 multiboot 写成非零 ——
而那要么靠串口手动设，要么靠 FSBL 失败回退。也就是说它既不会在开机时生效，
也就谈不上"先确认能启再依赖"。

**改 `boot.scr` —— 这才是这块板上真正在起作用的机制**（已经被改过：拆 FSBL
看门狗、开 DT 的 watchdog 节点、三振退备份镜像）。它就是 FAT 分区上的一个
文件，换回旧的即可回退。代价只是从上电到 U-Boot 那几秒风扇仍然满速，
对"太吵"这个诉求没有任何影响。

插入点在**拆看门狗那一段之后**：即使这一整段炸了，FSBL 那条 ~100 秒的看门狗
也已经拆掉，不会因此变成启动循环。三层 `if` 嵌套，任何一步失败（文件不在、
`fatload` 读不到、这版 U-Boot 没有 `fpga loadb`）都只打一行 echo 继续往下走，
PL 保持 FSBL 装的出厂设计 —— **退化回现状，不会退化成起不来**。

golden `BOOT.BIN` 和所有备份镜像一个字节都没动。

## 开机装的是「厂家设计 + 风扇」，不是密码版

板上的 `eth0` 是 `80000000.ethernet` —— **AXI Ethernet IP 在厂家 PL 里**。
密码 bitstream 里没有网卡，开机装它等于**那次启动没有网络**，只能靠串口，
而那条线的 TX 方向本来就是坏的。

所以持久化那份建立在厂家 Vivado 工程之上：网卡、DDR4、MIPI、串口全在，
唯一的改动是把出厂那句 `assign fan = 1'b1;` 换成按结温调速。密码核仍按需
运行时载入（已在真硅上 24/24 验证过）。

把两者合成一份是下一步 —— 需要先把密码从 `0x8000_0000` 挪开，那个地址正是
厂家 AXI Ethernet 占着的。

## 顺带修好的两道门

**Verilator lint 一直是红的，而且是全仓红。** 两个原因叠在一起：
`ring_osc.v` 里一行以 "Verilator" 开头的中文注释被当成元注释指令；顶层例化的
三个厂商原语让 Verilator 报 MODMISSING —— 而它是把命令行上所有文件一起看的，
一个缺失模块就让每一个模块都失败。

修法是给原语写桩（`hardware/tb/lint/vendor_stubs.v`，只进 lint 不进综合），
而不是把板级顶层从 lint 里排除掉。**板级顶层恰恰是最需要 lint 的那个文件**：
让板子挂死两次、断电两次的两个 bug 都在它里面，而且都是 lint 一眼能看出来
的那类。把它排除出去等于把唯一一道自动门关掉。

桩立刻回本了：Icarus 一够到顶层就抓出 `clk_sys` 在声明之前二十行就被用了 ——
**正是那类写法**。这一次 Vivado 恰好接对了（板子跑通了 24/24），纯属运气。

# P7：收尾 —— 真熵、三参数集、边界与隔离（2026-08-13）

## 一、TRNG 的真实最小熵，以及它推翻的两个参数

**H = 0.871234 比特/样本**，来自板上采集的 **1,048,576 个调理前**原始噪声比特。

为此在 RTL 里加了 `RAW_TAP` 抽头，接在 `src_valid/src_bit` 上 —— 也就是**健康
检测（RCT/APT）吃的同一条流**。检测的对象、评估的对象、被使用的对象是同一个，
三者才都有意义。产品形态下 `RAW_TAP=0`，整条通路连寄存器一起**不存在**
（不是"读了返回 0"）：把噪声源的原始比特摆在总线上等于把熵源内部状态交出去。

**必须用调理前的**：调理器（SHA-3 海绵）的输出无论输入熵多低看着都像均匀随机，
拿 `RDATA` 跑评估会得到一个非常漂亮、但毫无意义的数字，而且正好骗过想少做
一步的人。

### 工具的来源要说准

构建机上没有 NIST 官方 EntropyAssessment，也没有外网。`tools/sp800_90b.py`
是按 SP 800-90B（2018-01 最终版）§6.3.1–6.3.10 逐条实现的，**不是官方工具的
输出**，报告里不能这么说。

可信度不靠"我照着写的"，靠**规范每一节自带的算例逐字复现**（`--selftest`）：

| 估计器 | 规范算例期望 | 本实现 |
|---|---|---|
| 6.3.1 MCV | 0.5363 | 0.5363 |
| 6.3.2 碰撞 | 0.4483 | 0.4483 |
| 6.3.3 马尔可夫 | 0.761 | 0.7606 |
| 6.3.4 压缩 | 0.1345 | 0.1372 |
| 6.3.5 t-Tuple | 0.273 | 0.2731 |
| 6.3.6 LRS | 0.6146 | 0.6146 |
| 6.3.7 MultiMCW | 0.3908 | 0.3909 |
| 6.3.8 Lag | 0.735 | 0.7349 |
| 6.3.9 MultiMMC | 0.0755 | 0.0755 |

第十项 LZ78Y 规范没给算例，但它与其余四个预测器共用同一段（已验证的）
`P'_global` / `P_local` 收尾计算。

途中两处值得记：

- 碰撞估计的 `F(1/z)=Γ(3,z)z⁻³eᶻ` 可以化成闭式 `F(q)=q+2q²+2q³`
  （`Γ(3,b)=e⁻ᵇ(b²+2b+2)` 代进去指数项正好抵消），拿规范算例反向验过。
- MultiMCW 那条算例第一次没过。查下来是**规范正文印的序列与它自己的表格
  对不上**：按 `s_i` 列反推出唯一自洽的 12 元序列后，复现出的 `correct`
  向量与规范给的逐位一致。**是算例抄错了，不是实现错了** —— 这两者必须分清，
  否则会去"修"一段本来正确的代码。

### 十项实测

|---|---|
| MCV | 0.996191 |
| **碰撞** | **0.871234** ← 最小者 |
| 马尔可夫 | 0.996108 |
| 压缩 | 1.000000 |
| t-Tuple | 0.923437 |

原始数据本身：1 的比例 0.500064、最长游程 19（1M 比特期望约 20）、
lag 1–8 自相关全部 < 0.4%、32 位字内各位置无结构性偏置。采集期间健康检测
无报警。

回压会改变被评估的那条流本身）。这对最小熵估计没有影响，但**重启测试
（restart tests）不能用这份数据**，那一项要求按规定的重启结构采集。

### 推翻的两个参数

旧的 `RCT_CUTOFF=41` / `APT_CUTOFF=793` 是按 **H=0.5 假设**算的。拿实测 H
重算，两个都站不住，而且**坏的方向不一样**：

- `RCT=41` 在 H=0.871 下相当于 α=2⁻³⁴·⁸。这个源约 9.4 M 样本/秒，
  于是**平均 55 分钟就误报一次** —— 对常开熵源太频繁。
- `APT=793` 在 H=0.871 下的触发概率是 **5.5×10⁻⁵²**。
  **这道检测从来不会触发，等于不存在。** 它按 H=0.5（p=0.707）算，
  而真实 p 只有 0.547，793 离真实分布中心有二十多个标准差。
  也就是说：**过去所有"APT 没报警"的记录，一条证据都不构成。**

按 α=2⁻⁴⁰ 重算（约 33 小时一次虚警，对这个样本率是合理预算）：
**RCT 41→47，APT 793→672**。α 不照抄规范里那个 2⁻²⁰ —— 在 9.4 M/s 下
它是每 0.11 秒误报一次，没法用；**α 要按样本率选**。

公式先在 H=0.5 下重算，得到的正是 RTL 里原有的 41/793 —— 先证明公式与当初
的出处对得上，再拿它往前推。

## 二、ML-KEM 三套参数集在真硅上（20/20）

NIST ACVP 官方向量，512 / 768 / 1024 各 KeyGen / Encaps / Decaps 两组，
**全部逐字节一致**。参数集只靠 MODE 寄存器的 `pset` 字段切换，长度由 RTL
自己按 `pset` 算（软件不报长度，也就报不错）。

| | KeyGen | Encaps | Decaps |
|---|---|---|---|
| ML-KEM-512 | ek 800 + dk 1632 ✓ | K 32 + c 768 ✓ | K 32 ✓ |
| ML-KEM-768 | ek 1184 + dk 2400 ✓ | K 32 + c 1088 ✓ | K 32 ✓ |
| ML-KEM-1024 | ek 1568 + dk 3168 ✓ | K 32 + c 1568 ✓ | K 32 ✓ |

第一版六条 Encaps 全错、其余全对。**这个形状本身就指向输入构造**：
`mlkem_axi` 的 Encaps 输入是 **`m` 在前、`ek` 在后**（`ek_valid` 的条件是
`fp >= 32`，前 32 字节被吃进 `seed_a` 当 `m`），我写反了；而 KeyGen(`d‖z`)
和 Decaps(`dk‖c`) 碰巧写对了。判据也跟着改成 **K 和 c 都报**，不用 else-if：
两个同时错说明是输入构造问题，分别错才是输出解释问题，两种成因要能一眼分开。

## 五、PS 侧 XMPU / XPPU：实配是什么，以及为什么"配上"这半件事做不了

`board/xmpu_probe.c` 从普通世界读 XPPU、XMPU_DDR0..5、XMPU_FPD、XMPU_OCM
的全部控制与区域寄存器，共 149 次读：

- **146 次总线错误（硬件挡的），0 次映射失败。**
- 反证：`CSU_STATUS`(0xFFCA0000)、`CSU_MULTI_BOOT`(0xFFCA0010)、
  eFUSE 控制器(0xFFCC0000) 普通世界**全部够不到**。
- 对照：同一条 `/dev/mem` 路径读 PL 地址**成功**，证明访问路径本身是通的，
  挡是硬件在挡。

"总线错误"与"映射失败"必须分清 —— 前者说明 XPPU/XMPU 真的在拦，后者只说明
`/dev/mem` 这条路被内核限制了，跟硬件隔离没关系。第一版把两者打成同一句
"读不到"，等于把结论建在一个分不清成因的现象上。

**结论**：XMPU/XPPU 的**配置寄存器自己就受保护**，普通世界一个都读不到、
更改不了。所以"把内存保护配上"这半件事**在普通世界不可能完成**，
它需要一个安全世界主控 —— 这正是后来用 BL31 SiP 补上的那一块
（见下面的待办清单）。

另需说清楚：**PL 里那些密码核的边界不靠 XMPU**，靠的是 PL 内部做的 AxPROT
门控防火墙（`SECURE_ONLY=1` 的金丝雀实例已在真硅上验过每一次访问都 DECERR）。
XMPU 能加的是「哪些主控允许发到 PL 那段地址」，与 PL 内的门控是**两层，
互相不替代**。

## 一轮代码审计：五个 RTL 硬伤

外部审计指出五处，五处都成立。共同点值得先说：**它们全都活在既有测试的盲区里**
—— 不是测试写得少（当时 174 项全绿），而是每一条的判据都恰好落在测试没有在看的
那个维度上。这比"少写了几条用例"更值得记：

| 问题 | 既有测试为什么看不见 |
|---|---|
| xbar 地址别名 | xbar **根本没进 cocotb**（它在 `rtl/board/` 下，Makefile 的文件清单里没有）。而且镜像地址回的是 **OKAY** —— 只看响应码，一切正常 |
| zeroize 不擦 BRAM | 旧判据是 `OUT_LEN==0`、`IN_PTR==0`。这两条**都是真的**，只是它们证明的是"软件读不到了"，不是"数据没了" |
| tamper 同拍 | 所有用例都是"tamper 之后"，而窗口恰恰在"tamper 那一拍" |
| TRNG 丢样 | 没有任何用例去比较"健康检测吃到的"与"调理器吃到的"是不是同一条流。两边各自都对 |
| 非法 mode/pset | 没有 negative test。合法输入全对 |

于是这一轮的做法是：每修一条，配一个**能真正抓到它**的确定性用例，并且**在修复前
的 RTL 上跑一遍确认它确实变红**。这一步不能省——不做的话，"修好了"只是一个未经
检验的断言，而新用例可能只是换了个姿势验证同一件已经成立的事。

反证的结果（新用例 vs 旧 RTL）：

```
test_xbar             4/6 红   （正例与"槽号越界"那条本来就对，不动）
test_mlkem_axi        4/8 红
test_firewall         3/6 红   （"tamper 早一拍"那条对照档不动 —— 说明失败确实来自"同拍"）
test_key_vault_core   1/4 红   （只有纯组合那条动，其余三条是回归护栏）
test_trng_nodrop      红      「两条流的内容对不上：第一个不同在第 1088 位」
```

最后那一条值得单独看：1088 正是一个 rate 块的比特数，也就是**第一次置换**发生的
位置。症状与推断严丝合缝——不是"大概是这里丢的"，是"就是这里丢的"。

### 关于第 ④ 条：为什么"丢 0.6% 不要紧"这句话是错的

丢样的比例算下来只有约 0.6%，"损失的是熵率而不是安全性"这句话就熵率而言并没有
说错——第一版 `trng_cond.v` 的文件头就是这么写的。但它错过了真正的问题。

SP 800-90B 的整套论证建立在一条隐含前提上：**被评估的序列、被检测的序列、
被使用的序列是同一个东西**。而当时：

```
健康检测（RCT/APT）：吃每一个 src_valid
RAW_TAP 抽头：      抽每一个 src_valid      ← 熵评估用的就是这条
调理器：            只在 S_ABSORB 收样
```

于是从 A 序列测出来的 *H* = 0.871234 被拿去给 B 序列记熵账，中间少了哪些样本、
少的那些是不是**随机地**少（置换期是周期性的，丢样在时间上有结构），没有人回答
得了。**这是口径问题，不是精度问题**，所以"比例很小"不构成理由。

修法是最朴素的那个：中间加一个 32 深的 1 位 FIFO。按 DECIM=8 算，调理器最长一次
忙（置换 26 拍 + 挤出 8 拍 + 每 lane 一拍 XOR）折合约 7 个样本，32 深绰绰有余。
另外把溢出做成一个饱和计数并接到 `0x34` —— **"一个都没丢"这句话必须是可核对的，
不是推导出来的**。再加一条把 FIFO 压到 2 深的用例强迫它溢出，证明那条计数是活的：
一个永远读到 0 的寄存器和一个"确实没溢出"的寄存器，长得一模一样。

### 上板复验时又踩了一个：读的错误能接住，写的错误接不住

复验程序里写了一条"擦除期间写 `IN_DATA` 应当被拒（SLVERR）"的检查，因为已经装了
`SIGBUS` 处理，就默认它和读一样安全。**跑下去板子当场冻住，只能断电。**

两者根本不是一回事：

- 读的 DECERR 是**同步**外部中止，精确落在那条读指令上，`SIGBUS` 送到进程，
  `siglongjmp` 回得来。这条路早就验证过很多次。
- 写是 **posted** 的：指令早退休了，错误响应过一会儿才回来，在 aarch64 上以
  **SError** 的形式到达。SError 不属于任何一条指令，内核只能 panic。

而这时密码 bitstream 正载着——**eth0 的 MAC 在厂家 PL 里，此刻根本不存在**——
于是网络没了、harness 的恢复步骤没跑到、sysrq 看门狗也随内核一起死了。
表现是彻底失联，连 ARP 都不回。

顺带暴露出两个流程问题，一起改了：报告原先写在 `/tmp`（tmpfs），断电之后什么都
没剩下，"卡在哪一项"只能靠猜——现在直接落 SD 卡并逐节 `fsync`，每节开头先落一个
进度标记；以及一次 payload 里挤了两个程序，离 harness 那条 480 秒看门狗太近，
现在拆成两次跑。

### 上板复验：仿真的"默认姿势"本身就是一种假设

第一次上板 PASS=20 **FAIL=6**。六条红里一条是板上程序自己写错了（把
ML-KEM-768 的输出长度写成 2400，实际 ek 1184 + dk 2400 = 3584），
其余五条指向两个真问题 —— 而且两个都不是"RTL 写错了字"，是**仿真环境与
真实使用方式之间的差距**：

| 上板现象 | 仿真为什么没抓到 |
|---|---|
| `DROPS` 上电即饱和到 65535 | 测试台一直拉着 `rd_en`，输出 FIFO 从不满。板上的常态恰恰相反：**绝大多数时间没有人在读** |
| 非法 START 被拒后 `OUT_LEN` 仍是 2432 | 每条用例都从复位开始，`OUT_LEN` 本来就是 0。**板上是连着跑的** |

第一条的机理：输出 FIFO 满 → 调理器卡死在 `S_SQUEEZE` 等 `word_ready` →
`bit_ready` 一直是 0 → 入口的取样 FIFO 256 拍填满 → 此后每个样本都被丢。
**加大 FIFO 没有用**，卡住的时间没有上界。根子在于噪声源自由运行、压不住，
而消费者可以永远不来 —— 两者之间必须有一个地方允许丢东西。修法是让它丢在
**出口**：`word_ready` 恒为 1，输出 FIFO 满就丢弃那个调理后的字。丢一个已经
调理好的 32 位字完全无害（熵留在海绵状态里），丢入口的样本则直接破坏
"被检测的序列 = 被使用的序列"。反证：改回去，"全程不读"那条用例丢 454 个样本。

第二条的机理更值得记，因为它的表现是**看起来成功了**：软件轮询到 `DONE=1`、
读出 `OUT_LEN=2432`，拿着上一次的 ek‖dk 当成这一次的结果。比明确报错糟得多。
修法是一次 START 尝试就作废上一次的结果，不管这次是否被接受。

两条合起来的教训：仿真用例的**默认姿势**（每次从复位开始、消费者一直在读）
本身就是一组未言明的假设，而板上不按这个姿势来。所以两条修复各配一条
"把板上那个姿势搬进仿真"的用例——不是补一个断言，是补一个**场景**。

第二版实现：35592 LUT（50.44%）、25916 寄存器、WNS +3.174 ns、
**WHS +0.001 ns**。保持时间余量从 +0.013 收到 1 ps，仍是正的、Vivado 判通过，
但保持违例不是降频能救的，下次动 RTL 时这个数要重新看。
复验结果 PASS=25 FAIL=0 SKIP=6，算法回归 24/24。

## ⛔ 不可逆操作红线

**这一节优先于本文档其余全部内容。** 与它冲突的任何表述，以这一节为准。

### 规则

在这块 AXU3EGB / ZU3EG 板上，**任何一次性、不可逆的烧写一律禁止**。

- 禁的**不只是 eFUSE**，是**所有不可逆写入** —— 熔丝、OTP、一次性锁存位、
  永久写保护位，无论它在哪个器件上。
- 凡涉及不可逆动作，**必须先取得板子所有者（用户）的明确同意，默认一律"否"**。
- **会话 / 贡献者不得自行把"评估"扩成"执行"。** "查一下能不能做"到此为止；
  "那就做掉"是另一件事，必须单独得到许可。既往授权（哪怕是"能做就做真的"
  这种话）**不覆盖**这一类动作。
- 拿不准某个位属不属于这一类 → **按属于处理，先问**。

### 为什么规则要写成"按类封闭"而不是"按清单封闭"

因为清单一定会漏，而漏掉的那一条不会以"清单漏了"的形式表现出来，
它表现为一块回不去的板子。所以判据是**类别**：只要一个写入满足
"写下去就回不来"，它就在红线内 —— 下面那张清单是**举例，不是穷举**。

### 更要紧的一条：不可逆动作 + 会撒谎的状态读取 = 不可接受

2026-08-18 这块板上出过一次事故（见下面「现状」）。当时工具、判据、告警**全都
写过了**，照样出事。原因不在谨慎程度：这块 eMMC 的 RPMB 读**隔次返回陈帧**，
也就是说"设备说它没烧过"这句话**本身不可信**。

**在一个读不准的设备上做不可逆的事，风险不由操作者的谨慎程度决定。**

由此派生两条强制要求：

- **任何以"设备状态"为判据的不可逆决定，必须先证明那个读是准的。**
  RPMB 一律校验 `req_resp`（读 `0x0200` / 写 `0x0300` / 烧钥 `0x0100`）
  与 nonce 回显，**绝不信 `result` 字段**（它正是被陈帧污染的那个）；
  I/O 失败与"密钥不对"必须用**不同的返回码**区分开。
- **状态没确认之前，绝不删除任何唯一副本。** 那次真正致命的是这一步 ——
  不是烧写本身。

### 一次性烧写清单（出现即红线；举例，非穷举）

**ZU3EG / ZynqMP eFUSE 全系列**（权威枚举见 UG1085 第 12 章与 Xilinx XilSKey）：

| 类别 | 具体位 |
|---|---|
| 认证根 | `PPK0_HASH`、`PPK1_HASH`、`RSA_EN` |
| 加密 | AES 设备密钥、`ENC_ONLY`、`AES_RD_LOCK`、`AES_WR_LOCK` |
| 撤销 | `SPK_ID` / SPK 撤销位、PPK 作废位（`PPK0_INVLD` / `PPK1_INVLD`） |
| 调试关断 | `JTAG_DISABLE`、`DFT_DISABLE` |
| 锁定 | `SEC_LOCK`、`PROG_GATE` |
| 用户区 | `USER_0` … `USER_7` |
| PUF | syndrome（辅助数据）、`CHASH`、`AUX`、`SYN_INVLD`、`SYN_WR_LOCK`、`REG_DIS` |

**eMMC**：

- **RPMB 认证密钥**（`Program Key`）—— 一块设备一次，烧完读不出来；
- eMMC **永久写保护位**（permanent write protect）。

**兜底条款**：任何 OTP，以及任何名字里带 `*_LOCK` / `*_DISABLE` / `*_EN`
的熔丝位 —— 出现即按红线处理。

### 可逆的安全替代（允许，不受本节限制）

| 手段 | 为什么可逆 |
|---|---|
| **BBRAM 密钥** | 有电池供电，可反复改写 |
| **QSPI 重刷** | 普通闪存，可重写 |
| **SD 卡** | 换文件、换卡都行 |
| **位流重载** | `fpgautil` 随时重配 PL |
| **Device DNA** | **只读**，物理上写不了 |

⚠️ 一个已知的坑：BBRAM 虽然可逆，但**这块板的 `VCC_BATT` 没有电池** ——
掉电即失。所以它"可反复改"成立，"能持久保存"不成立。见本文档 BBRAM 一节。

### 现状：本板 eMMC RPMB（2026-08-18 事故，**已恢复**）

⚠️ **这一条的事实在 2026-08-18 当天变过两次，以此处为准。**

- **发生了什么**：`rpmb_tool provision` 的 `Program Key` **实际上成功了**，
  但工具读回一份**陈的响应帧**、报成"烧写失败"，随后那份"看起来没用上的"
  密钥文件被删除。
- **当时的判定**："认证密钥未知、RPMB 永久不可用" —— **那个判定是错的**。
- **实际结果**：密钥已从 SD 的**已释放块**里找回，并做了密码学确证
  （`Read Write Counter` + 校验 HMAC 与 nonce 回显：找回的密钥 3/3 通过，
  改一位与完全随机的密钥 0/8 通过）。**RPMB 现在可用**，防回滚锚点可以落地。
- **影响范围**：全程仅限 RPMB。启动在 SD（`mmcblk1`），PL、网络、OP-TEE、
  演示链路都不受影响 —— 事故之后板子完整启动过，九节演示全绿。
- **找回它靠的是运气，不是流程**：那 65 字节所在的块当时恰好还没被复用。
  换个时间点它被覆盖，这块 eMMC 的 RPMB 就真的没了。
  **所以这条事故仍然成立为教训，不因为结果好而降级。**

### 规则怎么落地的（不是只写在文档里）

`board/src/rpmb_tool.c` 的 `provision` 在 `#ifndef RPMB_ALLOW_PROVISION` 下
**根本不编译进去**，跑它只打印本节规则并退出。给一块**新板**做供应必须改代码
重编（`-DRPMB_ALLOW_PROVISION=1`）—— 让它成为一次**有记录的决定**，
而不是一条随手能敲的命令。

选编译期而不是运行时开关，理由很直接：**运行时开关拦不住"我知道我在干什么"
的那一刻**，而那一刻正是这类事故发生的时刻。

## 边界

**密码边界是硬件。** ML-KEM 核、对称核（AES-128/256、SM4、SM3）、环形振荡器熵源、
密钥仓与访问门控全部位于 FPGA fabric 之中。主机软件——密钥库、槽位元数据、包裹、
PKCS#11——跑在它*之外*。

边界由三个机制构成：

1. **`axi4lite_firewall`** 按 `AxPROT[1]` 对每个从机做门控。以 `SECURE_ONLY=1`
   构建的从机只接受安全事务，其余一律**读回 0、写被丢弃**，且不产生任何总线
   错误（RAZ/WI）。
2. **`axi4lite_xbar` 做完全译码。** 孔径高位、槽位号、槽内偏移高位与 32 位对齐
   必须全部成立，否则事务就地被拒 —— 同样是 RAZ/WI。不存在镜像地址。
3. **`key_vault` 没有读路径。** 密钥经总线写入，只通过私有的 `use_key` 线出来，
   进入密码核。这是 RTL 的结构性质，不是一次权限检查。

PL 防火墙是这条路径上**唯一**的强制层。UG1085 v2.5 对此有定论：`0x8000_0000`
不出现在任何 XPPU 孔径中（表 16-10），而 FPD_XMPU 不在 `M_AXI_HPM0_LPD` 的路径上
——到达 PL 是"不经过 FPD"的（p. 1092）。PS 侧的保护单元根本覆盖不到 PL 窗口。
这不是本设计的缺口；它正是译码必须精确的原因。

（顺带实测：这块板上 PS 侧的保护单元完全未配置——XPPU `CTRL = 0`，全部 400 条
权限项停在复位默认值，XMPU_OCM 各区域全部禁用，且 XPPU 未加锁。这与上文无关：
即便完全配置好，它们也够不到 PL。

DDR 侧原本同样是空的，后果更重 —— 那一条现在由 BL31 在开机时补上了，
见 [DDR 上的内存隔离](#ddr-上的内存隔离xmpu)。

这些实配是经 BL31 白名单里一个**只读**窗口读出来的 —— 在那之前从普通世界
读保护单元自己的寄存器一律是总线错误，"配了没有"根本无法回答。
⚠️ 这个只读口是**攻击面的净增加**（攻击者也能读出保护配置），列在残余能力里；
判断是值得：配置本身不是秘密，而看不见它就只能一直猜。）

## 威胁模型

**防护的对象。** 拥有普通世界（EL1-NS）代码执行权限、包括 root 在内、想把密钥
材料从模块中*读*出来的攻击者。他们可以经 `/dev/mem` 发起任意 AXI 事务，可以扫遍
整个窗口；他们无法从密钥仓中恢复出对称密钥，也无法读取任何以 `SECURE_ONLY=1`
构建的从机。

**不防护的对象。**

- 拥有**安全世界（EL3）代码执行**权限的攻击者。EL3 是这里的信任根；攻破 BL31
  就攻破了一切。
- 能**重配 PL** 的攻击者。装入另一份 bitstream 就把边界换掉了。这块板上没有任何
  东西能阻止它，因为安全启动没有开通（见[局限](#局限)）。
- 拥有**物理接触**的攻击者。没有机壳，没有接上的防拆响应，没有环境防护。RTL 里
  有一个能清零密钥仓的 `tamper` 输入；没有任何东西驱动它。
- 测量**功耗或电磁辐射**的攻击者。刻意排除在范围之外——见下文。
- 能**读取主机进程内存**的攻击者。主机栈在边界之外：明文密钥材料在那边的进程
  内存中是存在的。缓冲区在可能之处被清零并 `mlock`，仅此而已。

### root 仍然能驱动硬件 —— 这是一条**明知而不修**的残余能力

EL3 SiP 目前暴露的是白名单内的 MMIO 读与写，操作序列由**普通世界**的守护进程
拼装。所以普通世界*读*不到密钥材料（金库在 RTL 上没有读出通路），但 root 仍然
能装载、擦除和使用密钥仓槽位 —— 也就是说**它用得了密钥，只是看不见密钥**。

⚠️ **收紧白名单堵不住这条。** 根本原因不是白名单太宽，而是
**SiP 不校验调用来源**：EL3 分不清"是 daemon 在调"还是"另一个
root 进程在调"。只要 root 能发 SMC，他就能做 daemon 能做的一切；把白名单收窄
只会同时把 daemon 自己挡在外面。

**两条真正能堵的路，以及为什么这一版都不走：**

| 路子 | 能得到什么 | 为什么不做 |
|---|---|---|
| 操作粒度 SiP（"用句柄 H 解封装这段密文"，而不是"往这个地址写这个字"） | root 不能再拼装任意寄存器序列 | 等于把整条硬件时序搬进 EL3，**而 EL3 没有异常处理** —— 一次总线拒绝或轮询不落地就是一个核当场卡死、只能断电。本项目用一笔写实测过这个后果。而且**它仍然不校验来源**：root 照样能调那些操作 |
| 把驱动搬进安全世界的 TA（`tee/ta/` 已有骨架），普通世界只递操作请求 | 这才是真正能挡住 root 的形态 | 架构级改动，不在本轮范围 |

**所以本版的诚实口径是**：密码边界挡住的是"**读**私钥"，不是"**用**私钥"。
在普通世界内核里有 root 的攻击者仍然能命令硬件做运算。要把这一条也堵上，
需要安全世界的 TA，而不是更窄的白名单。

## 已经证明了什么

全部在真实设备上。

**门控双向生效。** 安全世界（EL3，`AxPROT[1] = 0`）读一个 `SECURE_ONLY=1` 的核，
得到 `VERSION = 0x00010000`。普通世界（EL1-NS，`AxPROT[1] = 1`）读同一个地址被拒
——而*同一个*普通世界能成功读到一个 `SECURE_ONLY=0` 的核。
两半都需要：第二半才排除掉"这个地址本来就不可达"。

> **"被拒"的观测方式在这次测量之后改了。** 上面这次运行早于 RAZ/WI 改动，
> 记录到的是 DECERR/SIGBUS。防火墙现在以数据 `0`、不产生总线错误的方式拒绝，
> 所以在当前位流上同一个实验会在放着 `0x00010000` 的地址上读到 **0**。
>
> 新判据是两者中更强的一条，这也是采用它而不只是容忍它的原因：DECERR
> 区分不了"门关着"和"这个地址根本没东西"——空地址回的也是 DECERR。而在一个
> 放着非零常量的地址上读到 `0`，**同时**证明了两件事：事务确实到达了那个从机，
> 并且值被扣下了。
>
> **在 RAZ/WI 位流上重跑这次双向测量还欠着。** 新观测量目前由仿真覆盖。

**对称密钥不越过边界。** 在两个从机上各扫了 256 字节——48 个读得到，80 个被防火墙
拒绝。密钥的四个字一个都没在任何地方出现，而用这些密钥算出的密文对照
GB/T 32907 逐字节一致。这里同样两半都需要："什么都没找到"和"密码算得对"单独
都不能证明任何事。

**算法正确性锚定在公开向量上，而不是本项目自己的模型上。** ML-KEM 512/768/1024
的 KeyGen/Encaps/Decaps 在真硅上与 NIST ACVP 逐字节一致（20/20）；AES 对照
FIPS 197，SM4 对照 GB/T 32907，SM3 对照 GB/T 32905。

**熵是测出来的，不是假设出来的。** 导出 1,048,576 个**调理前**样本，以
SP 800-90B 非 IID 估计器评估：H = 0.871234 bit/sample。这次测量随后确定了健康
测试的判决门限。也只能如此：先前的门限是在假设 H = 0.5 之下算出来的，给出的 APT
触发概率是 5.5 × 10⁻⁵²——这个测试根本不可能触发，所以此前每一条"无 APT 告警"的
记录都一文不值。见 [TESTING.zh-CN.md](TESTING.zh-CN.md#熵)。

**隐式拒绝路径上的时序是平的。** ML-KEM Decaps，一边是合法密文，另一边是翻转了
单个比特的密文，各跑 200 次：中位延迟相差 0.000 %。真正的提前退出会表现为数量级
的差异，而不是几个百分点。

## 哪些没有防护

**功耗与电磁侧信道刻意排除在范围之外**，理由有三条，写出来是为了让这读起来是一个
决定，而不是一处遗漏：

1. 验证一项对策需要侧信道实验台——示波器、功耗与电磁探头、TVLA 方法学。没有它，
   实现了掩码却无法证明它有效，等于把"看起来做完了"当成"做完了"，这比不做更糟。
2. 一阶掩码把每一个中间值拆成份额，每一份都需要随机数。放到 ML-KEM 数据通路上，
   这极可能超出 ZU3EG 的 71K LUT——已经用掉 50.5 %——从而被迫换更大的器件。
3. 时序与功耗/电磁是不同的攻击面。常量时间那部分工作覆盖前者，不能替代后者。

**对 liboqs 与 OpenSSL 不作任何主张。** 主机软件路径上的每一个 ML-KEM 与 ML-DSA
操作都跑在 liboqs 内部。那里的一个时序侧信道就是这里的一个时序侧信道，而本仓库中
没有任何检查能发现它。

**常量时间审计是词法级的，不是编译器级的。** 它看不见编译器引入的分支、编译器
拒绝发出的 `cmov`，也看不见被溢出到栈槽后又重新载入的秘密。经验性的时序测试覆盖
了比较原语；源码的其余部分只被扫描覆盖。

**对进程地址空间之外的内存不作任何主张**——CPU 寄存器、被换出的页面，或断电之后的
DRAM 内容。`mlock` 是尽力而为，且未在内存压力下验证过。

## 局限

下面每一项都足以单独卡住一次认证送检。列出它们，是为了让本文不被误当成一份就绪
声明。

| | |
|---|---|
| **RTL 里仍留着一条私钥导出路径** | `MODE.DK_TO_SLOT` 让 `dk` 留在片内、`DK_FROM_SLOT` 按槽号解封装，守护进程走的就是这条；ML-DSA 的 `sk` 同理。但"不进金库"那条路仍在，因为 ACVP 验证必须把私钥读出来核对。交付形态下它由一次性闩锁关掉 —— 是闩锁不是熔丝，断一次电就又开了 |
| **设备绑定默认不启用** | 派生根可以绑到这颗芯片的 Device DNA（`src/crypto/kdr_dna.c`），经 BL31 白名单里一个**只读**窗口（`0xFFCA0050-5C`）读出；EL1 直读是总线错误。`PQCHSM_KDR=device-dna` 才切。默认不开是因为换根会让既有 keystore 打不开、且症状与被篡改一模一样。⚠️ **DNA 不是秘密**，有 JTAG 就能读到 —— 所以 provider 报的是 `device_bound=1`、`hardware_backed=0`：防克隆，不是机密性 |
| **没有安全启动** | PL 配置是运行时装入的，不是来自一份签名的黄金镜像；而且在这块板上没有别的可能，见[启动与信任根](#启动与信任根) |
| **没有模块完整性检查** | 使用之前没有任何东西校验模块镜像 |
| **安全内存只挡得住"读"** | BL31 开机时把 OP-TEE 的 DDR 段毒化，普通世界读不到它。但仍然可以命令硬件做运算，见 [DDR 上的内存隔离](#ddr-上的内存隔离xmpu) |
| **没有物理安全** | 只有逻辑层面的强制。`tamper` 输入在 RTL 中存在并会清零密钥仓；没有任何东西接到它上面 |
| **缺少条件自测** | 对生成的密钥对没有成对一致性测试，也没有连续随机数发生器测试 |
| **没有 SM2** | SM4 与 SM3 已实现；SM2 非对称算法没有 |
| **没有算法证书** | ACVP 向量是在本地跑的。那是正确性的证据，不是证书 |
| **审计日志单写者** | 审计模块不对文件加锁 |
| **Shamir 份额校验和无密钥** | 它们检测的是损坏，不是篡改 |
| **keystore 的防回滚只挡得住"换一个文件"** | 头部有每次写盘 +1 的 `epoch`（进 MAC 覆盖），锚点由 `pqchsm/rbanchor.h` 的 provider 决定，装载时比锚点旧就**拒绝装载**。默认 provider 把锚点写在旁边的 `<keystore>.epoch`，**这不是真正的防回滚**：攻击者把两个文件一致地换回旧值就照样能过（`test_keystore` 里有一条用例专门钉住这个弱点）。真正的防回滚要一个攻击者退不回去的单调量 —— 见[防回滚锚点](#防回滚锚点) |
| **SO PIN 锁定未强制** | 失败次数有计数，但槽位不会被锁定，因为锁上就等于把设备变砖；恢复走 M-of-N |
| **`CKM_HASH_ML_DSA_*` 未实现** | PKCS#11 多段签名把整条消息缓冲起来，而不是流式地做摘要 |
| **主机 RNG 是 OpenSSL** | PL 熵源在边界之内，但主机软件仍然经 OpenSSL 从操作系统取种子 |
| **密钥种子经普通世界 daemon 的栈**（登记表 CODE-1） | 批 1 之前，`pqchsm_fpgad` 把 `d‖z` / `ξ` 从 TRNG 读进**自己的栈**，再写回核的 `IN_DATA`。种子完全决定私钥，所以 root 能读到它 —— 更糟的是能**换掉**它：灌一个自己知道的种子，此后这块板生成的每一把密钥他都算得出来，而板子照常工作、ACVP 照常过、没有任何一处报错。批 1 把生成收进 EL3（BL31 自己取熵、直接写进 PL 的种子暂存口 —— 那个口只认安全事务、没有读回路径），并把该偏移从通用 `PL_WR` 白名单里排除，于是 root 也没法绕过去。**尚未上板验证。** |
| **ML-DSA 的 `rnd` 仍经普通世界** | hedged 签名那 32 字节随机数仍由 daemon 送。它不决定私钥（泄露它最坏是把 hedged 签名降级成确定性签名），所以没有为它去动 Sign 的输入排布 —— 收益与风险不成比例。写在这里，而不是悄悄不做 |
| **保持时序余量很薄** | 经显式管理之后，有效保持余量为 0.110 ns。保持违例不能靠放慢时钟解决，所以 RTL 一改动就必须重新核对这个数字；实现流程在低于 0.050 ns 底线时中止 |

**这里面只有一项是"被永久排除"而不是"还没做"**：烧 eFUSE 在本项目的红线之后，于是
`ENC_ONLY` / `RSA_EN` 这类防替换的信任根永远拿不到。其余各项欠的是工作量、硬件或
测试台时间。

一份 FIPS 140-3 / GM/T 0028 风格的安全策略草稿，带有它自己的差距清单，见
[reference/security-policy.zh-CN.md](reference/security-policy.zh-CN.md)。

## 启动与信任根

**这块板上没有安全启动，而且这个结论是确定的。** PL 配置是运行时装入的，不是来自
一份签名过的黄金镜像。下面写的是**为什么** —— 因为"还没做"和"在这块板上做不成"是
两个不同的说法，成立的只有后者。

### 三样最常被混为一谈的机制

在 ZynqMP 上这三样是分开的，混起来就会得出一个夸大的结论：

| 机制 | 它买到什么 | 根放在哪 |
|---|---|---|
| **BBRAM** | 启动镜像的 AES-256 **机密性与完整性** | 电池维持的 RAM，可反复改写，JTAG 可编程 |
| **RSA 认证** | **防替换** | eFUSE：`PPK*_HASH` 加 `RSA_EN` |
| **`ENC_ONLY`** | 强制加密启动 | eFUSE |

不烧 eFUSE，BootROM 既不强制认证也不强制加密：攻击者换一份"声明为既不加密也不
认证"的镜像上去，它照样启动。**所以只有加密永远不构成防替换的信任根** —— 而烧
eFUSE 是本项目的永久红线（见本文开头）。这个天花板与下面哪条路走得通无关。

### BBRAM：卡在板级硬件上

烧完 BBRAM 密钥之后 `BBRAM_STS.PGM_MODE`（`0xFFCD0000` 第 0 位）会闩在 1，只要它是
1，CSU 就不会把密钥交给 BootROM。XilSKey 自带的 `PrgrmDisable()`、JTAG 直写
`0xFFCD0008`、`rst -system`、PMU 的 system 域复位，都清不掉它。**只有 POR 能清** ——
但这块板 **`VCC_BATT` 上没有电池**，同一次 POR 会把密钥连同闩锁一起清掉。两个条件
在这块硬件上互斥。

这不只是一个可以绕开的障碍。BBRAM 本来就靠电池维持，所以即便是有电池的板子，电池
一失效就等于镜像起不来 —— 对一个"上电即就绪"的形态而言这是不可接受的。

### PUF 黑钥：在碰到 PUF 之前就被拒了

PUF 引导头模式**不需要**烧 eFUSE（`bootgen -bif_help fsbl_config` 把
`bh_auth_enable` 定义为"做 RSA 认证但**跳过** PPK 摘要与 SPK ID 的校验"），因此它在
本项目的规则下是可做的。镜像里找到并修掉了三个缺陷 —— 每一个都值得记下来，因为它
们各有权威出处，且都不是猜得出来的：

| 缺陷 | 出处 |
|---|---|
| bif 少写 `puf4kmode`：bootgen **默认按 12K**，而注册用的是 4K | `bootgen -bif_help fsbl_config`；`xilskey_puf_registration.h` 的 `XSK_PUF_MODE4K` |
| bif 少写 `shutter=0x0100005E`（bootgen 的默认值 `0x01000020` 在这里是错的） | `xilskey_eps_zynqmp_puf.h` 的 `XSK_ZYNQMP_PUF_SHUTTER_VALUE` |
| 辅助数据最后一字是 `AUX << 4`，不是 `AUX` | `xilskey_eps_zynqmp_puf.c`：读出时 `Aux = (PufStatus & AUX_MASK) >> 4`，写入时 `SyndromeData[385] = (PufStatus & AUX_MASK) << 4` |

三处都改对、并且用**有效的测法**（真 POR 之后冷启动）验过之后，BootROM 仍然拒收；
JTAG 读 CSU 表明它是在**碰到 PUF 之前**就拒的：`PUF_CMD = 0`、`KEY_RDY = 0`、OCM
从未装载。

> 关于测法：加密启动**不能**用热重启测。安全态由 POR 闩定，热重启进加密镜像一律被拒
> （`0x53`），与镜像内容无关。这颗芯片是有软件 POR 通路的（把 PMU 的错误逻辑配成产生
> POR，见 `board/scripts/jtag_por.tcl`），正是它让有效的测法成为可能。

### 什么是通的，以及为什么还不够

RSA 认证启动是通的，**零 eFUSE**，上板验过。但它不是信任根：`bh_auth_enable` 的语义
本身就是跳过 eFUSE 里的 PPK 摘要校验，于是它所校验的那把钥匙就躺在攻击者要替换的
那份镜像里。

**净结论**：启动镜像的机密性与防替换在这块板上都拿不到 —— 前者因为板级硬件，后者
因为唯一的机制在红线之后。

## DDR 上的内存隔离（XMPU）

OP-TEE 在 `0x6000_0000` 的安全段原本普通世界用户态就读得到：`devmem 0x60000000`
读出 `0xAA0003F3`，一条 AArch64 指令，正是 OP-TEE 自己的代码。厂家启动链一个
XMPU_DDR 区域都没配。

**XMPU 本身不负责"挡"。** XAPP1320 v3.0 第 10 页写得很明白：遇到非法访问时 XMPU 置
`AxUser[10]`，事务**照样送到内存控制器** —— "由终点 gate，不是 XMPU 自己"。所以光配
区域只买到检测，别的什么都没有；实测正是如此：违例记下了，数据照样返回。

现在 BL31 在 EL3 里给六个 XMPU_DDR 实例都写上 `POISON.ATTRIB`（第 20 位），开机生效，
在默认形态里。**只动 `POISON`，绝不碰 `CTRL`**，两个理由都会咬人：

- `CTRL.DEFRDALWD` / `DEFWRALWD` 管的是"不落在任何区域里"的访问，清掉它们等于把整个
  DDR 都拒了；
- `CTRL.POISONCFG` 选的是按**地址**毒化、重定向到 `POISON.BASE`，而 `BASE = 0` ——
  一次非法**写**就会落到物理地址 0。

上板实测，上电即生效，无任何手工步骤：

```
devmem 0x60000000 → Bus error      OP-TEE core 段，已围住
devmem 0x10000000 → 0xEDFE0DD0     区域之外，不受影响
devmem 0x70000000 → 不受影响       OP-TEE 共享内存，有意不围
```

把毒化清掉再读同一地址，那条指令又回来了 —— 同址前后对照才是"这个洞真实存在"的
证明。证据：`board/logs/RESULT_xmpu_persist.txt`。

⚠️ **它挡的是"读"，不是"用"。** root 仍然能命令硬件做运算，因为 SiP 不校验调用来源，
见威胁模型里那条残余能力。共享内存段本来就该双向可读。


## 远程口

守护进程的 TCP 口曾经是明文的，靠一个静态预共享口令认证：在同一网段上抓一个包就
永久拿到凭据，整条会话没有完整性，认证帧还可以重放。

现在它跑在 **TLS 1.3 双向证书**之内（`SSL_VERIFY_PEER | SSL_VERIFY_FAIL_IF_NO_PEER_CERT`），
版本在两端都钉死，没有可降级的余地。身份从"知道一个字符串"变成"持有一把私钥"，于是
同网段的任何主机、任何旁观者、任何篡改者、任何重放都被挡在外面。

**它仍然不是**访问控制：

- 没有权限分离、没有按操作授权 —— 过了 mTLS 就等于拿到全部操作。
- ACL 的粒度是 CN（`pki/hsm_acl`，一行一个）。**文件不存在时接受任何由本 CA 签发的
  证书** —— 这是有意的默认值，理由写在 `service/pqcs_tls.h` 的声明处。
- 没有吊销。没有 CRL、没有 OCSP；客户端证书泄露就只能重签整个 CA。
- 限速是按 IP 的漏桶（60 秒内 8 次失败握手）。它针对的是可用性 —— 单线程守护进程被
  握手风暴占满 —— 不是机密性。

**这套 PKI 是原型级的**：CA 私钥就是操作员机器上一个 0600 的文件，没有硬件保护、没有
中间 CA、没有吊销。它足以把"共享口令"换成"持有私钥"，但它不是制度意义上的 PKI。

⚠️ **这块板的演示路径上，客户端身份是公开的，而且是有意的。** `demo/remote/creds/`
把一张客户端证书连同它的私钥提交在了这个公开仓库里，为的是让内网演示零配置可跑。
于是在这条链路上，mTLS 仍然挡得住旁观与篡改，**但挡不住冒充** —— 保证被削弱成
"谁够得着 9797 口"，而它能被接受的唯一理由是板子在私有网络里。CA 私钥与设备私钥
**没有**公开；真实部署要用 `tools/mkpki.sh` 生成自己的 CA、凭据带外分发，并用
`hsm_acl` 按 CN 限制。这段话在使用现场（`demo/remote/README.zh-CN.md`）也重述了一遍。

**本地 UNIX socket 有意不套 TLS。** 它是 0600 且只在本机，够得着它就已经是 root；加密
它挡不住任何人，只会多一份要给板上工具管理的证书。

**时钟是一个真实前提。** 证书有有效期，而这块板的时钟会落在 `notBefore` 之前。TLS 1.3
下这个拒绝发生在客户端认为握手已经完成**之后**，所以症状是"设备信息打印出乱码"，不是
"认证失败"。三重兜底：`demo_remote.sh --provision` 会对时并写 RTC；`hsm-boot.sh` 拒绝
让时钟停在比 SD 卡上凭据更早的时刻；客户端在 open 时强制走一次 `OP_PING` 往返，把这
类拒绝立刻暴露出来。

回归：`tools/tls_regress.sh`（ctest `tls_regress`）—— 一条正例加三条反例（换一个 CA
签的证书、干脆不带客户端证书、CN 不在 ACL 里）。**反例才是重点**；"能连上"只说明配置
没坏。

## 防回滚锚点

`include/pqchsm/rbanchor.h` 把"单调 epoch 存在哪"抽成了一个 provider：

| Provider | 锚点 | 是真防回滚吗 |
|---|---|---|
| `file`（默认） | 旁边的 `<keystore>.epoch` | **不是** —— 攻击者把两个文件一致地换回旧值就照样能过 |
| `rpmb` | eMMC RPMB 的**写计数器** | 是，在下面这个前提之下 |

**为什么锚在计数器上而不是锚在 RPMB 里存的一个值上**：RPMB 数据区可以被持有认证密钥
的人随意改写，包括改小。这块板没有秘密硬件根，密钥只能放在文件里 —— "攻击者拿得到
密钥"是必须做的假设。锚在计数器上让这个假设变得可承受：**它只能被推大，不能被拉回**，
于是旧快照再也对不上。

硬件是够的：这块板的 eMMC（`mmcblk0`，Q2J55L）报
`EXT_CSD[168] RPMB_SIZE_MULT = 32` → 4 MB RPMB，`/dev/mmcblk0rpmb` 存在，内核支持
`MMC_IOC_MULTI_CMD`。

⚠️ **这块 eMMC 的 RPMB 读会隔次返回陈帧。** 每一帧都按 `req_resp` 与 nonce 回显校验，
**绝不看 `result`**；I/O 失败与"密钥不对"返回不同的错误码。这不是为了防御而防御 ——
不这么做会发生什么，见本文开头的红线一节。

如果换一块板子没有可用的 RPMB，替代方案是：**TPM NV 计数器**（这块板没有 TPM，也没有
可用的接口）、**eFUSE 计数器**（在这里被永久排除）、**换一块 eMMC**，或者**远程锚点
服务** —— 后者把问题换成了"那台服务器必须始终可达"，对离线密码机不成立，对联网部署
则可行。

## 构建形态：DEV 与 PRODUCTION

桩派生根是一个**编译进二进制的公开常量**（那个字面量本身就写着 `NOT SECRET`）。默默
回落到它，意味着默认情况下 keystore 的包裹密钥是公开的，而代码里没有任何地方这么说。

现在有两个显式形态（`cmake -DPQC_PROFILE=…`，默认 `DEV`）：

| | DEV（默认） | PRODUCTION |
|---|---|---|
| 桩根密钥 | 编进二进制 | **整段 `#if` 掉 —— 二进制里翻不出来** |
| 没装 provider | 回落到桩 | provider 为 NULL，所有派生都失败 |
| 启动门 | 继续跑，但打印明确告警 | 要求 `hardware_backed`，否则**拒绝启动** |

`tools/check_profile.sh`（ctest `profile_no_stub_kdr`）在 PRODUCTION 的目标文件里扫那个
字面量，**并且带一个空对照** —— 它必须在 DEV 里仍然找得到，否则改个名字就能让这条检查
永远通过而什么都没测。

⚠️ **这块板到不了 PRODUCTION。** 它没有秘密硬件根（eFUSE 被排除、BBRAM 没电池、PUF
黑钥从来没通过），而 `device-dna` provider 是 `device_bound=1` 但 `hardware_backed=0`
—— DNA 每颗片子不同，防克隆成立，但它不是秘密。所以 PRODUCTION 构建在这块板上会拒绝
启动，这**正是这个开关要表达的东西**，不是缺陷。演示与回归都跑 DEV。

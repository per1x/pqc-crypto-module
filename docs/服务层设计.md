# 服务层设计：应用怎么像调用真正的密码机一样调用它

本文回答一个问题：**一个普通应用程序，怎么用标准密码机接口调到这块板子上的
FPGA 密码核。**

前面几节（说明文档 3.x/4.x）证明的是"硬件对、边界严"。那些证明用的是直接写
寄存器的测试程序 —— 那不是应用该看到的样子。真正的密码机对外是
SDF / PKCS#11 这样的标准接口，应用不知道也不该知道寄存器长什么样。

---

## 1. 分层：每一层解决一个问题

```
┌─────────────────────────────────────────────────────────────┐
│ 应用程序          业务代码，只认标准接口                      │
├─────────────────────────────────────────────────────────────┤
│ SDF / PKCS#11 库  标准 API → 内部协议。**无状态、可多进程**    │
│  libpqchsm-sdf.so                                            │
│  pqchsm-pkcs11.so                                            │
├─────────────────────────────────────────────────────────────┤
│ daemon (pqchsmd)  会话、句柄、ACL、审计、密钥库、串行化       │
│  Unix socket + TLV 协议                                      │
├─────────────────────────────────────────────────────────────┤
│ 内核设备节点      /dev/secmmio：把请求转成 SMC                │
│  misc device      **不是信任边界**，只是信使                  │
├─────────────────────────────────────────────────────────────┤
│ 安全世界 (EL3)    BL31 SiP：白名单 + 真正发出安全事务          │
│  AxPROT[1]=0      **信任边界在这里**                          │
├─────────────────────────────────────────────────────────────┤
│ FPGA 密码核       AXI 防火墙 → trng / key_vault / sym / mlkem │
│  SECURE_ONLY=1    非安全事务在总线上被拒                      │
└─────────────────────────────────────────────────────────────┘
```

每一层为什么必须存在：

| 层 | 它解决的问题 | 拿掉它会怎样 |
|---|---|---|
| 标准库 | 应用不用改代码就能换密码机 | 每个应用都要自己拼协议 |
| daemon | 多进程共享**一份**硬件状态：会话、句柄、密钥库、串行化 | 两个进程同时驱动 mlkem_axi，寄存器互相踩 |
| 内核节点 | 用户态发不出 SMC | 只能把 KAT 逻辑搬进内核 |
| EL3 SiP | 普通世界发出的事务 `AxPROT[1]` 恒为 1，被防火墙拒 | 核根本用不了（这一版 `SECURE_ONLY=1`） |
| PL 防火墙 | 门控本身 | 边界没有了 —— 而且 PS 侧没有任何东西能替它兜底（说明文档 5.5） |

**daemon 那一层最容易被误认为可以省掉。**不能：三个核都是"写寄存器 → 启动 →
轮询 → 读结果"的有状态序列，两个进程交错操作同一个核，出来的是**互相错位
但看起来合法**的结果。串行化必须有一个单点，而且那个单点要能记住会话。

## 2. 信任边界画在哪，以及现在画在哪

### 2.1 目标形态：安全世界只暴露**密码操作**

```
普通世界能说的话：  "用句柄 H 解封装这段密文"
普通世界不能说的话："往 key_vault 的 0x8001_0010 写这个字"
```

安全世界收到操作请求，自己去驱动寄存器序列；普通世界从头到尾接触不到寄存器。
这样**授权**（谁能用哪把密钥）也落在安全世界，而不只是**可达性**。

### 2.2 本原型的现状：SiP 是**受限的 MMIO 读写**，序列在 daemon 里

`boot/atf/patch_atf_secmmio.py` 提供的是 `PL_RD` / `PL_WR` 两个调用，白名单
限定到"哪个槽、哪些偏移、读还是写"。序列由普通世界组织。

这个差距要说准，不能含糊：

| 不变量 | 现状是否成立 | 为什么 |
|---|---|---|
| **私钥不出硬件** | ✅ 成立 | `key_vault` 在 RTL 上就**没有**通往总线的读路径（不是"读了被拒"）。密钥只经片内专线给对称核用 |
| **普通世界不能直接访问核** | ✅ 成立 | 四个核 `SECURE_ONLY=1`，普通世界读写一律 DECERR（说明文档 4.8 反证 6/6） |
| **普通世界不能决定"用哪把密钥做什么"** | ❌ **不成立** | 白名单允许写 `key_vault` 槽的寄存器，于是普通世界能装载/擦除密钥、能让对称核用任意槽号 |

第三条就是"原型"与"产品"的分界。补齐它要把 SiP 升级成操作粒度 —— 那是一段
在 EL3 跑的、带缓冲与状态机的代码，而 EL3 **没有异常处理**：一次取数错误就是
一个核当场卡死。所以这一步要配一套自己的验证手段，属产品化阶段（§7）。

**本文档其余部分按现状写，凡是靠"目标形态"才成立的话都标出来。**

## 3. 接口映射

### 3.1 SDF（GM/T 0018）—— 国密送检口径

SDF 是国内密码机的标准接口。映射到本设计：

| SDF 函数 | 映射 | 现状 |
|---|---|---|
| `SDF_OpenDevice` / `SDF_CloseDevice` | 连接/断开 daemon 的 Unix socket | 可落地 |
| `SDF_OpenSession` / `SDF_CloseSession` | `CMD_SESSION_OPEN` / `CMD_SESSION_CLOSE` | 已有 |
| `SDF_GetDeviceInfo` | `CMD_SLOT_INFO` + 静态能力表 | 可落地 |
| `SDF_GenerateRandom` | `trng_axi` 的 `RDATA`（经 EL3） | **硬件直供** |
| `SDF_GenerateKeyPair_ECC` | SM2 —— **本设计没有 SM2 核** | ❌ 缺硬件（§7） |
| `SDF_InternalSign_ECC` / `InternalVerify_ECC` | 同上 | ❌ 缺硬件 |
| `SDF_Encrypt` / `SDF_Decrypt`（SM4） | `sym_axi` + `key_vault` 槽号 | **硬件直供** |
| `SDF_HashInit/Update/Final`（SM3） | `sym_axi` 的 SM3 通路 | **硬件直供** |
| `SDF_ImportKeyWithISK_ECC` 等密钥交换族 | 依赖 SM2 | ❌ 缺硬件 |
| `SDF_ExportSignPublicKey_ECC` | 公钥可出；私钥永不出 | 结构上成立 |

**SDF 里"内部密钥"的概念与 `key_vault` 是天然对应的**：SDF 的
`InternalSign` 用的是设备内部密钥索引（`uiISKIndex`），不传私钥 ——
正好对上"以槽位/句柄引用、私钥不出硬件"。

⚠️ 但要说清楚：**本设计能覆盖的是 SDF 的对称与杂凑部分（SM4/SM3）加随机数**，
非对称那一族（SM2/ECC）**没有硬件**。送检口径下这是缺一大块，不能含糊 ——
补它需要一个 SM2 核（§7）。

### 3.2 PKCS#11

`src/p11/p11_module.c` 已实现 44 个 `C_` 函数。机制映射：

| PKCS#11 机制 | 硬件 | 现状 |
|---|---|---|
| `CKM_AES_ECB` / `CKM_AES_CBC` | `sym_axi` AES-128/256 | 硬件直供 |
| `CKM_SHA3_256`（Keccak） | `sha3_core`（ML-KEM 内部复用） | 需引出独立通路 |
| `CKM_ML_KEM`（v3.2，机制码 0x17） | `mlkem_axi` 三参数集 | **硬件直供** |
| `CKM_ML_DSA`（v3.2，0x1D） | ML-DSA 只有算子、未整核化 | ❌ 缺硬件 |
| SM4 / SM3 | PKCS#11 无标准机制码 | 走厂商自定义机制码 |

`C_GenerateKeyPair` → `CMD_GENERATE` → `mlkem_axi` KeyGen；
`C_DecapsulateKey` → `CMD_DECAPS` → `mlkem_axi` Decaps。这两条是**现成的**。

### 3.3 PQC（ML-KEM）：国内标准接口未定，两条路

国内还没有把 ML-KEM 纳入 SDF 的正式接口定义。两个选择：

**① 走 PKCS#11 v3.2 的 PQC 机制**（`CKM_ML_KEM`、`CKM_ML_DSA`）。
优点是国际标准已定、`third_party/pkcs11-v3.2` 头文件已在仓库里、
`C_Encapsulate`/`C_DecapsulateKey` 已实现。缺点是国内送检不认。

**② 自定义 API**（`SDF_*` 风格的扩展，如 `SDFE_GenerateKeyPair_MLKEM`）。
优点是与 SDF 调用习惯一致、将来标准定了容易改名；缺点是没有互操作性。

**本设计选 ①作为主路**：标准已定的东西优先，别自己发明。
② 作为一层薄封装保留（几十行，把 SDF 风格的名字转到同一套协议命令上），
这样将来国标落地时改动局限在那一层。

## 4. 密钥生命周期

```
生成    C_GenerateKeyPair / SDF_GenerateKeyPair
         → daemon 分配句柄 → mlkem_axi KeyGen（硬件）
         → 公钥回给应用；私钥…见下

使用    C_Decapsulate / SDF_Decrypt
         → 应用只传**句柄** + 密文
         → daemon 查句柄 → 驱动硬件 → 回明文/共享密钥

销毁    C_DestroyObject / CMD_DESTROY
         → 句柄失效（槽位世代 +1，此前所有句柄立刻无效）
         → 硬件侧 zeroize（key_vault 一拍全清；mlkem BRAM 8192 拍擦除）
```

### 私钥到底在哪 —— 分两种，必须分开说

| 密钥类型 | 私钥位置 | 是否出硬件 |
|---|---|---|
| **对称密钥（AES/SM4）** | `key_vault` 的寄存器阵列 | **不出**。RTL 上没有通往总线的读路径；只经片内专线给对称核 |
| **ML-KEM 私钥 `dk`** | 目前**会**经 AXI 返回给软件 | ⚠️ **出**。`KeyGen` 返回 `ek‖dk` 供 ACVP 核对 |

第二行是当前的真实状态，说明文档的 README 里也写着。产品形态应当把 `dk`
留在硬件、只回句柄 —— 需要在 `mlkem_axi` 里加一块私钥存储与"按句柄取 dk"
的通路（§7）。**在那之前，"ML-KEM 私钥不出硬件"这句话不能说。**

## 5. 会话与并发

- **会话**在 daemon 里，一个连接可开多个会话；句柄挂在会话上，会话关则句柄失效。
- **并发**：daemon 对**硬件**串行化。三个核各是一段有状态序列
  （写 MODE → 灌 IN_DATA → START → 轮询 STATUS → 读 OUT_DATA），
  两个请求交错会得到互相错位但看起来合法的结果。
  实现上一把大锁即可 —— 这是控制平面，吞吐不是目标（说明文档 4.1：
  ML-KEM-512 约 1000 次/秒，锁竞争不是瓶颈）。
- **多进程**：库是无状态的，多个应用各自连 daemon，互不可见对方的句柄。

## 6. ACL 与威胁模型

| 攻击者能力 | 现状挡不挡得住 | 靠什么 |
|---|---|---|
| 应用进程读别的应用的密钥 | ✅ | 句柄挂会话；daemon 不跨会话解析句柄 |
| 应用进程读私钥字节 | ✅（对称）/ ❌（ML-KEM dk） | `key_vault` 无读路径 / 见 §4 |
| **root 用户**直接 mmap `/dev/mem` 读核 | ✅ | 核 `SECURE_ONLY=1`，普通世界一律 DECERR（4.8 反证） |
| **root 用户**换掉内核模块，直接发 SMC | ⚠️ **部分** | 白名单在 EL3、改不了；但白名单允许写 `key_vault`，所以 root 能装载/擦密钥 —— 这正是 §2.2 第三条 |
| root 读 keystore 文件 | ✅ | 落盘的是 KEK 包裹后的密文 |
| 物理攻击（探针、DPA） | ❌ | 明确不做，见说明文档 5.4 |

**最值得记住的一条**：这套设计里 root **拿不到密钥材料**，但**能使唤硬件**。
把"使唤"也管起来，就是 §2.1 那个升级。

## 7. 哪些本原型能落地，哪些属产品化后续

### 本原型能落地（B 阶段做）

- SDF 风格的**代表性子集** + PKCS#11 子集，两者共用同一套 daemon 协议；
- 一个**独立应用程序**链接该库，调标准函数，请求经
  库 → daemon → `/dev/secmmio` → EL3 SiP → FPGA，跑真实运算并返回；
- 覆盖 ML-KEM（KeyGen/Encaps/Decaps）与 SM4/SM3；对称密钥留在 `key_vault`。

### 产品化后续（本原型不做，理由写清）

| 项 | 为什么现在不做 |
|---|---|
| **SiP 升级到操作粒度** | EL3 无异常处理，带缓冲与状态机的代码在那里跑，一次取数错误就是核卡死；要配一套自己的验证手段 |
| **ML-KEM 私钥留在硬件** | 需要在 `mlkem_axi` 里加私钥存储 + 按句柄取用的通路；当前 `dk` 经 AXI 返回是 ACVP 核对的需要 |
| **SM2 / ECC 核** | SDF 非对称那一族全靠它；ZU3EG 还剩约一半资源，能放下，但那是另一个核的工作量 |
| **ML-DSA 整核** | 算子已实现（13 个模块）未串成整核 |
| **多进程 ACL / 角色分离** | 现有 daemon 有 SO/User 角色，但没有按密钥的细粒度 ACL |
| **DPA 防护** | 需要侧信道测量台才能验证有效性，见说明文档 5.4 |

## 8. 复用清单：已有什么、要改什么

| 现有资产 | 复用程度 | 要改什么 |
|---|---|---|
| `cli/pqchsmd.c` daemon | 高 | 后端从软件切到硬件 transport |
| `include/pqchsm/proto.h` TLV 协议 | **原样** | 18 条命令够用；SM4/SM3 需加 2 条 |
| `src/slot/` 槽位 FSM、句柄世代 | **原样** | — |
| `src/store/` keystore + KEK 包裹 | **原样** | — |
| `src/p11/p11_module.c` | 高 | 机制表加 SM4/SM3 厂商码 |
| `include/pqchsm/pqc.h` 后端接缝 | **关键** | 实现 `pqc_backend_accel()`，底下走 `/dev/secmmio` |
| `board/kmod/secmmio.c` | **原样** | #1 已经做好 |
| `boot/atf/patch_atf_secmmio.py` | **原样** | 白名单已覆盖四个核 |

**最关键的一处是 `pqc.h` 那个接缝**：它当初就是为"把算法核搬到 FPGA 时上层
一行不改"设计的（见该文件头）。B 阶段要做的正是兑现这句话 ——
写一个 `pqc_backend_accel()`，把 `pqc_keygen/encaps/decaps` 转成对
`/dev/secmmio` 的 ioctl 序列，上面的槽位、会话、句柄、keystore、PKCS#11
一行不动。

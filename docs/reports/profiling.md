# Profiling 报告：性能基线与硬件切分决策

> 对应路线图 §5.2。日期 2026-07-29。
> 平台：Apple M 系列（arm64），macOS 27.0，liboqs 0.16.0，clang -O2

**结论先行**

1. **算法级基线已拿到**（下表），这是将来对比硬件加速效果的唯一参照系。
2. **符号级热点归因在本平台上失败了** —— 原因是 liboqs 0.16 对 ML-KEM/ML-DSA
   走的是**手写 aarch64 汇编**，没有帧指针可回溯，统计采样无法穿透。
   下面如实记录了排查过程与证据，并给出在**目标平台**上拿到真数字的做法。
3. **切分决策的工具已就位**（`tools/amdahl.py`），当前用路线图的文献占比跑出
   与 §5.2.3 完全一致的结论；换成实测占比即可重跑。

## 2. 符号级归因：失败的排查过程（如实记录）

§5.2 想要的是"Keccak 占多少、NTT 占多少"。本机排查了三轮，都没能拿到可信数字：

**第 1 轮：直接对 homebrew 的 liboqs 采样**
`sample(1)` 的叶子样本 **97% 落在 `run_op`**（我们自己的 benchmark 函数），
Keccak 只有 1.4%。这个数字与路线图的 ~55% 差了一个数量级 ——
**不是发现，是归因失败**：预编译的 `.a` 里 ML-KEM/ML-DSA 内部符号是 static，
栈回溯走不进去，全部记在了最近一个可解析的帧上。

**第 2 轮：从源码重编 liboqs（RelWithDebInfo，带 `-g`）**
符号确实出来了（能看到 `PQCP_MLKEM_NATIVE_MLKEM768_AARCH64_keypair`），
但叶子仍有 **88% 落在 `run_op`**，且样本行显示的是调用点
`run_op (in bench_sym) + 372 [...] bench.c:60` —— 说明**栈没有被展开**。

**第 3 轮：加 `-fno-omit-frame-pointer` 重编，再试通用 C 目标**
仍然 89% 落在 `run_op`。查符号表发现根因：

```
$ nm -a b3/lib/liboqs.a | grep -c aarch64_asm
65
```

liboqs 0.16 的 ML-KEM/ML-DSA 用的是 **mlkem-native / mldsa-native 的手写
aarch64 汇编**（`..._ntt_aarch64_asm`、`..._rej_uniform_aarch64_asm` 等），
即使 `OQS_DIST_BUILD=OFF -DOQS_OPT_TARGET=generic` 也照样编进去。
手写汇编不建立帧指针，基于帧指针的统计采样**在原理上就穿不过去**。

**结论**：这台机器上拿不到可信的符号级占比。硬凑一个数字去做硬件决策，
比没有数字更危险，所以这里不给。

### 怎么才能拿到真数字（下一步的具体做法）

§5.2 本来就要求在**目标平台**上测（Cortex-A53/A9），而不是在开发机上：

1. **交叉编译到 aarch64 Linux**（对应 §3.10 已经打通的交叉编译链路），
   liboqs 配 `-DOQS_DIST_BUILD=OFF`，并显式关掉 native 加速
   （必要时直接删掉 `mlkem-native`/`mldsa-native` 的 asm 路径，
   或改用 PQClean 的纯 C 实现 —— 反正 PS 侧要不要 NEON 汇编本身就是个决策点）。
2. 用 **`perf record -g --call-graph dwarf`**：DWARF 展开不依赖帧指针，
   能穿过没有帧指针的汇编（代价是采样开销大）。这是 Linux 上的正解，
   macOS 的 `sample` 没有等价能力。
3. 或者用**确定性计数**：数出每次 KeyGen/Sign 调用多少次 Keccak 置换，
   再单独微基准一次置换的耗时，相乘即得占比。
   → **这一条已经做了，见下面第 2.5 节**，而且不需要改 liboqs 源码。
4. 拿到占比后：`tools/amdahl.py --measured --keccak X --ntt Y` 重跑决策表。

## 2.5 确定性计数：绕开采样，拿到 Keccak 占比的下界

> 新增于 2026-07-29。工具：`tools/prim_count.py` + `tools/prim_bench.c`。

采样归因走不通，但占比可以拆成两个能分别拿到的因子：

```
占比 = 调用次数 × 单次代价 / 总耗时
```

**次数怎么拿到（精确值，不是估计）**：`hardware/model/ntt_oracle.py` 里那份 FIPS 203
KeyGen 实现**已经逐字节重现过 NIST ACVP 向量**（见该文件的预言机 B），
所以它就是真正的 ML-KEM。把它用的 hashlib 换成 `ref_model.keccak_f1600`
搭的海绵，边跑边计数即可 —— **不用改 liboqs 一行代码**。

一个坑值得单独记：`ntt_oracle.sample_ntt` 原本是"块数不够就把
`digest(168·n)` 从头再算一遍"。写着简单，但那样每次重试都重新吸收，
置换次数被凭空放大（一个要 3 块的元素会被数成 1+2+3=6 次）。
真实实现与硬件都是**吸收一次、按需继续挤压**，改成增量挤压后
KeyGen 从 70 降到 43 —— 差了 60%，足以让结论跑偏。

**计数结果（ML-KEM-768，8 组随机种子，范围为 0）**

| 操作 | Keccak-f 置换 | NTT | basemul |
|------|-------------:|----:|--------:|
| KeyGen | **43** | 6 | 9 |
| Encaps | **44** | 3 | 9 |

计数与**手推的解析式**独立对上了：
`1 (G) + ⌈1185/136⌉ = 9 (H(ek)) + 2k = 6 (PRF) + k²×3 = 27 (SampleNTT) = 43`。
两条推导路径互不依赖，这条已接进 ctest（`prim_count`，含反证）。

**单次代价（本机实测，`pqchsm-prim-bench`）**

| 项 | 值 | 备注 |
|----|---:|------|
| Keccak-f[1600] 一次置换（OpenSSL，差分法） | **~43 ns** | 用 t(2N)−t(N) 抵掉 EVP 固定开销 |
| 同上（本项目给对拍用的直白 C 版） | ~2900 ns | 慢约 **69×**，不能当代表 |
| ML-KEM-768 KeyGen（liboqs） | 9.7 µs | |

**结论**

| 操作 | Keccak 耗时 | 占总耗时 |
|------|-----------:|--------:|
| KeyGen | 2.16 µs | **≈ 22%** |
| Encaps | 2.21 µs | **≈ 21%** |

这是**下界**：用 OpenSSL 的 Keccak 当代表，liboqs 自己那份若更慢，
真实占比只会更高。与文献值 55% 的差距是可解释的 —— 文献针对没有 SIMD
汇编的嵌入式核，本机 Apple M 系列上 liboqs 走手写 NEON 汇编，
分母被压得很小，占比自然低。

**NTT 的占比：本机量不出可信值，如实记为不可用。** 手上没有优化过的独立
NTT 可作代表，只有本项目的直白 C 版；代进去算出来的 KeyGen NTT 占比
超过 100%。这个荒谬结果本身就是结论 —— 这条路对 NTT 不成立，不硬凑数字。

## 2.6 硬件侧：RTL 仿真实测的 cycle 数

`pqchsm-prim-bench` 顺带把两个核在 Verilator 里跑一遍，取真实 cycle：

| 核 | cycle/次 |
|----|--------:|
| `keccak_f1600`（单轮迭代） | **24** |
| `ntt_core`（单蝶形） | **1153** |

代进上面的次数（**只算这两个核自身**，不含采样/编码/PS-PL 搬运）：

| 操作 | 组成 | 合计 | @100 MHz |
|------|------|-----:|--------:|
| KeyGen | 43×24 + 6×1153 | 7950 cycle | 79.5 µs |
| Encaps | 44×24 + 3×1153 | 4515 cycle | 45.2 µs |

**★ 直说：79.5 µs 比 liboqs 整个 KeyGen 的 9.7 µs 还慢。** 不回避这一点。
原因是比较对象不对 —— 本机是 Apple M 系列 + 手写 NEON 汇编，而这两个核
的设计目标是 Cortex-A53 @ ~650 MHz、无 SIMD、liboqs 走通用 C 路径。
结论不是"硬件没用"，而是**本机不是能下这个结论的平台**；真正的加速比
要等板子上跑同一套 `tools/bench` 才算数。

能从这张表**确定**的有两件事：

1. Keccak 核在 KeyGen 里一共才 1032 cycle，相比 NTT 的 6918 cycle
   微不足道 —— **24 轮全展开毫无必要**，当初选单轮迭代是对的。
2. **瓶颈在 NTT 核**：单蝶形 1153 cycle/次。要提速就是加蝶形单元与
   BRAM bank，`tools/cycle_budget.py` 正是算这个的。

## 3. 切分决策表（当前用文献占比）

`tools/amdahl.py` 的输出，占比取路线图 §5.2.3 的 SHAKE 55% / NTT 30%：

| 方案 | 剩余时间 | 端到端加速比 |
|------|--------:|-----------:|
| ① 全软件（基线） | 1.000 | 1.00× |
| ② 只做 NTT 硬件（10×） | 0.730 | **1.37×** |
| ③ 只做 Keccak 硬件（20×） | 0.477 | **2.09×** |
| ④ 两个核都做 | 0.207 | **4.82×** |
| ⑤ 两个都做 + 10% 传输开销 | 0.307 | 3.25× |
| ⑥ 两个都做 + 20% 传输开销 | 0.407 | **2.45×** |
| ⑦ 整条流程进 PL（无搬运） | 0.150 | 6.67× |

（②③④⑥ 与路线图 §5.2.3 正文的 1.37/2.09/4.82/2.45 逐项吻合，
说明工具的计算是对的 —— 不确定的只是占比输入。）

**三条可直接用的结论**

1. **只做 NTT 的端到端收益只有 1.37×。** 如果目标是性能，
   它不该是第一个做的核；如果目标是学 RTL 与格密码结构，先做 NTT 仍然合理。
   ——**这是两个不同的目标，不要混着谈。**
2. **若目标是端到端性能，Keccak 是第一顺位投资**（单独做就有 2.09×）。
3. **PS-PL 搬运开销能吃掉一半收益**（4.82× → 2.45×）。
   接口设计（DMA、批处理粒度、是否把整条 KeyGen 都放进 PL）必须在
   **架构阶段**决策，不能等 RTL 写完再补救。

⚠️ 这三条结论建立在**文献占比**上。在换成目标平台实测值之前，
它们是"合理的默认判断"，不是本项目的实测结论。
